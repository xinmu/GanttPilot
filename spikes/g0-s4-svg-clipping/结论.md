## 一、结论速览（能 / 不能 / 需降级 + 代价）

**能。** T-4 / P-8 把"裁剪"定为纯 SVG 路线**唯一的失败模式**；本实验把它从假设变成了可复现的数字：

1. **裁剪成立，且与文档总规模解耦**——元素预算 `#elements ≤ c₁·visibleRows + c₂·visibleEdges + c₃`
   在 **12/12** 组（4 个数据集 × 3 档位）成立；规模梯度 200 → 2,000 任务（**10×**）只让元素数从
   **317 → 350**（**1.104×**），而**关掉窗口裁剪**是 **1,348 → 14,439**（**10.71×**）。
   `c₁ = 3`、`c₂ = 3`、`c₃ = 116 / 70 / 89`（日/周/月，视口 1280×640、行高 24、缓冲 5）。
2. **求交是必需的，不是"保险起见"**——只按"两端点都可见"裁剪，在 4 个滚动位置分别误裁
   **33 / 97 / 96 / 88** 条边（合计 **314**），其中**跨屏长边 268 条**。
3. **首屏与滚动都有一到两个数量级的余量**——首屏（就绪 → 含依赖线首帧）**18.0–31.2 ms**
   （4 次运行 × 3 档的日/周/月包络，1,000 任务 / 1,500 依赖）对 1,000 ms 预算；10× 滚动**总墙钟 164.8–167.2 ms**，
   而《评估报告》§5.4 的同尺反例（2,200 边、行已虚拟化、10× 滚动）是**约 2.0 s**。
4. **4 类关系箭头同尺可区分**——真实渲染尺寸（12 × 7.2 px）下两两 Jaccard 距离最小 **0.3023**（阈值 0.15）；
   折点参数（`EDGE_STUB_PX` / `EDGE_WRAP_PX`）在 `pxPerDay` 细扫下**逐值恒等**，比例式 stub 的负向对照被检出。

**不能**（**不需要降级**，但必须写进 G4 的实现约束与 README 已知限制）：

- 首屏数字来自**无打包器**的探针页：它能判"排程 + 几何 + 首帧 + 依赖线"这一段，**不能**代表生产壳的加载；
  **G4/G8 必须在打包产物上复测**（本实验给的是同一套分层字段）。
- 滚动是**程序化步进**（每步一屏 + 同步重绘 + 单帧 rAF），不是真实滚轮事件序列；
  与 §5.4 的对照是"同样的滚动量与断言方式"，不是"同样的输入通道"。
- 只测了 `--headless=new` + 软件光栅 + DPR 1；headed / DPR>1 / 真机 GPU 未测。

**代价（明确接受）**：

- **gutter 以"天数"表达**（ADR 0007 §3）⇒ 固定像素的回绕走廊在最窄档位（月档 3 px/day）反推出 8 天，
  于是**日档左边距 = 192 px**，占 1280 px 视口的 **15%**。改成本档位推导是**语义变更**，须另立 ADR（本实验不动）。
- **同侧多线避让不做**（P-8 遗留 3）⇒ 实测 **70.7%** 的边其竖向段穿过条形（最小间距 −264 px）。
  v0.1 可接受，但这是"日后出现真实取舍就另立 ADR"的**量化触发依据**。
- **回绕判据随缩放翻转**：扫描的 120 条边里有 **2 条**在某个 `pxPerDay` 上翻转（`l69` SF @10、`l84` SS @16），
  翻转点竖向段位置会跳变。这是 §5 规则的**固有性质**，不是实现缺陷。
- 浏览器计时仍是**记录制**（见 §二 `S4-c` 的工具链结论）。

### `S4-c` 的工具链结论（P-16 让它由本实验驱动 → 追加裁决）

- **不进 `pnpm gate`，维持记录制**。理由：① 它需要**本机 Chrome**（门禁要在任何机器上可跑）；
  ② 它是"测量快照"，换 Chrome 大版本数值必变（证据按大版本分文件）；
  ③ 真正需要门禁的判据（几何、裁剪、元素预算、负向对照）已经**全部在 Node 侧**进了 `pnpm gate` 的收集范围。
- **零新增依赖**：用 Node 内置 `fetch` + 内置 `WebSocket` 通过 CDP 驱动本机 Chrome；静态资源用 `node:http`。
  不引入 Playwright/Puppeteer/jsdom（ADR 0007 §9 的"优先零新增依赖"由此落地，**无需走依赖准入流程**）。
- **缺 Chrome 时失败，不跳过**（P-12 口径）；`GANTTPILOT_CHROME` 可指定可执行文件。
- 需要**动手做**的只有一件：把 `node src/browser-run.mts` 的**复现命令与"记录制"结论**写进 CONTRIBUTING（已做）。

## 三、关键证据

### 3.1 L0 几何期望值表（声明式，内核无权改基准）

[`evidence/geometry-expectations.md`](evidence/geometry-expectations.md)：**13/13 通过**。
期望值写成 **ISO 日期**（`xLeft = dayOfOrdinal(es)`、`xRight = dayOfOrdinal(ef − 1) + 1`），
并同时给出"误用 `dayOfOrdinal(ef)`"会得到的 `naiveRightIso`——它证明了**跨周末右边界规则真的被检查到了**：

| 用例 | 正确右边界 | naive 写法 | 两者是否相同 |
|---|---|---|---|
| 日档·周一至周五（`es=0, ef=5`） | `2026-10-10`（六） | `2026-10-12`（一） | **不同** ⇒ 判据真的在区分 |
| 日档·周五+周一（`es=4, ef=6`） | `2026-10-13` | `2026-10-13` | 相同（对照：规则不总是不同） |

**NC3（故意错的几何必须被检出）**：右边界用 `dayOfOrdinal(ef)` 被检出 3/13、
交换出/入边被检出 3/13、箭头朝向取反被检出 6/13 ⇒ 期望值表**不是恒真式**。

### 3.2 L1 裁剪（S4-a / S4-b）

[`evidence/clipping-report.md`](evidence/clipping-report.md)。元素模型（与渲染器一一对应）：
每渲染行 ≤ 3（`<g>` + 条 + 进度；里程碑行 2）、每条渲染边 = 3（折线 + 箭头 + **ADR §5 要求的透明热区**）。

| 规模 | 依赖总数 | 渲染行 | 渲染边 | 元素总数 | 渲染边占比 |
|---|---|---|---|---|---|
| 200 | 300 | 32 | 48 | 350 | 16.00% |
| 500 | 750 | 32 | 37 | 317 | 4.93% |
| 1000 | 1500 | 32 | 41 | 329 | 2.73% |
| 2000 | 3000 | 32 | 43 | 335 | **1.43%** |

**NC2**（关掉窗口裁剪）：1,348 / 3,524 / 7,170 / 14,439 ⇒ **10.71×**。
两条判据相差一个数量级，说明"与规模无关"有判别力。

**S4-b**：求交 vs 端点可见性 = 41/8、109/12、104/8、101/13 ⇒ 误裁 **314**。

**裁剪健全性（正面表述）**：凡是"与可见行窗口相交"的边，求交路径**一条都不丢**（不变量 16/16 通过）；
折叠隐藏的行在**两条路径下都不画其边**（宽而浅 134 条、密集交叉 53 条逐条一致）。

### 3.5 L2 路由与折点（S4-d）

[`evidence/routing-report.md`](evidence/routing-report.md)：

- **箭头可区分性**（真实尺寸 12 × 7.2 px，1 CSS px 采样，Jaccard）：`FS|SS = 0.3023`、`FS|FF = 1.0000`、

### 3.7 P-8 遗留 1/2（WPS，用户已确认纳入本轮）

- **遗留 1**（[`evidence/wps-idx-probe.md`](evidence/wps-idx-probe.md)）：`idx_OOXML = COM − 1`
  **四站点全部实测成立**——上 `1→0`、左 `2→1`、下 `3→2`、右 `4→3`；
  横向样本 `BeginConnect($barA,4)` / `EndConnect($barB,2)` → 落盘 `stCxn idx="3"` / `endCxn idx="1"`，
  与 P-8 第 4 条的外推值一致（竖向样本 `3/1 → 2/0` 与 S1 参照脚本同参同值，证明两脚本可比）。
  ⇒ **P-8 第 1 条 FS 依赖的 `idx=3`/`idx=1` 不再是外推值。**
- **遗留 2**（[`evidence/wps/elbow-retest.md`](evidence/wps/elbow-retest.md)）：右出 → 左入 肘形
  **5/5 量化判据通过**（水平引线向右 Δx=+2540000 EMU；竖直段 x = 两条参与边 x 的中值 5080000 EMU；
  包围盒 = 两端点外接矩形；`prst=bentConnector3`、`adj1=50000`、`rot`/`flipH`/`flipV` 全空）。
  负对照有判别力（同页面改站点为 `3/3` → 0/4 通过、`2/2` → 2/4 通过）。
  **新发现（对 G7 重要）**：WPS 把"竖直走向"的肘形用 **`rot` + `flip` 规范化**
  （实测 `rot=5400000/10800000/16200000` 三种）⇒ **G7 还原几何必须先读 `rot`/`flip`，不能只读 `off`/`ext`**；
  只有右 → 左（两站点都在竖边）是未旋转形态——这正是 P-8 选 FS 用"右出→左入"的**实测依据**。
- **未验证、不阻塞**：本机 `soffice` 不在 PATH、OnlyOffice 未安装 ⇒ **只出 WPS 口径**（与 P-4 同源）；
  未用 Microsoft PowerPoint 验证（WPS COM 自报 `Name="Microsoft PowerPoint"` 是伪装字符串，不构成证据）。

## 四、ADR 0007 §11 回填清单（七项全部有值）

| # | 待定项 | 回填值 |
|---|---|---|
| 1 | `pxPerDay` 三档与是否离散 | **日 24 / 周 8 / 月 3 px·day⁻¹**；切换**离散**（只改 `pxPerDay` 与表头分组）；选取判据见 §3.4 |
| 2 | `ROW_HEIGHT`、`ROW_BUFFER`、`AXIS_LEFT_GUTTER_DAYS` | **24 px**、**5 行**、**8 天**（= `ceil((8+12+4)/3)`；代价：日档 192 px 左边距） |
| 3 | `EDGE_STUB_PX`、`EDGE_WRAP_PX`、4 类箭头形态 | **8 px**、**12 px**；箭头 = 填充（FS/FF 实心、SS/SF 空心）× 朝向（左入 +x、右入 −x），真实尺寸 12 × 7.2 px，两两 Jaccard ≥ **0.3023**；P-8 遗留 2 的 WPS 复测见 §3.7 |
| 4 | 元素预算常数 `c₁/c₂/c₃` | **`c₁ = 3`**（行）、**`c₂ = 3`**（边：折线 + 箭头 + 透明热区）、**`c₃` 按档位 = 116 / 70 / 89**（日/周/月，视口 1280×640）；三者**均与文档总规模无关** |
| 5 | 首屏与 10× 滚动的实测值与帧预算阈值 | 首屏 **18.0–31.2 ms**（4 次运行 × 3 档的日/周/月包络，1,000/1,500；1,000 ms 预算 ⇒ 约 32× 余量）；10× 滚动 **164.8–167.2 ms**（1,500 边与 2,200 边两组，对照 §5.4 的约 2.0 s ⇒ 约 1/12）；帧预算（候选、记录制）：**主线程 p95 ≤ 16.7 ms**，实测 **1.1–2.5 ms**；帧间隔 p50/p95 = 16.6/18.0 ms |
| 6 | 汇总条/里程碑/进度填充的具体呈现常量 | 条高 = 行高 × **0.6**、汇总条高 = 行高 × **0.35**；里程碑菱形边长 = 行高 × **0.5**、中心 = 所在工作日**格的中点**（+0.5 天）；进度填充上下内缩 **1 px**；**汇总条不加端帽**（加了就要把它算进 `c₁`）；轴标签格式：日档 `DD`、周档 `MM-DD`（取周一）、月档 `YYYY-MM`（取 1 日） |
| 7 | 被传播忽略的边（汇总端点）的样式键 | **`edge-ignored`**（与正常边 `edge` 区分；ADR 0007 §6.4：照画、**不新开诊断码**） |

### 口径澄清三条（**只澄清，不改语义**；若判定为契约缺口，另立 ADR 0008）

1. **ADR §3 的右边界公式在 `ef === 0` 时未定义**：项目起点处的零时长任务（典型是里程碑）会让
   `dayOfOrdinal(ef − 1) = dayOfOrdinal(-1)` 抛 `RangeError`。里程碑本来就该画菱形而非条形，
   因此本实验让它走**菱形分支**（取格中点 + 菱形包围盒），**条形分支的公式一字未改**。
2. **§6.2 的"可见行窗口"应读作 §6.1 的渲染窗口（可见行 + `ROW_BUFFER`）**：否则缓冲行内出现的边会被漏画，
   与 §6.1 自相矛盾。本实验按渲染窗口实现。
3. **§6 只写了"行窗口"与"边窗口"，轴与刻度还有第三维：水平窗口**。探针按视口 x 范围裁剪轴元素，
   `c₃` 因此只与"视口宽 ÷ `pxPerDay`"有关（实测 116/70/89，按档位各一个常数），与文档总规模无关。
   **G4 落地必须照此实现**；若要把它写进契约，属 §6 的补充（另立 ADR）。

## 五、过程中发现并记录的工程事实（值得留痕）

1. **"帧时长"不能用双 `requestAnimationFrame` 测**。双 rAF 的等待（约 33 ms）会被算进"帧时长"，
   把 **1.2 ms** 的工作量报成 **33 ms**（本探针第一版就是这么错的）。正确做法：分开记
   **主线程耗时**（几何 + DOM 的同步部分，判据用它）与**连续 rAF 的真实帧间隔**（记录制）。
2. **一次导航只能测一个档位**：首屏口径是"就绪 → 首帧"，多档同页会让后续档位的"自就绪起"累计前面轮次的时间
   （第一版把周档报成 183.9 ms、月档报成 351.6 ms，均为污染值）。
3. **检查器不得复制几何公式**：本探针第一版在"端点贴合"检查里重写了条形右边界公式，
   于是**里程碑端点被误判**（差 8 px）——正是 CONTRIBUTING 反复强调的"两个真相源"陷阱。
   修法：检查器与渲染器共用 `taskBounds`。
4. **规模梯度必须保持"局部结构一致"**：第一版让 `maxJump` 与每汇总叶子数随规模变化，
   于是"元素数与规模无关"被边的跨度分布污染（实测比值 1.11–1.19 但仍可读）。
   固定 `maxJump` + 每 20 个任务一个汇总后，比值收敛到 **1.104×**。
5. **引擎要消费 `dist`，且不要用 mtime 判过期**：引擎源码的相对 import 写的是 `./x.js`（`tsc` 产物约定），
   Node 类型剥离不会把它解析成 `.ts`；而 `tsc -b` 是**增量**构建，源码没变时不重写产物，
   mtime 必然比 src 旧 ⇒ 正确做法是"产物存在 + API 面齐全 + **文档版本/能力块与源码文本一致**"。
6. **WPS 用 `rot`/`flip` 规范化竖直肘形**（见 §3.7）——这条对 G7 是**实现级**的坑，已单独记入证据。
7. 夹具侧观测（非判据）：引擎校验对"有工期无日期"的叶子报 `TASK_DURATION_WITHOUT_DATES`（info 级），
   1,000 任务夹具约 930–999 条；汇总端点边报 `LINK_SUMMARY_ENDPOINT`（warning 级），与声明的汇总端点边数一致。
   两条都**不影响渲染**，但会让"诊断条数"这个数字看起来很大——引用时请带口径。

## 六、本结论的边界（必须与结论一起读）

1. **探针不是产品**：没有左表、没有行内编辑、没有拖拽、没有导入向导、没有导出、没有持久化。
   首屏数字**不含**左表与 xlsx 导入（`exceljs` 只准动态 `import()`）。
2. **无打包器**：探针页是单页 + 原生 ESM。"模块加载"这一层不代表生产壳；**G4/G8 必须在打包产物上复测**。
3. **滚动是程序化步进**（每步一屏、同步重绘、单帧 rAF 等待），不是真实滚轮事件序列；
   与 §5.4 的对照是"同样的滚动量与断言方式"。
4. **单机单浏览器**：Chrome 152 / headless / 软件光栅 / DPR 1 / 1280×640。换机器、换 Chrome 大版本、
   headed、DPR>1 都可能改变绝对值（这也正是"记录制"的原因）。
5. **只测了 1,000 任务**（规模梯度到 2,000 用于"解耦"判据，但不是性能承诺）；
   2,000 任务正式压测归 v0.5（路线图 §五）。
6. **`.mjs` 的 `noImplicitAny` 关闭**：探针的计算层用 JSDoc 标了**接口级**类型（`ViewModel` / `RowBox` /
   `EdgeGeom` / `AxisElement` / `ProbeResult`），但函数**形参**的隐式 `any` 不报错——
   这是"丢弃式探针"的取舍，**不适用于产品包**（产品包按 `tsconfig.base.json` 全严格）。
7. **S4-c 是记录制**，不是门禁；它不阻断任何东西，也不会在 CI 上跑（需要本机 Chrome）。

- **gutter 档位相关化**（§一 代价）若要做，需**另立 ADR**（ADR §3 的"天数"语义要改）。
- **同侧多线避让**（P-8 遗留 3）：本轮给出"70.7% 的边竖向段穿过条形"这一量化触发依据，仍未做。

- **2,000 任务 + headed + DPR>1 的首屏/滚动复测**：归 G4/G8（不是本实验的边界内工作）。

## 八、G4 交接清单（给 `packages/render-core` 的实现约束）

1. **几何与裁剪进 `render-core`，纯函数、零 DOM**，沿用 ADR §2 的函数名
   （`buildView` / `visibleRows` / `visibleEdges` / `dayAtX`）；一处必要偏离已记录：
   `ordinalAtX(view, x, calendar)` 显式收日历，保持 `ViewModel` 只有数字与枚举。
2. **元素模型照抄**：行 ≤ 3（`<g>` + 条 + 进度；里程碑行 2；汇总条**不加端帽**）、
   边 = 3（折线 + 箭头 + 透明热区）⇒ `c₁ = 3`、`c₂ = 3`、`c₃` 逐档位 116/70/89（同一视口口径）。
   若给行加交互热区（G5 的拖拽），**必须另加常数**并同步 §11 第 4 项。
3. **裁剪四条 + 两条口径**：行窗口（可见行 + 5 行缓冲）、**边所跨行区间 ∩ 渲染窗口**、
   折叠隐藏行不画边（与上一条同一遍完成）、裁剪先于几何计算；轴要**水平裁剪**（第三维）。
4. **里程碑走菱形分支**，不要对 `ef === 0` 调 `dayOfOrdinal(ef − 1)`；条形的右边界仍必须是
   `dayOfOrdinal(ef − 1) + 1`。
5. **常量从 `manifest` 式的单点声明取**（本实验的 `src/manifest.mjs` 可直接搬成 TS 常量模块），
   并保留"常量必须能由判据复推出来"的一致性断言。
6. **不变量与负向对照必须一起搬**：反算往返、端点贴合（**共用 `taskBounds`**，不得复制公式）、
   汇总覆盖、哨兵守卫、NC1/NC2/NC3。
7. **标注为"记录制"的东西不要塞进门禁**：浏览器计时与帧预算。

## 九、依赖许可

**零新增依赖**（运行时与开发侧都是零新增）：浏览器计时用 Node 内置 `fetch`/`WebSocket` + 本机 Chrome；
静态服务器用 `node:http`；类型检查用仓库根已有的 `typescript`；WPS 侧只用 PowerShell 与 COM。
`pnpm license:check` 的口径**不受影响**（spike 不在 workspace 内）。

## 十、如何复现

```powershell
pnpm --filter @ganttpilot/engine build          # 探针消费 dist

cd spikes/g0-s4-svg-clipping
pnpm typecheck                                  # 两个 tsconfig（计算层无 DOM / 浏览器层含 DOM）
node src/run-all.mts                            # L0 几何 + L1 裁剪 + L2 定标（写 evidence/）
node src/browser-run.mts                        # S4-c 浏览器计时（需要本机 Chrome）
pwsh -File src/wps-connector-idx.ps1            # P-8 遗留 1（需要本机 WPS）
pwsh -File src/wps-elbow-retest.ps1             # P-8 遗留 2（需要本机 WPS）
```

- 主口径运行时为 **Node 24.15.0**（CONTRIBUTING / CI）；本次实跑为 **Node 26.7.0**（本机默认）。
  计时数字与运行时一起引用（见 `evidence/env.md`）。
- **Node 侧 6 份报告**（`env` / `geometry-expectations` / `invariants-report` / `clipping-report` /
  `routing-report` / `scale-params-report`）由 `run-all.mts` 每次重写，**重复运行逐字节一致**（已复核 6/6）。
- **浏览器计时**是**测量快照**（按 Chrome 大版本分文件，机器/版本变化必然改变数值）。
- **WPS 侧证据**（`wps-idx-probe.md`、`wps/elbow-retest.md` + 7 个 XML 快照）是**采集快照**：
  由 `src/wps-*.ps1` 采集、`gen-wps-evidence.py` 生成；生成器对**同一份采集 JSON** 的输出是确定的
  （已复核二次运行逐字节一致），但报告内含**采集时刻**、且 XML 取决于 WPS 版本 ⇒ 重跑**不承诺逐字节相同**，
  承诺的是"同一台机器上重跑的**判定与数值**一致"。
