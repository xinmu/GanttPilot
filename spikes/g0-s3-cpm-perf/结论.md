## 一、结论速览（能 / 不能 / 需降级 + 代价）

| 能力 | 判定 | 依据层级 | 代价 / 附注 |
|---|---|---|---|
| 1,000 任务 / 1,500 依赖**全量重算** ≤ 100 ms | **能，且余量约 1,900×** | L2 | 最差数据集 p99 = **52.1 µs**（D3 密集交叉）；Node 26 记录口径 78.2 µs |
| **非关键编辑的后继闭包传播** ≤ 10 ms | **能，且余量约 16,000×** | L2 | 最差 p99 = **0.6 µs**（闭包 25–26 个任务） |
| **关键路径编辑**用 10 ms/帧 作通用保证 | **不需要这种保证** | L2 | 关键编辑的闭包传播 p99 = 0.8 µs（D1）/ 2.0 µs（D3）/ **27.1 µs（D2 深链，闭包 940/1000）** |
| 松手后**合并重算**（含浮动/关键路径）≤ 200 ms（IX-04） | **能，余量约 3,300×** | L2 | 最差 p99 = **60.3 µs**（D2 深链） |
| **增删依赖边**（CSR 重建 + 重算） | **能，是单项最贵操作** | L2 | 重建 p50 ≈ 52–61 µs、p99 ≈ 123–180 µs @1,000/1,500；5,000/7,500 时 p99 ≈ 0.62 ms |
| 5,000 任务 / 7,500 依赖（**非门禁观测点**） | **能** | L2 | 全量重算 p50 = 191.5 µs / p99 = 345.1 µs；仍比 100 ms 低两个数量级 |
| 排程语义正确性 **不依赖外部商业工具** | **能** | L1 + L1b | 4 关系 × lag 正/负/0 × 跨层级 × 日历例外的手工用例全过；1,000 张随机图不变量零违规；**与独立 Python 参照实现 1,000 个项目逐字段 0 不一致** |
| 拖拽 ≥30fps（**含渲染与绘制**） | **不能由本 spike 判定** | — | 本 spike 只测 Node 侧内核，**未测浏览器 `rAF`/样式/布局/GC**；G5 必须复测（§六.1） |
| 主干 `packages/engine/src/date.ts` 直接支撑 G2 | **需改造** | L1 + L3 | 语义与索引日历等价（400 样本 0 不一致），但实现是**逐日循环**且**不支持 `exceptions`**；同一工作负载下比索引日历慢约 **340×**（§五.5） |

**没有出现需要产品叙事降级的证据。** 按 [首版能力顺序 §四](../../docs/01-roadmap/首版能力顺序.md) 的延后规则，
本结论**不触发**任何叙事降级分支；变的是**DoD 的数值口径与理由**（§四）与 **G2 的实现约束**（§八）。

## 二、门禁判定（逐条对应协议）

| 门禁 | 判据（协议原文） | 实测（Node 24.15.0 主口径） | 判定 |
|---|---|---|---|
| **G3-a** | 全量重算 p99 ≤ 100 ms @1,000/1,500 | D1 宽而浅 **27.8 µs**、D2 深链 **49.1 µs**、D3 密集交叉 **52.1 µs** | **通过**（余量约 1,900×） |
| **G3-b** | 非关键编辑传播 p99 ≤ 10 ms | D1 **0.60 µs**（闭包 25 个任务）、D3 **0.55 µs**（闭包 26 个任务）；D2 深链**无浮动任务**（全链关键），按协议跳过并留痕 | **通过**（余量约 16,000×） |
| **G3-c** | 关键路径编辑的耗时**被量化**（预期不满足 10 ms） | 关键任务改工期 +3 工作日的**闭包传播** p99：D1 **0.8 µs**（闭包 27/1000）、D3 **2.0 µs**（89/1000）、D2 **27.1 µs**（**940/1000**）；同时量化**松手后合并重算**（见下） | **已量化**；预期"不满足 10 ms"**未出现**——因为 10 ms 是"含渲染的整帧预算"，引擎侧只占其中约 0.3% |
| 附加（非 Spike-3 门禁，供 DoD 定标） | IX-04：松手后 ≤200 ms | D1 25.7 µs、D2 **60.3 µs**、D3 45.4 µs | **通过**（余量约 3,300×） |

**判定规则（事先声明，避免事后解读）**：实测余量 ≥10× ⇒ 收紧 DoD（产品承诺仍保留原阈值作为不回归天花板）；
余量 3–10× ⇒ 维持原阈值并记录余量；<3× ⇒ 维持阈值但把优化列为 G2 必做；超阈值 ⇒ 触发 §四延后规则
（只允许收窄到 FS + 0 lag）。本 spike 三条门禁都落在**第一档**。

**数据点（非门禁）**：D4 = 2,000 任务 / 3,000 依赖，全量重算 p50 = 62.2 µs、p99 = 129.8 µs；
D5 = 5,000 任务 / 7,500 依赖，p50 = 191.5 µs、p99 = 345.1 µs。这两点用于支撑 README 的
规模承诺（≤2,000 任务 / 3,000 依赖）；**2,000 任务的正式压测仍按 §五 留在 v0.5**。

## 三、关键证据

全部证据在 [`evidence/`](evidence/)：稳定的两份（`correctness-report.md`、`differential-report.md`）
可重跑逐字节比对；性能两类（`perf-node<N>.md`、`breakdown-node<N>.md`）是**测量快照**。

### 3.1 L1 正确性：手工用例 + 不变量 + 双日历互证（81/81 通过）

- **10 个手工推导用例、76 条判定全过**（`evidence/correctness-report.md`）：4 类关系 × lag ∈ {−2, 0, +3}
  × 跨层级（跳层依赖）× 日历例外（整周放假、6 天工作周）+ 0 工期里程碑 + 游离节点（DM-05）+ 成环检出。
  期望值由人工推导后写进 `src/manifest.ts` 的声明式表，**内核无权修改基准**；
- 两个"日历真的参与算术"的判据：整周放假把序号 5 从 `2026-10-12` 推到 **`2026-10-19`**；
  6 天工作周把序号 6 落在 `2026-10-12`（周一）而非周日；
- **两套日历实现互证**：索引前缀和 vs 逐日循环，在 600 天逐日判定 + 201 个序号映射 + 全部区间计数上逐项一致；
- **1,000 张随机图不变量零违规**：`EF = ES + D`、`LF = LS + D`、`TF = LS − ES`、`TF ≥ FF ≥ 0`、
  四类关系的**前向边界方程**、**自由浮动的独立重算**（不信任实现给出的值，按定义重算）、纯 FS 图关键任务非空；
- **正确性侧的负向对照**（证明判定集不是恒真式）：改期望值、把 SS 改成 FS、手工篡改排程结果，三条全部被检出。

### 3.2 L1b 差分：与独立 Python 参照实现逐字段一致（0 不一致）

- 参照实现 `reference/cpm_reference.py`（8,600 字节）是**独立写法**（**该文件已随 P2/D9 删除**——
  探针代码属"可再生"一级，初版原文见 `git show v0.1.0:spikes/g0-s3-cpm-perf/reference/cpm_reference.py`；
  现行参照实现是同口径但**已演进**的
  [`tools/cpm-reference/cpm_reference.py`](../../tools/cpm-reference/cpm_reference.py)，与初版不是同一文件）：
  递归 + 记忆化、`datetime.date`、显式工作日集合、**DFS 三色染色检环**；
  TS 侧是迭代 + 整数序号 + CSR + **Kahn 入度法**——两侧不共享任何代码，只共享 `manifest.ts` 声明的字段契约；
- 规模：**1,000 个随机 DAG**（5–200 任务、四类关系混合、lag ∈ [−3, 3]、含 5% 里程碑）
  + **200 个成环图**；**比对字段 0 处不一致，成环判定 200/200 一致**；
- 项目序号取模轮换**三种日历**（Mon–Fri、整周放假、Mon–Sat），两侧用**各自实现**的日历把序号翻译成 ISO 日期
  再比对——因此这一层同时交叉验证了"工作日序号 ↔ 日期"的语义；
- 比对走**文件进出**（`out/diff/inputs.json` → Python → `out/diff/outputs.json`），不走 stdio 管道：
  可复算、可调试，也不受子进程管道实现差异影响。

### 3.3 L2 性能：门禁数字与结构性事实

`p50/p95/p99` 均为 **median-of-suites**（每场景 5 个 suite × 1,000 次迭代），同时记录最差 suite 的 p99。
计时用 `process.hrtime.bigint()`，并按"单次耗时 ≥ 10 × 计时器分辨率"的要求做**批量计时**
（本机分辨率约 100 ns，而闭包传播只要 30–60 ns，不批量会把 p50 测成"等于分辨率"）。

| 数据集（V=1000 / E=1500） | 全量重算 p50 → p99 | 非关键编辑闭包传播 | 关键编辑闭包传播 | 松手后合并重算 |
|---|---|---|---|---|
| D1 宽而浅（3 层，关键任务 10） | 18.1 → **27.8 µs** | 0.60 → **0.60 µs**（闭包 25） | 0.60 → **0.80 µs**（闭包 27） | 18.2 → 25.7 µs |
| D2 深链（单链 + 跨链，关键任务 1000） | 22.8 → **49.1 µs** | **无浮动任务 → 跳过** | 13.7 → **27.1 µs**（闭包 **940**） | 23.1 → **60.3 µs** |
| D3 密集交叉（6 层，关键任务 5） | 20.3 → **52.1 µs** | 0.50 → **0.55 µs**（闭包 26） | 1.90 → 2.00 µs（闭包 89） | 20.3 → 45.4 µs |

**三条结构性事实比计时本身更重要**（它们解释了 DoD 该怎么写）：

1. **闭包规模决定帧内成本**，而闭包规模与图的形状强相关：同样是"非关键任务改工期"，
   闭包可能是 25 个任务（宽而浅）也可能是 **940 个任务**（深链上从第 60 个任务起全部是后继）；
2. **深链上"增量 ≈ 全量"**：D2 的闭包传播 13.7 µs vs 全量重算 22.8 µs——只有约 1.7× 的差别。
   也就是说，在长依赖链上"只传播受影响子图"几乎没有收益，**真正的收益是不重复做分析层与不重建 DOM**；
3. **增删边是单项最贵操作**：CSR 重建 + 重算的 p99 在 1,000/1,500 下为 **123–180 µs**（重建本身 p50 ≈ 52–61 µs），
   5,000/7,500 下为 **0.62 ms**。它仍是 O(V+E)，但没有出现"动态拓扑序维护"的算法性崩塌。

### 3.4 L3 常数因子与判别力（对照未达阈值则性能数字不成立）

| 编号 | 基准（快） | 对照（慢） | 实测倍率 | 阈值 | 判定 |
|---|---|---|---|---|---|
| NC1 | 索引前缀和日历 | 逐日循环日历（对齐主干口径） | **2,360×** | ≥3× | ✅ 有判别力 |
| NC2 | 后继闭包传播 | 每个受影响任务各做一次全量重算 | **820×** | ≥10× | ✅ 有判别力 |
| NC3 | 扁平数组 + CSR | `Map` + 对象图 + 邻接对象数组 | **2.8×** | ≥1.5× | ✅ 有判别力 |

- 主干 `countWorkdays`（逐日循环）在同一工作负载上 **1.086 ms / 200 次区间查询**，
  索引日历 **3.20 µs / 200 次**——约 **340×**（§五.5）；
- NC3 的阈值刻意设为 1.5× 而不是 2×：实测约 2.8–3.4×，跨机器/跨运行时会有波动，
  **阈值必须低于实测值并留余量**，否则会把"有判别力"误判成"测量无力"；
- 同理，NC2/NC3 的对照绑在**闭包最大**的场景上：非关键编辑的闭包常只有几个节点，
  在那个规模上比值会被噪声淹没（同一台机器上实测可在 0.5×–2× 之间跳）。

## 四、DoD 定标（本 spike 的主要交付物）

按 §二的判定规则，实测余量全部落在 ≥10× 档，因此**建议收紧**：

| 条目 | 原口径 | 建议口径（本 spike 依据） | 余量 |
|---|---|---|---|
| **G2 `compute()` 全量重算** | p99 ≤ 100 ms @1,000/1,500（EN-08） | **p99 ≤ 1 ms** @1,000/1,500（Node 24 参照机）；**100 ms 保留为产品侧"不回归天花板"** | 实测 52.1 µs ⇒ 约 **19×** |
| **G5 拖拽期引擎侧传播** | EN-04：非关键编辑 ≤10 ms/帧 | **引擎侧 ≤1 ms/帧**；**10 ms/帧 保留为"含渲染的整帧总预算"** | 实测 0.6 µs ⇒ 余量极大 |
| **松手后合并重算** | IX-04 ≤200 ms | **维持 200 ms**（措辞不动，仅补实测依据） | 实测 60.3 µs ⇒ 约 3,300× |
| **增删依赖边** | 无独立条目 | **新增：重建 + 重算 p99 ≤ 1 ms** @1,000/1,500 | 实测 180 µs ⇒ 约 **5.5×** |
| **规模承诺** | README：≤2,000 任务 / 3,000 依赖 | **维持**，并补一条实测支撑：2,000/3,000 全量重算 p99 = 129.8 µs | 约 770× |
| **EN-04 的改写理由** | 评估报告 §5.3：浮动全局耦合 ⇒ 关键编辑会引发 O(V) 位移 | **理由从"引擎算不动"改为"避免整表 DOM 重建"**：引擎侧关键编辑的闭包传播最差 27.1 µs、全量重算最差 60.3 µs，**在 1,000 任务规模上引擎不是瓶颈** | — |

> **建议的 EN-04 措辞（供裁决）**：
> "拖拽期间只做**受影响子图的日期传播**（引擎侧 ≤1 ms/帧；整帧含渲染 ≤10 ms/帧）；
> **浮动与关键路径在松手后合并重算**（≤200 ms）；深链上受影响子图可能覆盖全图，
> 此时增量与全量同阶，优化收益来自**避免 DOM 重建与分析层重复计算**，而非传播本身。"

## 五、过程中发现并记录的语义/工程事实（值得留痕）

1. **日历不参与 CPM 传播——这是架构层最重要的一条。**
   一旦用「工作日序号」承载日期（`ES/EF/LS/LF` 全是整数），传播就是纯整数加法/比较，
   `Date` 只在"序号 ↔ 日期"翻译时出现。G2 的热路径因此没有日期对象、没有时区陷阱，
   也没有"日历查询进内层循环"的性能悬崖。代价是：**序号 ↔ 日期的翻译必须另做优化**
   （1,000 任务 × 2 个日期/次导出），且容量规划（地平线天数）要留余量并在不足时扩容重算。
2. **在 1,000–5,000 任务规模上，引擎不是瓶颈。** 全量重算 p99 在 52–345 µs 区间，
   离"帧预算"还有两到三个数量级；因此首版的性能风险**不在引擎，而在渲染与 DOM 重建**
   （这与评估报告 §5.4 指出的"2,200 条 SVG 边滚动约 2.0s"是同一件事的不同侧面）。
3. **混合关系图上"关键集合"可能为空（44/1,000 张随机图）。** 当图里混有 SS/FF/SF 关系时，
   "完成最晚的任务"不一定是任何终端的祖先，于是**所有任务的总浮动都 > 0**，
   `totalFloat === 0` 判据给出空集。纯 FS 图不存在该现象。**v0.5 的关键路径高亮必须定义退化行为**
   （例如回退到"总浮动最小者"），否则会出现在真实数据上的"高亮为空"。
4. **负 lag 会把开始推到项目起点之前。** 本 spike 按 0 截断并**计数诊断**（`clampedStarts`），
   而不是静默改写。G2 需要在 schema 层定义这一类越界的语义（约束？告警？）——属 G-3 的范围。
5. **主干 `date.ts` 与 G2 的差距（需要 G1/G2 处理）**：
   `countWorkdays` 是逐日循环、且**没有 `exceptions` 参数**（DM-06 的"例外"目前无处表达）。
   本 spike 的 `IndexedCalendar` 给出了等价（400 样本 0 不一致）且快约 **340×** 的参考实现，
   并把 `exceptions` 建模为"工作日→非工作日"与"休息日→工作日"两个集合——**可直接移植**。
6. **`process.hrtime.bigint()` 的批量计时不可省。** 本机分辨率约 100 ns，而闭包传播只要 30–60 ns；
   不批量会把 p50 测成"等于分辨率"，从而把一个"通过"的门禁测成"存疑"。本 spike 的 `harness.ts`
   先校准、再按批计时，并在报告里保留 `batchSize` 与最差 suite p99。
7. **Windows 上 `python` 可能是 `.bat` 垫片**：`spawnSync` 返回 **9009** 而不是 `ENOENT`，
   容易被误读成"脚本失败"。本 spike 显式退回 `cmd.exe /d /s /c`，并避免 `shell: true` 的 DEP0190。

## 六、本结论的边界（必须与结论一起读）

1. **只测了 Node 侧内核，没有测浏览器与绘制。** 没有 `requestAnimationFrame`、样式/布局、
   GC 停顿、SVG 元素数对帧时间的影响数据，因此**"拖拽 ≥30fps"（G5 门禁）未被本 spike 验证**，
   Node 数字**不能替代**它。G5 必须在真实浏览器复测整帧预算。
2. **`p99` 是 median-of-suites，不是分布尾部极值。** 单机、单核、测量期机器空闲是前提；
   报告同时给出了最差 suite 的 p99（例如 D2 全量重算最差 suite p99 = 53.4 µs）供判断。
3. **未覆盖**：Worker 化、增量拓扑序维护的工程实现、约束类型（G-3/G-4）、多日历（v0.1 只启用项目日历）、
   2,000 任务的正式压测（v0.5）、以及 xlsx 导入侧对性能的影响（属 G3）。
4. **参照实现是"另一种写法"，不是"标准答案"。** 它覆盖了 5–200 任务的随机图与我方声明的字段契约；
   两侧同时犯同一个语义错误的概率很低，但不为零——G2 仍应保留不变量测试与手工用例。
5. **spike 代码不进主干**：本目录只交付可复现的判定与约束；产品实现（含单测）在 G2 由
   `@ganttpilot/engine` 重写，届时本目录整体删除。

## 八、G2 交接清单（给 `@ganttpilot/engine` 的实现约束）

**A. 数据表示（有实测支撑）**

1. **日期一律用「工作日序号」（整数）承载**，`Date`/ISO 字符串只出现在 I/O 边界；
   日历**不进入传播热路径**（`computeInto` 的签名里不需要 `Calendar`）；
2. **CSR 邻接 + 类型化数组**：`Int32Array` 存序号与 lag、`Uint8Array` 存关系类型；
   对照实验：换成 `Map` + 对象图慢 **2.8–3.4×**（NC3）；
3. **结果写入调用方提供的缓冲（`computeInto` 复用）**，热路径零分配；
4. **遍历全部迭代实现、零递归**：1,000 节点深链不得依赖调用栈。

**B. 算法**

5. 正向/逆向两趟 + 总浮动 + 自由浮动 + 关键路径（`totalFloat === 0`）——关系方程见 `src/cpm.ts` 头部表；
   **自由浮动按定义重算可作不变量**（本 spike 的 L1-c 即如此）；
6. **Kahn 入度法检环**，成环时**不产出排程结果**并给出成环节点（DM-04/EN-05）；
7. **增量传播**：迭代 DFS 收集后继闭包 → 按闭包的逆后序（即闭包上的拓扑序）重算 ES/EF，
   闭包外节点不动；闭包规模本身就是可断言的**结构性指标**（不依赖计时）；
8. **增删边的 CSR 重建是 O(V+E)**，本机 p99 ≤ 180 µs @1,000/1,500——**不需要动态拓扑序维护**即可达标，
   G2 如果实现更复杂的增量算法，必须先用本 spike 的骨架证明有收益。

**C. 日历与日期**

9. `IndexedCalendar` 的做法可直接移植（前缀和 + 序号表 + `exceptions` 双集合）；
   **主干现有 `countWorkdays` 是逐日循环且无 `exceptions`**，需在 G1/G2 重写（约 340× 的常数差）；
10. `dayOfOrdinal(k === workdayCount)` 的语义定为"**最后一个工作日之后的首个工作日**"——
    与地平线长度无关，否则 golden/差分比对会因容量差异假失败；
11. 容量：地平线按"全部工期 + 正 lag"的上界规划，并在不足时扩容重算（本 spike 用 2× 重试）。

**D. 验证策略（R-4 落地，可直接复用本 spike 的基建）**

12. **不变量/性质测试**（`EF = ES + D`、`TF ≥ FF ≥ 0`、四类关系边界方程、FF 独立重算）；
13. **手工推导用例**（声明式期望值表：4 关系 × lag 正/负/0 × 跨层级 × 日历例外）；
14. **独立参照实现差分**：把 `reference/cpm_reference.py` 与 `src/differential.mts` 的文件式 IPC
    搬进 G2，纳入 CI 门禁（本 spike 已证明 1,000 图 + 200 成环图零不一致是可自动化的）；
15. **负向对照必须有**：正确性侧（打坏期望值/语义必须被检出）与性能侧（已知更慢的实现必须被量出差别），
    否则判定集与计时骨架都可能是恒真式。

**E. 必须重测、不能直接继承的数字**

16. 浏览器/绘制侧的整帧预算（G5）；
17. 若 G2 改变数据布局或引入 Worker，需重跑本 spike 的 L2 骨架（`src/bench.mts`）并更新数字；
18. 2,000 任务以上的正式压测（v0.5）。

## 十、如何复现本结论

```bash
cd spikes/g0-s3-cpm-perf
pnpm install --ignore-workspace

# 主口径（Node 24.15.0，与 CONTRIBUTING / CI 一致）
& "$env:LOCALAPPDATA\nvm\v24.15.0\node.exe" src/run-all.mts
# 记录口径（本机默认 Node 26.7.0）
node src/run-all.mts
```

- 两次运行分别写 `evidence/perf-node24.md` / `perf-node26.md` 与 `breakdown-node24.md` / `breakdown-node26.md`（测量快照）；
  `correctness-report.md`、`differential-report.md`、`env.md` 与运行时无关，重跑应**逐字节一致**
  （实测：连续两次运行的 SHA256 相同）；
- 差分测试需要本机 Python；缺失时该层显式判为「未验证」并让 `run-all.mts` 非零退出。
  可用 `GANTTPILOT_PYTHON` 指定解释器（Windows 上的 `.bat` 垫片会自动经 `cmd.exe` 执行）；
- 原始迭代数据（每个 suite 的分位数、`batchSize`、min/max）落在 `out/raw/perf-node<N>.json`（不入库，可复算）；
- `run-all.mts` 的退出码只反映**测量基础设施是否可信**（L1/L1b/判别力对照），
  门禁 G3-a/G3-b/G3-c 的判定是数据（见 §二与 §四）。
