## §1 门禁步骤顺序：构建前移到类型检查之前（增补）

**声明**：**修订正文 §1 的实现方式（语义不变）**。

### 1.1 触发：远端 CI 的首次真实运行即失败

正文 §1 原写 `.github/workflows/ci.yml` "**未经真实运行验证**"。仓库接入 GitHub
（`xinmu/GanttPilot`，2026-10-06）后该文件**首次真实运行**，在 **Typecheck** 一步失败
（job 计时 20 秒），而**同一条 `pnpm typecheck` 在本地是绿的**。
"本地绿 / 远端红"这个分叉本身就是最有力的判据：两边唯一有意义的差别是
**工作区里有没有残留的构建产物**。

### 1.2 机制（已定位到可复现的最小条件）

- 消费者的类型检查**经包清单的 `types` / `exports` 解析工作区依赖**，例如
  `packages/render-core/package.json` 的 `"types": "./dist/index.d.ts"`；
- 而 `dist/` **不入库**（`.gitignore` 的"依赖与构建产物"一节）；
- 原 `STEPS` 次序是 `lint → typecheck → test → build`
  ⇒ **干净检出上，typecheck 跑在任何 `.d.ts` 存在之前**。

失败形态（`TS2307` 为因、`TS7006` 为果——模块解析不到，引用其类型的回调参数就退化成隐式 `any`）：

| 错误 | 形态 |
|---|---|
| `TS2307 Cannot find module '@ganttpilot/engine' or its corresponding type declarations.` | 遍布 `render-core` 的 `domain.ts` / `gesture.ts` / `viewModel.ts` / `index.ts` / `viewText.ts` … 与 `apps/web` |
| `TS7006 Parameter '…' implicitly has an 'any' type.` | `diagnostic` / `task` / `item` / `link` / `at` 等，**全部**出现在引用引擎类型的回调位置 |

**为什么本地长期是绿的**：本地工作区留着上一轮 `pnpm build` 的 `dist/`，
`typecheck` 于是解析到**陈旧但存在**的 `.d.ts`。
⇒ 结论：门禁此前**不是自洽的（hermetic）**，它只在一台"暖"工作区上成立，
**新贡献者克隆后第一次跑 `pnpm gate` 必然失败**——这与"合并硬门槛"的定位直接冲突。

### 1.3 复现（最小条件）

```text
# ① 移走构建产物：工作区即等价于干净检出
#    （packages/*/dist、apps/web/dist、apps/web/dist-offline）
# ② 只跑类型检查
pnpm typecheck
#    ⇒ §1.2 的 TS2307 / TS7006 全量复现（与原 CI 报文同族）

# ③ 反向验证：先构建再检查
pnpm build && pnpm typecheck
#    ⇒ 全绿（5 个工作区包全部 Done）
```

### 1.4 修法（采"改序"，不改任何一步的判定内容）

`scripts/gate.mjs` 的 `STEPS`：`build` 由第 4 位**提前到第 2 位**（紧随 `lint`），
`typecheck` 顺延为第 3 位。`.github/workflows/ci.yml` 同步把 `Build` 提到 `Typecheck` 之前。

**为什么选"改序"而不是"让 typecheck 不依赖产物"**：后者（给消费者包加 `tsconfig` 的 `paths`
指向 `packages/*/src`）会让类型检查**对着源码**而不是**对着真实的 `.d.ts` 表面**判定；
而 `exports` / `types` 本身就是本仓已冻结的契约面
（见 [0002-文档模型与序列化契约](../0002-文档模型与序列化契约.md) 一线各包的契约文档），
对着源码检查会**丢掉"发布出去的声明文件是否真的够用"这一条**。
改序保留该判定，代价只是次序。

**代价（明确接受）**：最贵的一步（构建）提前 ⇒ 机械性错误的暴露**晚于**构建；
整链耗时增加（实测见 §1.6）。

### 1.5 一并纠正的两处正文失准

本次同时订正正文 §1 里两处与事实不符的陈述（都属于"契约里写了会过期的东西"）：

同类的"会过期的当前值"清理：正文里"实测整链约 7 秒"与"推送前约 7 秒的门禁成本"

### 1.6 实测与回归判据

- **回归判据（本条的判据）**：`STEPS` 里 `build` 必须**早于** `typecheck`；
  等价的最小检查是"**删掉全部 `dist` 后 `pnpm gate` 仍全绿**"。
- **实测（2026-10-06，Windows 本机，工作区**无任何** `dist`）**：
  整链 **87 s**；其中前 8 步**全绿**（`test` 为 **809 条 / 55 个文件**），
  第 9 步 `docs:check` 因**本文件当时尚未创建**（正文链接已先落地）而失败并中止
  ——即本次落地的中间态，不是最终状态。最终状态以推送时 `pre-push` 的整链为准。
- ⚠️ 上述秒数**只登记在此**（记录层），正文不写死一个会过期的数字。
- **进 `pnpm gate`**：本文件的链接/锚点、`doc-index.json` 双射与体量由 `docs:check` 判定。
