## §1 `compute` 交出**真正用到的日历**（P-48 增补）——**新增**（只增字段，不改 `Schedule`）

> **起因**：`apps/web` 的拖动预览把**另一份文档**喂给 `compute`，而渲染层仍用"按**已提交文档**
> 规划的那份日历"翻译序号 ⇒ 向右拖远时完成序号越过该日历容量 ⇒ `buildView` 抛 `RangeError`
> ⇒ Vue 卸载整棵树、**整页空白**（人工报障 2026-10-05，取证见 [裁决 R46 §2(b)](../../00-baseline/裁决R46.md)）。
> [SCHEDULE.md](../../../packages/engine/SCHEDULE.md) §七 当时把容量写成**调用方义务**，实践证伪了这条。
> 裁定（**采"交出日历"这一路**，而非"给规划加一个猜的余量"）与两个候选的比较见
> [裁决 R47 §2](../../00-baseline/裁决R47.md)。

**1. 形状（只增加一个字段，判别联合与 `Schedule` 都不动）。**

```ts
type ScheduleResult =
  | {
      readonly ok: true;
      readonly schedule: Schedule;
      /**
       * `compute` 本次调用**真正用到**的日历：入参日历按 `expandToCoverDates` 覆盖到
       * 本次调用里出现过的全部文档日期（含项目开始日）之后的那一份。
       *
       * **凡把本结果的序号翻译成日期（或把日期翻译成序号），一律用它**——
       * 它是"这次计算可翻译"的载体，与 `schedule` 同源同次。
       */
      readonly renderCalendar: Calendar;   // 命名可微调，语义不可变（沿仓库成例）
    }
  | {
      readonly ok: false;
      readonly code: 'cycle';
      readonly message: string;
      readonly cyclePath: readonly string[];
      readonly diagnostics: readonly ScheduleDiagnostic[];
    };
```

**2. 三条边界（与形状同等重要）。**

| 边界 | 内容 |
|---|---|
| **`Schedule` 一字不改** | 索引约定、哨兵 `-1`、`es/ef`、`summaryEs/summaryEf/summaryProgress`、**"序号与容量无关"这条不变量**全部不变；新增字段只是"可翻译性"的载体 |
| **不是第二真相源** | 它是**派生量**：同一 `document` + 同一入参日历 ⇒ 逐值相同；**不落盘、不进文档、不进 xlsx/PPTX 导出物**（ADR 0002 §2 的序列化面不变） |
| **`ok: false` 时不产出** | 照 §1 正文："失败结果不产出半成品 `Schedule`"——成环路径不附日历 |

**3. 为什么不是"给 `createScheduleCalendar` 加编辑余量"。**

余量是**猜的常数**：一次拖动可以改工期、可以沿依赖链级联到链尾，"够不够"取决于链长与拖动幅度，
总存在把余量用光的编辑 ⇒ 同一个缺陷会以更靠后的位置复发（**仍是白屏**）。
而"交出真正用到的日历"是**结构性的**：序号按定义落在该日历覆盖的日期范围内，
渲染层与 `compute` 从此**共用同一份日历**。代价为零——那份日历本来就已经在 `compute` 内部构造出来了
（`expandToCoverDates`），本条只是把它交出来。

**4. 判据与迁移（实现轮的验收口径）。**

| 层 | 判据 |
|---|---|
| 引擎（`packages/engine`） | ① `ok: true` 时 `renderCalendar` 覆盖本次调用的全部文档日期与全部 `es`/`ef`（**逐任务断言**，含"文档比入参日历年长"的用例）；② `ok: false` 时该字段不存在；③ **容量无关性不受影响**（同一文档 + 不同容量入参 ⇒ `Schedule` 逐项相同这条既有不变量照旧） |
| 应用层 | `apps/web` 的渲染路径改用 `result.renderCalendar`（`useProject` 一处）；拖动预览与已提交两条路径共用它 |
| **看门人（翻红即收口）** | `packages/render-core/src/dragHorizon.spec.ts` **第 3 例**当前钉的是"向右拖远**必须抛错**"；本项实现后它**必须翻红**，断言改写为"**必须能建出视图**" |
| 记录制 / 人工 | 打包产物上"向右拖远不再白屏"（结构完整、`__GANTTPILOT_ERROR__` 为空）——归 G8 的那次人工复验 |

**5. 明确不做（与本条一并冻结）。**

- **不放宽"序号 ≥ 0"**：把项目起点上的任务继续向左拖**不产生位移**（[P-47 §3](../../00-baseline/裁决R46.md)），
  要支持"排到项目起点之前"须走 v0.5 的约束/手动模式（R-3）；
- **不改 `HORIZON_GUARD_DAYS` 的显式抛错语义**：引擎自己的扩容被拦住时**照旧抛错**——
  那是"文档日期不可表示"的真实失败，不能靠本字段掩盖；
- **不引入"渲染层自己扩容"**（`calendar.withHorizon(...)` 的第二份实现）：那会重新制造两个容量口径。

**6. 落地回填（2026-10-05）——一处**必要**的口径补齐。**

实现时发现 §1 的形状不足以兑现它在**判据表**里承诺的那条不变量（"`renderCalendar` 覆盖本次调用的
全部文档日期**与全部 `es`/`ef`**"）：

| 事实 | 后果 |
|---|---|
| `expandToCoverDates` 只按**文档日期**扩容（`maxDocumentDay`） | **文档日期定不住计算出来的完成序号**——一旦依赖链把任务推到远期，`projectFinish` 就落在文档日期之外 |
| `dayOfOrdinal(k)` 的合法域是 `k ∈ [0, workdayCount]` | `contentWidthFor` 要翻译 `projectFinish − 1`；不覆盖它 ⇒ `buildView` **照旧**抛 `RangeError` ⇒ 仍然白屏 |

**处置**：`compute` 在返回前追加一次 **`expandToCoverOrdinal(projectFinish − 1)`**——
按"工作日数上界"（`ceil((k+1) × 7/5) + 14`）翻倍扩容，**不依赖日历自身的容量**
（反推 `dayOfOrdinal(k+1)` 在容量不足时会自己抛，那正是要修的状态）。
两次扩容都是"够用就原样返回"的幂等操作，**代价为零**。

**落地值**：

- `ScheduleSuccess.renderCalendar` 已实现；**`ok: false` 侧不产出**（照 §1 的边界）；
- `Schedule` 一字未改（容量无关性不受影响：`schedule.contract.spec.ts` 的逐项相等断言仍绿）；
- **看门人已按计划改写**：`packages/render-core/src/dragHorizon.spec.ts` **第 3 例**由
  "必须抛错" ⇒ **"必须能建出视图"**，并加一条"入参日历明显偏小时 `renderCalendar` 严格更大"
  的**前提自证**用例（4 例全绿）；
- **应用层改道**（"一处 + 消费点"，不新增第二口径）：`useProject` 的 `renderCalendar` 计算属性
  **由 `scheduleResult` 派生**（同一份 `compute` 结果），`useChart` / `useExport` / `useGesture`
  与 `App.vue` 的翻译点一律改用它；
- **真机**：`smoke:build` 把 `t1` 向右拖 120 个工作日格 ⇒ 拖动期与松手后 `__GANTTPILOT_ERROR__` 为空、
  结构完整（判据进 `pnpm gate`）。

> **本节 §1 的"命名可微调、语义不可变"没有用到**：字段名就叫 `renderCalendar`。
