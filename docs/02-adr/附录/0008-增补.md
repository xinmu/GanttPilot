## §1 连接点的**可见图形**：正方形 → 圆（P-42 增补）——**新增**（**命中盒、判定区与显形规则一字未改**）

> 起因：`P-32` 的遗留行 ①"手柄与连接点的视觉打磨"（[待定清单 §一](../../01-roadmap/首版-待定清单.md)）。
> 维护者的人工裁决（[P-42](../../00-baseline/裁决R41.md)）：
> **现状**是"与条体等高的正方形白框"，**改为**"直径较条体高度略小的圆圈"。

**几何（纯函数，`packages/render-core/src/interaction.ts`）**

```
connectDiameterFor(bounds, rowHeight)
  = max(CONNECT_MIN_DIAMETER_PX,
        min(CONNECT_SIZE_PX, barHeightOf(bounds, rowHeight) - 2 * CONNECT_DIAMETER_GAP_PX))
圆心 = (connectLeftEdgeFor(bounds, side) + CONNECT_SIZE_PX / 2, bounds.y)
```

| 量 | 值 / 规则 |
|---|---|
| 直径（标准叶子条，条高 `24 × 0.6 = 14.4`） | **12** = `CONNECT_SIZE_PX`（**略小于条高**） |
| 直径（汇总条 8.4 / 里程碑菱形 12） | **6.4 / 10**（各自条高 − 2，随行收缩） |
| 下限 | `CONNECT_MIN_DIAMETER_PX = 6`（退化条上也看得见） |
| **三条不变量** | ① 圆心在**命中盒中点**上（跨在条端上）；② 圆心竖向 = **条心**；③ **可见 ⊆ 命中盒**（`diameter ≤ size`） |

**为什么不改命中区**：`connectSideAt` / `connectRevealFor` / `rowHandlesFor` 的命中判定**本来就只按 x**
（P-32 第三次复验的结论），而圆的外接盒正是那个 `<rect>` 的替代物 ⇒ 命中几何**一行未动**；
由此 §16.7 的三条结论（"看得见的图形一定点得中"、可用宽度 14 → 20 px、内侧不抢端点判定区）**继续成立**。

**判据（`interaction.spec.ts`，**进 `pnpm gate`**）**

- 正例：直径 ≤ 条高 − 2（略小于条高）且 ≤ 命中盒边长、圆心 = 命中盒中点 + 条心；汇总/里程碑/退化行同理（**逐行**复核）；
- **负向对照**：把直径换回"与条体等高"（`diameter = barHeight`）⇒ 上面两条不变量**同时变红**
  （这正是本批次要改掉的现状，NC 因此有判别力）；
- **记录制（打包产物）**：`--drag` 的 `collectHandleSample` 新增 `connectTag` / `connectBox`，
  判"DOM 真的是 `<circle>`""可见盒是正方形且 ≤ 命中盒边长"；选择器改为**不限定标签**的 `.connect-point`
  （否则换标签会让那条判据静默失效——P-32 落地时踩过一次同类的选择器失效）。

**代价（明确接受）**：连接点的**可见面积变小**（标准条 144 → 113 px²，约 −21%），
汇总行与里程碑行的可见面积收缩更多（12×12 → 6.4/10 的圆）；
换来的是"图形与元素的形状语言"分离（**圆 = 连接点、短竖线 = 端点手柄、方块 = 条体**），
以及"直径随条高变化"这条不再抢注意力的视觉口径。**命中可用宽度不变**（仍是 20 px）。

**不变的东西**：元素预算（连接点仍是每渲染行 2 个元素，`c₄ = 6·rows + 12` 一字未改）、
判定区（`zonesFor`）、判定区随条宽收缩（§16.1）、`Alt` 的处置（§16.3）、
重复边预检（§16.8）。

## §2 汇总条与里程碑的**交互面**、以及里程碑的工期不变量（P-43 增补）——**新增**（**上界不变**，只收紧"实际发射"与"入口"）

> 起因：批次③ 之后的人工复核报文（[P-43](../../00-baseline/裁决R42.md)）——
> ① "汇总条两端不能拖动，但鼠标会改变样式"；② "里程碑两端可拖动改长度，图上回退为菱形、左表工期已变"；
> 另有维护者对汇总端点依赖的裁定（文档层容忍 + warning + 图形层忽略）。**三条都是缺陷，不是待定项。**

**1. 汇总条：判定区、手柄、连接点、光标**全部撤下**。**

| 面 | 改动 |
|---|---|
| `zonesFor` | `kind === 'summary'` ⇒ `{ edgeL: null, move: null, edgeR: null }`（**整条没有判定区**）⇒ "能不能拖"**只有这一处判**（旧实现里光标按几何判、手势按语义判 ⇒ **两个真相源**，光标因此承诺了拖不动的动作） |
| `cursorForPointer` | 汇总整条返回 `default`（不承诺任何动作：日期是**子树聚合结果**） |
| `rowHandlesFor` | 汇总的 `connectPoints` 为空数组（**汇总端点上的依赖在传播中"等同不存在"**，SCHEDULE.md §四.6 ⇒ 不给"引擎不会兑现的承诺"） |
| `linkEntryFor` | 汇总返回 `null`（不能再从阶段拉线；**导入/手写进来的仍容忍 + warning + 灰线**——"UI 不给入口 ≠ 不支持读入"） |
| 计数 | `count.ts` 的**两路**（分类累加 + 逐项枚举）成对收紧；`ELEMENT_MODEL_G5.perRenderedRow` 是**上界**，值不变 |

**2. 里程碑：工期恒为 0，菱形只可整体移动（人工裁决）。**

| 面 | 改动 |
|---|---|
| 拖拽 | `dragModeOfZones` 的里程碑分支恒 `move`——**删掉** §5 的"按菱形中心分半（右半 = `resize-duration`）"；光标整条 `move`、**不随位置变化** |
| 左表 | `editToCommand` 的 `duration` 列在 `milestone === true` 时**拒绝**（`ok:false` + 可执行文案"请先在「里程碑」列改为'否'"）；"解除标记"是唯一出口（该列本就可编辑） |
| 依据 | 文档层**早有** `TASK_MILESTONE_WITH_DURATION`（warning："里程碑的 `durationDays` 应为 0"）⇒ 本条是把**已有的 warning 变成"UI 不给入口"**，不是新语义 |
| 一条一起读的口径 | `isMilestone = 里程碑标记 ∨ durationDays === 0 ∨ ef ≤ es` ⇒ **解除标记后工期仍为 0 的行图形上仍是菱形**（"0 工期即里程碑"是引擎口径）；"标记是唯一开关"属**引擎语义变更**，本轮不做 |

**3. 为什么 §5 能被改而 §16.1 不被动**：§16.1 管的是**条宽收缩**（几何），本条删的是里程碑**独有**的
"按中心分半"（语义），两者不重叠；汇总条则**从未**在 §16.2 的图元表里被授予过拖拽能力
（表里写的是"含汇总行"的**连接点**，而本条第 1 项正是把那一格收紧）。

**代价（明确接受）**：里程碑**不能再拖成任务**（要变任务：先解除标记 → 再改工期）；
汇总行**不能再作为建线端点**（导入物里的历史边仍照旧容忍 + 灰线 + warning）。

## §3 拖动期的**下游**也所见即所提交（P-45 增补）——**新增**（**契约面一字未改**：`SessionAnchor` 仍是 `{taskId, startOrdinal}`）

> 起因：`P-24` 的遗留 1（[§14.3](../0008-列身份所有权与拖拽交互契约.md) 的"明确不做"）——
> `resize-duration` 拖动期**条体本体**已画结果几何（§14 的 `drawnBarForRow`），
> 但**下游**仍按**文档里的旧工期**算、松手后一次到位。
> 裁决与实测见 [P-45](../../00-baseline/裁决R44.md)。

**1. 为什么不能只靠锚点。** 会话锚点只承载**位置**（`startOrdinal`）；**工期是文档字段**。
`compute` 看不见新工期 ⇒ 下游不动。要让 `compute` 看见，只有两条路：
把工期塞进锚点（**引擎契约修订**），或者把"新工期"以**文档**的形式喂进去（**零契约变更**）。
本轮裁**后者**，理由见 [P-45 §3](../../00-baseline/裁决R44.md)（锚点不落盘、v0.5 重做锚点解析、
ADR 0004 §1 拒绝"把未启用的语义写进签名"的同族理由）。

**2. 形状与口径（三条一起读）**

| 面 | 口径 |
|---|---|
| 内核产出 | `GestureUpdate.dragOutcome`（`DragOutcome \| null`）：**凡由拖动产生的更新**（`dragging` 与松手的 `released`）都带上；建线/空闲为 `null`。它带着**松手要提交的那个 `patch`** ⇒ 预览与提交**不可能**分叉 |
| 应用层 | `previewDocumentFor({document, taskId, patch})`：**结构性共享**的副本（只替换那一个任务对象，`links`/`project` 同引用）；`patch === null` 或 id 不存在 ⇒ 返回 `null`（回落已提交文档，不造"内容相同、身份不同"的副本） |
| `compute` 的入参 | `compute(previewDocument ?? document, calendar, anchors)`——**副本只替第一个入参**；锚点仍承载位置 |
| **不走**的路 | 副本**不进命令通道、不进撤销栈、不落盘**；落库仍然只有"松手 → `task.update` 经命令层"（[ADR 0003](../../02-adr/0003-命令层与事务契约.md)） |
| **日历与文档诊断只由已提交文档派生** | `createScheduleCalendar` 扫全表日期/工期总和定 `baseDay`（决定**序号 ↔ 日期的映射**）⇒ 让每帧都变的副本参与会改掉锚点路径的既有语义；`validateDocument` 同理（不该对"未提交的意图"报警） |
| 清预览的两个闸 | 手势侧"非 `dragging` 即清" + `commit()` 的"**一落库即作废**"（覆盖行内编辑/导入/撤销/重做/重置）。顺序上命令先落地、预览后清 ⇒ **不会出现"锚点已清、工期还是旧的"那一帧回弹** |

**3. 判据（进 `pnpm gate`，`packages/render-core/src/gesture.spec.ts`）**

- `previewDocumentFor` 的语义：只改那一个任务、其余**按引用共享**、原文档一字不动、两种 `null`；
- **下游同源**：`resize-duration` 拖动期 `compute(副本, 锚点)` 与**落库后重算**的后继行开始序号**逐位一致**；
  **负向对照**（写在同一条断言里）：只喂锚点（= 本轮之前的实现）在同一手势上必须给出**另一个**值；
- `dragOutcome` 与松手命令的 `patch` **逐字段相等**（"预览的那一份就是提交的那一份"）。
- 记录制（`--drag` 扩为 `move` / `resize-duration` 两种语义 × 两个滚动状态）：抓取点自证
  （`gestureMode === 'resize-duration'`）、位移判据（工期 = 拖动前 + N）、**下游跟随**
  （拖动期 == 松手后 **且** ≠ 拖动前）、**预览不落库**（拖动期 `revision` 不变、松手后 +1）。

**4. 本条的边界（明确接受）**：左表的「工期 / 完成日」单元格仍是**文档值**（松手后更新）——
本轮只让**图表**的下游跟随；左表是**文档视图**，"拖动期文档不写"这条既有口径不变。

**5. 不变的东西**：§5 的三语义与判定区、§13 的坐标口径与 `resolveDragOutcome`（预览与提交**同源**的
既有依据）、§14 的 `drawnBarForRow`（条体本体仍是结果几何）、`c₁`–`c₄` 与元素预算、
`SessionAnchor` 的形状、任何 DoD 数值。

>
> 维护者的 14 项人工复核确认了 **6 个根因缺陷**。其中 **R1（指针坐标取错参照物）与 R2（按下不判命中条体）
> 说明本 ADR §5 的"判定区"在实现里**没有被真正执行**——判定区的前提是"指针落在条体上"，
> 而实现先取坐标、再判区域，而坐标本身就已经错了。**§5/§6 的语义不变，被违反的是它的前提。**
>
> 另有三项**需要改本 ADR 才能修**，因此本轮只登记、不动代码：
>
> | 待改条款 | 现状 | 拟改方向 |
> |---|---|---|
> | **§5 判定区的可见性** | 条体两侧没有手柄、光标不随位置变化 ⇒ "可拖动区域"完全不可见 | 补端点手柄 + 光标暗示（命中区不变，只加**可见**图元） |
> | **§7 建线的入口** | 用 `Alt+拖动` 区分建线；**Windows 的 Chrome 把 Alt+左键拖动当"移动窗口"的系统手势**，事件到不了页面 ⇒ 建线在当前平台**不可用** | 换成不依赖系统修饰键的入口（候选：端点旁的独立连接点手柄 / 行左侧 gutter 连点拖出），并写明"建线的起手位置" |

- **第二次复验（维护者，2026-10-04）与真正的根因**：连接点按需出现**通过**；但"突起仍在且与条体不相连"、
  "方块仍偏上"、"方块仍不可交互"三条仍在。用**真实 `pnpm dev` 页面 + 只读 CDP 探针**逐值采数后定位到同一个根因：
  渲染层把 **`RowBox.y`（＝行顶）** 当成条心——**`TaskBounds.y`（条心）与 `RowBox.y`（行顶）相差 `rowHeight / 2 = 12 px`**：

  ```
  t1: 条 <rect y="28.8" h="14.4">  ⇒ 28.8 .. 43.2（条心 36）
      手柄 <line y1="22" y2="26">   ⇒ 22 .. 26（**浮在条体上方 4.8 px**）
  ```

  ⇒ 手柄悬空（且因高度从 8 改 4，"形式不同了"）、连接点整体上移 12 px；
  命中判定只按 `x`（**纯几何、本身正确**）⇒ 用户按"看到的位置"点不到。
  **修法**：`rowHandlesFor` 新增显式入参 **`barCenterY`**（`row.barY + row.barHeight / 2`）并在文档串写明两种 `y` 语义；
  `GanttChart.vue` 与 `measure.ts` 都传条心；`interaction.spec.ts` 新增"**竖向中心同源**"一例（**旧实现下必然变红**）。
- **第三次复验（维护者，2026-10-04）**："显示基本正常了，但仍**不可通过拖动连接点来拉线**"。
  用 **CDP `Input.dispatchMouseEvent`（真实指针，走浏览器命中测试）** 复现出两条：
  ① 可见方块（8 px、内缘贴条端）与**可用命中区**（14 px）不一致，条端右侧 `dx = −1..+2` 全部落空；
  ② **量到的是旧产物**——`packages/render-core/dist` 停在上一轮构建而 dev 服务器一直在用它
  （P-25 那条"负向对照之后必须强制重建"的**正向版本**：`pnpm dev` 之前先 `pnpm build`）。
  修法：连接点**跨在条端上**（`CONNECT_INSET_PX = 2`）、`CONNECT_SIZE_PX` 8 → **12**、
  命中区 = 可见方块 + 外侧 `CONNECT_HIT_PAD_PX = 4`（可用宽度 14 → 20 px）；
  拖动/建线期间连接点与手柄**一律不显示**（"结果几何"上不留幽灵方块），交互图元因此画在条/菱形**之前**；
  判据加"方块的每一处都点得中" + 回归断言 `dx = −1..+2` 必须命中。
  真实指针复验：方块 `1201..1213`（宽 12）× `515.4..527.4` vs 条 `514.2..528.6`（**跨条端且竖向居中**）、
  悬停光标 `crosshair`、**从方块中心按下拖到另一行松手产出 1 条依赖**。
- **返工带出的两处记录制订正**（都属于"改可见性/改模板后记录制会静默给假结果"）：
  ① `collectHandleSample` 原来在 hover **之前**读全图连接点条数 ⇒ 与"按需显形"冲突（恒 0，**假红**）；
  修法 = "`hoverAt` → `await nextTick()` → **只数指针所在那一行**"（判据 `= 2`）。
  ② 采样点的 x **从 DOM 属性读**（端点手柄在判定区边界，与条端相差 `edgePx`；连接点在条端外侧）——
  用 `row.xRight` 当"手柄处"会采到连接点上（**采错点**，不是实现错）。

**批次 B 的判据清单（`packages/render-core/src/interaction.spec.ts` 新增 + `gesture.spec.ts` 增量）**

- **判定区**：日档宽条上「左端 ⇒ 改开始 / 中部 ⇒ 整体移动 / 右端 ⇒ 改工期」，且与 `DRAG_EDGE_PX = 6`
  的旧式**逐值一致**（宽条行为不变是可验证的，不是承诺）。
- **随条宽收缩**：9 px 条的 `move` 区 = 6 px（`MIN_MOVE_ZONE_PX` 是条够宽时的下界）、3 px 条的 `move` 区**非空**（= 整条）；**负向对照**＝把边界公式换回
  "固定 6 px"后同一输入的 `move` 区**为空**（月档判定区被两端吃掉的字面复现）。
- **手柄与判定区同源**：手柄 x 恰等于 `zones.edgeL.end` / `zones.edgeR.start`；条外无手柄。
- **连接点**：落在两个手柄的**外侧**；只在连接点 ±`HIT_TOLERANCE_PX` 内起建线；
  **负向对照**＝把连接点 x 换成手柄 x ⇒ 同一按下点从"建线"变成"改开始"（正是 R4 里用户以为在连线的那个误判）。
- **光标**：`cursorForZone` 四值映射；`cursorForPointer` 在端点/中部/连接点/空白分别给出
  `col-resize` / `move` / `crosshair` / `default`；**并取非 0 滚动位置**（P-25 的纪律）。
- **建线类型**：`linkTypeFor` 的四格与 `FS`/`FF`/`SS`/`SF` 逐格一致；出端侧由连接点决定、
  入端侧由目标相对位置决定（两个输入不共变量的用例）。
- **回归与返工**：`Alt` 入口**已删除** ⇒ 判据是"只按住 `Alt` 拖动仍是拖动语义"；同一行的空白处（含手柄位置）按下**不产生手势**；
  连接点的命中区"内缘只留容差、外侧覆盖整个方块"（复验第 ③.3 条）、显示时机"靠近条端才显形"（第 ③.2 条）、
  手柄高严格小于条高（第 ② 条）。
