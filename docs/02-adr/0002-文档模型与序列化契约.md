## 背景

G1.2 要交付的是**冻结的文档形状**——它是 G2（排程）、G3（xlsx）、G4（渲染）、G6（持久化）
与 G1.3（命令层）的**公共输入**。按裁决 P-10：

- **G1.2 不可延后**（[首版能力顺序 §四](../01-roadmap/首版能力顺序.md)）；
- 它的设计决定已随分解一并冻结：**文档落盘用 ISO 日期 + 工作日工期，
  工作日序号只出现在引擎入参边界**（P-10 第 4 条，依据 S3 结论 §八）。

但原文 §6 只给了字段名清单，没给语义。落地时必须回答五个会渗透到所有下游的问题：
怎么表示"无日期"？`outlineNumber` 是存还是算？版本骨架是空壳还是真迁移？
调级是重排还是改父指针？校验失败怎么报告？本 ADR 记录这些决定的取舍。

## 决策

### 1. 落盘用 ISO 日期 + 工作日工期；序号只出现在引擎入参边界

文档里 `startDate: "2025-01-06"` 是「项目时区的日期」，`durationDays: 4` 是「4 个工作日」。
只有喂给 `Calendar` 时才翻译成整数序号（`Calendar` 的地平线由调用方按容量规划构造）。

**理由**：G1.1 的序号是**相对 `Calendar.baseDay`** 计的，且受地平线容量约束（容量不足要
`withHorizon()` 扩容重算）。若把序号写进文档，文档就被某一次日历构造的容量绑定了
——换一个 `baseDay` 或更小的地平线，同一份文档就读不出来。日期是**稳定**的，序号是**派生的**。

**代价**：每次进引擎都要做一次翻译（1,000 任务 × 2 个日期）。已由 G1.1 的 O(1) 索引前缀和覆盖
（S3 §八 C.9/C.11）。

### 2. `null` 表示缺失，且序列化始终显式写出全部规范字段

- `null` 是"无日期/无工期/未知进度"的**唯一**写法；`undefined` 在类型上不出现（模型内一律 `T | null`）。
- `serializeDocument` **总是写出**全部规范字段，包括 `null` 与空数组。
- `parseDocument` **同时容忍"缺键"**（归一为 `null`），但产出 `info` 级 `DOC_FIELD_OMITTED`
  ——**容忍而不静默**。

**理由**：这条让"往返一致"可以用 `toStrictEqual` 深比较来判定，而且是**真的**在验证
（若夹具漏写字段，规范化会补齐它，往返断言立刻失败）。若采用"省略 `null` 字段"的写法，
就会出现"显式 `null`"与"缺键"两种历史文件并存，往返断言必须先归一化才能比——
判据变成恒真式的风险大幅上升。

**代价**：文件略大（1,000 任务约多出十几 KB 的 `null`）。**明确接受**。

### 3. 一处刻意的不对称：`workDays` 省略，`exceptions` 显式

`CalendarSpec.workDays` 的语义由 G1.1 钉死：`undefined` = 用默认工作日（周一至周五），
空数组 = "没有任何工作日"（`Calendar` 会抛错拒绝）。若规范化把省略的 `workDays` 补成 `[]`，
往返回来的文档就变成**非法文档**。因此规范形状在 `workDays` 为空时**省略该字段**——
这是**语义的一部分**，不是省字节。

`exceptions` 的两个集合则始终显式写出：空数组对 G1.1 是合法输入，
显式写出让"未启用例外"与"误删字段"在 diff 中可区分。

### 4. `outlineNumber` 是派生值，校验只读、修复显式

真相源 = 层级（`parentId`） + 文档序（`tasks[]` 出现顺序）。编号只是它的像。

- **为什么仍然存进文档**：G3 的 xlsx 导出必须自足——不能"导出时现算"，
  否则导出的列语义就依赖引擎内部状态。
- **为什么不许它成为真相源**：`validateHierarchy` 对"存值 ≠ 计算值"报 `TREE_OUTLINE_STALE`；
  修复动作是调用方显式调用 `reindexDocument()`。**校验从不改写文档。**
- 迁移 v2→v3 对缺失的 `outlineNumber` 计算填入，但**已有值一律保留**
  （即使与层级不符）——否则"谁是真相源"就有两处，职责分叉。

### 5. 版本策略：CURRENT=3，v1/v2 作为未发布的历史形状冻结

原文 §6 写死 `version: 3`，而 v0.1 是首发（评估报告 §2 的 I-7 已指出这处矛盾）。
本决策的处理：

- `CURRENT_DOCUMENT_VERSION = 3`，**遵从原文**，不改写；
- `MIN_SUPPORTED_DOCUMENT_VERSION = 1`，实现**完整 v1→v2→v3 两跳链路**；
- **v1/v2 是"原文优先期"的历史形状，从未发布**——它们的差异由原文 §6 与 DM-08/09 反推冻结，
  并在 `schema.migration.spec.ts` 里作为夹具写死；
- 迁移表是**逐跳注册表 + 跳数上界**：每一步要求版本严格递增，成环会以 `MIGRATION_CYCLE` 抛错
  而不是死循环。

**理由**：出口条件要求"旧版本 → 当前版本可迁移"。只接受 v3 会让这条断言变成空壳
（"迁移骨架"只剩一个 registry 外壳）；而实现两跳链路使骨架被**真实走过**，
并且"未知版本明确报错"的负向用例因此有判别力。

**代价（明确接受）**：要为两个从未发布的形状写冻结夹具与迁移测试（约 21 例）。
**未来规则**：一旦某个版本**真实发布**，其形状**不得再改写**，只能追加新版本与新迁移函数。

### 6. 调级：重排文档序、带走整棵子树、全量重编号

- **兄弟顺序 = 文档序**，不引入 `order` 字段（用户自定义排序属 P1-04）。
- **移动带走整棵子树**：只移动任务本身会破坏「父节点先于子节点出现在文档序」这一不变量
  ——父节点挪到后面、子节点留在前面，而该不变量是编号算法与"兄弟顺序 = 文档序"的共同前提。
  移走整棵子树则天然保持子树内部关系，唯一变化的只有子树根节点的 `parentId`。
- **落点的首选措辞是"插到某任务的整棵子树之后"**，而不是"同级第几位"：
  位置型语义在"移动块 + 子树"下极易算错一格（开发过程中实际因此写出过三个错误判据），
  子树型则天然满足不变量与"最后一个子节点"的直觉。
  `moveTask` 仍接受 `index`（供 G5 的拖拽落点使用），但 `indent`/`outdent` 走子树型。
- **全量重建，不做增量索引**：依据 S3 §八 B.8，1,000 规模上 CSR 全量重建 p99 ≤ 180 µs，
  **先要可测的正确性**；增量优化必须先用实测证明有收益。
- 内部还有一条**兜底断言**：结果序列里父节点必须早于子节点，否则返回 `WBS_CYCLE`
  （"算法 bug"宁可显式失败，也不产出静默损坏的文档）。

### 7. 校验失败用结构化诊断，不用异常文本

`validateDocument(input): readonly DocumentDiagnostic[]`，`code` 是稳定的字符串字面量联合，
`severity ∈ { error, warning, info }`，并带 `path`（如 `tasks[3].startDate`）、
`taskId`、`linkId`。

**理由**：G3 的导入向导必须逐条展示"哪一行/哪一列/为何失败"（G-8），
调用方不应去解析错误消息文本。`parseDocument` 在 `error` 级诊断上抛 `DocumentError`
（携带**全部**诊断，含 `warning`/`info`），因此调用方永远拿不到"半合法"的文档。

**调级操作则不抛错**（返回 `WbsResult` 判别联合）："拖到最外层再按 Shift+Tab"是正常交互，
不是异常；`WBS_SAME_POSITION` 让 G5 据此跳过撤销栈压入。

### 8. 日历校验直接调用 G1.1 的 `Calendar` 构造器

`validateDocument` 不重写日历规则，而是对每份 `CalendarSpec` 试构造 `new Calendar(spec, ...)`
并捕获 `RangeError`。**这样"文档里合法的日历"与"引擎构造得出的日历"不可能分叉**——
G1.1 收紧规则时文档侧自动跟随。

## 备选方案与为何未采用

| 方案 | 未采用原因 |
|---|---|
| 用 `undefined`/缺键表示"无日期" | JSON 往返天然丢键；`exactOptionalPropertyTypes` 下类型与运行时不一致；往返断言要先归一化才能比（判据有变成恒真式的风险） |
| 只接受 `version: 3`，未知版本一律拒绝 | 出口条件的"旧版本可迁移"会变成空壳；迁移骨架不被真实走过 |
| 把 `outlineNumber` 改成"只在导出时计算" | G3 导出就不自足；且 xlsx 往返的编号列无法对账 |
| 让校验顺便修好编号（归一化型校验） | 会同时存在"校验"与"修复"两条写路径；本决策把修复收口到 `reindexDocument` 一个显式动作 |
| 用 `order` 字段表达兄弟顺序 | 文档里出现两个顺序来源（数组序 vs `order`）必然分叉；P1-04 需要时再立字段 |
| 移动只改 `parentId`、不动文档序 | 会破坏「父节点先于子节点」不变量，编号算法随之失效 |
| 引入 zod/valibot 做 schema 校验 | 违反"三包零框架依赖"与最小依赖面取向；本块校验规则不需要外部库，且诊断信息需要自定义码 |
| 用抛错报告校验失败 | G3 的导入向导需要**逐条**收集问题（不能第一条就中断），异常控制流不适合 |
| 为 v1/v2 引入真实迁移数据 | 它们从未发布，没有真实样本；反推冻结是唯一可行做法，代价已登记 |

## 影响

- **G2**：`compute()` 的入参形状即本模型（`tasks`/`links`/`calendars`/`constraints`）；
  进引擎前需把 ISO 日期翻译成序号并规划地平线容量。`constraints`/`manual` 的语义归 v0.5。
- **G3**：导入向导复用 `validateDocument` 的诊断面；导出的规范列序来自 `reindexDocument`
  之后的任务顺序；`outlineNumber` 可直接作为 WBS 列。
- **G4**：渲染只读文档 + `Schedule`；`collapsed` 只是状态字段。
- **G6**：持久化落盘就是 `serializeDocument` 的产物；IndexedDB 里存这份文本即可。
- **G1.3**：命令层可以按本形状设计 before 镜像（R-2 要求"在设计时就定"），
  且调级已由 `wbs.ts` 的纯函数承担，命令层只需包装成 `Command`。
- **新增依赖**：**零**。`pnpm gate` 的 `license:check` 仍为 24 个运行时依赖。
- **不改动**：`tsconfig` / `vitest.config.ts` / `eslint.config.mjs` / `eslint-rules.mjs`
  均无需变更——新文件落在既有覆盖内（spec 由 `*.spec.ts` 规则排除于构建之外）。
