## 背景

ADR 0004 在 G2 开工前冻结了排程契约：锚点规则（含会话锚点）、汇总任务与里程碑、项目起点与负 lag 截断、
`Schedule` 形状与诊断码表、检环 API、容量与扩容、验证与门禁口径。**冻结内容本 ADR 一字不改。**

但落地时发现一批它**没有写、而实现必须定**的口岸，其中三处会影响下游的公共形状：

1. **`ScheduleResult` 的整体形状**（ADR 只有 `compute(...): ScheduleResult` 这一行，从没展开过它）；
2. **`Schedule` 数组的索引约定与哨兵**：ADR 说"汇总任务派生值（叶子任务为 -1）"，但没写
   汇总行在 `es`/`ef` 里放什么、也没写数组按什么序索引——而 G4 要靠它"一行一槽"地画；
3. **项目起点第②级的"锚点"到底指哪些日期**（ADR §4 的措辞是"全部锚点序号的最小值"）。

另有一处**必须显式改口径**的地方：ADR §6 的 `wouldCreateCycle(links, candidate)` 签名里**没有文档**，
因此它看不到"谁是汇总任务""哪些边端点是汇总"。于是"传播中忽略汇总端点边"这条规则**不可能**
同时施加在 `wouldCreateCycle` 上。ADR §3 的措辞（该边"在传播中被忽略"，"同一事实只有一个实现口径"）
留下了两种读法，本 ADR 选定其一并说明理由（见 §4.8）。

本 ADR 的手法与 ADR 0002 §8 / 0003 §4 / 0004 §3 一致：**同一类事实只有一个实现口径**——
能复用 G1.2/G1.1 既有判定的地方一律复用（`summaryTaskIds`、`Calendar` 的序号翻译），不新造规则。

## 决策

### 1. `ScheduleResult`：照仓库成例的判别联合

```ts
type ScheduleResult =
  | { readonly ok: true; readonly schedule: Schedule }
  | {
      readonly ok: false;
      readonly code: 'cycle';
      readonly message: string;
      readonly cyclePath: readonly string[];   // 成环路径（首尾同一 id），G5 高亮用
      readonly diagnostics: readonly ScheduleDiagnostic[];  // 本情形下只含 cycle 一条
    };
```

**理由**：`CommandResult`（ADR 0003）/`SessionResult` 已是 `{ok:true,…} | {ok:false, code, …}`；
失败结果**不产出半成品 `Schedule`**（ADR 0004 §6"不产出排程"）。失败时不附带其它诊断，
是为了让"成环"这一条**确定性**地可断言；G3 的问题清单由"文档校验诊断 + 本结果"两层拼装。

### 2. 索引约定与哨兵

- `Schedule` 的每个数组**按 `document.tasks` 的文档序索引**，`taskCount === document.tasks.length`。
  理由：G4 是"一行一槽"的渲染，索引若换成"叶子压缩序"，渲染层就要再维护一张映射表；
  而 ADR 0004 §5 已经用了 `taskCount` 与"叶子任务为 -1"的措辞，文档序是唯一自然读法。
- 哨兵（`LEAF_SENTINEL = -1`）：

  | 字段 | 叶子任务 | 汇总任务 |
  |---|---|---|
  | `es` / `ef` | 排程序号 | **-1**（不参与排程，无排程序号） |
  | `anchored` / `driven` | 0/1 | **0** |
  | `summaryEs` / `summaryEf` / `summaryProgress` | **-1** | 聚合值 |

- 因此 **`es[i] === -1` ⟺ 第 i 行是汇总任务**——这是冻结形状里唯一的汇总判别式（形状里没有 `isSummary` 位），
  G4 必须用它来选"汇总条"的绘制分支。`-1` 不是合法序号（G1.1 已定负数序号无定义），不会与真实值混淆。
- `summaryProgress` 是 `Float64Array`：**叶子为 -1**；汇总为工期加权进度；权重和为 0 时为 `NaN`（ADR 0004 §5）。

### 3. 工期解析优先级（不改写文档）

叶子任务的**解析工期**：

1. `durationDays !== null` → 用它；
2. 否则 `startDate` 与 `endDate` 均非空 → `calendar.workdaysBetween(start, end)`（半开区间，与 G1.1 同口径）；
3. 否则 → `0`。

`endDate` 是**派生显示值**（ADR 0004 §2）：当 `startDate`、`endDate`、`durationDays` 三者齐备而
`workdaysBetween(start, end) !== durationDays` 时给 `info` 级 `endDateStale`，**不报错、不改写文档**
（验收基线：G1.2 的四个夹具在此定义下**零诊断**）。

### 4. 锚点四情形与 `anchored` / `driven`

判定一律在**有效图**上做（有效图 = 传播时使用的图，见 §8）：

| 行 | 判定 | 排程语义 | 位 |
|---|---|---|---|
| ① | `startDate !== null` ∧ 无有效入边 | `ES = 文档 startDate 的序号` | `anchored=1` |
| ② | `startDate === null` ∧ 无有效入边 | `ES = 项目起点`，报 `undated`（warning） | `anchored=1` |
| ③ | 有有效入边 ∧ 无会话锚点 | `ES = max(全部入边约束)`；文档日期被覆盖 | `driven=driven?`（见下） |
| ④ | 有有效入边 ∧ 有会话锚点 | `ES = max(锚定序号, 全部入边约束)`；锚定早于入边约束时报 `anchorConflict` | `anchored=1` |

- `driven = 1` **当且仅当**：情形③ ∧ `startDate !== null` ∧ **该日期的序号 ≠ 推导出的 ES**。
  这与 ADR 0004 §2 的 `dateOverridden`（"仅当与文档日期不同"才报）**严格同源**，
  避免出现"位说被覆盖、却没有诊断"的分叉；情形③但日期恰好吻合时不设位、不报诊断。
- 会话锚点的健壮性口径：`taskId` 未知 → 忽略 + `anchorUnknown`；指向汇总任务 → 忽略 + `summaryIgnored`；
  `startOrdinal` 不是有限整数 → 忽略 + `anchorUnknown`；同一任务重复给出 → **后者胜**
  （会话里最后一次拖动才是用户意图）。负整数序号不特殊处理：它参与 §5 的截断（raw < 项目起点 ⇒ 截断）。
- 情形①②④ 的 `anchored=1` 是**结构位**（位置由锚点决定），不随"入边约束是否更大"翻转（ADR 0004 §5 的措辞是"情形①②④"）。
  情形④ 中入边约束更大时，位置实际由入边决定——这由 `anchorConflict` 表达，不用再增一个位。

### 5. 项目起点（ADR 0004 §4 第②级的"锚点"指什么）

**三级回落**：

1. `project.startDate` 非空 → 其工作日序号；
2. 否则 → **文档中全部非空 `task.startDate` 的序号的最小值**；
3. 否则 → `0`（即 `Calendar.baseDay` 的序号）。

- **第②级取"全部任务日期"而不是"仅情形①的锚点日期"**：ADR 0004 §4 的不变量是
  "起点**不得**由日历容量参数（`baseDay`、地平线长度）决定，**除非**文档完全没有日期信息"。
  若只取情形①的日期，则"所有源任务都无日期、但下游任务有日期"的文档会回落到 `baseDay` ——
  而该文档**有**日期信息，直接违反自己的不变量。取"全部任务日期"后，第③级**只在文档真的没有日期时**触发。
- **会话锚点不参与项目起点**：项目起点是**文档级**概念，会话锚点是会话级状态（ADR 0004 §2：不进文档）。
  若纳入，拖动 A 会改变**其它任务**的截断下限，产生"拖一个任务、别的任务日期跟着跳"的耦合。
  在情形④里锚点早于起点时，该任务自己的 `ES` 仍按 §6 截断到项目起点——与纳入起点相比，
  差异只出现在**其它**任务上，而那正是我们要避免的。
- 日期早于 `Calendar.baseDay` 时该日期按**序号 0** 处理（§7），该情形也会计入 `clampedStart`。

### 6. 截断、计数与诊断

`ES` 的求解是**两步**（ADR 0004 §4 已定，这里只把它写成可实现的顺序）：

1. `raw = max(全部入边约束, 锚定序号?)`（无入边且无锚点时 `raw = 文档日期序号 ?? 项目起点`）；
2. `raw < 项目起点` → `ES = 项目起点`、`clampedStarts += 1`、并报一条带 `taskId` 的 `clampedStart`（warning）。
   **不阻断排程、不改写文档、不产出负序号。**

### 7. 地平线边界（ADR 0004 §7 的落地机制）

ADR 0004 §7 要求"容量不足时 `withHorizon(2×)` 重建重算、且对调用方不可见"。落地后**机制**与 ADR 的
字面描述略有不同，**可观察语义完全相同**，在此写清映射：

- 传播本身是**纯整数算术**（闸 ADR 0004 §5：`Schedule` 只出序号），不需要地平线——
  因此"扩容后重算"在实现里只可能影响**日期 → 序号**这一步；
- 实现改为**入口一次性扩容**：取文档中全部日期（含 `endDate`）的最大日序号，若它超出
  `calendar.lastDay`，则以 `withHorizon(spanDays × 2)` 循环扩容（上限 `HORIZON_GUARD_DAYS`）后再做翻译；
- **不变量**：同一文档在"任意足够/不足够的容量"下得到**逐项相同**的 `Schedule`（单测口径照 G1.1 的
  "先抛错、扩容后与直接构造大窗口逐项相同"）；
- **日期早于 `baseDay`** → 该日期的序号取 `0`（并计入 `clampedStart`）；
- **日期超出 `HORIZON_GUARD_DAYS` 可表示域** → 抛 `RangeError`（见 §10）。
- **调用方职责（重要）**：`Schedule` 只出序号，ISO 翻译仍由调用方自己的 `Calendar` 承担。
  若调用方日历容量小于 `projectFinish`，`isoOfOrdinal()` 会抛错——**扩容后序号不变**，调用方用
  `withHorizon()` 扩容即可。为了不让这条规则只活在文档里，G2 提供 **`createScheduleCalendar(document)`**
  （§11）：它按本 ADR 的口径一次性把 `baseDay` 与 `spanDays` 规划好，用它构造的日历**永不触发内部扩容**（有单测）。

### 8. 图的两种口径：**传播**忽略汇总端点边，**检环**是结构性的

这是本 ADR 唯一对 ADR 0004 措辞做出**明确选择**的地方：

| 用途 | 用到的边 |
|---|---|
| 传播（`ES`/`EF`、汇总聚合） | **排除**任一端点为汇总任务的边（ADR 0004 §3：该边"等同不存在"），并报 `summaryIgnored`（warning，对齐 G1.2 的 `LINK_SUMMARY_ENDPOINT`） |
| 拓扑序与**检环**（`compute` 的成环判定、`cyclePath`） | **全部边**（结构性） |
| `wouldCreateCycle(links, candidate)` | **全部入参边**（结构性） |

- **为什么检环不看汇总端点**：ADR 0004 §6 的 `wouldCreateCycle` 签名只有 `links` 与 `candidate`，
  **看不到任务层级**；让 `compute` 用"排除汇总端点"的图检环，就会出现"预检说成环、`compute` 说没问题"
  （或反过来）的两个真相源——而 ADR §3 的立论正是"同一事实只有一个实现口径"。
- **为什么"结构性检环"可接受**：环是**图的性质**，与端点是否汇总无关；汇总端点的边只是"不参与传播"。
  后果是一个只经由汇总端点的环也会让 `compute` 拒绝排程——这是**保守**方向（G3 导入会丢弃成环边、
  G5 预检会拒绝建边），不会产出错误排程。
- **实现**：只有一份 CSR，附一个逐边 `ignored` 标志（端点含汇总 ⇒ 1）。Kahn 入度法与拓扑序按**全部边**算，
  正向传播只读 `ignored === 0` 的入边，且"有有效入边"的判定同样只数 `ignored === 0` 的边
  （所以只连汇总端点的任务在传播上是**源任务**，走情形①②）。
- `affectedClosure` 沿**全部出边**取后继闭包（宽进：多收行不会出错，少收行会留下脏几何）。

### 9. 汇总派生值、里程碑与空项目

- 汇总任务 = **有子任务的任务**（判定直接复用 `wbs.ts` 的 `summaryTaskIds`，不新造规则）。
- 聚合口径（ADR 0004 §3/§5 只给了"子树聚合"与"工期加权"，这里补齐 null 进度与权重为 0 的口径）：

  | 字段 | 定义 |
  |---|---|
  | `summaryEs` | `min(子树内全部叶子的 es)` |
  | `summaryEf` | `max(子树内全部叶子的 ef)` |
  | `summaryProgress` | `Σ(dᵢ · p̃ᵢ) / Σ dᵢ`，其中 `dᵢ` 为叶子解析工期、`p̃ᵢ = progress ?? 0`；`Σ dᵢ === 0` → `NaN` |

  `progress === null`（"未知"）按 **0** 计入分子**且照常计入分母**——与"未知即未开始"的口径一致，
  也是 `summaryProgress` 唯一不用额外哨兵就能算完的做法。
- 汇总任务**一定有子树**（有子任务才有汇总），故不存在"空子树"的聚合；`min/max` 不会取到空集。
- `milestoneCount` = 叶子任务中 `milestone === true` **或** `durationDays === 0` 的个数
  （字面照 ADR 0004 §3 的"`milestone: true` / `durationDays === 0` 的叶子任务"；
  用**字段值**而非解析工期，避免"无日期无工期"的占位节点被误计为里程碑）。
- 里程碑**照常参与传播**（工期为解析工期，通常 0）。
- **空项目 / 全是汇总任务**：`projectFinish = projectStart`、`milestoneCount = 0`、所有叶子槽为 -1。
  不抛错、不产出 `NaN` 序号。

### 10. 诊断码表与消息口径（ADR 0004 §5 码表的落地）

| code | severity | 触发 | 附带 id |
|---|---|---|---|
| `undated` | warning | 情形②（源任务无日期） | `taskId` |
| `dateOverridden` | warning | 情形③且文档日期与推导 ES 不同（**与 `driven` 同源**） | `taskId` |
| `clampedStart` | warning | `raw < 项目起点`，或文档日期早于 `baseDay` 被按序号 0 处理 | `taskId`（文档级起点回落时不带） |
| `anchorConflict` | warning | 锚定序号 < 入边约束的最大值 | `taskId` |
| `anchorUnknown` | warning | 未知 `taskId`，或 `startOrdinal` 非有限整数 | `taskId` |
| `summaryIgnored` | warning | 汇总端点边被传播忽略；或锚点指向汇总任务 | `linkId` / `taskId` |
| `endDateStale` | info | §3 的 `endDate` 与工期不一致（**对所有任务判定，含汇总任务**：这是文档级一致性事实，不该被静默吞掉） | `taskId` |
| `constraintsUnused` | info | 任务 `constraints` 非空**或** `manual === true`（R-3：语义 v0.5，v0.1 只报不解释） | `taskId` |
| `cycle` | error | 只在失败结果里出现，**不产出排程** | 无（路径在 `cyclePath`） |

- 诊断条目复用 `wbs.ts` 的 `DiagnosticLike`（`{code, severity, message, path?, taskId?, linkId?}`），
  不新造形状；**码值小写驼峰**是 ADR 0004 §5 冻结的排程侧码表，与文档侧的 `SCREAMING_SNAKE` 是两个码空间。
- **`constraintsUnused` 一个码承担两个留位字段**（`constraints` / `manual`），消息文案区分；
  理由：ADR 0004 §5 的码表是**闭集**，不为"同一个原因（v0.5 未启用）的两种写法"再开一个码。
- **不新增码**：悬空/自环之外的"不可解析边"一律**忽略且不报告**——`compute` 的前置条件是
  "文档通过 `validateDocument` 且无 `error`"（ADR 0002 §8 / 0003 §4 的同一手法），
  非法文档不由内核兜底；上表**不加**这一条，避免码表膨胀成"校验层的副本"。
- **两处有意抛出**（都是"调用方/数据超出契约"而非用户数据可恢复的情形）：
  ① 文档日期超出 `HORIZON_GUARD_DAYS` 可表示域；② `parentId` 违反 G1.2 的"父先于子出现在文档序"不变量
  （见 §12）。二者都抛 `RangeError` 并在消息里给出下一步动作，**不做静默截断**。

### 11. 容量规划的公共入口：`createScheduleCalendar(document)`

```ts
function createScheduleCalendar(document: ProjectDocument): Calendar;
```

- `baseDay` = 文档中最早的非空日期（`project.startDate` 与全部 `task.startDate`/`endDate` 取最小）；
  全无日期时用 `DEFAULT_PROJECT_BASE_DAY_ISO`；
- 生效日历规格 = `project.baseCalendarId` 指向的那份，空串 → `calendars[0]`（R-1：v0.1 只有项目日历生效）；
- `spanDays` = `horizonDaysFor(需要的自然日上界)`，上界取
  "文档日期跨度 + Σ叶子解析工期 + Σ正 lag"；
- **它只做容量规划**，不改变排程语义：调用方也可以自己按 ADR 0004 §7 的口径构造日历，
  只要容量足够、`baseDay` 不晚于任何文档日期即可。

**理由**：ADR 0004 §7 把"容量按 `horizonDaysFor(Σ工期 + Σ正 lag)` 规划"写成了调用方义务，
但**没有**给出"生效日历是哪一份""`baseDay` 取什么"的落地入口；这两件事又是 G3/G4/G7 三处**都会重复实现**的。
把它收敛成一个函数，等价于 ADR 0002 §8 让"日历校验直接调用 `Calendar` 构造器"的手法。

### 12. 汇总聚合的实现依赖：G1.2 的文档序不变量

汇总聚合按"**逆文档序**一遍累加到 `parentId`"实现（O(V)、零递归）。它成立的前提是
G1.2 已冻结的不变量——**父节点先于子节点出现在文档序**（`wbs.ts` 的兜底断言）。
因此实现里加一条 O(V) 的前置检查：任一 `parentId` 的索引 > 自身索引即抛 `RangeError`（§10 的有意抛出②），
**不静默算出错误汇总值**。

### 13. 检环 API 的路径语义

```ts
function wouldCreateCycle(
  links: readonly DocumentLink[],
  candidate: DocumentLink,
): { readonly cyclic: boolean; readonly path: readonly string[] };
```

- 当且仅当**已存在**路径 `candidate.to → … → candidate.from` 时 `cyclic = true`；
  `path = [candidate.from, …, candidate.from]`（**首尾同一 id**，G5 直接照序列高亮）；
- 自环候选（`from === to`）→ `cyclic = true`，`path = [from, from]`；
- 端点不在 `links` 里出现（悬空）→ `{cyclic: false, path: []}`：**预检只管成环，不管有效性**（有效性归 `validateDocument`）；
- 邻居遍历顺序 = `links` 的数组序（确定性）；`compute` 的 `cyclePath` 同构同序；
- **不判汇总端点**（§8）：`links` 里给了什么就按什么算，调用方若要与传播口径一致需自行过滤——**默认不滤**（保守）。

### 14. 纯函数与确定性

- `compute` **绝不修改** `document`、`calendar`、`anchors`（单测用"前后深比较"证明）；
- 不引入时钟、随机数、全局自增：同一 `(document, calendar, anchors)` → **深比较相同**的 `Schedule`；
- **排程结果不写回文档**（ADR 0004 §2 已定）；命令层不需要为级联引入新形状；
- 返回的 `Schedule` 是新鲜分配（含类型化数组），调用方拥有它；`computeInto`/预分配复用照 ADR 0004 §5
  作为**实现细节**保留，**不进公共 API**。

## 备选方案与为何未采用

| 方案 | 未采用原因 |
|---|---|
| 汇总行在 `es`/`ef` 里镜像聚合值 | 形状里没有 `isSummary` 位，渲染层需要一个判别式；镜像又制造"同一个值两处"的第二个真相源。-1 让"不是排程行"可判别，且不可能与真实序号混淆 |
| 叶子压缩索引（只给叶子分配槽位） | G4/G7 要按文档行遍历，压缩索引强迫渲染层维护映射表；且 ADR 0004 §5 的 `taskCount`/"-1 表示叶子"措辞指向文档序 |
| 项目起点只取"情形①锚点"的最小值 | 会让"源任务全无日期、下游有日期"的文档回落到 `baseDay`，直接违反 ADR 0004 §4 自己的不变量 |
| 项目起点纳入会话锚点 | 拖动 A 会改变其它任务的截断下限（跨任务耦合），而项目起点本应是文档级概念 |
| 汇总锚点当作普通锚点处理 | 汇总任务不参与排程，锚点无处可落；静默忽略又违反"不静默"惯例 ⇒ 忽略 + `summaryIgnored` |
| `summaryProgress` 只对"进度已知"的叶子加权 | 会让"进度未知"的叶子完全不参与汇总进度，与"权重=工期"的措辞冲突，且需要再定义"权重为 0"的第三种情形 |
| 里程碑计数用**解析**工期为 0 | "无日期无工期"的占位节点解析工期也是 0，会被误计为里程碑；用字段值才与 ADR 0004 §3 的措辞一致 |
| 检环也排除汇总端点边 | `wouldCreateCycle` 的签名看不到层级 ⇒ `compute` 与预检必须各有一套图 ⇒ 两个真相源（ADR §3 的立论正是反对这个）|
| 悬空边报一个新诊断码 | 会破坏 ADR 0004 §5 已冻结的闭集码表，且把校验层的职责搬进内核；改为写明"前置条件 + 忽略" |
| 容量不足时抛错要求调用方扩容 | ADR 0004 §7 已定"扩容对调用方不可见"；且 `Schedule` 只出序号、容量不改变任何一个序号 |
| 新增 `plannedWorkdays(document)` 之类的纯数值导出 | 只给数值仍然要调用方自己决定 `baseDay` 与"哪份日历生效"；`createScheduleCalendar` 把这三件事一次收口 |
| 汇总聚合用递归/显式栈的树遍历 | 文档序不变量（§12）已经保证"逆序累加"正确，O(V) 一遍且零栈；递归还会在深 WBS 上碰调用栈 |
