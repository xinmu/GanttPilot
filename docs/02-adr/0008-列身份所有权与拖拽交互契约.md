## 背景

G5 是**第一个"所感"能力块**：它把 G4 的"看得见"变成"改得动"，因此它的风险与 G1–G4 不同——
不再主要是"口径有多种都说得通"，而是**三类跨块耦合**：

1. **列身份的所有权**：左表列集合（ADR 0007 §8）、`cellText` 的列分支、编辑通道的可编辑列集合、
   G7 导出投影都要同一份列身份，而它们**都不需要 `exceljs`**。G3 把列契约放在 `xlsx-protocol`，
   于是"渲染侧要用列名"就必须 import 协议包；[P-19](../00-baseline/裁决记录.md) §5 ② 把这条依赖方向
   列为**待裁决的开工前置**（两条候选：A 反转所有权 / B 仅 `import type`）。
2. **一次手势跨了五处既有契约**：`Schedule` 的会话锚点入参（ADR 0004 §2）、`task.update` 的字段口径
   （[COMMAND.md](../../packages/engine/COMMAND.md) §二）、事务 = 一个撤销单元（同 §五）、
   检环预检与成环路径（[SCHEDULE.md](../../packages/engine/SCHEDULE.md) §八）、
   元素预算与"拖拽期不做逐帧 DOM 重建"（ADR 0007 §6.6/§6.7）。
3. **P-19 暴露的落点问题**：可测的纯函数若留在 `apps/web`，就**不在门禁覆盖内**（ADR 0007 §2 早已写过这条代价）。

本 ADR 与 ADR 0004/0006/0007 的分工相同：**把形状与语义在开工前冻结**（§4–§11），
数值类判据（拖动帧预算、松手耗时）按 [P-9](../00-baseline/裁决记录.md)/[P-17](../00-baseline/裁决记录.md)
进**记录制**，需要门禁的部分落 Node 侧。

## 1. 决策（列身份）：所有权反转给 `render-core`（候选 A）

**`ColumnKey` / `ColumnSpec` / `ColumnRequirement` / `COLUMN_SPECS` / `SHEET_NAME` / `HEADER_ROW` /
`DATE_LIKE_COLUMNS` / `columnSpecOfHeader` / `columnKeyOfIndex` / `columnIndexOfKey` 的唯一真相源
迁到 `packages/render-core/src/columns.ts`**；`packages/xlsx-protocol/src/columns.ts` 改为**转型再导出**。

依赖方向变为：

```
engine  ←  render-core  ←  xlsx-protocol
   ↑            ↑               ↑
   └── 排程/文档/命令   列身份+几何+日期文本   字节流 ↔ 文档（exceljs 只在这一层）
```

**为什么列身份属于渲染侧而不是协议侧**：列是**视图抽象**——用户看到的是"9 列"，
xlsx 只是它的**序列化形态之一**（还有 CSV、以及 G7 的 PPTX 表）。ADR 0007 §8 早就把左表列集合
锚到这 9 列上，也就是说"列"这件事在渲染侧的消费强度不低于协议侧；而协议侧真正独有的是
**必需性/容差/公式口径**这类导入口径。

## 3. 依赖方向的**可执行**护栏（不靠人记）

`packages/render-core/src/boundary.spec.ts`（新增，进 `pnpm gate`）断言：

1. 本包**发布源**（`src` 下的非 `*.spec.ts`）零 `@ganttpilot/xlsx-protocol`、零 `exceljs` 引用；
2. **构建产物**（`dist/*.js`）里没有指向 `exceljs` 的模块边（先剥注释，只认真实 `import`/`require`）——
   这是对 P-19 §5 ② "类型依赖是否会牵出 `exceljs` 的类型图"这句**待实测**的正面回答；
3. 本包的 `lint-boundary/*.fixture.ts` 被铁律拦下（ADR 0007 §2 要求每个计算层包自带这组夹具）；
4. 真实 ESLint 配置下本包源码零报错。

> **实测结论（本轮）**：候选 B 未被采纳，因此不需要"类型图是否牵出 `exceljs`"这一测；
> 而候选 A 下 `render-core` 的产物里**没有**指向 `exceljs` 的模块边（断言 2 直接守住这条性质）。

## 4. G5 交什么、不交什么

- **交**：① `render-core` 的**纯手势内核**（指针 → 状态机 → `{anchors, commands, highlight}`）、
  **命中反算**与**冲突/高亮集合**、`cellText` 的列文本与编辑派生值（原在 `apps/web`）；
  ② `apps/web` 的交互接线（指针事件、拖动覆盖层、撤销/重做 UI、诊断清单与冲突标记）；
- **不交**：命令压缩/检查点/IndexedDB/多标签页防护（**G6**）；导出投影（**G7**）；
  Tab/Shift+Tab 调级、键盘操作流、批量操作（**v0.5**，P1-07/08）；
  季刻度与折叠动画、同侧多线避让（ADR 0007 §10 / P-8 遗留 3）。
- **不做**排程与会话锚点的语义变更：锚点四情形、`clampedStart`、诊断码表**一字不改**（ADR 0004 §2/§5、
  [SCHEDULE.md](../../packages/engine/SCHEDULE.md) §四.3/§六）；本块只是它的**首个消费者**。

## 5. 三语义的判定区与命令映射

**判定区**（按指针按下点与该行的条/菱形的关系，`DRAG_EDGE_PX = 6`）：

| 判定 | 条件 | 语义 | 命令（松手时提交） |
|---|---|---|---|
| `resize-start` | `x ≤ xLeft + 6`（非里程碑） | 改开始 | `task.update{ startDate, durationDays }`（**保持完成日不变**） |
| `resize-duration` | `x ≥ xRight − 6`（非里程碑） | 改工期 | `task.update{ durationDays, endDate }` |
| `move` | 其余 | 整体移动 | `task.update{ startDate, endDate }`（工期不变） |
| **拒绝** | 汇总行、或行不在渲染窗口内 | — | 不进入手势（`idle`） |

- **里程碑（零时长叶子）只有 `move`**：它的"开始/完成"是同一个点，改工期即改变它在语义上是不是里程碑；
- **改开始 = 调工期**（IX-01 的"改开始"语义）：移动左端意味着开始变、完成日不动，
  因此命令同时写 `startDate` 与 `durationDays` —— 这正是"一次手势跨字段」示例
  （[COMMAND.md](../../packages/engine/COMMAND.md) §八）的形态；
- 命令一律是 **`task.update` 一个 kind**：不新增命令类型（IX-03 的"一次手势 = 一个 Command"由此天然成立，
  撤销栈一层就够）。**只有当一次手势确实需要多步**（未来引入"拖拽改层级"之类）才用事务。

## 6. 吸附、会话锚点与"允许 + 标红"（IX-05）

**每帧都吸附**：候选序号 = `ordinalAtX(view, x, calendar)`（ADR 0007 §3 已把"出候选"归 G4、
"定时机"归 G5）；指针每移动一次就按当前候选重算。

**拖动期不写文档**：

| 项 | 口径 |
|---|---|
| 拖动中的位置来源 | **会话锚点**（`Schedule` 的 `anchors` 入参，ADR 0004 §2）——`compute(document, calendar, anchors)` |
| 文档 | **一字不改**；因此 `Schedule.es` 对"有文档日期者"仍是文档锚定者的序号 |
| 「整体移动」的显示 | 拖动行取锚点序号（跟手），**其余行取 `compute` 的结果**（下游实时跟随，US-2） |
| 松手 | 提交命令（§5 的表）→ 清空锚点 → 重算 |
| 取消（`Esc`） | 清空锚点，不提交任何命令 |
| 撤销/重做 | **不参与锚点**：锚点不进文档、不进撤销栈（ADR 0004 §2 已冻结"重开后不保留"） |

**两种模式（`anchorMode`）**：

| 模式 | 拖动中的锚点取值 | 松手时的提交值 | 冲突呈现 |
|---|---|---|---|
| `snap`（**默认**） | 候选**夹**到 `[0, 入边约束]`（`snapCandidate`；拖动"顶住"边界） | 与锚点一致 | **无**（夹过之后不可能触发 `anchorConflict`） |
| `allow`（可切换） | 候选**原样**（允许排到约束**之后**） | 与锚点一致 | 候选**早于**入边约束时由 `compute` 报 `anchorConflict` ⇒ 该行**标红** |

- `maxEntryConstraint`（入边约束）由**拖动行自己的入边**按 4 类关系算出（与 `Schedule` 的边界方程同式）：
  FS `ef_pred + lag`、SS `es_pred + lag`、FF `ef_pred + lag − duration`、SF `es_pred + lag − duration`；
  取全部有效入边的**最大值**。**有效入边** = 排除端点含汇总任务的边（[SCHEDULE.md](../../packages/engine/SCHEDULE.md) §四.6）；
- **两个方向必须分清（本 ADR 初稿在此写反了，见 §12 的落地订正）**：
  - **晚于约束不是冲突**：`compute` 取 `max(约束, 锚点)`，结果是"任务往后排、下游一起往后"——
    这正是用户拖动想要的，因此 `allow` 在该方向**不标红**（`snap` 则夹回去）；
  - **早于约束才是冲突**：`compute` 会把 `ES` 抬到约束（任务顶在边界上），
    此时 `anchorConflict` 是**唯一**的冲突判据（[SCHEDULE.md](../../packages/engine/SCHEDULE.md) §四.3 情形④ + §六）；
- **因此"标红"永远不是 UI 猜的**：它就是 `Schedule.diagnostics` 里的 `anchorConflict`，
  UI 只做样式映射 —— 不新开诊断码、不新造判据。两种模式下"任务最终落在哪"由引擎决定，**答案相同**；
  差别只在**用户是否被告知"你拖过头了"**；
- 松手后写进文档的值必须**通过 schema 校验**（命令层保证），因此"允许违反依赖"不改变"文档永远合法"。

## 7. 拖拽建线（IX-02）与检环即时反馈（G-7）

- **起点**：非汇总行条形的**上/下沿中点**（ADR 0007 §5 的连接点口径：左右连接点 = 边中点；
  建线手势从行侧出发，取该行条的**竖直中点**作为出端，方向由落点决定）——`routeSides(type)` 决定出/入侧；
- **落点**：另一非汇总行 ⇒ 目标；空白 ⇒ 取消；
- **生成的关系类型**：由**出端与入端相对位置**决定（与 P-8 第 1 条同式的反推）：
  `to.xLeft > from.xLeft` ⇒ 目标在右侧 ⇒ `FS`（右出→左入）；否则 ⇒ `SS`（左出→左入）。
  **`lagDays = 0`，`type` 可随后编辑**（本块不做关系类型的手势切换，改类型走 `link.update` 的表单入口）；
- **预检即拒绝**：`link.insert` 之前先 `wouldCreateCycle(document.links, candidate)`；
  `cyclic === true` ⇒ **不提交**，并把返回的 `path`（首尾同一 id）作为**高亮集**画出来（G-7 的"高亮成环路径"）；
- **导入的成环边**已经由 G3 的确定性丢弃顺序处理并进问题清单（ADR 0006 §1/§7、G3 出口条件）——
  本块只负责**在 UI 里呈现**该清单（§9）。

## 8. 成环路径的高亮（不改 `ViewModel` 形状）

`highlightForCyclePath(document, path)` 产出 `{ rows: 文档序索引[], edges: links 下标[], styleKey: 'cycle' }`，
由 `apps/web` 作为**独立覆盖层**渲染。理由：`ViewModel` 是**几何真相源**（ADR 0007 §2 冻结形状），
高亮是**交互态**而非几何；把它塞进 `ViewModel` 会让"几何只由文档 + Schedule + 视口决定"这条性质失效。

## 9. 冲突标记与诊断清单（G-8 / IX-04，**受控收口**）

- **清单来源是三层单一数组**：协议层 + 文档校验层 + 排程层（ADR 0006 §7 已冻结"三层拼接"），
  本块只做**呈现**：计数 + 可展开列表 + 每条 `{severity, code, message, 定位}`；
- **不做**列映射向导的完整形态（那是 XL-02 的 UI 打磨，G3 已交 `detectColumns`）；
- **冲突标记的最小集**：拖动行的 `anchorConflict` 标红、成环路径高亮、`compute` 失败时的"不可排程"占位
  （含 `cyclePath` 长度摘要）——**不新开诊断码**，`undated`/`clampedStart`/`dateOverridden`/`endDateStale`
  只在清单里列出，不上图标（避免"标记通胀"）；
- 本条的**范围收口**明确记录：若后续要求"行内徽标 + 悬浮卡"的完整形态，需单独裁决并单列一块。

## 10. 撤销/重做（IX-03）

- **一次手势 = 一个撤销单元**：§5 的三语义各是**一条** `task.update`；建线是**一条** `link.insert`；
  因此 `applyToSession` 的一层 step 就是一次手势（[COMMAND.md](../../packages/engine/COMMAND.md) §五）；
- **UI**：工具栏按钮 + `Ctrl+Z` / `Ctrl+Y`（`Ctrl+Shift+Z` 等价）；**编辑态优先**——
  左表单元格正在编辑时，`Ctrl+Z` 交给输入框的原生撤销，不触发会话撤销；
- **无操作不压栈**：`changed: false`（恒等 patch / 同位置调级）时**不压撤销栈**（[COMMAND.md](../../packages/engine/COMMAND.md) §一.4）；
- **锚点与撤销**：撤销/重做**不清除**锚点栈（锚点只在手势期间存在，松手即空）。

## 11. 性能、元素预算与门禁口径

| 项 | 口径 | 层级 |
|---|---|---|
| 引擎侧 | 拖动期**允许整图重算**：全量 `compute` 1,000 任务 p99 = 530 µs（[SCHEDULE.md](../../packages/engine/SCHEDULE.md) §十 实测） | 已有门禁（G2） |
| 渲染侧 | **"受影响子图" = 渲染侧最小重建**：`affectedRenderSetWithAnchors(document, anchors)`（闭包 + 祖先链；边取"任一端点受影响"） | **进 `pnpm gate`**（结构断言） |
| 元素预算 | G5 新增的每帧元素（拖动覆盖层 + 建线预览 + 冲突标记 + 成环高亮）另立常数 **`c₄`**：`#elements ≤ c₁·rows + c₂·edges + c₃ + c₄`，**不动 `c₁`/`c₂`/`c₃`**（ADR 0007 §6.7 明写"G5 若给行加交互热区必须另加常数"） | **进 `pnpm gate`** |
| 逐帧 DOM | **拖拽期不做逐帧 DOM 重建**（ADR 0007 §6.6）：复用 `v-for` 的稳定 `key`，只更新受影响行/边的属性 | **进 `pnpm gate`**（结构断言） |
| 拖动帧预算 | 帧间隔 p50/p95、主线程同步工作量 p95、longtask 计数；**目标 ≥30 fps**（US-2） | **记录制**（`node scripts/measure-render.mjs --drag`，需本机 Chrome，P-17 口径） |
| 松手耗时 | "松手 → 命令落库 → 全量重算 → 冲突标记完成"的墙钟 **≤200 ms**（IX-04） | **记录制**（同上） |

**新增的明确限制（写进 README 已知限制）**：拖动指针移出图表窗格时**不做边缘自动滚动**（v0.1 不做）；

## 13. 批次 A 的口径修订（P-22）

> **本条只增不改**：§1–§12 的原文一字未动（沿用 P-7/P-13/P-14 的"只增不改"手法）。
> 修订的触发是 [P-21](../00-baseline/裁决记录.md) 的人工复核（6 个根因）与执行**批次 A** 时的两处实测发现。

### 13.1 指针归一化：屏幕坐标 → 内容坐标只有一条路（R1）

**唯一入口**：`pointerFromClient({clientX, clientY, paneLeft, paneTop, scrollLeft, scrollTop, buttons, altKey?, shiftKey?, escPressed?})`
（`render-core/src/gesture.ts`，**只收数字**、不收 `MouseEvent`/`DOMRect`）：

```
x = clientX − paneLeft + scrollLeft
y = clientY − paneTop  + scrollTop
```

**禁止** `MouseEvent.offsetX` / `offsetY`：它们**相对事件目标元素**——`mousedown` 落在条体 `<rect>` 上时目标就是那个条，
`offsetX ≈ 0` 被当成内容坐标，候选序号随即变成"鼠标所在的屏幕位置"（P-21 §2 的 R1）。
把换算放进本包（而不是组件里）的理由与 P-19 同源：**"入口层算出来的输入"是两次都漏掉的判据面**——
它住在 `apps/web` 时不在 `pnpm gate` 覆盖内。

### 13.2 命中条体是判定区的前提（R2）

`beginGesture` 的第三条前置：指针必须**命中条体**（`barHitFor`），否则 `idle`。

| 项 | 口径 |
|---|---|
| 横向 | `x ∈ [xLeft − HIT_TOLERANCE_PX, xRight + HIT_TOLERANCE_PX]`（`HIT_TOLERANCE_PX = 2`；只补手抖，**不改变** `DRAG_EDGE_PX = 6` 的判定区） |
| 竖向 | **不设限**：行（固定行高，ADR 0007 §4）就是竖向单位。再加"必须落在条高内"只会新增"点在行内条的上下 3 px 就拖不动"的失败面，而它并不是复核指出的缺陷 |
| 里程碑 | 包围盒 = 菱形包围盒（`xLeft/xRight` 由 `milestoneCenterX ± size/2` 给出），因此不需要第二条规则 |

因此"同一行的空白处按下"不再产生手势——这正是 P-21 复核第 2 项（左空白改开始、右空白工期翻倍）的成因。

### 13.3 候选序号：**抓取点相对**，且按模式分别定义（R7）

`delta = ordinalAtClamped(view, pointer) − grabOrdinal`（`grabOrdinal` = **按下那一刻**指针所在的工作日序号，
存进 `GestureState.dragging`——初稿存的是 `pointerStartX` 像素值，**从未被使用**）。

| 模式 | 候选的语义 | 位移基准 | 松手 patch |
|---|---|---|---|
| `move` | 新**开始**序号 | `originOrdinal + delta` | `{startDate, endDate}`（工期不变） |
| `resize-start` | 新**开始**序号 | 同上 | `{startDate, durationDays}`（**不含** `endDate` ⇒ 完成日不动） |
| `resize-duration` | 新**完成**序号 | `originOrdinal + max(1, D) − 1 + delta` | `{durationDays, endDate}`（**不含** `startDate`） |

四条必须一起读的口径：

1. **基准是"按下时捕获的序号"，不是"指针当前所在行的 `es`"**。拖动期视图带着会话锚点重算，
   `bounds.es` 已经跟着候选走了；用它当基准会让每帧"再前进一段"**累积成加速拖动**
   （实测：拖 3 个工作日落到 21 个工作日之后）。这一条由记录制 `--drag` 新增的位移断言当场抓出，
   判据见 `gesture.spec.ts` 的"带会话锚点重算也不会累积"一例。入参一律取**被拖的那个任务**的
   `taskId`/`durationDays`/`originOrdinal`（跨行拖动也不换基准）。
2. **零位移不产出命令**：`resize-duration` 按 `delta === 0` 判定（按住里程碑右半区不动**不得**
   把它变成 1 天任务），其余两模式按"结果开始 == 原开始"判定（指针被夹回项目起点也算无操作）。
   由此"按下不动即松手"**文档一字不改**、也不压撤销栈（IX-03 的"无操作不压栈"提前到手势层）。
3. **零时长的完成日 = 开始日**：`durationDays ≤ 0 ⇒ endOrdinal = es`。旧式 `候选 + 工期 − 1`
   在里程碑上给出"前一个工作日"（P-20 在显示层修过同一个式子，拖拽 patch 漏了）。
4. **夹取按模式分工**：`snap` 把"开始"语义的候选夹到 `[0, 入边约束]`（约束是开始的上界，
   而 `es ≥ 约束` 恒成立 ⇒ **按下第一帧不会跳位**）；`allow` 原样放行；`resize-duration` **不夹取**
   （其候选是新完成序号，0 下界与最小工期在结果解析处兜住）。**上界一律夹回日历地平线**
   （`workdayCount − 1`），与 `ordinalAtClamped`"越界夹回边界、不抛错"同一精神。
5. **拖出地平线 = "不可表示"，不是异常**：`Calendar.isoOfOrdinal` 在 `序号 > workdayCount` 时**抛错**，
   而拖动可以把结果（尤其"开始 + 工期"的**完成日**）推到地平线之外；预览函数还在**渲染期**被调用。
   因此本 ADR 冻结两条：① 完成日越界 ⇒ `endDate: null`（**派生显示值**的既有口径，
   与 `editToCommand` 的工期分支同形，左表回落到"开始 + 工期"的显示值）；② 开始序号本身不可表示
   ⇒ 整条手势按"无操作"处理、预览返回 `null`（调用方保持上一帧的呈现）。
   **判据**：`gesture.spec.ts` 的"拖动结果超出日历地平线"一例（换回直接调用 `isoOfOrdinal` 即变红）。

### 13.4 预览与提交同源（`resize-duration` 的可见反馈）

会话锚点只有 `startOrdinal`（ADR 0004 §2 的形状**不扩**），因此：

- `move`/`resize-start`：拖动期条体本体跟手（锚点即新开始）；
- `resize-duration`：**条体本体不动**（锚点是原开始），松手才生效 —— 可见反馈由**预览轮廓**承担。

`resolveDragOutcome({state, document, calendar})` 是**唯一**的结果解析处：
`{delta, anchorOrdinal, es, ef, resultDuration, patch}`。覆盖层用 `dragPreviewFor(...)` 取
`{xLeft, xRight, y, barY, barHeight, isMilestone, milestone}` 画轮廓 + 两条起止标记
（**仍是 3 个元素**，`c₄` 与两路计数口径不变）。
判据："预览区间 == 把松手 patch 落库 + `compute` + `taskBounds` 之后的区间"（进 `pnpm gate`）——
"看到的"与"松手得到的"不可能分叉。

**里程碑与 `milestone` 标志**：改工期**不改** `milestone` 标志（显式标志优先）；
`durationDays === 0` 的零时长叶子改工期后自然变成条形。预览的形状判据与 `taskBounds` 同源
（`task.milestone || 结果工期 ≤ 0` ⇒ 菱形），因此不会出现"预览是条形、落库是菱形"。

### 13.5 与 P-21 的关系

## 14. 拖动期**画出来的条** = 结果几何（P-24 增补）

> **本条只增不改**：§1–§13 的原文一字未动（§13.4 的措辞由本条的"取代"声明处理）。
> 触发是[裁决 P-21](../00-baseline/裁决记录.md) §3 批次 D 落地后的人工复核：
> `resize-start` 拖动期"遮罩与条体一起平移、右端不固定"，松手才回弹成正确形状。

### 14.1 决策

`packages/render-core/src/gesture.ts` 导出 `drawnBarForRow(row, dragPreview)`：

| 行 | 画什么 |
|---|---|
| **被拖行**（`preview.taskId === row.id`） | **`dragPreviewFor` 的结果几何**（`fromPreview: true`）——与松手提交同源 |
| 其余行 | 该行自身几何（不受影响） |

- 进度不重算，按 `结果宽度 × row.progressRatio` 跟随（`resize-*` 期间它在轮廓内等比伸缩）；
- 覆盖层（`.drag-outline` + 起止标记）**保留**：它现在是"结果轮廓"的高亮，元素数仍计入 `c₄`（**不变**）。

**取代（§13.4 的措辞）**：原文写"`resize-duration` 拖动期条体本体不会动、`resize-start` 拖动期的
右端也会先跟着走再回弹"——那是"只画锚点视图"的必然结果。**自本条起**：
条体本体画结果几何，**拖动期所见 = 松手所得**（三语义都是）。

### 14.2 判据（进 `pnpm gate`）

`gesture.spec.ts`（24 → **26 例**）：

1. 三语义（`move` / `resize-start` / `resize-duration`）：`drawnBarForRow` 的
   `xLeft`/`xRight`/`y`/`barHeight` 与**落库 + 重算**后的 `taskBounds` 逐字段一致，
   且竖向几何符合"行内垂直居中"的既有口径；
2. 与**锚点视图**的对照：`resize-start` 下"画出来的右端 = 原右端（固定）"，
   而 `compute(document, calendar, [{startOrdinal}])` 的锚点视图右端确实已经跟着走了（差 ≥ 1 天）
   ——**这一条就是"必须画结果几何"的理由**，缺了它前一条会退化成恒真式；
3. 未被拖动的行 / 没有预览：逐字段等于自身几何（不动别人的条）。

### 14.3 明确不做（本条的代价）

**不扩会话锚点形状**（ADR 0004 §2 的 `{taskId, startOrdinal}` 不动）：因此拖动期 `compute`
仍用**文档里的旧工期**，于是

- `resize-duration` 拖动期的**下游传播**仍按旧工期算（条体本体已正确，下游要等松手后一次到位）；
- `resize-start` 这一侧不受影响：它的完成日不变 ⇒ 下游本来就不该动。

要连下游一起 WYSIWYG，需要把锚点扩成 `{taskId, startOrdinal, durationDays?}`——那是**引擎契约修订**
（ADR 0004 §2 + `compute` + 判据），P-24 §2 已列为**待裁决项**，不在本条内顺手决定。

## 15. 归一化的下游必须同口径（P-25 增补）

> **本条只增不改**：§1–§14 的原文一字未动；§13.1 的公式与"唯一入口"这句**一字未改**。

## 16. 端点手柄、连接点与按条宽收缩的判定区（P-32 增补）

> **本条只增不改**：§1–§15 的原文一字未动（沿用 P-22/P-24/P-25 的"只增不改"手法）。
> 触发是 [P-21](../00-baseline/裁决记录.md) §3 的**批次 B**（三项同时欠着：**R3** 无可拖动区域的视觉暗示、
> **R4** `Alt` 被 Windows 窗口管理器吃掉 ⇒ 建线不可用、**§11 的 `c₄` 未按"每行加交互热区"重定），
> 外加 `P-22` 遗留 3（`DRAG_EDGE_PX = 6` 未随条宽收缩，月档 1 个工作日的条只有 3 px ⇒ "整体移动"判定区为空集）。
> 执行顺序由 [P-28](../00-baseline/裁决记录.md) 定为 `C → B → G6`，因此本条是 **G6 出口条件① 的前置**
> （B 改了元素数与行模板 ⇒ 先测的"拖拽期间不产生可见掉帧"必然作废，须在 B 之后重测）。

### 16.1 判定区随条宽收缩（**修订 §5 的实现，语义不变**）

§5 的语义（左端改开始 / 右端改工期 / 其余整体移动）**一字不改**，改的是**判定区的宽度公式**——
它此前写死为 `DRAG_EDGE_PX = 6`，于是当条宽 < 12 px 时两端吃掉整条、`move` 区成为**空集**
（月档 1 个工作日的条 = **3 px**，实测；`P-22` 遗留 3）。

```
halfGap  = max(0, (barWidth − MIN_MOVE_ZONE_PX) / 2)      // MIN_MOVE_ZONE_PX = 6
edgePx   = min(DRAG_EDGE_PX, halfGap)                     // 6 是**上界**，不是定值
edgeL    = [xLeft,            xLeft + edgePx]
move     = [xLeft + edgePx,   xRight − edgePx]            // 恒 ≥ MIN_MOVE_ZONE_PX（宽条除外：见下）
edgeR    = [xRight − edgePx,  xRight]
```

- **宽条与今天逐值相同**（条宽 ≥ 18 px 时 `edgePx = 6`）：日档（`pxPerDay = 24`）下 `|Δ| = 0`，
  因此 §5 的表、既有判据与 `--drag` 的抓取点口径**全部不变**；
- **窄条不再出现空集**：月档 1 天的条（3 px）⇒ `edgeL = edgeR = [0, 0]`（退化点），`move = [0, 3]`（3 px）；
  月档 3 天的条（9 px）⇒ 每侧 1.5 px、`move = 6 px`。**"整体移动"是三条语义里最常用的**，
  让它永远存在优先于让端点区永远够宽（后者可由手柄的视觉位置如实表达）；
- **唯一产出函数**：`interaction.ts` 的 `zonesFor(bounds)` 是这条公式的**唯一**实现处；
  `dragModeFor`、手柄位置、光标提示全部从它派生 ⇒ **"看到的"与"点到的"不可能分叉**（本条的核心理由）；
- **里程碑**不适用本条：§5 已冻结"按菱形中心分半"，`zonesFor` 对它给出 `edgeL = edgeR = null`、
  `move` = 左半、另加 `resize-duration` = 右半（`zoneAt` 的内部形态），行为与初稿一致。

### 16.2 端点手柄与连接点（**R3 + R4**）

**决策：给每渲染行加两类**可见**图元，命中判定仍走几何（`barHitFor` / `zonesFor`），
SVG 保持 `pointer-events: none`（ADR 0007 §14.2 的既有形态，本条的图元不参与 DOM 命中）。

| 图元 | 数量 | 何时发射 | 落点（内容坐标） |
|---|---|---|---|
| 端点手柄 `.handle` | 2（`<line>`） | **有条形端**的行（非汇总）；**恒显** | `zones.edgeL.end` / `zones.edgeR.start`；竖向居中、高 `HANDLE_HEIGHT_PX = 4`、视觉宽 `HANDLE_WIDTH_PX = 2` |
| 连接点 `.connect-point` | 2（`<rect>`） | **有可画条形的行**（含汇总行）**且指针在该行的条端附近**（按需显形） | 内缘**贴住条端**、整体向外伸：左 `[xLeft − CONNECT_SIZE_PX, xLeft]`、右 `[xRight, xRight + CONNECT_SIZE_PX]`；边长 `CONNECT_SIZE_PX = 8`，**竖向中心 = 条形中心**（`bounds.y`） |

- **为什么手柄落在判定区边界而不是条的两端**：它让"看起来能抓的那一点"与"真的按判定区分类的那一点"
  是同一个数（`zonesFor` 的产物），于是**第 16.1 条的窄条退化也如实可见**（两个手柄在里程碑之外退到同一处）；
- **为什么手柄高必须小于条高**（`HANDLE_HEIGHT_PX = 4` vs `ROW_HEIGHT × barHeightRatio = 14.4`）：
  初值 8 与里程碑菱形同高，视觉上**越过了条体的上沿** ⇒ 复验报"条体两端各有一向上的突出，界面杂乱"（§16.7 第 ② 条）；
- **为什么连接点贴住条端（而不是留间隙）**：`HIT_TOLERANCE_PX = 2` 的容差**不足以**让"视觉方块"与"命中区"重合——初版
  方块中心距条端 `CONNECT_GAP_PX + CONNECT_SIZE_PX/2 = 6 px`，而命中区是"以条端 + gap 为中心的一条带"，
  于是复验报"两个白色方框**不可点击或拖拽**，没有任何作用"（§16.7 第 ③ 条）。
  现在的关系是 **显示区 ⊇ 命中区**：任何"看得见的方块"都点得中；
- **为什么连接点按需显形**：常显时 1,000 任务下有 32（渲染行）× 2 = **64 个白框**，画面杂乱（§16.7 第 ③.2 条）。
  显形判据 `connectRevealFor` = **命中区向外扩 `HIT_TOLERANCE_PX × CONNECT_REVEAL_FACTOR`**，
  且**必须指针在该行内**（`rowConnectVisibleAt`）；两者都只是"何时发射"，**命中语义一字不变**；
- **汇总行只有连接点、没有手柄**：汇总条可作建线端点（§5/§13 的既有口径），但不可拖（改汇总要改子树）；
- **里程碑只有连接点**：菱形的"端"不是条形的端，§5 的"按中心分半"继续管它的两种拖动语义；
- **光标暗示**（R3 的另一半）：`cursorForPointer(view, document, schedule, calendar, pointer)` 是**纯函数**，
  由 `interaction.ts` 给出 `'col-resize' | 'move' | 'crosshair' | 'default'`；`apps/web` 只把它**赋值**给窗格
  （`pane.style.cursor`）。**不放进响应式状态**：它是逐 `mousemove` 变化的 DOM 表现，
  放进 Vue 响应式会让拖拽帧预算为此付费（§11 的判据）。
- **可见图形（P-42 批次③ 的增补，见[附录 §1](附录/0008-增补.md)）**：`.connect-point` 由"正方形白框"改为
  **圆**——直径 `connectDiameterFor` = `min(CONNECT_SIZE_PX, 条高 − 2)`（**略小于条高**、且 **≤ 命中盒边长**），
  圆心 = 命中盒中点 + **条心**。**命中盒、判定区与显形规则一字未改**（命中区本来就只按 x 判定），
  因此 §16.7 的三次复验结论（"看得见的图形一定点得中"、可用宽度 20 px）继续成立。
- **汇总条与里程碑的交互面（P-43 的增补，见[附录 §2](附录/0008-增补.md)）**：
  **汇总条整条没有判定区、没有手柄、没有连接点**（光标 `default`；"能不能拖"由 `zonesFor` **一处**决定）；
  **里程碑的工期恒为 0**（左表 `duration` 列在标记为真时拒绝，唯一出口是先在「里程碑」列解除标记），
  菱形**只可整体移动**（删掉"按菱形中心分半、右半 = 改工期"）。图元预算的**上界不变**。

### 16.3 建线的起手位置：连接点（**修订 §7 的入口**）

**决策**：§7 的"起点 = 非汇总行条形的上/下沿中点、用 `Alt` 区分"**不再成立**——`Alt` 在 Windows 上
被窗口管理器当"移动窗口"系统手势吃掉，事件到不了页面，建线在**当前平台不可用**（P-21 的 R4）。

| 项 | 新口径 |
|---|---|
| **起手位置** | **任一连接点**（§16.2 的两个之一）；从连接点按下即进入 `linking`，**不需要任何修饰键** |
| **出端侧** | 由**所抓的连接点**决定（右连接点 ⇒ 出端 = 条右缘；左连接点 ⇒ 出端 = 条左缘）——这是用户的显式选择，不由几何反推 |
| **关系类型** | `linkTypeFor(exitSide, enterSide)`：入端侧由**目标相对位置**决定（目标在出端右侧 ⇒ 入端 = 左；否则 ⇒ 右），两输入**不共变量** |

| 出端 | 目标相对位置 | 入端 | 类型 |
|---|---|---|---|
| 右 | 右侧 | 左 | `FS` |
| 右 | 左侧 | 右 | `FF` |
| 左 | 右侧 | 左 | `SS` |
| 左 | 左侧 | 右 | `SF` |

- **入端侧由关系类型给，不由相对位置给**（落地期的一次订正）：相对位置只用来**判定类型**
  （`linkEnterSideFor`），类型定了之后出入边就取 **P-8 第 1 条**的 `routeSides(type)`
  （`FS`/`SS` 左入、`FF`/`SF` 右入）。若端点再按"目标在左就在右"取一次，就会出现
  **边自身声明 `FS`、端点却落在目标右缘**（而 `routeEdge` 按类型把折点引到左缘）⇒ 预览与提交分叉；
- `lagDays = 0`（§7 不变）；`X → X` 仍拒绝；成环仍 `wouldCreateCycle` 预检即拒绝并把 `path` 交高亮层（§7/§8 不变）；
- **选中规则**（一次定清，避免"连接点永远赢"）：**近者优先**；在 `HIT_TOLERANCE_PX` 容差内并列时
  **`link-out` 优先**。**不做**"更远者胜/gutter 连点"——那条规则会让连接点吃掉整个端点判定区；
- **`altKey` 已删除**（**修订 §16.3 初稿的"保留为兼容别名"**）：P-32 的人工复验第 ⑤ 条给出"Alt 仍然无效，

  初稿的兼容别名写法保留在此以便追溯，**其效力由本条取代**：
  入口文案与 README 一律指向连接点；
- **判据的分层**：几何与类型判定是**纯函数**（进 `pnpm gate`）；"手柄是否真的可见、光标是否真的变了"
  属记录制（`--drag` 的采样）与人工目视（P-9 的"哨兵 ≠ 门禁"）。

### 16.4 `c₄` 的重定（**修订 §11 的口径**）

§11 把 `c₄` 定为"**每帧的固定开销**"（`ELEMENT_MODEL_G5.overlay = 12`），因为初稿的 G5 只加了"拖动期覆盖层"。
本条的图元是**每渲染行**的（ADR 0007 §11 第 4 项点名的"G5 若给行加交互热区必须另加常数"那一类），因此：

```
#elements ≤ (c₁ + perRenderedRow)·rows + c₂·edges + c₃ + overlay
c₄(rows)  = ELEMENT_MODEL_G5.perRenderedRow · rows + ELEMENT_MODEL_G5.overlay
          = 6 · rows + 12
```

- `perRenderedRow = 6` 是**逐类点位相加的上界**，不是估的：最"胖"的行是**有进度的叶子**——
  条 1 + 进度 1 + 端点手柄 2 + 连接点 2 = **6**（汇总行 3、里程碑行 3、无进度叶子 5，都在其上界之下）。
  **§16.7 把连接点改成"按需显形"不改变这条上界**：它只减少实际发射量，上界仍是"每行都显示"的口径
  （预算按最坏情况给，不按常态给）；
- `c₁`/`c₂`/`c₃` **一字未改**（ADR 0007 §11 第 4 项的原文口径）；
- **"每帧固定开销"这句作废**（`c₄` 现在是"每渲染行 + 每帧固定"两部分），因此 §11 表格里那一行的措辞
  由本条取代；**"与文档总规模无关"这条性质不变**——`rows ≤ 视口行数 + ROW_BUFFER`（ADR 0007 §6.1），
  10× 规模跨度下 `rows` 不变 ⇒ 元素总数仍与规模解耦（`S4-a` 的判据口径不变）；
- **两路计数继续互等**：`countElements` 按类别累加、`countElementsByEnumeration` 逐项枚举，
  两者都必须发射 `row-handle-left` / `row-handle-right` / `row-connect-point-left` / `row-connect-point-right`
  （按 `RowBox.kind` / `isMilestone` 的发射规则，与 `interaction.ts` 的 `rowHandlesFor` 同源）；
  与 `apps/web` 模板**一一对应**的维护纪律不变——**改模板必须同步这里的常数与两路计数**；
- **负向对照**：把 `perRenderedRow` 改回 `0`（＝旧模型）时，`apps/web` 的 DOM 互证必须报
  `实际 DOM 与元素模型不一致`——这正是"计数不是恒真式"的证据。

**修法（判据面）**：`interaction.spec.ts` 新增"**竖向中心同源**"一例——遍历真实 `ViewModel.rows` 断言

**第三次复验（2026-10-04）：连接点的"可见方块"必须就是"命中区"，而且 `render-core` 的产物要先于 dev 服务器更新。**

得到两条硬结论：

1. **命中区确实比"看起来能按住的地方"窄**：当时的方块 8 px、内缘贴条端 ⇒ 命中区只有
   `[xRight − 2, xRight + 10]`（14 px），实测条端右侧 `dx = −1..+2`（方块中心line附近）**全部落空**——
   鼠标按下去被当成"点空白"，既不建线也不拖动。**可见宽度与可用宽度不一致**是 3.3 与 3.4 两次报文的共同成因；
2. **那次量到的其实是"旧产物"**：`packages/render-core/dist` 当时停在上一轮构建（`tsc -b` 的时间戳早于源码），
   而 dev 服务器一直在用它 ⇒ **DOM 里量到的是 `CONNECT_SIZE_PX = 8` 的旧几何**。
   这是 P-25 记过的同一条教训（"负向对照之后必须强制重建"）在**正向修改**上的版本：
   **`pnpm dev` 之前必须先 `pnpm --filter @ganttpilot/render-core build`**（或 `pnpm build`）。

**修法（契约面，取代 §16.2 的"贴条端向外伸"）**：

| 项 | 新口径 |
|---|---|
| 连接点位置 | **跨在条端上**：`[xRight − CONNECT_INSET_PX, xRight − CONNECT_INSET_PX + CONNECT_SIZE_PX]`（左点镜像）；`CONNECT_INSET_PX = 2` |
| 连接点尺寸 | `CONNECT_SIZE_PX` 8 → **12**（可用宽度 14 → 20 px） |
| 命中区 | **= 可见方块 + 外侧 `CONNECT_HIT_PAD_PX = 4`**（内侧不再额外占端点判定区）⇒ 判据"方块的每一处都点得中"仍成立，且回归断言 `dx = −1..+2` 必须命中 |
| 拖动/建线期间 | 连接点与端点手柄**一律不显示**（那时行画的是"结果几何"，显示会变成幽灵方块）；交互图元因此必须画在条/菱形**之前**（否则跨进条内的 2 px 会被条盖住） |
**第四次复验（2026-10-04）：问题不在几何，在"事件投递"。** 报文："仍在任务 3 右方块按下、拖到任务 4 左方块松开"
不出线。用 **CDP 的真实指针输入**（`Input.dispatchMouseEvent`，走浏览器命中测试）逐值定位，三条证据：

1. **事件顺序实测**为 `mousedown → selectstart → mousemove …`：`mousedown` 启动了浏览器的**文本选择**，
   随后 `mousemove` 不再按窗格路径派发——实测"按下之后**只收到 1 次移动**"，`mouseup` 同样收不到
   ⇒ 连接预览停在第一帧、松手不落库。**这解释了三轮"几何都对了却拖不出线"**；
2. 因此 `onChartPointerDown` 必须 **`preventDefault()`**（让选择根本不开始）；
3. **拖动期行元素会被重建**：连接点按需显形 ⇒ "指针所在行"一变，那一行的 `<g>` 就换掉了，
   绑在窗格路径上的派发可能随之中断。因此手势期的 `mousemove` **同时挂到 `window`**（与 `mouseup` 同一手法），
   并在 `pointerdown` 时对窗格 **`setPointerCapture`**（浏览器保证后续事件都派发给它，与指针下面是哪个元素无关）。

**验证到的与没验证到的（如实记录）**：修复后，**长位移拖动**（`t3 → t8`，6 步、跨约 6 行）稳定出线
（依赖 1500 → 1501）；**相邻行之间的短拖动**（`t3 → t4`，约 1 行）在**合成输入**下仍不稳定，
而同一路径在第一批探针里曾经成功过 ⇒ 更可能是合成输入的边界效应，但也**不能排除**真实浏览器里
"短距离等于点击"的行为差异。**因此本条的结论是"事件投递层已按证据修好"，不是"用户侧已确认可用"。**

**第五次复验（2026-10-04）找到了真正的根因：候选不可解析时**作废了整条手势**。** 报文："没有虚线出现；
经过/不经过相邻行都试了，都不行"——这条信息把范围压到了"手势根本活不下来"。

```
paneMove=linking → reduce state=linking buttons=1 esc=false → link-target=t3 → candidate NULL → 状态 idle
之后 5 次移动全部 paneMove=idle（被 `state.kind === 'idle'` 直接忽略）→ 松手不提交
```

即 `updateForLink` 里旧写法的 `if (candidate === null) return idleGesture();`：当**指针还在源任务那一行**时
（`fromTaskId === toTaskId` ⇒ 候选不可解析；拖动开始时几乎必然出现——手指按在方块内缘再往右拖、
或拖到同一行别处），它**终止整条手势**（清锚点、后续事件全被忽略、松手不提交）。
**这不是"落点无效"，而是"手势被杀"**——所以从第一次移动起就再也不会出现预览。

**修法（契约面）**：候选不可解析时的语义是"**这一帧没有目标**"，不是"取消整条手势"——
回到 `toTaskId: null` 的 `linking` 状态（与"刚按下、还没移到目标行"同态），预览清空、手势与锚点保留。
判据见 `gesture.spec.ts` 的「指针还在源任务那一行时不作废手势」（**旧实现下必然变红**，已用负向对照确认）。

> 这一条与前面三轮的关系：① 几何（条心/跨条端/命中区）都是**真缺陷**、都已修对；
> ② 事件投递（`selectstart`）也是**真缺陷**、也已修对；但**它们都不是"没有虚线"的直接原因**——
> 直接原因是这一条"手势被自己的守卫杀掉"。三次都没白修，但只有逐帧 dump 状态才看得见最后这一层。

### 16.8 重复边的预检拒绝（P-32 第六次复验的第 3 条）

**问题**：建线只有"成环"一道预检，同一条关系可以反复建立 ⇒ 左表"前置任务"出现 `1.3; 1.3; 1.3`
（既无用，又让"这份文档有多少依赖"失去可读性）。

**决策**：同 `from`/`to`/`type`/`lagDays` 的边已存在 ⇒ **预检拒绝**，与成环同一套机制、同一处实现
（`buildCandidateLink` 的 `duplicate` + `updateForLink` 的 `rejected`）：

| 项 | 口径 |
|---|---|
| 判据 | `document.links.some(l => l.from === from && l.to === to && l.type === type && l.lagDays === 0)`（手势产出的 lag 恒为 0，§16.3） |
| 拖动期 | 预览**存在且标红**（与成环同一警戒色）——用户当场看得见"这条建不了"，而不是松手后静默失败 |
| 松手 | `state.kind === 'rejected'`、`reason: 'duplicate'`、**不产出 `link.insert`** |
| 高亮 | **不产出 `cyclePath`**：重复不是环（既不改变图，也不存在"环路径"）⇒ 用成环高亮会误导 |
| 提示 | 应用层按 `reason` 分流：`cycle` ⇒ "会形成环（路径）"；`duplicate` ⇒ "这条依赖已经存在（同类型、同 lag）" |

**不做什么**：不做"合并成一条并取并集 lag"（那是**编辑已有边**的语义，归 `link.update` 的表单入口，
本块 §4 已把"关系类型/ lag 的编辑"排除在外）；也不因此放宽"文档永远合法"这条（重复边在 schema 上本来就合法，
拒绝它纯粹是**手势入口**的策略）。
