## 背景

G6 要交付 R-2 的三层，且三层各自的**失败模式不同**：

| 层 | 内容 | 载体 | 它解决的问题 |
|---|---|---|---|
| **L1** | 命令回退栈（会话内，O(变更量)） | `DocumentSession.undoStack`（G1.3 已落地） | 撤销/重做的**唯一真相源** |
| **L2** | 低频检查点（保留数份） | `snapshots` store | L3 那份被写坏时的可恢复点 |
| **L3** | 当前状态自动保存 ≤5s | `sessions` store | 重开/崩溃后"接着干" |

R-2 的关键判断**不是容量，而是写入延迟与主线程占用**：2,000 任务的一份快照约 300–600 KB，
"每 ≤5s 把 400 KB 序列化一次"在拖拽时是**可见的掉帧**；而单条命令 delta 约 0.1–2 KB。
G6 因此必须回答两个形状问题：

1. **落盘的是什么**——整份会话快照，还是"基线快照 + 其后的增量"？
2. **谁在什么时候写**——写盘逻辑住在哪一层、以什么为触发条件，才能既满足 ≤5s、又**绝不进帧**？

以及两个**必须诚实**的口径问题（否则出口条件会被读成它不成立的样子）：

3. **"强制杀进程后恢复到最近检查点"到底能恢复到哪一刻**——浏览器杀进程不触 `beforeunload`；
4. **多标签页并发写**要不要做合并。

## 决策

### 1. 落盘的是「基线快照 + 其后的增量」，**自动保存永不序列化整份文档**

```ts
interface StoredSession {
  readonly docId: string;
  readonly rev: number;                    // 写入时的 session.revision（缓存失效口径）
  readonly undoDepth: number;              // 写入时可撤销的步数（**位置**口径：`post` 的切分位置）
  readonly base: StoredSnapshot | null;    // 最近一次检查点（含整份文档 + 它自己的 rev / undoDepth）
  readonly post: readonly StoredStep[];    // 检查点之后的 undo 步（LIFO：栈顶在末位）
  readonly redo: readonly StoredStep[];    // redo 栈（LIFO）；有 post 时必为空（见 §4）
  readonly writerId: string;               // 写者标签页 id（多标签防护）
  readonly updatedAtMs: number;
}
interface StoredStep { commands: readonly DocumentCommand[]; journal: DocumentJournal }
```

**为什么 `rev` 与 `undoDepth` 两个都要**：检查点**之前**那些步的日志不在记录里（它们由基线快照
本身承载），因此"恢复出来的会话"其 `undoStack` 长度不等于 `revision`。
`post` 只能按**位置**切开，位置口径用 `undoDepth`；`rev` 保留为缓存失效与"恢复到哪一版"的口径。
**两者不混用**，`post` 的切分因此永远是精确的；恢复侧把
"`base.undoDepth + post.length === undoDepth`"当不变量校验。

**理由**：

- **增量部分的体积与文档规模解耦**（每步 `commands` + `journal` 的 delta）——这是 R-2
  「把每次保存一整份文档变成每次操作一小段 diff」的落地；`post` 里每步的日志条目数
  只与**变更量**同阶（`persistence.spec.ts` 有跨规模的方向断言）；
- **诚实口径**：记录形状里 `base` 带**整份基线快照**，因此基线建立之后每次写入都含一份
  固定的基线体积——正是"杀进程后仍能恢复"的代价（ADR 0009 §8 的窗口口径依赖它）。
  实测（2,000 任务，`--storage-metrics`）：整份文档 **623.4 KB / 序列化 1.4 ms**、
  增量记录 **0.15 KB**、单条 put **0.3–0.8 ms**；把基线改成"存储引用"（写盘时不带快照）
  属**后续优化**（v0.5），本块按"能恢复"优先；
- 恢复读路径不需要"从基线重放命令"：`post` 里每步都带 `journal`（before/after 镜像），
  正向应用 `applyDocumentJournal` 就是那一步的结果——**语义精确，且不依赖命令的可重放性**；
- `post` 是**有界**的：每 `CHECKPOINT_EVERY_STEPS` 步或每 `CHECKPOINT_INTERVAL_MS` 就会产生新检查点，
  `post` 随之清空。

**替代方案（未采用）**：每次自动保存写整份 `DocumentSession`。它在 2,000 任务上就是
"每 ≤5s 序列化 300–600 KB"——正是 R-2 点名的主线程成本，与出口条件①的意图相反。

### 2. 写入纪律：**策略是纯状态机，时钟与手势状态都是显式入参**

`packages/engine` 的 `persistence.ts` 只交**纯函数与纯状态机**（零 DOM、零定时器、零存储）：

- `sessionRecordOf(session, base, { rev, updatedAtMs, writerId })` → 要写的那条记录（纯构造）；
- `restoreSessionOf(record)` → `{ ok, session, resolvedFrom: 'latest' | 'checkpoint', stepsApplied }`；
- `planCheckpoint(set, keep, { atMs, docId })` → 保留/删除集合（确定性，与时钟无关）；
- `policyReduce(state, event)` → `{ state, action: 'none' | 'flush' | 'checkpoint' | 'degrade' }`；
- `SnapshotStore` 接口 + `createMemorySnapshotStore()`（测试与降级路径**共用同一实现**）。

**理由**：这一层是"正确性关键模块"，必须能进 `pnpm gate`。把 `Date.now()`、`requestIdleCallback`、
`indexedDB` 全部推到 `apps/web` 的接线层之后，"5 分钟 / 200 步 / 关闭时"这些触发条件可以用**假时钟**
逐条断言，而不是靠"跑五分钟看看"。

**手势期不写盘是可断言的**：`policyReduce` 收到 `active`（`idle | dragging | linking`）时**不产出 `flush`**，
待 `inactive` 后补写。因此"自动保存不吃拖拽帧预算"不依赖运气。

### 3. 分层触发（数值见 [`PERSISTENCE.md`](../../packages/engine/PERSISTENCE.md)，形状在此冻结）

| 触发 | 动作 |
|---|---|
| `revision` 变化（且手势空闲） | **L3 写入**（去抖，但**最大间隔**封顶，故最坏延迟 ≈ 封顶值而非整个会话） |
| 距上次检查点 ≥ 时间阈值，或累计命令数 ≥ 步数阈值 | **L2 检查点** + 清空 `post` |
| 文档隐藏/关闭（`visibilitychange`/`pagehide`） | **尽力**提交一次（异步 IDB 在卸载期不保证完成，故只承诺"尽力 + 下一次写覆盖"） |
| `QuotaExceededError` | **降级**：只保留最近 1 份检查点 + 提示（不改编辑行为） |
| IndexedDB 不可用 | **降级**：改用内存适配器（本次会话内行为不变）+ 提示"本次会话不自动保存" |

### 4. 恢复语义：**先 L3、后检查点、最后回落到全新会话**，且"坏候选只跳过它"

- `planRestoreOf({ latest, snapshots }, calendar)` 给出优先级：最新状态 → 各检查点（`createdAtMs` 新到旧）
  → `null`（全新会话）；
- 每个候选都要过**三道守卫**：`validateDocument`（文档合法性，复用 G1.2，不重写规则）、
  命令形状（`checkCommandShape`）、**journal 一致性**（`applyDocumentJournal` 的 before 守卫）；
  三者任一失败 ⇒ 该候选报 `PERSIST_RECORD_INVALID` 并被**跳过**，继续下一个；
- 一条**免费的不变量**：`post` 非空时 `redo` 必须为空（任何成功的新命令都会清空 redo 栈），
  违反即判 `PERSIST_RECORD_INVALID`；
- 会话锚点、滚动位置、档位**不恢复**（见 §6）。

**恢复出的撤销栈覆盖到哪**：`post` 的每一步按 LIFO 挂好，因此**能逐步撤销到基线文档**；
"基线之前"那段历史被折叠成基线快照本身（撤销到底给出的就是那份文档）。
这正是本层必须记 `undoDepth` 的原因：没有位置口径，`post` 就会被切错，而**切错的后果是静默丢步**。

**注**：恢复结果**无需**再跑一遍 `validateDocument`——`applyDocumentJournal` 写出的文档由
`unknown` 起经守卫构造，且 `post` 的每一步都来自 `applyCommand` 产出（其 `after` 已通过 schema）。

### 4bis. 打包产物必须经 HTTP 服务器打开（**不是** `file://`）

产物是 ES module 入口，浏览器**拒绝在 `file://` 下加载**（CORS）⇒ 直接打开 `dist/index.html`
会**空白**（维护者报文，实测）。因此：

- 人工复验一律 `pnpm build` + `pnpm preview`（README「预览与人工复验」）；
- `pnpm gate` 增 **`smoke:build`**：HTTP 伺服 `dist/` + 无头 Chrome 断言"无应用级错误 + 界面已渲染"。
  它补的是"**此前没有任何门禁碰过 `dist/`**"这个缺口（缺 Chrome 即失败，不跳过）。

### 5. 存储接口（`SnapshotStore`）与两个实现

```ts
interface SnapshotStore {
  loadLatest(docId): Promise<StoreResult<StoredSession | null>>;
  saveLatest(record: StoredSession): Promise<StoreResult<void>>;
  loadCheckpoints(docId): Promise<StoreResult<readonly StoredSnapshot[]>>;
  saveCheckpoint(snapshot: StoredSnapshot): Promise<StoreResult<void>>;
  deleteCheckpoints(refs: readonly CheckpointRef[]): Promise<StoreResult<void>>;
}
```

- **错误是结构化失败码**（`PERSIST_UNAVAILABLE` / `PERSIST_QUOTA_EXCEEDED` /
  `PERSIST_BLOCKED_BY_OTHER_TAB` / `PERSIST_RECORD_INVALID` / `PERSIST_WRITE_FAILED`），
  **不抛错**——与 `WbsResult` / `SessionResult` 同风格（浏览器配额溢出是用户级事件，不是异常）；
  失败码是**闭集**，由 spec 断言。
- **两个实现**：`apps/web/src/persistence/idb.ts`（IndexedDB，库名 `GanttPilotPersistence` v1；
  `snapshots` 自增主键 + `docId` 索引；`sessions` 以 `docId` 为主键）与引擎内的
  `createMemorySnapshotStore()`（Node 侧测试 + 浏览器降级）。
- **门禁侧零新增依赖**：不引入 `fake-indexeddb` 之类。判据测的是**记录形状与策略**，
  而 IDB 的字节行为**只在浏览器侧可测**，本就归记录制（P-9/P-17 的分层）。

### 6. 明确不恢复：会话锚点、滚动位置、档位

ADR 0004 §2/§影响 把"会话锚点是否跨会话恢复"留给本块。**本块的答案是"不恢复"**：

- 锚点表达的是"**拖动期的临时意图**"（ADR 0008 §6：不进文档、不进撤销栈）；
  持久化它会让"重开就看到的日期"与文档记录不一致，用户无法判断哪个是真的；
- 滚动位置与档位是**视图状态**，不是文档语义；
- 代价必须写进 README 已知限制：「钉住的位置与滚动位置重开不保留」。

### 7. 多标签页：**互斥停写 + 提示**，不做合并

- 每次写入附带 `writerId`；若发现记录里的 `writerId` 与本标签页不同，且其 `updatedAtMs` **更新**，
  则本标签页**停止写入**并给 `PERSIST_BLOCKED_BY_OTHER_TAB` 提示（`BroadcastChannel` 只用来
  让另一个标签页**立刻**知道，不承担正确性）；
- **理由**：多标签合并（CRDT/OT）是非目标（NG-01）；而"两个标签页互相覆盖"是**静默数据损坏**，
  比"停写 + 提示"严重得多。出口条件只要求"基础防护"。

### 8. 诚实口径：杀进程能恢复到哪一刻

浏览器**杀进程时不触发 `beforeunload`/`pagehide`**，因此：

- 活下来的是**最后一次已完成的写入**（L3 的最大间隔封顶 ⇒ 丢失窗口 ≈ 一个写入周期）；
- **L2 检查点不是"崩溃时的额外保障"**，它的作用是"L3 那份被写坏/被覆盖时的可恢复点"
  （由 spec 与真机各覆盖一次）；
- 「强制杀进程后重开可恢复到最近检查点」这条出口条件因此按**字面**判：恢复的产物
  **等于或新于**最近检查点——而不是"等于崩溃前最后一步"。

## 备选方案与为何未采用

| 方案 | 未采用原因 |
|---|---|
| 每次自动保存写整份 `DocumentSession` | 2,000 任务上每 ≤5s 序列化 300–600 KB——正是 R-2 点名的主线程成本 |
| 只写"基线快照 + 命令序列"，恢复时重放命令 | 恢复要跑一遍 `applyCommand`（O(N) × 步数）；journal 已含 `after`，正向应用它就是结果，更便宜也更少失败面 |
| `localStorage` | G-6 裁决已排除：2,000 任务 + 多份检查点在 5 MB 配额下必然溢出 |
| 引入 `fake-indexeddb` 让 Node 侧测 IDB | 违反最小依赖面；且它测的是"我的适配器像不像 IDB"，不是"记录形状与策略对不对" |
| 把 `Date.now()` / 定时器放进引擎的持久化模块 | 触发条件就只能靠"跑五分钟看看"，无法进门禁（本仓库对时序断言的一贯立场：不做会抖的门禁） |
| 自动保存写在帧内（如 `watch` 的同步回调里直接序列化） | 与出口条件①的意图相反；手势期不写盘必须是**策略层事实** |
| 多标签页做合并（CRDT/OT） | 非目标 NG-01；出口条件只要求"基础防护" |
| 把会话锚点/滚动/档位一起恢复 | 锚点是拖动期临时意图（ADR 0004 §2），持久化它会让"所见"与"文档事实"分叉 |
| 用抛错报告配额溢出 | 配额溢出是**用户级事件**，要提示而不是中断编辑（同 ADR 0002 §7 / ADR 0003 §5 的取舍） |
| 恢复时"最后一个候选也失败就抛错" | 仓库存量数据的原则是**容忍而不静默**：跳过坏候选并如实报告，最终回落到全新会话 |

## 影响

- **G6**：本 ADR 是开工前置（形状冻结）；数值与逐条判据见 [`PERSISTENCE.md`](../../packages/engine/PERSISTENCE.md)。
- **G7**：导出读"当前文档"，与持久化解耦；本块不改 `RenderProjection`。
- **G8**：README 已知限制需含两条——「会话锚点/滚动位置/档位不跨会话恢复」与
  「杀进程后恢复到**最后一次写入**（≈ 一个写入周期的丢失窗口），并非崩溃前最后一步」。
- **`apps/web`**：`useProject` 新增 `restore(...)`（保留 undo 栈，区别于 `reset` 的清栈语义）；
  提示一律走既有 `notice` 通道（P-30/P-31 的"提示随命令通道走"不变）。
- **新增依赖**：**零**（`pnpm gate` 的 `license:check` 口径不变）。
- **明确延后**：命令压缩/合并、Worker 化、云同步、多标签合并、
  会话锚点/视图状态恢复、按时间点的浏览式历史（US-5 的措辞已按 R-2 改写为"跨会话恢复至最近检查点"）。
