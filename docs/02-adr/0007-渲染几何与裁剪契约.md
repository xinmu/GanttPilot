## 背景

G4 是第一个**浏览器侧**能力块，也是唯一一个把「所见」变成产品的能力块。它的风险与 G2/G3 不同：

- G2/G3 的不确定性是**口径**（同一需求有多个都说得通的实现），G4 的不确定性是**口径 + 一条未验证的工程假设**——
  T-4 与 P-8 都写明"**裁剪是纯 SVG 路线唯一的失败模式**"，而"在裁剪正确的前提下，SVG 元素数与项目总规模无关"
  这句话在 [评估报告 §5.4](../00-baseline/评估报告.md) 的反例（2,200 条边、行已虚拟化、10× 滚动仍约 2.0s）面前，
  **目前是假设而不是事实**；
- G4 当前的出口条件**大多是定性的**（"无可见掉帧""元素数与总任务数解耦"），没有起止事件、没有数据来源、
  没有环境口径——[P-6](../00-baseline/裁决记录.md) 已明确把"浏览器/绘制侧整帧预算未测"留给 G4/G5。

本 ADR 的作用与 ADR 0004 对 G2、ADR 0006 对 G3 相同：**把形状与语义在开工前冻结，G4 内不再做设计决定**。
契约若需变更，追加 ADR 并同步 [首版能力顺序 §三 G4](../01-roadmap/首版能力顺序.md)。

**本 ADR 与 G4-S 的分工**：ADR 冻结**形状与语义**（本文件 §2–§10）；[G4-S](../00-baseline/证伪实验计划.md)
用 1–3 天的丢弃式探针给出**数值与可行性判定**（元素预算、缩放档位、gutter、首屏与滚动实测），
回填 §11 的待定表。**数值未回填不影响开工，但出口条件不得在数值缺失时判"通过"。**

## 1. 契约边界：本块交什么，不交什么

- **交**：① `packages/render-core` 的**纯函数几何与裁剪内核**（零 DOM、零框架，可在 Node 侧完整断言）；
  ② `apps/web` 的 Vue 视图层（SVG 元素、左表、分屏滚动、行内编辑接线）；
- **不交**：拖拽三语义、拖拽建线、撤销/重做 UI、冲突标记、诊断清单 UI（**全部归 G5**）；
  导出（SVG/PNG/PPTX）归 G7；持久化归 G6；导入向导归 G3 协议层 + G4 的接线（UI 形态在 G5 打磨）；
- **不做排程、不聚合汇总**：所有日期/进度/里程碑派生值都来自 G2 的 `Schedule`
  （[`SCHEDULE.md` §四.4](../../packages/engine/SCHEDULE.md)："G4/G7 只排版、不自己聚合"）；
- **不写文档**：编辑一律经命令层唯一通道（ADR 0003）。

## 2. 几何真相源与包边界

**决策**：新增零 DOM / 零框架包 **`packages/render-core`（`@ganttpilot/render-core`）**，
承载"**文档 + `Schedule` + `Calendar` + 视口 → 几何**"的全部纯函数计算；`apps/web` 与 G7 的导出投影**共用**它。

| 候选 | 否决理由 |
|---|---|
| 放进 `apps/web/src/geometry` | ①**根 `vitest.config.ts` 的收集范围是 `packages/*/src/**/*.spec.ts`（`environment: 'node'`）**——几何放进应用就**自动在 `pnpm test` / `pnpm gate` 之外**；②G7 的 `pptx-renderer` 零 DOM，无法 import Vue 应用内的模块，只能复制一份 = 两个真相源 |
| 放进 `packages/engine` | 违背既有分层（engine = 日期算术 + 文档 + 命令 + 排程），会把渲染口径的迭代绑进引擎的 semver；几何不是"排程" |
| 放进 `packages/pptx-renderer` | 包名与职责不符（该包是 OOXML 写出器），且会让 `apps/web` 依赖导出器 |

**与"三包零框架/零 DOM"铁律的关系**：铁律约束的是**计算层各包**（ADR 0001 的原文写的是当时的三包）。
本 ADR 把 `render-core` **并入同一约束集**：`tsconfig` 无 DOM lib、ESLint 三条边界规则、护栏自检一律适用。
既有文档中的"三包"措辞**不改写**（同 [P-10](../00-baseline/裁决记录.md) 第 3 条的手法），
自本条起按「**计算层各包（含 `render-core`）**」解读。

**公共 API（形状冻结，命名可微调但语义不可变）**

```ts
import type { Calendar, ProjectDocument } from '@ganttpilot/engine';
import type { Schedule } from '@ganttpilot/engine';

/** 视口：唯一的滚动/尺寸真相源（见 §4 与 §6）。 */
interface Viewport {
  readonly scrollTop: number;         // 内容坐标系（不含表头）
  readonly scrollLeft: number;
  readonly width: number;             // SVG 视口宽（CSS 像素）
  readonly height: number;
  readonly rowHeight: number;         // 固定行高（虚拟化前提）
  readonly pxPerDay: number;          // 由刻度档位决定（§3）
}

/** 视图模型：几何的唯一产出。渲染层只做"把数字写成 SVG 属性"。 */
function buildView(
  document: ProjectDocument,
  schedule: Schedule,
  calendar: Calendar,
  viewport: Viewport,
): ViewModel;

/** 反算（G5 的拖拽/命中必需）：x 像素 → 工作日序号与日期。 */
function dayAtX(view: ViewModel, x: number): number;      // → DayNumber（自然日）
function ordinalAtX(view: ViewModel, x: number): number;  // → 工作日序号（吸附用）

/** 行窗口与边窗口（§5/§6；纯函数，可独立断言）。 */
function visibleRows(view: ViewModel): readonly number[];       // 文档序索引
function visibleEdges(view: ViewModel): readonly number[];      // links 数组索引
```

- `ViewModel` 里**只出数字与枚举**（矩形、折线点列、文本锚点、样式键），**不出 SVG 字符串、不出 DOM**；
- 渲染层（`apps/web`）与导出投影（G7）**都只消费 `ViewModel`**——这就是"双投影共享几何"（铁律 #2）的载体。

## 3. 时间轴与 x 坐标（**本块最重要的口径**）

**决策：x 轴按「自然日连续」排列，非工作日照常占位并在视觉上区分；工期/序号语义仍是工作日。**

依据：[D-4](../00-baseline/裁决记录.md) 已把日历/工期语义定为 MS Project 惯例，而 MS Project 的时间轴正是
"全宽日历 + 周末/假日区分"；若改用"工作日压缩"轴，则周末被折叠、用户无法把条形与日历对读，
且 G7 的导出一旦被贴进汇报 PPT，"哪一天"会失去可核对性。

**映射公式**（全部 O(1)，只用 G1.1 已冻结的 `Calendar` API）：

```
axisOriginDay  = 轴线起点（见下）
xLeft(i)       = (calendar.dayOfOrdinal(schedule.es[i]) − axisOriginDay) * pxPerDay
xRight(i)      = (calendar.dayOfOrdinal(schedule.ef[i] − 1) + 1 − axisOriginDay) * pxPerDay
```

- **右边界必须用 `ef − 1` 再 +1**，不能用 `dayOfOrdinal(ef)`：`ef` 是**排他**结束序号，
  跨周末的任务（如周五 + 周一）若直接用 `ef`，条形会多出一整段空隙；用"最后一个工作日所在格的终点"
  才得到连续条形（这与 MS Project 的呈现一致）；
- **汇总条**同规则，取 `summaryEs` / `summaryEf`（`es[i] === -1` ⟺ 汇总任务，
  这是 `Schedule` 形状里唯一的汇总判别式，[`SCHEDULE.md` §三](../../packages/engine/SCHEDULE.md) 已指定 G4 必须用它）；
- **里程碑**（`durationDays === 0` 或 `milestone === true` 的叶子）：时序上是零时长点，
  几何上**以所在工作日格的中点为中心**画菱形（`dayOfOrdinal(es) + 0.5`），边长取行高的固定比例——
  这是**视觉约定**（为了左右连接点都有意义），不改变"零时长"的语义；
- **轴线起点**：`dayOfOrdinal(schedule.projectStart)` 按当前刻度档位**向前取整到该档位的起点**
  （日档 = 当天；周档 = 该周周一；月档 = 该月 1 日），再向左留 `AXIS_LEFT_GUTTER_DAYS`。
  **左边距不是装饰**：P-8 的 SS/SF"左出回绕"走线需要图表左侧有空间，否则折线会压在左表上；
- **刻度档位**：日 / 周 / 月（**季刻度延后**，与路线图 G4「可延后」一致）；档位只改变
  `pxPerDay` 与表头分组，**不改变任何序号↔日期的对应**；
- **序号 → 日期的翻译必须用同一个日历**：调用方用 G2 的 `createScheduleCalendar(document)`
  （[`SCHEDULE.md` §七](../../packages/engine/SCHEDULE.md)），否则容量不足时 `isoOfOrdinal` 会抛错；
  **`-1` 是哨兵，绝不可喂给 `dayOfOrdinal`**。

**为什么这条要与 G5 一起读**：G5 的"改开始 / 改工期 / 整体移动"三语义都在**工作日**上运算
（`durationDays` 与 lag 的单位是工作日），但在**自然日**上拖动，因此
**"拖动吸附到工作日格"是 G4 的反算（`ordinalAtX`）与 G5 的手势状态机共同的责任**：
G4 提供 `ordinalAtX`（吸附候选），G5 决定何时吸附。这条分工不在 G5 重新定义。

## 4. 行模型

| 项 | 冻结内容 |
|---|---|
| 行的真相源 | **可见行序列 = 树序（文档序，父先于子）经折叠过滤**后的子序列；`Schedule` 的数组仍按**文档序**索引（不压缩），渲染层负责两次映射，**不改变 `Schedule` 的索引约定** |
| 行高 | **固定行高**（虚拟化的前提，[评估报告 §5.4](../00-baseline/评估报告.md)）；折叠/展开**不得改变行高假设**，只改变行数 |
| 折叠状态 | 文档字段 `collapsed`（G1.2 承载），变更经 **`task.update`**（ADR 0003 的唯一通道）⇒ 折叠/展开天然可撤销；**折叠态不随 xlsx 往返**（不在 G3 的 9 个可见列里，ADR 0006 §2） |
| 汇总行 | `es[i] === -1`；进度取 `summaryProgress`，**`NaN`（子树工期权重和为 0）时不画进度填充**，不是 0% |
| 进度 | 叶子取文档 `progress`（`null` 视为未知 ⇒ 不画填充，与 ADR 0006 §4 的"进度缺失"同理） |

## 5. 依赖线的路由几何

- **出/入边策略的唯一登记处是 [P-8](../00-baseline/裁决记录.md) 第 1 条**（FS 右出→左入、SS 左出→左入、
  FF 右出→右入、SF 左出→右入；左右连接点 = 该边中点）。**本 ADR 不重述该表**，避免两处真相源；
- 本 ADR 冻结的是**参数化折点规则**：每条边一律「**出端水平 stub → 竖直段 → 入端水平 stub**」；
  - `EDGE_STUB_PX`：固定像素常数（**不随 `pxPerDay` 缩放**，以免缩放时折点跳变、并让 G7 在给定
    `pxPerDay` 下拿到同一几何）；
  - 竖直段 x：同一行或目标在前方的常规情形取"出端 stub 末点与入端 stub 起点的**中点**"；
    **需要回绕**（SS/SF 且目标在前置左侧）时取 `min(两端 x) − EDGE_WRAP_PX`，落在 §3 的左侧 gutter 内；
  - 折点全部**正交**（水平/垂直），不允许斜线段；
- **4 类关系的箭头必须可区分**：判据是"给定同一对条，4 类关系的箭头形态两两不同"，
  具体形态（实心三角/空心三角/朝向）为视觉约定，随 §11 回填；
- **同侧多线分道 / 避让规则**：v0.1 **不做**（P-8 遗留 3）。若 G4 落地时出现真实取舍（同侧多线完全重叠不可读），
  **另立 ADR**，不在本 ADR 内顺手决定；
- SVG 工程细节（T-4）：线条 `shape-rendering="crispEdges"`；缩放线宽用 `vector-effect="non-scaling-stroke"`；
  交互热区用**独立透明 `<path>`**，不得给可见图元加大热区（会破坏命中判定与 G5 的拖拽起点）。

## 6. 裁剪契约（纯 SVG 路线唯一的失败模式）

1. **行窗口裁剪**：渲染行 = 可见行 + **上下各 `ROW_BUFFER` 行**缓冲；`ROW_BUFFER` 为常数；
2. **边窗口裁剪：必须用「边所跨行区间 ∩ 可见行窗口」求交**——仅按"两端点是否可见"裁剪会
   **错误隐藏跨屏长箭头**（T-4/评估报告 §5.4 的原话）。边所跨行区间 = 两端点**可见行序号**的闭区间；
3. **折叠隐藏的行不画其边**（否则会出现指向不存在行的悬空线）；判定与第 2 条同一处、同一遍；
4. **文档里的全部 `links` 都画**（含端点为汇总任务、被传播忽略的边）——与 `SCHEDULE.md` §四.6 的
   "有效图 vs 结构图"**不冲突**：渲染呈现的是**文档数据**，不是"排程用了哪些边"；
   被忽略的边用**样式区分**（本 ADR 冻结该样式键，**不新开诊断码**，诊断码表仍是闭集）；
5. **裁剪先于几何计算**：先按窗口筛行与边，**再**算 path 与坐标（不得先算全量再过滤）；
6. **拖拽期不做逐帧 DOM 重建**（G5 复用本条）；
7. **元素预算可测**：渲染出的 SVG 元素数必须满足
   `#elements ≤ c₁ · visibleRows + c₂ · visibleEdges + c₃`（`cᵢ` 为常数，不随文档总规模增长）；
   判据形式与实测数值见 §9 与 §11；
   **口径落地（G4 本体）**：元素模型与计数器落 `packages/render-core/src/count.ts`
   （`countElements` 按类别累加 + `countElementsByEnumeration` 逐项枚举，两路必须逐项相等），
   并与 `apps/web` 的 SVG 模板**一一对应**——改模板必须同步 `ELEMENT_MODEL` 的 `c₁`/`c₂`；
8. **负向对照必须存在**：把求交换成"端点可见性裁剪"必须被检出（跨屏长边丢失）；
   关掉窗口裁剪必须被检出（元素数随规模增长）。**没有这两条，第 7 条可能是恒真式。**
   **口径落地（G4 本体）**：`clipMode: 'endpoints' | 'none'` 是 `selectEdges` 的正式入参，
   由 `clipping.spec.ts` 的 NC1/NC2 使用（314 条误裁 / 10.71× 增长）。

## 7. 状态与退化

| 状态 | 渲染行为 |
|---|---|
| `compute` 失败（`ok: false`，`code: 'cycle'`） | **不画条形与连线**，渲染"不可排程"占位（含 `cyclePath` 的行数摘要）；**不**实现诊断面板（G5） |
| `undated` / `clampedStart` / `dateOverridden` / `endDateStale` 等诊断 | **G4 不做任何诊断 UI**（不画徽标、不画角标）——诊断的呈现是 G5 的 G-8/IX-04 范围；G4 只保证"有日期可画、没日期不崩" |
| 无日期任务（情形②回落项目起点） | 照常按 `es` 画（序号已被截断到项目起点），不特殊标记 |
| 空项目 / 全汇总 | 只画刻度与左表，不画条形；不得出现 `NaN` 坐标 |

## 8. 左表与行内编辑的边界

- **左表列集合锚 G3 的 9 列契约**（`wbs` / `name` / `start` / `end` / `duration` / `predecessors` /
  `progress` / `milestone` / `notes`）——
  **不新造第四套列语义**；`wbs` 列展示派生值 `outlineNumber`（真相源是层级 + 文档序，ADR 0002 ③）；

## 14. 两栏行对齐与表头带（P-23 增补）

> **本条只增不改**：§1–§13 的原文一字未动（沿用 P-7/P-13/P-14/P-22 的"只增不改"手法）。
> 触发是[裁决 P-21](../00-baseline/裁决记录.md) §3 的**批次 D（R6）**：两栏行对齐此前**只靠肉眼**，
> 于是"条体与对应任务错位 / 图形区滚动比左表更快 / 下方留白 / 新滚出的区域没有网格线与周末灰度带"
> 四类现象同时穿过了全绿门禁。[裁决 P-23](../00-baseline/裁决记录.md) 的只读诊断
> （4 个滚动位置 × 逐行 `getBoundingClientRect()`）把它们拆成 **5 个机制**，本条把修好后的几何冻结成契约。

### 14.1 行屏幕几何（两栏同一式）

```
行屏幕 y = 列顶 + HEADER_HEIGHT_PX + row × ROW_HEIGHT − scrollTop
```

- `HEADER_HEIGHT_PX = 28`（`packages/render-core/src/manifest.ts` 的**单点声明**）：左表表头与图表表头带的**外高**。
  两栏都必须 `box-sizing: border-box`，否则"28 + 1 px 下边框"与"− 28"会差 1 px（实测 `header-height-mismatch`）；
- **图表列的绘制区 = 滚动容器的可视区**：`Viewport.height = 滚动容器 clientHeight`
  （已扣表头带与滚动条）。§2 写的 `Viewport.scrollTop // 内容坐标系（不含表头）` 由此**字面成立**——
  本条是让实现符合既有契约，不是新增语义；
- **左表整列外高 = `HEADER_HEIGHT_PX` + 绘制区高**（`useChart` 的 `columnHeight`），
  表体高 = `columnHeight − HEADER_HEIGHT_PX`；
- **行的外高必须等于 `ROW_HEIGHT`**（§4 的"固定行高"）：`.row` 的 `height: 24px` 若落在 `content-box`
  上、再加 1 px 下边框，外高就是 **25 px** ⇒ 每行漂 1 px（P-23 实测：32 行漂 32 px，记为 **R9**）。

### 14.2 SVG 必须钉在 scrollport 上（**禁止**作为滚动容器的 abspos 子元素）

滚动容器的 abspos 子元素**定位在内容原点**，因此会**随内容一起滚**；再叠加内层
`translate(−scrollLeft, −scrollTop)` 就是**双重偏移**——图形区滚动速度是左表的**两倍**、
下方留白、轴元素被推出绘制区（P-23 机制③；实测最差行差 **22,909 px**，`scrollTop=0` 处该机制**不可见**，
因此诊断**必须**在 ≥2 个滚动位置采数）。

落地形态：`.chart-pane-wrap`（定位祖先）+ `.chart-pane`（`overflow: auto`，**滚动容器**）
+ `<svg>` 作为**兄弟**、`position: absolute; left: 0; top: 0; pointer-events: none`
（命中判定走几何 `barHitFor`，不靠 DOM 事件目标）。

**尺寸必须 1 用户单位 = 1 CSS px**：SVG 的盒子**只由 `width`/`height` 属性**给出（= 绘制区尺寸），
**不得**用 `inset: 0` 拉伸——`inset: 0` 取的是外层 wrap 的 padding box（含滚动条那 15 px），
与 `viewBox` 不等时默认 `preserveAspectRatio` 会**等比缩放 + 居中留白**，让条形既偏 x 又偏 y
（判据 `svg-box-not-1to1`；本环境实测**不成立**，判据保留以防复发）。

### 14.3 轴是标尺：只随横向滚动

轴（色带 / 网格线 / 标签）在 `ViewModel` 里就是 `y = 0 .. height`，语义上**不随纵向滚动移动**；
它住在外层内容坐标系的 `<g>` 里，因此必须补一次纵向抵消（`translate(0 +scrollTop)`）——
否则整条标尺随内容上移、绘制区下部没有网格线与周末灰度带
（P-21 第 14.2 项；P-23 实测 `axis-not-covering`，且**行对齐可以同时完美**——两者是独立判据）。

### 14.4 可判定的检查（两层，缺一不可）

| 层 | 载体 | 判据 | 进 `pnpm gate`？ |
|---|---|---|---|
| **判读逻辑** | `packages/render-core/src/align.ts` 的 `diagnoseRowAlignment` / `summarizeAlignment` | 正例"未变造时零检出" + **每条机制一条负向对照** | **进**（`align.spec.ts`） |
| **真实 DOM** | `node scripts/measure-render.mjs --align[=<label>]` | ≥4 个滚动位置（含 `0` 与 `maxScroll`）逐行 \|Δ\| ≤ `THRESHOLDS.rowAlignTolerancePx`（**0.5 px**）；`pinned` / `svgBoxAligned` / `headerAligned` / `heightAligned` / `rowHeightAligned` / `scrollInSync` / `hitTestOk` 全真；文档比绘制区长时顶/底空白带 = 0 | **不进**（记录制，需本机 Chrome） |

**机制标签**（不是诊断码——诊断码表仍是闭集）：`svg-scrolls-with-content`、`svg-not-pinned`、
`svg-box-not-1to1`、`pane-measure-stale`、`table-body-height-mismatch`、`table-row-height-mismatch`、
`header-height-mismatch`、`scroll-out-of-sync`、`table-header-offset-missing`、`row-offset`、
`bar-x-offset`、`hit-test-mismatch`、`coverage-gap`、`axis-not-covering`、`no-samples`。

**两栏行中心的取法**（采数口径，容易搞错）：图表行的 `<g>` **没有自己的盒子**，
`getBoundingClientRect()` 返回的是子元素（条 / 菱形）的并集，而条在行内**垂直居中**
（`ViewModel.barY`）⇒ 取**条中心 = 行中心**；左表侧取"DOM 行顶 + 模型行高 / 2"（**不按 DOM 外高**，
外高含边框——那正是 R9 现形的地方）。第一版诊断用"行顶"比，把"条内缩 4.8 px"当成了错位，已订正。

### 14.5 不改的东西

- `c₁`/`c₂`/`c₃`/`c₄` 与元素预算**一字未改**：表头带是 HTML 布局、`data-task-id` 是**属性**
  （不产生 SVG 元素）；轴分组只加一次纵向抵消，元素数与 DOM 计数的互证不受影响；
- §1–§13 原文不动；`ViewModel` / `Schedule` / 文档 schema / 诊断码表**不变**；
- 屏幕坐标 → 内容坐标仍只有 `pointerFromClient` 一条路（ADR 0008 §13）：
  表头带是**真实布局**，`paneRect.top` 已经含它，因此**不需要任何 −28 补偿**；
- 导出投影（G7）不受影响：它复用 §2/§3/§5 的几何，不复用布局。

## 15. 内容横向范围、轴的坐标系与覆盖（P-24 增补）

> **本条只增不改**：§1–§14 的原文一字未动。
> 触发是[裁决 P-21](../00-baseline/裁决记录.md) §3 批次 D 落地后的**人工复核**（A 区，2026-10-04）：
> 复核确认 §14 的两栏对齐已修好，但**同一族**里还剩三处——向右滚不到项目末端、
> 向右滚出的新区域没有网格线/灰度带、日期刻度压在第一行上。
> [P-24](../00-baseline/裁决记录.md) 把它们定位为 **R11**（内容宽给少了）与 **R12**（轴的横向双重偏移），
> 并按维护者的选择把刻度搬进表头带、让拖动期条体画结果几何（后者见 [ADR 0008](0008-列身份所有权与拖拽交互契约.md) §14）。

### 15.1 内容横向范围（`ViewModel.contentWidth`）——R11

**决策**：内容的横向范围由**文档的日期范围**推出，不由窗格宽外推；它是滚动容器 spacer 宽度的唯一真相源。

```
contentWidth = max(窗格宽,
                   最末任务右缘 + EDGE_STUB_PX + EDGE_WRAP_PX + CONTENT_RIGHT_PAD_PX)
最末任务右缘  = (dayOfOrdinal(Schedule.projectFinish − 1) + 1 − axisOriginDay) × pxPerDay
```

- `CONTENT_RIGHT_PAD_PX = 32`（`manifest.ts` 单点声明）：让最末任务之后还有可滚的余地；
- 用 `Schedule.projectFinish`（叶子行的最大**排他**完成序号）⇒ O(1)，且与 §3 的右边界公式
  `dayOfOrdinal(ef − 1) + 1` 同源；`projectFinish ≤ 0` 时回落到窗格宽（不可滚、不给负范围）；
- **代价（实测）**：旧式"按窗格宽推导"的公式（`max(60, 窗格宽 / pxPerDay + 32)`）在 1,000 任务夹具上
  只给到约 **61 天**，而项目实际跨度约 **440 天**——用户向右滚到某个位置就再也滚不动了。

### 15.2 轴的坐标系与覆盖（R12）——**修订 §14.3 的实现方式，语义不变**

**决策**：`buildAxis` 的元素 `x` 是**窗口坐标**（§11.1 ③ 的既有口径：已扣 `scrollLeft`、只发射视口内的元素），
因此**轴必须渲染在滚动组之外**，与内容组并列在 SVG 根下，不加任何 `translate(−scrollLeft, …)`。

- **违规形态（R12）**：把轴放进内容滚动组 ⇒ 叠加一次 `−scrollLeft`（**横向双重偏移**）。
  它在 `scrollLeft = 0` 处**不可见**，于是"向右滚出的新区域没有任何网格线与灰度带"——
  与 §14.3 处理的纵向形态同源；P-24 实测最差：轴整体偏离 `scrollLeft`（600 px 时偏 600 px）；
- §14.3 的纵向抵消（给轴补 `translate(0 +scrollTop)`）**不再是实现方式**：轴不进滚动组，
  纵向自然不需要抵消。**语义（轴是标尺：只随横向）一字未变**，只是实现更短、更不可能叠错；
- **覆盖判据（四边，P-24 扩）**：
  - **纵向**：色带（无则退到网格线）的并集必须铺满绘制区 `[paneTop, paneTop + paneHeight]`；
  - **横向**：**刻度（网格线）**的并集必须铺满视口——第一个刻度离绘制区左缘 ≤ 一个刻度间距、
    最后一个离右缘 ≤ 一个刻度间距（`tickSpacingPx = pxPerDay × 该档位单位天数`）。
    **不得用色带判横向**：色带是稀疏的（只有周末/假日），它的并集本来就不该触到左右缘（P-24 踩过）。

### 15.3 SVG 盒 = 表头带 + 绘制区——**修订 §14.2 的"盒 = 绘制区"**

**决策**：SVG 覆盖**整列**（表头带 + 绘制区），且仍满足"盒 = `viewBox`"（1 用户单位 = 1 CSS px）：

```
svgHeight = Viewport.height + HEADER_HEIGHT_PX   // 属性与 viewBox 同时取它
内容组      : translate(−scrollLeft, HEADER_HEIGHT_PX − scrollTop)
色带/网格线 : translate(0, HEADER_HEIGHT_PX)      // y = 0..height 落到绘制区
日期刻度    : 不偏移                                // 画在 0..HEADER_HEIGHT_PX 的**表头带**内
```

- SVG 的定位祖先是 `.chart-column`（表头带 + 绘制区），因此 `top: 0` 就是表头带顶；
- **表头带的底色与边框仍由 HTML 的 `.chart-header` 出**（SVG 背景透明）：底色不是几何，
  且这样 `c₃` 与元素预算一字不改（只是把轴拆成"色带/网格线组"与"刻度组"，元素数不变）；
- **代价**：`align.ts` 的三条判据随之上移——`pinned` 变为"横向对齐绘制区左缘、纵向
  = 绘制区顶 − 表头带"，`svgBoxAligned` 变为"宽 = `ViewModel.width`、高 = `ViewModel.height + 表头带`"，
  另新增 `labelsInHeader`：**刻度文本的并集必须落在 `[绘制区顶 − 表头带, 绘制区顶]` 内**
  （否则它压在**第一行**的条形上——这正是 P-24 复核第 ③ 条；机制名 `axis-labels-not-in-header`）。

### 15.4 记录制判据：`--align` 扩为"横向 × 纵向"

`node scripts/measure-render.mjs --align[=<label>]` 的探测位置由 4 个**纵向**位置扩为 6 个
**（top, left）成对**位置：`(0,0) / (120,0) / (480,600) / (max,0) / (0,max) / (max,max)`。

- 理由是 R12 的教训：**轴的横向双重偏移在 `scrollLeft = 0` 处完全不可见**，
  只探纵向的判据结构上抓不到它（P-23 的 4 个位置全部漏过）；
- 证据新增四行：`内容宽（spacer / ViewModel）`、`轴覆盖（色带上下 / 刻度左右）`、
  `刻度文本（上..下）`、`ViewModel` 的**两个方向**与 DOM 的同步；
  逐行误差表只列首 10 + 末 4 行（逐行值在 raw JSON）。

### 15.5 不改的东西

- `c₁`/`c₂`/`c₃`/`c₄` 与元素预算**一字未改**（轴只是换了个父 `<g>`；表头带仍是 HTML）；
- `ViewModel` / `Schedule` / 文档 schema / 诊断码表**不变**；新增的 `contentWidth` 是**只读派生字段**
  （与 `width`/`height`/`rowCount` 同类），不影响既有消费方；
- §1–§14 原文不动；屏幕坐标 → 内容坐标仍只有 `pointerFromClient` 一条路（ADR 0008 §13）。

## 16. 命中反算与反算函数的坐标系（P-25 增补）

> **本条只增不改**：§1–§15 的原文一字未动。
> 触发是 P-24 之后维护者的人工复核：**"仅首屏（左上）渲染出来的条可以拖动，向下、向右滚出来的条都不能交互"**。
> 本条把"内容坐标"这条口径从**指针归一化**（ADR 0008 §13.1）一贯到底，并补上**只有滚动后才现形**的判据。

### 16.1 唯一坐标系：内容坐标（一处归一化，处处按内容坐标取值）

```
屏幕 → 内容：x = clientX − paneLeft + scrollLeft
              y = clientY − paneTop  + scrollTop        （ADR 0008 §13.1，唯一入口 pointerFromClient）
```

归一化之后，`pointer.x / pointer.y`、`row.xLeft/xRight`、`row.y`、`edge.points`、`bounds.*` **全是内容坐标**。
因此**任何下游再叠加一次 `scroll*` 都是重复计数**，且**在 `scroll = 0` 处完全不可见**：

| 位置 | 违规写法（R13/R14） | 现写法 |
|---|---|---|
| `resolvePointerTarget`（命中行号） | `Math.floor((y + view.scrollTop) / rowHeight)` | `Math.floor(y / rowHeight)`（§16.2） |
| `dayAtX`（x → 自然日） | `axisOriginDay + (x + view.scrollLeft) / pxPerDay` | `axisOriginDay + x / pxPerDay`（§16.2） |
| `ordinalAtXSafe`（`gesture.ts` 内的**第二份**反算） | 同一个公式**又抄了一份**（同样多加 `scrollLeft`） | **删除重复公式**，委托 `dayAtX`（唯一一处） |

### 16.2 修复（三处）

1. **`resolvePointerTarget` 去掉 `+ view.scrollTop`**（R13）：否则向下滚动后行号凭空多出
   `scrollTop / rowHeight` 行、落到渲染窗口之外 ⇒ **按下根本不进手势**（实测：`scrollTop = 480`
   时行号 +20，命中直接为 `null`）；
2. **`dayAtX` 去掉 `+ view.scrollLeft`**（R14）：否则向右滚动后反算整体偏
   `scrollLeft / pxPerDay` 个**自然日**（实测 600 px ⇒ 偏 25 天 ≈ 19 个工作日），拖动候选随之跳位；
3. **`ordinalAtXSafe` 委托 `dayAtX`**：这一处是"同一公式抄两份"的必然代价——修了 `dayAtX` 也修不到它
   （本条落地时当场踩到：纯函数修好后记录制仍红）。反算公式**只允许有一处**。

`PointerInput.x/y` 的文档也一并收紧：它们是**内容坐标**，且本包内**所有**消费者
（`resolvePointerTarget` / `dayAtX` / `ordinalAtX` / `barHitFor` / `dragModeFor`）都按内容坐标取值。

### 16.3 判据（**凡坐标换算类判据，至少取一个非 0 滚动位置**）

| 层 | 载体 | 内容 |
|---|---|---|
| 几何不变量 | `geometryExpectations.spec.ts`（+3 例） | 三个数据集各一例：**滚动视图**（`scrollTop = 480, scrollLeft = 600`）下的反算往返、端点贴合、汇总覆盖必须与不滚动时**逐值一致** |
| 手势 | `gesture.spec.ts`（+1 例） | 滚动视图上：条左缘仍映射到该行 `es`；`resolvePointerTarget` 命得中同一行；能起手势；**候选与抓取点的工作日差 == 指针移动的工作日差**（滚动不参与） |
| 记录制 | `scripts/measure-render.mjs --drag` | **两个滚动状态各拖一次**：`(0,0)` 与 `(480,600)`，各自断言"松手后 `startDate` = 按下时的开始序号 + 天数" |

**记录制的一条纪律（P-25 踩到）**：`--drag` 的目标行必须**无有效入边约束**（`entryConstraintFor` 非有限值）
——`snap` 模式会把候选夹到约束之下，"拖 N 天"的位移判据对有前置约束的行**必然**报错；
`gesture.spec.ts` 的 `pickLeaf` 一直是这么过滤的，记录制这一侧必须同口径，否则判据会给出**假红**。

### 16.4 教训

这一族缺陷（R10/R12/R13/R14）有同一个形状：**只在某个滚动位置才现形**，
而此前**所有**判据（纯函数 spec 与记录制）都取 `scrollTop = scrollLeft = 0` ⇒ 结构上不可能抓到。
因此：**凡"坐标换算/命中/反算"类判据，必须至少取一个非 0 滚动位置，横向纵向各一个**。

### 16.5 不改的东西

- `c₁`–`c₄`、`ViewModel` 形状、`Schedule` 形状、文档 schema、诊断码表**不变**；
- 屏幕 → 内容仍只有 `pointerFromClient` 一条路（ADR 0008 §13.1）；本条只是让**下游**回到同一条口径；
- §1–§15 原文不动。
