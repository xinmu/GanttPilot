## 背景

G1.3 要交付的是**命令层与事务**：文档的**唯一变更通道**（IX-03 的载体），以及
"命令自带逆操作"的 before 镜像（R-2 的前置——[裁决记录](../00-baseline/裁决记录.md) 明写
"命令必须携带逆操作（或 before/after 镜像）……**不需要手写**"）。

R-2 还给了一个量级承诺：**单条命令 delta 约 0.1–2 KB**（对比整份快照 300–600 KB），
"回退栈把'每次保存一整份文档'变成'每次操作一小段 diff'"。

这一块之所以必须在 G5/G6 之前定死，是因为它的形状**难逆**：G5 的编辑事务、G6 的回退栈
与检查点都建立在"命令是什么、日志是什么、无操作怎么表示"之上。因此本 ADR 记录形状与取舍。

## 决策

### 1. 命令是**可序列化的纯数据**，`applyCommand` 是纯函数；变更只有一个通道

```ts
type DocumentCommand =
  | { kind: 'document.replace'; document: ProjectDocument }
  | { kind: 'project.update';   patch: ProjectMetaPatch }
  | { kind: 'task.insert';      task: DocumentTask; parentId: string | null; afterTaskId?: string; index?: number }
  | { kind: 'task.update';      id: string; patch: TaskFieldPatch }
  | { kind: 'task.remove';      id: string }
  | { kind: 'task.indent' | 'task.outdent'; id: string }
  | { kind: 'task.move';        id: string; target: WbsMoveTarget }
  | { kind: 'link.insert';      link: DocumentLink }
  | { kind: 'link.update';      id: string; patch: LinkFieldPatch }
  | { kind: 'link.remove';      id: string };
```

**理由**：

- **不是闭包**：只有纯数据才能重放、留痕、被 `JSON.parse` 校验、被 G6 落盘
  （`serializeCommand` / `parseCommand` 是外部输入的唯一入口）；
- **枚举 11 个 kind 而不是一个通用 patch**：通用 JSON-Patch 会把"层级的真相源"
  （`parentId` + 文档序）暴露给调用方自由改写，`wbs.ts` 的调级不变量就失去保护；
- **`document.replace` 是批量替换的唯一出口**（导入/新建/迁移后落库）——
  这样"唯一变更通道"不是口号：连导入也走命令。

**代价**：命令类型是显式联合，新增能力要加一个 kind（并在 `COMMAND.md` 登记）。
这是**刻意**的：`COMMAND_KINDS` 是清单，测试会断言每个 kind 都被覆盖。

### 2. before 镜像 = **按 id 的差分**（+ 两个顺序字段），不是下标式 undo log

```ts
type DocumentJournal =
  | { kind: 'delta';
      project: ProjectChange | null;
      tasks: readonly TaskChange[];      // { id, before: DocumentTask | null, after: DocumentTask | null }
      links: readonly LinkChange[];
      taskOrder: OrderChange | null;     // { before: string[], after: string[] }
      linkOrder: OrderChange | null }
  | { kind: 'document'; before: ProjectDocument; after: ProjectDocument };  // 批量替换
```

**理由**：

- **逆操作退化成"逐字段对调"**，因此**不需要反转条目顺序、没有差一格的坐标问题**。
  ADR 0002 §6 记录过：位置型语义在本仓库实际写出过三个错误判据；
- 条目**按 id 定位**，所以同一份 delta 内条目应用顺序无关紧要（顺序字段最后应用），
  失败面比"必须严格逆序回放"小得多；
- **`document` 形态只留给批量替换**（导入是用户级事件，O(N) 明示），
  细粒度命令一律 delta —— 这就是 R-2 的 0.1–2 KB 口径（见 `documentPerformance.spec.ts` 的体积断言）；
- 同时保留 `after` 有两个直接收益：**redo 免费**（对调即可，不必重跑命令），
  以及一条可断言的互证律 `apply(apply(d, j), swap(j)) ≡ d`；
- **顺序必须记**：任务顺序是文档语义（「兄弟顺序 = 文档序」），而依赖边的数组顺序虽无语义，
  却出现在规范序列化文本里。开发中实测到：只记"插入到末尾"时，删除边再回滚会把边排到末尾，
  往返就不是逐项相等 —— 于是补上 `linkOrder`（`journal.spec.ts` 有对应用例）。

**代价**：排列只能用 id 序列表达（≈10 B/任务，仍远小于整份任务对象）；
层级调级的最坏情况是"所有任务的值都变了"（整层重编号），日志随之 O(N)。
**明确接受**：正确性优先，压缩优化归 G6（见"明确延后"）。

### 3. 日志 **clone-then-freeze**，应用日志**写出新鲜克隆**（绝不冻结调用方文档）

- 构造日志时：`deepFreezeJson(cloneJsonValue(value))` —— 冻结的是**克隆体**，
  日志与任何文档**零共享引用**；
- `applyDocumentJournal` 写回的是**新鲜（未冻结）克隆**。

**理由**：R-2 的失败模式是"共享可变对象导致回滚失败"。第 3 条同时满足 G1.3 出口条件
（单测：构造日志后改写源文档，回滚仍还原**原值**）。

**为什么不直接冻结文档**：文档会被 `apps/web`（Vue）持有；冻结会污染响应式语义。
"克隆后冻结克隆体"把不可变性留给**日志**，把可变性留给**应用层**。

### 4. 日志即**唯一变更内核**：`applyCommand` 返回的是"日志应用的结果"

`applyCommand` 的流水线固定为：

```
版本守卫 → 命令形状校验 → 目标/前置条件 → 构造候选文档 → 差分日志
        → 结果合法性校验（复用 validateDocument，零 error 才放行）
        → 返回 applyDocumentJournal(document, journal)
```

**两条关键理由**：

- **结果合法性校验直接复用 G1.2 的 `validateDocument`**，不重写任何文档规则——
  同 ADR 0002 §8 的手法（"日历校验直接调用 `Calendar` 构造器"）：这样
  "命令产出的文档"与"合法文档"**不可能分叉**（例如"结束日早于开始日"不是命令层新写的规则，
  而是 schema 的诊断 `TASK_END_BEFORE_START` 原样返回，`code = CMD_RESULT_INVALID` + `diagnostics`）；
- 返回值取"日志应用"而非"候选文档"，使"日志就是唯一变更内核"成为**运行时事实**，
  而不是测试期的期望。测试另用**独立第二路**（既有领域函数 `indentTask`/`outdentTask`/`moveTask`
  + 手工数组操作）逐命令互证命令产出——被验证的是新增的日志路径，参照物是 G1.2 已测过的路径。

**代价**：每条命令多做一次数组重建（O(N) 次引用拷贝）与一次 schema 校验。
命令按"**一次手势一次命令**"计费（拖拽期的逐帧传播是 G2 的传播闭包，不在本层），
这个常数代价换来了"不可能产出非法文档"的强保证，**明确接受**。

### 5. 三种结果语义；失败码归一；异常只留给程序员错误

| 情形 | 返回 | 类比 |
|---|---|---|
| 目标/载荷/结果不合法 | `{ok:false, code, message, diagnostics?}`，**不抛错** | `WbsResult` |
| 恒等变更（patch 无实际变化、`WBS_SAME_POSITION`） | `{ok:true, changed:false}`，**不压撤销栈** | `SCHEMA.md` §3.2 |
| 真的变了 | `{ok:true, changed:true, document, journal}` | — |

失败码归一表（`WbsFailureCode` → 命令层）：`WBS_TASK_NOT_FOUND → CMD_TASK_NOT_FOUND`、
`WBS_TARGET_NOT_FOUND → CMD_PARENT_NOT_FOUND`、`WBS_SAME_POSITION → changed:false`，
其余（`WBS_NO_PREVIOUS_SIBLING` / `WBS_ALREADY_AT_ROOT` / `WBS_TARGET_INDEX_OUT_OF_RANGE` /
`WBS_CYCLE` / `WBS_DEPTH_EXCEEDED`）**逐值透传**（G5 已经要按这些码给文案）。

而"日志与文档自相矛盾"这类**程序员错误**抛 `RangeError`（同 `parseIsoDate`/`Calendar` 的口径）。
守卫必须有牙：过期日志被拒绝，而不是静默产出错误文档（`journal.spec.ts` 有负向用例）。

### 6. 事务 = **一个撤销单元**；IX-03 的落地解释

- `Transaction` = 一组按序执行、**原子**提交的命令；
- 提交成功只压**一条** step → **一次 Ctrl+Z 回退整次手势**；
- 任一成员失败 → **会话完全不变**（在局部变量上跑完全部成员才落地），并给 `failedIndex`；
- 合并日志 = **起点与终点的差分**（`diffDocument`）：它天然处理"插入后又删除"这类相互抵消，
  且符合"一个撤销单元只需回放端点"的口径；单命令事务直接用该命令的日志（`document.replace`
  因此保留整份镜像形态）。

**IX-03 的原文措辞是"一次手势 = 一个 Command"。** 本层的解释是：
**能表达成一条命令的手势就是一条命令**（改开始/改工期/整体移动都是 `task.update`/`task.*`）；
需要多步的手势（G2 若把级联结果写回文档、批量调级）提交为一个事务，
**仍然是一个撤销单元**。这样既满足 IX-03 的可观察语义（Ctrl+Z 一次回退整次手势），
又不需要引入"嵌套复合命令"这一层新形状。

### 7. 确定性优先：命令层**不生成 id**

`task.insert`/`link.insert` 的 id 由载荷显式给出；`suggestTaskId`/`suggestLinkId` 只提供
**确定性**的候选值（最小未占用整数后缀）。命令层内无时钟、无随机、无全局自增——
因此"同一文档 + 同一命令序列 → 深比较相等"是可断言的（含经 JSON 往返后的序列）。

### 8. 成本口径（写清楚，避免后来者误判）

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `applyCommand` | O(N) | 索引 + 差分 + `validateDocument`；按手势计费 |
| 日志体积 | O(变更量) | 字段级命令 1 条条目；与文档规模解耦（有结构性断言）；层级调级最坏 O(N) |
| `undoSession` / `redoSession` | O(变更量) | 只应用日志，**与命令本身无关**——这是 R-2 的收益 |
| `commitTransaction` | 成员命令 + 端点差分 | 均为 O(N) 级 |

**不做时序门禁**（沿用 G1.2 的立场）：一个会抖动的 p99 断言只会制造假失败；
这里断言的是**结构性事实**（条目数、体积比、撤销可用性）。

## 备选方案与为何未采用

| 方案 | 未采用原因 |
|---|---|
| 下标式 undo log（数组下标 + 逆序回放） | 逆操作要"反转条目 + 逐条减下标"，极易错一格（ADR 0002 §6 的教训）；按 id 差分让取逆退化成逐字段对调 |
| 整片 `tasks.replace`（before/after 整个数组） | 字段级命令的日志退化成 O(N) 整份镜像，违背 R-2 的 delta 口径与体积断言 |
| 每个命令手写一个逆函数 | R-2 明确说"不需要手写"；且逆逻辑与正向逻辑两处实现，必然分叉 |
| 命令层自带 warning 级诊断 | 与 `validateDocument` 分叉；需要 warning 的调用方（G5 冲突提示）在提交后自行校验即可 |
| 用异常报告用户级错误 | G3/G5 需要**逐条**收集问题文案，不能第一条就中断（同 ADR 0002 §7 的取舍） |
| 嵌套复合命令（CompositeCommand） | 需要额外的嵌套失败语义、嵌套日志与多层还原；事务已覆盖"一个撤销单元"的语义 |
| 拼接式事务合并（逐条 fold 日志） | 需要逐实体折叠与抵消判定；端点差分等价且更简单（还能覆盖抵消） |
| 冻结调用方文档来保证不可变 | 会污染 `apps/web` 的 Vue 响应式；改为"克隆后冻结克隆体" |
| 依赖边只记"追加到末尾"、不记顺序 | 实测回滚后边被排到末尾，往返不逐项相等——顺序字段是必须的 |
| 命令层自增/随机生成 id | 破坏"同一命令序列 → 同一结果"（重放与 G6 恢复都要靠它） |

## 影响

- **G5（编辑体验）**：一次手势 = 一条命令或一个事务；失败码出文案；无操作（`changed:false`、
  `WBS_SAME_POSITION`）应**跳过撤销栈压入**；需要冲突标记时在提交后调 `validateDocument`
  取 `warning`。拖拽期的逐帧传播仍归 G2（本层不做增量）。
- **G6（持久化）**：`DocumentSession.undoStack` 就是 R-2 的 **L1 命令回退栈**（会话内，O(变更量)）；
  `SessionStep`（`commands` + `journal`）是纯 JSON，可直接落盘。**检查点策略、配额、压缩、
  IndexedDB、多标签页防护全部归 G6**——本块不碰存储。
- **G2（传播内核）**：文档形状不变（命令层不新增字段）；排程结果是派生值。
  **"排程结果是否写回文档"仍按 `SCHEMA.md` §五 留给 G2 决定**；若选择写回，
  级联用事务承载即可，命令层无需改动。
- **G3（xlsx）**：导入走 `document.replace`（唯一通道），因此"导入进来的文档"必然合法；
  导入前的诊断仍用 `validateDocument`。
- **G4（渲染）**：`journalScope(journal)` 给出受影响 id 集合与"是否整份替换"，
  支撑"只对可见窗口 + 受影响子图做响应式"的缓存失效。
- **明确延后**：命令压缩/合并（G6 的检查点策略）、会话与日志的持久化对接（G6）、
  日历单独编辑命令与 `baselines[]` 编辑（v0.5）、协作/OT/CRDT 预留（非目标 NG-01）。
- **新增依赖**：**零**。`pnpm gate` 的 `license:check` 口径不变（运行时依赖数不变）。
- **不改动**：`tsconfig.json` / `tsconfig.check.json` / `vitest.config.ts` / `eslint.config.mjs`
  均无需变更——新文件落在既有覆盖内（`*.spec.ts` 由既有规则排除于构建之外）。
