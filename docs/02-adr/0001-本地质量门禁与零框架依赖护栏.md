# 0001 本地质量门禁与零框架依赖护栏

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（能力块 G0） |
| 日期 | 2025 |
| 相关裁决 | D-1（不做严格排期）、T-1（选 Vue）、T-4（纯 SVG）、P-3（文档治理） |
| 相关条目 | PRD-06（依赖许可）、EN-06（纯函数引擎）、路线图 G0 出口条件 |

## 背景

G0 要求"安装 → 类型检查 → 测试 → 构建"成为**合并硬门槛**，并要求把"三包零框架依赖"这条
铁律从文档约定变成**可执行的检查**。仓库当时是空骨架（无 `package.json`），且**没有远端仓库**。

## 决策

### 1. 门禁落在本地 `pre-push` 钩子，而不是远端 CI

选择"仅本地 git 钩子"，原因是个人项目、单人维护，且当前没有远端仓库。落地方式：

- `core.hooksPath=.husky`（由 `pnpm install` 的 `prepare` 钩子自动设置，也可手动 `pnpm hooks:install`）；
- `.husky/pre-push` → `pnpm gate` → `scripts/gate.mjs`；
- 门禁步骤的**唯一定义处**是 `scripts/gate.mjs` 的 `STEPS`（本节只登记契约，不复述每一步的实现），
  任一步非零即阻断推送。当前顺序：
  **lint → build → typecheck → test → smoke:build → bundle:offline → smoke:build:file → license:check → docs:check**。
- **构建必须先于类型检查**（本节的顺序约束，勿颠倒）：消费者的 typecheck 是经各包
  `exports.types` → `dist/*.d.ts` 解析工作区依赖的，而 `dist/` **不入库**（见 `.gitignore`）
  ⇒ 顺序反了在**干净克隆上必然失败**。该约束的机制、实测与代价见
  [0001 增补 §1](附录/0001-增补.md#1-门禁步骤顺序构建前移到类型检查之前增补)。

**代价（必须诚实记录）**：

- 出口条件原文是"CI 在 PR 上真实运行且失败会阻断合并"。本地钩子只能做到
  "**推送前全绿**"，无法阻止在 GitHub 上直接合并未经门禁的提交。
- 因此仓库同时保留 `.github/workflows/ci.yml`（Node 24，单版本）。它**不是** `pnpm gate` 的等价物：
  只跑不依赖无头 Chrome 的那几步（安装 → lint → 构建 → 类型检查 → 测试 → 许可审计），
  `smoke:build` / `bundle:offline` / `smoke:build:file` / `docs:check` 不在其中 ⇒ **比 `pnpm gate` 弱**。
  该文件接入远端后的**首次真实运行**（2026-10-06）即暴露"类型检查先于构建"的顺序缺陷；
  该次运行、根因与修复见 [0001 增补 §1](附录/0001-增补.md#1-门禁步骤顺序构建前移到类型检查之前增补)。
  顺序一致性是**两条链的共享不变量**：改 `scripts/gate.mjs` 的 `STEPS` 时必须同步本文件。
- `git push --no-verify` 可绕过钩子。门禁是纪律，不是强制；绕过时须在提交信息里说明原因。

### 2. 零框架 / 零 DOM 依赖用"三层执行"，而不是靠约定

1. **类型层**：`tsconfig.base.json` 里 `lib: ["ES2023"]`（不含 `DOM`）、`types: []`。
   `document`、`window`、`HTMLElement` 在计算层**类型上不可表达**；`apps/web` 单独放开。
2. **Lint 层**：`eslint-rules.mjs` 定义三条限制规则（`no-restricted-imports`、
   `no-restricted-globals`、`no-restricted-properties`），对 `packages/{engine,xlsx-protocol,pptx-renderer}`
   生效，对 `apps/web` 显式关闭。
3. **自检层**：`packages/engine/src/boundary.spec.ts` 对**同一份定义**做断言——
   故意违规的夹具（`packages/*/lint-boundary/*.fixture.ts`）必须被拦下，
   而无害等价代码必须不被误伤。护栏若被放开，该测试立即失败。

### 3. 类型感知 lint 关闭：tsc 负责类型，ESLint 负责结构

`eslint.config.mjs` **不**设置 `projectService`。原因：

- 类型感知检查要求被 lint 的每个文件都隶属于某个 `tsconfig` 项目；
- 这会把测试文件与故意违规的夹具拖进构建项目，把 `*.spec.js` 之类的产物带进 `dist/`；
- 本仓库用到的规则（含三条铁律）都**不需要**类型信息，而类型正确性由 `tsc -p tsconfig.check.json`
  与 `vue-tsc` 分别把关，没有覆盖损失。

落地代价：若将来要引入 `@typescript-eslint` 的类型感知规则（如 `no-floating-promises`），
必须重新处理"specs 与夹具如何归属 tsconfig"，届时再评估是否用 `tsconfig.eslint.json` 统一纳管。

### 4. 依赖许可审计分两种口径

- **门禁口径（默认 `--prod`）**：只审计运行时依赖（PRD-06 的原文约束）。当前 24 个包全部落在白名单内。
- **全域口径（`--all`）**：连开发依赖一起看，当前存在 `lightningcss`（MPL-2.0，Vite 的 CSS 转换器）
  与 `minimatch`（BlueOak-1.0.0）；它们不进产物，登记在脚本的 `KNOWN_DEV_ONLY_LICENSES` 里。
  新增未登记的许可会让 `--all` 失败，避免"新依赖悄悄带入奇怪许可"。
- `THIRD_PARTY_NOTICES.md` 由 `pnpm notices:write` 生成并入库，便于 PR diff 审阅。

## 备选方案与为何未采用

| 方案 | 未采用原因 |
|---|---|
| 远端 CI 作为唯一门禁 | 立项时没有远端仓库，出口条件无法落地；已用本地钩子 + 待启用的 workflow 覆盖（后者弱于 `pnpm gate`，见 §1） |
| 用 ESLint 插件（如 `eslint-plugin-import` 的 `no-restricted-paths`）做边界 | 需要额外依赖；`no-restricted-*` 三条核心规则足够，且没有解析器耦合 |
| 用 `allowDefaultProject` 让夹具也能走类型感知 lint | typescript-eslint 的该选项按 glob 匹配**相对路径**，Windows 上是反斜杠分隔，跨平台不可靠（已实测失败） |
| 在 test 里 spawn `eslint` 子进程 | 依赖进程管道与 PATH；改用 ESLint Node API 后无此约束 |
| 依赖许可引入 `license-checker-rseidelsohn` | 审计工具本身会增加依赖面与许可义务；`pnpm licenses list --json` 已足够 |

## 影响

- 新增/修改依赖时必须同步 `pnpm notices:write` 的产物；
- 三包内任何 `vue`/`react` 导入、任何 DOM 全局访问都会在 `pnpm lint` 与 `pnpm test` 两处暴露；
- 推送前的门禁成本：整链耗时随能力块增长，**实测值登记在增补**（契约里不写死一个会过期的秒数），
  见 [0001 增补 §1](附录/0001-增补.md#1-门禁步骤顺序构建前移到类型检查之前增补)；
- G4/G5 引入 Vue 生态的虚拟滚动与拖拽库时，只能加在 `apps/web`。
