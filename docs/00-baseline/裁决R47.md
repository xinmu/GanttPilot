### 2. `P-48`：为什么是 B 而不是 A

| 维度 | **A：`createScheduleCalendar` 加"编辑余量"** | **B：`compute` 交出真正用到的日历** |
|---|---|---|
| 做法 | 在规划容量时预留一段拖动可达的余量 | 把 `compute` 内部**已经算出**的那份扩容日历作为结果的一部分交出来，渲染层用它翻译序号 |
| 能否**证明**够用 | ❌ 不能。余量是个**猜的常数**：拖动一次可以改工期、可以级联到链尾，"够不够"取决于链长与拖动幅度；总存在把余量用光的拖动 | ✅ 能。序号按定义就落在"输入日历被 `expandToCoverDates` 覆盖到文档日期之后"的那份日历里；**渲染层与 `compute` 用同一份日历**是结构性的，不是余量 |
| 口径影响 | 改 ADR 0004 §7 的容量口径（同时被 G3/G4/G7/导出投影消费） | 只**增加** `ScheduleResult` 的一个字段；`Schedule` 本身的形状/语义/容量无关性**不变** |
| 成本 | 一次性的规划成本变化 + 余量取值需要判据推出 | **零额外计算**（那份日历本来就已经构造出来了） |
| 失败模式 | 余量不够时**仍是白屏**（同一个缺陷以更靠后的位置复发） | 只有在"引擎自己的扩容被 `HORIZON_GUARD_DAYS` 拦住"时才可能失败——那条路径已有**显式抛错**的语义 |

**采 B 的理由一句话**：A 是把"够不够"从"调用方的义务"变成"另一个猜的常数"，
B 是把"够不够"变成**结构性的同一份日历** —— 后者才配叫收口。

**B 的边界（一并冻结）**：

- **不改 `Schedule` 的形状**（`ScheduleResult` 的 `ok: true` 侧**新增**字段）；
- **不改容量无关性**（`Schedule` 逐项与容量无关这条不变量一字不改；新增字段只是"可翻译性"的载体）；
- **不让字段成为第二真相源**：它是**派生量**（同一 `document` + 同一入参日历 ⇒ 同一份），
  不落盘、不进文档、不进 xlsx/PPTX 导出物；
- **`ok: false`（成环）时不产出**（照 ADR 0005 §1："失败结果不产出半成品"）。

**看门人与验收**：`packages/render-core/src/dragHorizon.spec.ts` **第 3 例**（当前钉的是"必须抛错"）
在本项实现后**必须翻红**，断言改写为"**必须能建出视图**"；另加"向右拖远"的真机复核
（打包产物：`projectFinish` 越过旧容量时页面仍完整）。

**不修的地方（明确）**：拖动**仍受**"序号 ≥ 0"约束——把项目起点上的任务继续往左拖**不会产生位移**
（[P-47 §3](裁决R46.md) 已登记），这与"序号 0 = `baseDay`"的冻结口径一致；要支持"排到项目起点之前"
需走 v0.5 的约束/手动模式。

### 3. `P-49`：离线单文件分发（方案与**探针计划**）

**问题（一句话）**：现在的分发方式是"打包产物 + 一个本地 HTTP 服务"（`pnpm preview`），
**它把环境要求推给了用户**——没有 Node 或 Python 的人拿到的是一堆打不开的文件。
而"断网可用"（[US-4](../00-baseline/需求基线.md)）当前的实现只是"**零后端依赖**"，
不是"**不需要网络就能打开**"。

**方案（四步，实现轮照此做）**

| # | 动作 | 理由 / 约束 |
|---|---|---|
| 1 | 资源改**相对路径**（`base: './'`） | `file://` 下绝对路径 `/assets/...` 会解析到盘根 ⇒ 全部 404 |
| 2 | **单文件构建**：入口与其同步依赖合并为**一个 chunk**、并以 IIFE/内联方式嵌入 HTML | `<script type="module">` + 外部 chunk 在 `file://` 下被浏览器按 **CORS 拒绝**（README 已写明"不要直接打开 `dist/index.html`"的真因） |
| 3 | 两个**动态 `import()`**（`exceljs` 用于导入与模板、`pptxgenjs` 用于导出）在单文件变体里改为**静态内联** | 动态导入同样受模块 CORS 限制。**代价如实接受**：体积从约 190 KB（gzip 67 KB）涨到约 1.4 MB——单文件分发的场景里体积不敏感；**在线 Demo 的口径不变**（首屏主 chunk 不含这两者这条断言照旧） |
| 4 | 产物命名与发布：与在线产物**分开**，进 tag 的 release 资产 | 两套产物服务两个场景（在线 Demo / 离线单文件），不互相污染 |

**探针计划（实现轮的前置，**本轮不做**）**：用一个**丢弃式探针**回答四个问题，
**每个问题必须有明确的判读与"不达标时怎么办"**——不达标不是失败，而是**降级登记**：

| # | 探针问题 | 判读 | 不达标 ⇒ 处置 |
|---|---|---|---|
| 1 | `file://` 下 **IndexedDB 是否可用**（各浏览器对 opaque origin 的存储策略不同） | 能开库、能写、重开后能读回 | 若不可用或不可持久：**明示**"本次会话不自动保存" + 写入 README 已知限制；**不得**静默假成功（G6 的"诚实口径"同精神） |
| 2 | `file://` 下**下载（导出物落盘）是否可用**（SVG/PNG/PPTX 走的是 Blob + `<a download>`） | 三个格式都能真的落盘且文件可用 | 若被拦：改用"在新标签页打开并由用户另存"，并在 UI 与 README 写明 |
| 3 | 单文件体积与**首屏时间** | 体积与首屏时间**记录制**登记（不进 `pnpm gate`） | 超标不阻塞发布，但必须**如实登记**（与记录制既有口径一致） |
| 4 | 单文件产物在**离线**（断网）下三条主链路 | 导入 / 拖动 / 导出全部可用 | 任一条不可用 ⇒ 该条**不写进发布说明**，README 已知限制里点名 |

**判据（实现轮进 `pnpm gate` / `smoke:build`）**

1. **门禁**：单文件构建产物的**形状**（恰好一个 HTML 文件、无外部 `assets/` 引用、
   `<script>` 不含 `type="module"` 的外链）——纯字符串/文件系统判定，**可进门禁**；
2. **`smoke:build` 的 `file://` 变体**：以 `file://` 打开单文件产物 → **无应用级错误**
   （`window.__GANTTPILOT_ERROR__ === undefined`）→ 三条主链路各走一次（含一次真实导出落盘）；
3. **不动**既有在线产物的一切判据（首屏 chunk 断言、PPTX golden、记录制证据）。

**明确不做（本轮与实现轮一致）**

- **不做 PWA / Service Worker**（"离线单文件"解决的是"打开"，不是"安装"；PWA 仍在 v0.5 的 §五 口径下）；
- **不追求单文件与在线产物同体积**（两套产物两张账）；
- **不做"单文件里带示例数据"**（示例已由模板下载那条覆盖，避免两个真相源）。

### 4. Docker 容器化部署：评估结论（归 v0.5）

维护者问"部署方式增加 Docker 容器化部署是否合理、是否纳入 G8"。**评估结论：方向合理、但不纳入 v0.1**，
三条独立理由（任一即足）：

1. **上游原文已把它排在 v0.5**：PRD §16 的 **M2（W21–28）W21–22** 写的是
   "GitHub Pages 官方 Demo（全功能、纯前端）；**自部署文档（Docker/静态托管两路）**"，
   而 v0.1（M1）只承诺"**纯前端静态部署可用**"（[PRD-03](../00-baseline/需求基线.md)）；
2. **对 v0.1 的 DoD 零贡献**：静态产物 + 本地存储已满足 US-4；容器化服务的是"用户自建服务器提供给他人访问"这个
   v0.1 不存在的场景。而 v0.1 的诚实边界**不允许**它：镜像一旦对外就是**不可回撤的承诺**，
   而当前仓库自己声明 CI"**尚未经过真实运行验证**"（[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)）；
3. **本仓对"引容器"已有一次带实测的否决**（[P-9](裁决R07-12.md)：镜像落盘 3.32 GB、拉取 500 s、
   闲置 737 MiB–1.35 GiB），方向同族；且**本机与 CI 都没有容器通道**（容器验证必须落到外部机器）。

**何时该复议**：当"自部署"变成真需求时（与 [P1-09](../00-baseline/需求基线.md) 云同步、
飞书 L0/L1 同批），且**两个前置先满足**：① CI 真的跑过（撤掉"未验证"声明）；
② 先定**镜像产物来源**（建议 CI 构建后 `COPY dist/`，而不是镜像内跑 monorepo 构建——
三包未发 npm 之前，镜像内构建会把网络与 pnpm 版本一起冻进镜像）。

**替代关系（重要）**：`P-49` 的"单文件分发"与 Docker **不是二选一**，它们服务两个不同场景——
前者**去掉所有人的环境要求**（下载一个文件双击即可），后者是"给已经有服务器的人多一种部署格式"。
v0.1 选前者，是因为它直接服务"发布 + 邀请种子用户"。

**第四十七轮遗留待定**：**无**。两项都已定：`P-48` 候选选定且契约冻结、`P-49` 方案与探针计划冻结
（实现归 G8 收尾批，与 `P-46` 的三项**同一轮**落地）。
