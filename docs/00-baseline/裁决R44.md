### P-45 批次④：会话锚点的形状与拖动期的下游

### 1. 问题（承 P-24 遗留 1）

[P-24](裁决R24-26.md) §3 明确**不扩会话锚点形状**，因此拖动期只修到"条体本体所见即所提交"：

| 语义 | 拖动期条体本体 | 拖动期**下游** |
|---|---|---|
| `move` | ✅（锚点带着位置走，下游的 FS/FF 约束含完成日） | ✅ 跟随 |
| `resize-start` | ✅ | ✅ **本来就不该动**（完成日不变） |
| `resize-duration` | ✅（[ADR 0008 §14](../02-adr/0008-列身份所有权与拖拽交互契约.md) 的 `drawnBarForRow`） | ❌ **按文档里的旧工期算**，松手后一次到位 |

根因是结构性的：**会话锚点只承载位置**（`{taskId, startOrdinal}`），而"工期"是**文档字段**——
`compute` 看不见新工期，下游自然不动。要让它看见，只有两条路：把工期塞进锚点（契约修订），
或者把"新工期"以**文档**的形式喂进去（零契约变更）。

### 2. 先探针：口径与数字（**同机同会话，先关后开**）

探针按 [P-40](裁决R39.md) §3 批次④ 的预先承诺执行：**只量打包产物上的拖动期帧预算**
（`pnpm build` + `node scripts/measure-render.mjs --drag`），判据沿用记录制既有口径
（主线程同步工作量 p95 ≤ 16.7 ms、帧间隔 p95 ≤ 33.3 ms）。**探针就是候选实现本身**——
不实现它就量不出"每帧多做了什么"。

| 轮次 | 语义 | 主线程同步 p95 | 帧间隔 p50 / p95 | 松手 | 备注 |
|---|---|---|---|---|---|
| **关**（`P-45` 之前＝只喂锚点） | `move` | 7.70 ms | 16.6 / 34.1 ms | 13.1 ms | 本会话基线（改动前的 `HEAD` 产物） |
| **关**（负向对照，`previewDocument` 恒空） | `move` | 8.40 ms | 16.7 / 34.5 ms | 12.4 ms | 同一产物、同一会话的 A/B |
| **开**（采副本；**入库证据**取最差） | `move` | **8.40 ms**（三次重复 7.90 / 8.40 / 9.10） | 16.6 / **36.3 ms**（三次 34.1–41.3） | 11.4–12.1 ms | `drag-timing-chrome154.md` |
| **关**（负向对照） | `resize-duration` | 6.20 ms | 16.7 / 16.9 ms | 9.5 ms | **下游跟随判据当场变红** |
| **开**（采副本；**入库证据**取最差） | `resize-duration` | **5.90 ms**（三次 5.00 / 5.90） | 16.6 / **17.0 ms** | 9.3 ms | 下游跟随 ✅ |
| **开**（2,000 任务规模对照；入库证据） | `move` / `resize-duration` | **11.70 / 9.00 ms** | 16.6 / 34.1 与 16.7 / 16.9 ms | 19.8 / 14.4 ms | `drag-timing-dense-2000-chrome154.md` |

**读法（三条，缺一条就会读错）**

1. **达标的是"主线程同步工作量"这一栏**：最差 11.70 ms（2,000 任务）≤ 16.7 ms。
   **帧间隔 p95 在本机本来就会超过 33.3 ms**——`move` 那一栏关/开两组都给 34–41 ms，
   与 [P-41 §8(b)](裁决R40.md) 记过的"量到的其实是机器当时有多忙"（P-26 同族）逐字同源；
   把这一栏当门槛会得出"本轮把帧率改坏了"的**错误归因**；
2. **新增开销在测量分辨率以下**：同会话 A/B（关 **8.40** vs 开 **7.90 / 8.40 / 9.10**）的差异
   落在重复运行自身的抖动区间里；机制上也如此——`schedule` **本来就是每帧重算的 `computed`**
   （锚点每帧都变），所以备选方案**不是**"每帧多一次全量 `compute`"（[P-40](裁决R39.md) §3 的预算是**高估**的），
   而是**每帧多做一次 O(n) 的结构性拷贝**（1,000 任务 = 一次数组拷贝 + 一个任务对象）；
3. **规模对照**：2,000 任务（拷贝量翻倍）下 p95 仍为 11.70 / 9.00 ms ⇒ 结论不依赖小夹具。

### 3. 裁决：**不扩锚点形状**；拖动期的下游改由**未提交文档副本**承担

按 [P-40](裁决R39.md) §3 批次④ 的预先承诺规则：**达标 ⇒ 采备选方案**（零契约变更）。

**为什么不扩 `SessionAnchor` 成 `{taskId, startOrdinal, durationDays?}`**（三条，都是既有裁决的口径）：

1. **没有跨会话收益**：锚点**不落盘**（[ADR 0009 §6](../02-adr/0009-持久化契约.md)），
   它只在一次手势里活着 ⇒ 扩形状解决的是一个只在"几十毫秒的拖动期"内存在的问题；
2. **一次注定被覆盖的契约变更**：[ADR 0004 §2](../02-adr/0004-排程契约.md) 已写明 v0.5 会随
   `constraints`/`manual` **重做锚点解析**（"约束 = 锚点的另一种来源、手动模式 = 锚点的一种来源"）；
   现在给锚点加字段，等于让 v0.5 的解析器多背一个只服务渲染的字段；
3. **与 ADR 0004 §1 拒绝同类改动的理由同族**：§1 之所以不把 `constraints` 写进 `compute` 签名，
   理由是"**把未启用的语义写进公共签名，只会得到'测了但没有语义'的死条目**"；
   给锚点加一个"只被 UI 用来画下游"的字段，是同一类"签名承载了内核不拥有的语义"。

**因此**：机制落在**应用层**（它本来就把 `compute` 的入参与文档一起持有），内核**只多认一个纯函数**。

### 4. 机制（**契约面一字未改**）

```
拖动每一帧：
  内核    → GestureUpdate.dragOutcome（结果几何 + patch + 锚点），**patch 的唯一来源**
  应用层  → previewDocumentFor({document, taskId, patch})      // O(n) 指针拷贝，只替换那一个任务
  compute → compute(previewDocument ?? document, calendar, anchors)
  松手    → task.update 经命令层（ADR 0003）⇒ commit() 里"一落库即作废预览"
```

| 决定 | 内容 | 为什么 |
|---|---|---|
| 副本只喂 `compute` | **不进命令通道、不进撤销栈、不落盘** | 落库仍然只有一条路（ADR 0003）；"所见即所提交"靠**同源**而不是靠提前落库 |
| `patch` 取自 `dragOutcome` | 应用层**不得**自己推第二份"这次拖动改了几天" | 预览与提交共用 `resolveDragOutcome` ⇒ 不可能分叉（ADR 0008 §13） |
| **日历**仍由**已提交**文档派生 | `createScheduleCalendar` 每帧不重建 | 它扫全表日期/工期总和定 `baseDay`（序号 ↔ 日期的映射）⇒ 让每帧都变的副本参与会改掉锚点路径的既有语义 |
| 文档诊断同样只看已提交文档 | `validateDocument(document)` | 同上；且它本来就不该对"未提交的意图"报警 |
| 清预览有**两个**闸 | 手势侧"非 `dragging` 即清" + `commit()` 的"落库即清" | 后者覆盖**所有**落库路径（行内编辑/导入/撤销/重做/重置）；顺序上命令先落地、预览后清 ⇒ **不会出现"锚点已清、工期还是旧的"那一帧回弹** |
| 零位移不造副本 | `patch === null` ⇒ `previewDocumentFor` 返回 `null` | 缺省回落已提交文档；不造"内容相同、身份不同"的副本去白白失效一遍 computed |

### 5. 判据

**门禁（`packages/render-core/src/gesture.spec.ts` +3 例）**

1. `previewDocumentFor`：只改那一个任务（其余任务**按引用共享**、`links`/`project` 同一对象）、
   原文档一字不动、`patch === null` / 未知 id ⇒ `null`；
2. **下游同源**（本条的核心）：`resize-duration` 拖动期 **`compute(副本, 锚点)`** 与
   **落库后重算**的后继行开始序号**逐位一致**；
3. `GestureUpdate.dragOutcome` 就是松手要提交的那一份（`moved.dragOutcome.patch`
   与 `released.commands[0].patch` 逐字段相等；建线/空闲产出为 `null` ⇒ 应用层据此清预览）。

**记录制（打包产物，`node scripts/measure-render.mjs --drag`）**

`--drag` 由"一种语义两个滚动状态"扩为 **两种语义 × 两个滚动状态**，`resize-duration` 那一轮新增：

| 判据 | 口径 |
|---|---|
| 抓取点自证 | `gestureMode === 'resize-duration'`（**先自证抓在 `edgeR` 上**，否则"下游跟随"会在退化成整体移动时换个理由成立） |
| 位移判据 | 松手后 `durationDays` = 拖动前工期 + 拖动天数（`move` 那一栏仍看 `startDate`） |
| **下游跟随** | 后继行开始序号：**拖动期 == 松手后**（预览 == 提交）**且 ≠ 拖动前**（前提自证：这条边真的由被拖任务的完成日决定） |
| **预览不落库** | 拖动期已提交 `revision` **逐位不变**；松手后 **+1** |

### 6. 负向对照（**跑完即还原**；工件在 gitignore 的 `tmp/nc-evidence/`）

把 `previewDocument` 那一半关掉（`scheduleResult` 回到 `compute(document, …)` ＝ `P-45` 之前的实现），
**只改这一处**、重建、跑同一条记录制命令：

| 变造 | 必须变红 | 实测 |
|---|---|---|
| `scheduleResult` 只喂锚点 | 记录制的**下游跟随**（两个滚动状态都要） | **2/2 全红**：`t15` 拖动期 es = 1 vs 松手后 4；`t36` 9 vs 12 ✅ |
| 同上 | 记录制的"预览不落库" | **仍绿**（`0 → 0 → 1`）——它守的是"别提前落库"，**判别力在下游跟随那一条上** |

> 这条对照同时说明一件事：**"预览不落库"单独不足以证明这条链路是对的**（旧实现也是绿的）。
> 两条判据必须成对读——这也是第 5 节把它们写在同一轮的单元里的理由。

### 7. 代价与边界（**明确接受**）

- **每帧一份 O(n) 拷贝**：结构性共享（只换那一个任务对象、`links` 与 `project` 同引用），
  1,000 任务下在测量分辨率以下、2,000 任务下主线程 p95 仍为 8.20 ms；
- **左表的「工期 / 完成日」单元格仍是文档值**（松手后才更新）：本轮只让**图表**的下游跟随。
  左表是**文档视图**（它显示的是文档事实，不是渲染投影），"拖动期文档不写"这条既有口径不变
  （README 的已知限制）；
- **`resize-start` 刻意不受影响**：它的完成日不变 ⇒ 下游本来就不该动；
- **`move` 也走了同一条路**（`patch` 含 `startDate`/`endDate`）：语义不变，只是"图上的条"与
  "喂给 `compute` 的文档"从此共用同一个 `patch`；
- **复制的是"文档字段"而不是"意图"**：因此它**必须**由 `resolveDragOutcome` 的产出驱动
  （应用层不得自推），否则预览会与提交分叉——这条已写进 `UseProject.setPreviewPatch` 的文档串；
- **一处瞬态副作用（如实登记）**：`allow` 模式下把**有前置**的任务拖到约束**之前**时，
  副本的 `startDate` 是"过头的候选"，而引擎按"前置优先"把 `ES` 推到约束上 ⇒ 拖动期会**多出**
  一条 `dateOverridden`（[SCHEDULE.md §四.3](../../packages/engine/SCHEDULE.md) 情形③）。
  它**只影响诊断计数**（几何仍由 `ES = max(约束, 锚点)` 决定），且**松手即回到文档事实**；
  本轮不改引擎的这条口径（"文档日期被推导覆盖"本来就成立），也不因此调整判据。

### 人工复验（维护者，2026-10-05）

> 报文（逐字）：**"复验通过"**（无缺陷报文）。
