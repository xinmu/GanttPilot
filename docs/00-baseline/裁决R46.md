### 1. 现象与取证（打包产物，2026-10-05）

三个一次性探针（走 `?measure=1` 的真实指针入口 + CDP 真实鼠标事件；用完即删，工件在 gitignore 的 `tmp/`）：

| # | 手段 | 结果 |
|---|---|---|
| 1 | 真实鼠标事件拖 `t1` 的条体向左，逐步加深 | 到 `dx = -96 px` 时页面**结构全空**：`#app` 子节点 0、`svg` 0、`rect.bar` 0、左表行 0；`window.__GANTTPILOT_ERROR__` 有值 |
| 2 | `Debugger.setPauseOnExceptions('caught')` + 读调用帧 | 两条分化：序号 **96** 的越界来自 `isoOfOrdinalSafe`（**预期失败、被 catch**，即 `gesture.ts` 的既有安全层）；序号 **102** 的越界来自 `buildView` |
| 3 | 把"真实手势产出的 patch"喂进 **Node 侧同一条管线**（`beginGesture` → `resolveDragOutcome` → `previewDocumentFor` → `compute` → `buildView`） | 复现且**可量化**：向左拖 96 px 时 `candidate` 从 **4 变成 94**（日历只有 95 个工作日），`patch.startDate` 写成 **2027-02-12**（+130 天），`projectFinish` **129** ⇒ `buildView` 抛 `RangeError` |

**异常栈（打包产物，两次探针一致）**：

```
[组件] App / RangeError: 工作日序号越界：102（合法范围 0..95；容量不足时用 withHorizon() 扩容后重算）
    at Calendar.dayOfOrdinal
    at contentWidthFor        （viewModel.ts：projectFinish − 1）
    at buildView
```

**为什么"整页空白"而不是"这一行画不出来"**：异常发生在 Vue 的**渲染期**（`buildView` 是 `computed` 的求值），
抛错后 Vue 卸载整棵组件树 ⇒ `#app` 只剩空壳；刷新时状态由 G6 的检查点恢复，因此"刷新可恢复"。
⇒ 这条现象同时说明：**渲染期异常没有兜底**，一个数值越界会升级成整站不可用。

### 2. 根因（两处，第二处本轮只登记不修）

**(a) 已修：夹取把"左侧越界"判成了"右侧越界"。**

`ordinalAtClamped` 的旧实现是"先算序号、抛错后按 `x <= 0` 猜方向"：

```ts
try { return calendar.ordinalOfDay(Math.floor(dayAtX(view, x))); }   // ① 左侧越界时抛
catch { return x <= 0 ? 0 : calendar.workdayCount - 1; }             // ② 猜方向
```

两处都错，且**只有向左拖时才现形**：

1. `Calendar.ordinalOfDay(day)` 对 `day < baseDay` **抛错**（G1.1 冻结：负序号无定义），
   而 `baseDay` 左侧在屏幕上**不是 `x <= 0`**：轴线起点 = `dayOfOrdinal(projectStart) − AXIS_LEFT_GUTTER_DAYS`
   （日档 192 px），因此"条体左缘左边的正常位置"（`x` 仍是正数）已经落在 `baseDay` 左侧 ⇒ 抛错；
2. catch 于是把它判成"向右越界"，返回**最右序号**（`workdayCount − 1` = 94）。
   ⇒ 向左拖 96 px 会把候选**甩到约 130 个工作日之后**（实测 4 → 94）——这正是本缺陷的入口。

**(b) 待裁决：预览的完成序号超出"调用方日历"的容量。**

即便候选被正确地夹在 `[0, workdayCount − 1]` 内，**起点 + 工期 + 级联**的**完成序号**仍可越界：
本轮实测**向右**拖 `t1` 90 个工作日后 `projectFinish = 100`，`buildView` 同样抛错、同样白屏。
按 [SCHEDULE.md](../../packages/engine/SCHEDULE.md) §七，"容量够不够"是**调用方**的义务，
而 App 的日历由**已提交文档**经 `createScheduleCalendar` 规划（[ADR 0004 §7](../02-adr/0004-排程契约.md) 的口径），
拖动预览喂给 `compute` 的却是**另一份文档** ⇒ 两者的容量假设必然可能分叉。
**本轮不擅自改**：修法要动契约（`createScheduleCalendar` 的口径，或让 `ScheduleResult` 交出真正用到的日历），
必须先按 [P-42](裁决R41.md) 的登记义务走契约面。

### 3. 修法（**只改一处反算式**）

新实现只做两件事：**用唯一的反算式 `dayAtX` 得到自然日 → 把日夹进可表示域 → 再算序号**。

```ts
const firstDay = calendar.baseDay;
const lastDay  = calendar.dayOfOrdinal(Math.max(0, calendar.workdayCount - 1));
const day      = Math.floor(dayAtX(view, x));
const clamped  = Math.min(Math.max(day, firstDay), lastDay);
return Math.min(Math.max(calendar.ordinalOfDay(clamped), 0), calendar.workdayCount - 1);
```

| 决定 | 为什么 |
|---|---|
| **在"自然日"这一层夹，不在"序号"那一层夹** | `ordinalOfDay` 是"自然日 → 序号"的唯一口径（含**周末吸附**：落在周末的日吸附到下一个工作日）。先算序号再夹会丢掉这层语义，并让"哪一天"与"哪个序号"的边界各写一遍——那正是 R13/R14 的同族陷阱 |
| **删掉 `ordinalAtXSafe`（第二份反算式）** | 它只是把 `dayAtX` 抄了第二遍（P-25 已因此踩过一次：修了 `dayAtX` 却漏了它）。反算公式**只允许有一处** |
| **取消 `x <= 0` 这个方向判据** | 它从来不是"左/右"的正确判据（`baseDay` 的屏幕位置取决于 gutter 与 `pxPerDay`）。夹取之后不再需要方向判断——"越界"退化成一次钳制 |
| **不改 `ordinalAtX` 的抛错语义** | 它是"精确反算"，调用方（如记录制断言 `ordinalAtX(xLeft) = es`）需要真实失败；夹取是**手势层**的要求，只在 `ordinalAtClamped` 里做 |

**副作用（如实登记）**：修好之后，"把项目起点上的任务继续向左拖"**不再产生任何位移**
（候选夹到 0、`patch === null`、无命令）。这是**符合语义**的结果——它此前之所以"有效果"，
只是因为缺陷把候选甩到了 130 天之后。v0.1 的承诺环境不含"把任务排到项目起点之前"
（它会与"序号 0 = `baseDay`"的冻结口径冲突），如需支持应走 v0.5 的约束/手动模式。

### 6. 遗留（**必须在下一轮结清**）

**"预览把完成序号推出调用方日历容量"这一半仍然存在**，且**向右拖**同样能弄白页面（本轮已实测）。
它是**渲染期异常 ⇒ 整树卸载**这条放大路径的同一个出口，两个候选修法（都要走契约面）：

| 候选 | 内容 | 代价 |
|---|---|---|
| **A** | `createScheduleCalendar` 的 `spanDays` 加上**拖动可达的余量**（编辑余量），使"任何一次拖动预览"都落在容量内 | 容量口径（ADR 0004 §7 / SCHEDULE.md §七）要改；余量取值要由判据推出，不能手选 |
| **B** | 让 `ScheduleResult` 交出**它真正用到的日历**（`compute` 内部已经在用 `expandToCoverDates` 扩容），渲染层改用它 | `ScheduleResult` 是 [ADR 0005](../02-adr/0005-排程内核落地补齐与结果形状.md) 冻结的形状 ⇒ 追加 ADR + 同步 SCHEDULE.md |

**本轮不动 A/B 的理由**：两者都会改"序号 ↔ 日期"的容量口径，而该口径同时被 G3/G4/G7 与导出投影消费；
按 [P-42](裁决R41.md) 的先例，这类改动必须**先在契约层登记**，不能在缺陷修复里顺手改。
`dragHorizon.spec.ts` 的用例 3 是这条遗留的**看门人**。
