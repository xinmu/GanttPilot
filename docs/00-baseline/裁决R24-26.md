### P-25 报文与判定

**报文**："仅首屏渲染出来的条（左上区域）可以交互，向下、向右滚动出来的条都不能拖动交互。"

**判定：确认，且是三个同族缺陷**——形状都是"**只在某个滚动位置才现形**的坐标重复计数"：

| # | 根因 | 位置 | 现象 |
|---|---|---|---|
| **R13** | 命中反算又加了一次 `scrollTop` | `gesture.ts` 的 `resolvePointerTarget`：`Math.floor((y + view.scrollTop) / rowHeight)` | 向下滚动后行号凭空多出 `scrollTop / rowHeight` 行（实测 480 px ⇒ +20 行）、落到渲染窗口之外 ⇒ **按下根本不进手势**（纯函数实测：命中返回 `null`） |
| **R14** | 反算又加了一次 `scrollLeft` | `viewModel.ts` 的 `dayAtX`：`axisOriginDay + (x + view.scrollLeft) / pxPerDay` | 向右滚动后反算整体偏 `scrollLeft / pxPerDay` 个**自然日**（实测 600 px ⇒ 偏 **25 天** ≈ 19 个工作日）⇒ 拖动候选跳位、落库日期错 |
| **第三处** | 同一公式**抄了两份** | `gesture.ts` 的 `ordinalAtXSafe` | 修 `dayAtX` 修不到它（本条落地时当场踩到：纯函数修好后记录制仍红） |

**为什么此前全部判据都放过了它们**：这三处都要 `scroll ≠ 0` 才有效应，而**纯函数 spec 与记录制
此前一律取 `scrollTop = scrollLeft = 0`**（`--drag` 也只拖首屏那一行）⇒ 结构上不可能抓到。
这是 R10（轴随纵向滚动）/R12（轴的横向双重偏移）同一族缺陷的第三次出现。

### 修法（三处 + 判据两层）

1. `resolvePointerTarget`：`row = Math.floor(args.y / view.rowHeight)`（`y` 已是内容坐标）；
2. `dayAtX`：`axisOriginDay + x / pxPerDay`（`x` 已是内容坐标）；
3. `ordinalAtXSafe`：**删除重复公式**，委托 `dayAtX`——反算公式**只允许存在一处**；
4. `PointerInput.x/y` 的文档收紧为"内容坐标 + 本包内所有消费者都按内容坐标取值"。

**判据**：`geometryExpectations.spec.ts` **+3 例**（三个数据集各一例：滚动视图下的反算往返、端点贴合、汇总覆盖必须与不滚动时逐值一致）；`gesture.spec.ts` **+1 例**（滚动视图上：条左缘仍映射到 `es`、命得中同一行、起得了手势、**候选与抓取点的工作日差 == 指针移动的工作日差**）。

### 记录制（`--drag` 扩为两个滚动状态）

| 滚动位置 | 目标任务 | 期望 `startDate` | 实际 | 判定 |
|---|---|---|---|---|
| `(0, 0)` | `t1` | 2026-10-08 | 2026-10-08 | ✅ |
| `(480, 600)` | `t16` | 2026-10-08 | 2026-10-08 | ✅ |

**两条负向对照都只在滚动状态变红**——这就是"只跑首屏的判据抓不到它们"的直接证据：

| 变造 | `(0,0)` | `(480,600)` |
|---|---|---|
| `resolvePointerTarget` 加回 `+ scrollTop`（R13） | ✅ 绿 | ❌ 红："**按下后未进入拖动（实际 idle）**" |
| `dayAtX` 加回 `+ scrollLeft`（R14） | ✅ 绿 | ❌ 红：`startDate = 2026-10-06`（期望 2026-10-08） |

**记录制的一条纪律（本轮踩到）**：`--drag` 的目标行必须**无有效入边约束**（`entryConstraintFor` 非有限值）——
`snap` 会把候选夹到约束之下，"拖 N 天"的位移判据对有前置约束的行**必然**报错；
`gesture.spec.ts` 的 `pickLeaf` 一直是这么过滤的，记录制这一侧必须同口径，否则判据给出的是**假红**

### P-26 事实：同一条 DoD，两种跑法给出两种结论

同一台机器、同一份代码，唯一变量是"这条 spec 与多少个测试文件**并行**跑"：

| 跑法 | 自适应 `batchSize` | p50 | p95 | **p99** | 判定（DoD：`medianP99 ≤ 1 ms`） |
|---|---|---|---|---|---|
| `pnpm test`（48 个文件并行；vitest 默认多 worker） | **3** | 530 µs | 724 µs | **1.03 ms** | ❌ **失败**（`medianP99 = 1,030,967 ns`） |
| `vitest run packages/engine/src/schedule.performance.spec.ts`（单独） | **8** | 314 µs | 357 µs | **393–455 µs**（4 次） | ✅ 全过 |

- 该 spec 的 `batchSize` 是**自适应**的（按可用时间自校准）⇒ 负载一变，连"测多少"都变；
- 因此**门禁是否变绿取决于当时机器上并行跑了多少东西**：本轮共约 10 次全量 `pnpm test` 中出现 **2 次**该条失败
  （两次都是它），单独跑则 **4/4 通过**；
- **这不是回归**：P-6 的 52.1 µs / 19× 余量来自 S3 的**独占测量**；把同一个绝对阈值放进并行测试进程里断言，
  量到的其实是"**机器当时有多忙**"。同理，本轮 S3 的 `p99` 本身也已在 P-6 里写明是 **median-of-suites**、
  不是分布尾部极值。
