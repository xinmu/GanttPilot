### P-40 批次①的四项口径

**0. 为什么"口径类"要排在前面。** 这四项都不是能力缺口，而是**判定前提**：

- 它们决定 README 的**已知限制与非目标怎么写**——而"已知限制清单完备"本身是 G8 的**出口条件**之一，
  口径未定则该条无法判定（写多了虚、写少了漏，两种都无法判定"完备"）；
- 它们的成本是**文档级的**（零产品代码），而后三项的成本是代码/契约级的 ⇒ 先做零成本的、把
  未决面从 10 行压到 5 行，再动需要探针的那一项；
- 其中三项（应用层判据入口 ×2、复核口径）从 [P-19](裁决R19-21.md)（第十九轮）起**连续六轮原样承接下来**
  （P-19 → P-21 → P-23 → P-24 → P-25 → P-32），每轮都写"**未预先承诺方向**"。**"不预先承诺"本身
  也是一种口径**，只是它从未被写进任何契约文档，于是每次复核都要重新讨论一次——本轮把它变成明文。

**1. 承诺环境：桌面浏览器（鼠标 + 键盘）；触屏/移动端不进 v0.1 的承诺范围。**

| 项 | 内容 |
|---|---|
| 裁定 | v0.1 的**对外承诺环境 = 桌面浏览器（鼠标 + 键盘）**。触屏/移动端**不在** v0.1 的范围内：不做响应式布局承诺、不做触屏手势入口承诺；**归 v0.5**。README 的「已知限制」写明；[首版能力顺序](../01-roadmap/首版能力顺序.md) §五 增一行 |
| 依据 | ① **入口设计本身依赖悬停与光标**：P-32 落地的连接点是**按需显形**（`connectRevealFor`），端点手柄靠 `col-resize` 光标暗示，而触摸设备**既没有 hover 也没有 `col-resize`**（[ADR 0008](../02-adr/0008-列身份所有权与拖拽交互契约.md) §16.2）——"够不够用"要真机 + 新判据才能答，属**依赖准入**问题；② **它不在 v0.1 的承诺链上**：飞书 L0/L1 **本来就已排在 v0.5 之后**（[首版能力顺序](../01-roadmap/首版能力顺序.md) §五），因此"移动端场景"对 v0.1 不构成入口承诺；③ **不写清就是隐性承诺**：`需求基线` 的 P1-10（飞书）与目标用户的"周度汇报"场景都含移动端，而全仓文档从未表态——**沉默会被读成"支持"** |
| 代价（明确接受） | 触屏用户可能在 v0.1 上**用不了建线与端点改期**（拖动改期能否工作未验）；这不是"已知缺陷"而是"**范围外**"，README 按范围外写法表述，不承诺、不阻止用户反馈；范围裁决**不追认**为触屏缺陷，日后若要进入范围，须另立裁决 + 真机判据 |
| 落地 | README「已知限制（诚实声明，随版本更新）」增一条；[首版能力顺序](../01-roadmap/首版能力顺序.md) §五 增一行（v0.5）；待定清单两行结转（`P-32` 的 ② 与"移动端范围"那行**同源**，一次裁决同时闭） |

**2. 应用层判据入口与依赖准入：v0.1 不引入组件级测试框架；走两条已有通道。**

| 项 | 内容 |
|---|---|
| 裁定 | **显式承诺方向**：v0.1 内**不引入** `jsdom` / `happy-dom` / `@vue/test-utils` / Playwright 一类依赖，**`apps/web` 不新建判据入口**。应用层的判定由两条**既有**通道承担（表见下）；**可测纯函数继续一律落 `packages/*`**（既有纪律，不新造） |
| 通道①（**门禁**） | `pnpm smoke:build`：HTTP 伺服 `dist/` → 无头 Chrome 打开 → 断言"无应用级错误 + 标题/工具栏/图表窗格/SVG/状态栏持久化那一栏都渲染了"，并真的点三次导出校验落盘。**它已经在 `pnpm gate` 内**，是应用层目前唯一的门禁口 |
| 通道②（**记录制，打包产物**） | `node scripts/measure-render.mjs`（`--align` / `--drag` / `--import` / `--persist-drag` / `--storage-metrics` / 主口径）：用 Node 内置 `fetch` + `WebSocket` 经 CDP 驱动本机 Chrome，采**真实指针**输入。**不进 `pnpm gate`**（P-9/P-17 分层：需要本机 Chrome 的不进门禁） |
| 依据 | ① [P-19](裁决R19-21.md) §4.1 的因果判定：缺口是"**落点判断**"而不是"缺测试框架"，最优解是执行 ADR 0007 §2 的"落点即门禁"，**零新增依赖**；② 该判定已被两次事实检验：P-21 与 P-25 两轮人工复核的**关键发现**（R1 指针参照物、R13/R14 坐标重复计数）**都来自打包产物的记录制探针**，而没有一次来自组件级断言——引入框架**不是本仓库缺陷史的决定性手段**；③ 依赖面本身就是护栏要守的东西（[ADR 0001](../02-adr/0001-本地质量门禁与零框架依赖护栏.md)：三包零框架/零 DOM）；④ `vitest.config.ts` 的收集范围（`packages/*`）与 `environment: 'node'` **是显式设计**，不是遗漏（P-19 §4.1 证据①）；⑤ 入口层的坐标换算缺陷已被 P-33 的 13 处盘点、[ADR 0007](../02-adr/0007-渲染几何与裁剪契约.md) §16 与 [ADR 0008](../02-adr/0008-列身份所有权与拖拽交互契约.md) §15 收口 ⇒ 余下形态天然是记录制 |
| 代价（明确接受） | **组件级**（Vue 模板/生命周期/事件绑定）仍**只能**靠 `smoke:build` 的端到端断言 + 人工复验；"某条 DOM 路径没被覆盖"这类缺口**不会**被自动发现——这条如实写进 CONTRIBUTING，不写成"应用层已有判据"；若未来版本要引入组件级框架，**仍按「新增依赖的准入流程」并需一条新裁决**（本节只承诺 **v0.1 范围内**不引入） |
| 落地 | [CONTRIBUTING](../../CONTRIBUTING.md) 的「新增依赖的准入流程」末段增一节"应用层判据入口的口径"；待定清单两行结转（`P-19` 行 + `P-24` 的"应用层判据入口与依赖准入"行） |

**7. 与既有裁决的关系。** **不取代、不修改**任何 `Dn/Rn/Tn/Pn` 条目；**ADR 正文一字未改**
（本轮不动契约：四项全是判定前提与应用层/文档口径）；**不放宽**任何 DoD
（`c₁`–`c₄`、元素预算、性能的 1 ms / 2 ms、文档 schema 与诊断码表全部不变）；

**批次①的明确不做**

1. **不给 `apps/web` 搭任何测试环境**（含"只加一个 vitest project"这种最小形态）——见 §2 的代价段；
2. **不为触屏做任何入口降级**（不做"长按替代 hover"、不做触摸命中容差调整）——归 v0.5；
3. **不改 `pnpm dev` 的行为**（不加自动 build 钩子）——只把口径写成纪律，工具链不变；
4. **不动 `--align` 的参数面与记录制脚本**（属批次②）；
5. **不裁会话锚点**（属批次④，需先有探针数字）。
