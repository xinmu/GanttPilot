### P-38 G7 二次复验：SS/SF 空心箭头、图例对齐与侧栏垂直居中；P-26 以两条判据收口

**报文（逐字要点）**：① 结论"明显改善，下面没有提的就是通过"；② PPT 中 `SS`/`SF` 箭头是"→"形、
不是空心三角形，与图例/SVG/PNG 不一致——**问题不大、不影响理解**；③ PPT 图例的图元与文本**垂直错位**
（图元纵中点对齐到文本上沿），且**左右间距过密**；④ 图例摘要区与甘特本体区**没有垂直居中**，
侧栏浮在右上，既不视觉对齐也不省空间；⑤ 关于 `p99 < 1 ms`：与本机负载有关，偏差不大且可接受，
**考虑是否放宽标准**。

**②③④ 的根因与修法**：

| # | 报文 | 根因 | 修法 |
|---|---|---|---|
| ② | `SS`/`SF` 是"→"形 | **OOXML 的原生箭头里没有"空心三角形"**：`type="triangle"` 实心、`type="arrow"` 是开放折线箭头。**先试了"自绘白底三角"（与 SVG 同形），但被实测否掉**——自绘形状没有 `stCxn/endCxn` 吸附锚点，WPS **从不重算它的位置**，拖动"入端"那条任务条时**线走而箭头留在原地**；G7 的招牌行为（拖动跟随）优先 ⇒ **改用原生 `type="arrow"`**，并让 **PPT 图例与画布同形**（`SS`/`SF` 画开放箭头、`FS`/`FF` 画实心三角） |
| ③ | 图例图元与文本错位、间距过密 | 图元按 `row.y − 9` 摆（文本行中心其实在 `row.y`）；图元右缘到文本左缘只有 **2 px** | 图元一律以 **`row.y` 为中心**摆放；色块占 `[x+6, x+24]`、文本从 `x+34` 起 ⇒ **净间距 ≥ 8 px** |
| ④ | 侧栏浮在右上方 | 甘特内容在框内**居中**（`fit.offsetY`），而侧栏内容**从框顶**往下排 ⇒ 两块基准不同 | 侧栏内容按总高**居中**到侧栏框内（与甘特同基准）⇒ 两块的视觉中心一致 |

**⑤ 的处理（`P-26` 收口）**：**不放宽 `1 ms` 这个数值**，而是把**断言口径拆成两条**——
[ADR 0004 附录 §1](../02-adr/附录/0004-增补.md)：

| 判据 | 值 | 管什么 | 实测（本机 Node 26） |
|---|---|---|---|
| `medianP50` | **≤ 1 ms**（数值不变） | **实现退化** | 空闲 326 µs / **全量并行门禁实测 533–545 µs**；朴素实现慢 **2.97×** ⇒ 满负荷 p50 ≈ 1.3 ms，**必被拦下** |
| `medianP99` | **≤ 2 ms**（放宽的那一档） | **并行争用抖动** | 空闲 530 µs / 满负荷 **1.04–1.40 ms** |

**为什么这不是"调大阈值掩盖回归"（`P-26` 的候选④）**：`1 ms` 是 S3 在**独占机器**上定标的数字
（p99 = 52.1 µs），而该 spec 与 50+ 个用例共享并行池——`P-26` 早就指出"**正文没写它是在哪跑的**"。
把绝对性能交给**中位数**（稳定估计）、把调度抖动交给**尾部**，两条判据各管一件事；
对 3× 级真实退化的判别力**保留在前一条**。`P-26` 的候选①（给该 spec 独占并行槽）**仍是备选**：
若这两条仍偶发红，再上配置层隔离，而不是继续放宽数值。

**代价（明确接受）**：尾部从 1 ms 放宽到 2 ms ⇒ **1–2 ms 区间的真实尾部退化**不再被门禁拦住。
接受理由：S3 的余量是 19×（52.1 µs 对 1 ms），放宽后仍有 ≥9×；而"1–2 ms 的尾部"在本机并行口径下
与"机器忙"**不可区分**（同一实现同一工作区反复测即跨越该区间）。**判据宁可少报噪声，
不可养成"红了就重跑"的习惯**。

**落地与实测**：

- spec：`packages/pptx-renderer/src/template.spec.ts`（第 ③ 条改为"`triangle` 数 == FS/FF、`arrow` 数 ==
  SS/SF，且 **`tailEnd` 合计 == 依赖线条数**——**不允许"没有吸附锚点的自绘箭头"**"；第 ④ 条要求图例的
  `SS`/`SF` 箭头**与画布同形**（两条臂拼尖角）；新增第 ⑦ 条"图例图元垂直居中 + 间距 ≥ 8 px +
  侧栏与甘特同基准居中"）；`PPTX.md` §三/§五/§七 同步；`pptx-renderer` 用例 **18 → 20 例**；
- 性能侧：`packages/engine/src/schedule.performance.spec.ts`（两条阈值 + 日志分别报出，
  便于区分"真退化"与"机器忙"）；`SCHEDULE.md` §十 ④、ADR 0004 正文 §9 ④ 与文首、`CONTRIBUTING`
  的性能条目同步；
- 实测（隔离跑）：性能 p50 = **331.8 µs** / p95 = 420.2 µs / p99 = **478.0 µs**（最差 suite p99 = 611.4 µs）
  ⇒ 两条判据分别有 **3.0× / 4.2×** 余量；
- 实测（**全量 `pnpm gate` 并行**，即原先会红的那个口径）：p50 = **533 / 545 µs**、
  p99 = **1.28 / 1.40 ms** ⇒ 分别有 **≥1.8× / ≥1.4×** 余量，**连续两次七步全绿**（53 spec / 773 例）；
- `P-26` 状态：由「未决」改为**已闭（P-38）**；待定清单同步（未决项 6 → 5 条）。

**二次复验状态**：②③④ 返工已落地并通过门禁，**待第三次人工复验**（只需看 PPT 的箭头形态、
图例对齐与侧栏居中三项）。

**一条值得复用的判据（本轮最贵的一课）**：**"形状对"不等于"行为对"**。
自绘箭头让 PPT 与 SVG 同形，却在 WPS 里**不跟随端点**——因为**跟随来自 `stCxn/endCxn` 吸附，
而不是来自"画得像"**。凡是"看起来更漂亮但脱离宿主模型"的改法，都必须先问：
**它还能被宿主重算吗？** 门禁因此把"`tailEnd` 合计 == 依赖线条数"写成硬判据，
把"自绘箭头"这条歧路直接堵住。

**第三次人工复验又抓到一条（同轮修掉）**：图例里 `SS`/`SF` 的开放箭头**朝向反了**——
两条臂的 `rot` 正负写反（`rot` **顺时针为正**、旋转绕**包围盒中心**：水平细矩形转 `θ` 后
两端在 `center ± (L/2)·(cosθ, sinθ)`），于是两臂改为**共用左端**顶点、尖角朝左，
呈现 "-<" 而不是 "->"。修法：上臂 `+45°` / 下臂 `−45°`；并把"**一端落在尖端（≤0.6 px）、
另一端在尖端左侧**"写成**几何判据**（由 `<a:xfrm rot>` 与 `off/ext` 反解端点），
**判别力用负向对照验过**（把 `θ` 写反，该用例立刻红）。目视复核见
[`evidence/template-a-demo-roundtrip-addendum.md`](../../packages/pptx-renderer/evidence/template-a-demo-roundtrip-addendum.md) §二。
