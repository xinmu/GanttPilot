### P-32 批次 B 的三项欠账与判定区收口

**1. 本批为什么必须先改契约。** P-21 §3 把批次 B 标为"**是（改契约）**"，理由有三条，每一条都不是实现细节：

| # | 契约面 | 现状 | 本批修订 |
|---|---|---|---|
| 1 | **§5 判定区宽度** | `DRAG_EDGE_PX = 6` 写死 ⇒ 条宽 < 12 px 时"整体移动"成**空集**（月档 1 个工作日的条 = **3 px**，`P-22` 遗留 3） | §16.1：`edgePx = min(6, max(0, (条宽 − 6) / 2))`。**宽条与今天逐值相同**，窄条保证 `move` 区非空 |
| 2 | **§7 建线入口** | `Alt+拖动`；Windows 的 Chrome 把它当"移动窗口"系统手势，**事件到不了页面** ⇒ 建线在本平台不可用（R4） | §16.3：入口改为**连接点**（任一侧），出端侧由所抓的连接点决定，`linkTypeFor(exitSide, enterSide)` 给出四类关系 |
| 3 | **§11 元素预算** | `ELEMENT_MODEL_G5.overlay = 12` 只按"拖动期覆盖层"估，措辞是"**每帧**固定开销" | §16.4：`c₄(rows) = 6·rows + 12`（手柄 + 连接点是**每渲染行**的，ADR 0007 §11 第 4 项点名的那一类）；"每帧固定开销"这句作废，**"与文档总规模无关"不变** |

**2. R3 的形态：手柄为什么落在判定区边界上。** R3 是"没有可拖动区域的视觉暗示"。最省事的做法是"在条的两端画两个小方块"，
但那样会立刻产生**第二个真相源**：视觉端点与 `zonesFor` 给出的判定区边界可能不是同一个数（窄条上尤其明显——
月档 1 天的条只有 3 px，两端各画一个 2 px 的方块就把它铺满了，而判定区已经退化成"只在 0 点上有端点区"）。
因此本批把**判定区本身**做成唯一产出函数 `zonesFor(bounds)`，手柄画在 `zones.edgeL.end` / `zones.edgeR.start`：

- 宽条上它看起来就是"条的两端"（`edgePx = 6`，手柄落在两端内 6 px 处）；
- 窄条上它**如实退到同一处**（两个手柄叠在一点），于是"这条现在主要靠整体移动"是**看得见**的；
- 判据因此可以写成"手柄 x == 判定区边界"（同源断言），而不是"手柄看起来在两端"（不可判定）。

**3. R4 的形态：连接点。** 两条候选（P-21 §3 B 原文：端点旁的独立连接点手柄 / 行左侧 gutter 连点拖出），本批选**前者**：

- **落点**：条的两端**外侧**（左：`xLeft − 2 − 8`；右：`xRight + 2`），与端点手柄的最短中心距 **10 px**
  （`CONNECT_GAP_PX + CONNECT_SIZE_PX = 10`），而命中容差 `HIT_TOLERANCE_PX = 2` ⇒ 两者不会互相抢命中；
- **为什么不做 gutter 连点**：gutter 是**行**的概念（左表一侧），而连接点必须能表达"出端在条的哪一侧"
  （它决定 `FS`/`SS`/`FF`/`SF` 里的出边侧）。把连接点挂在 gutter 上会让"出端侧"只能靠几何反推，
  正是 P-22 §13.3 那类"基准取错"缺陷的温床；
- **选中规则**：**近者优先**；容差内并列时 `link-out` 优先。**不做**"更远者胜"——那会让连接点吃掉端点判定区；
- **`Alt` 的处置**：保留为**兼容别名**（旧 `Alt+拖动` 仍产出同一条 `link.insert`，回归判据守住），
  但入口文案、README 与人工验收清单一律指向连接点——`Alt` **不再**是任一平台的承诺入口。

**4. `DRAG_EDGE_PX` 随条宽收缩：判据必须指向"反方向"。** 本条这一处沿用 P-22 的教训（"夹到边界"与"冲突方向"
两次都是**方向**写反，只有反向断言抓得住）：

- **正向**断言：`zonesFor` 在 3 px 条上给出的 `move` 区**非空**（宽 ≥ `MIN_MOVE_ZONE_PX`）；
- **负向对照**：把边界公式换回"固定 `DRAG_EDGE_PX = 6`"⇒ 同一输入上 `move` 区**为空**
  （这就是月档判定区被两端吃掉的字面复现）；
- **同源**断言：日档宽条上 `zonesFor` 与 `DRAG_EDGE_PX = 6` 的旧式逐值一致（保证"宽条行为不变"是可验证的，
  而不是一句承诺）。

**5. 被本批顺手救回的一处记录制假绿（P-23 的同族）。** 批次 B 把图元加进行 `<g>` 之后，`measure.ts` 里两处
"取第一个 `rect`"的选择器会**先命中手柄**：

| # | 位置 | 若不同步改会怎样 |
|---|---|---|
| 1 | `runAlignMeasurement` 的 `group.querySelector('rect')`（取"条形"算两栏对齐） | 量到的是手柄矩形 ⇒ `--align` 的逐行判据整片**假红**（而它是记录制，不会在 `pnpm gate` 里报警） |
| 2 | `collectBarGeometry` 串 `.rows rect, .rows polygon`（判断"条形真的变了"） | 手柄也被串进去 ⇒ `--drag` 的"DOM 变化 N/12 帧"变成**假绿**——与 P-23 修过的那次**假阴性**同族 |

修法：条形与菱形补 `class="bar"` / `class="milestone"`，两处选择器改为 `rect.bar` / `polygon.milestone`。
**这条不新造口径**：P-23 已经把"这类选择器必须能被坏结构照样采到数"写进 §14.4 的判读纪律；
本批只是把"图元增加"这一新增风险一并守住。

**6. 记录制必须重跑（B 的直接代价）。** P-28 已预告："B 会给行加交互热区、重定 `ELEMENT_MODEL_G5.overlay` / `c₄`，
届时**必须**重测并刷新证据（先例：两栏布局改动后由 P-23 同轮刷新 `drag-timing`）"。本批据此重跑四条：

**第二次复验（2026-10-04）与真正的根因。** 报文：① "左右向上突起仍然存在，但与之前形式不同，视觉上和条体不再相连"；
② 连接点按需出现（通过）；③ "方块显示时仍在条体两端的偏上位置，不是条体两端外部居中"；
④ "方块仍然不可交互，不能拉线"。在**真实 `pnpm dev` 页面**上逐值采数后定位到**同一个根因**：

```
t1: 条 <rect y="28.8" h="14.4">    ⇒ 28.8 .. 43.2（条心 36）
    手柄 <line y1="22" y2="26">     ⇒ 22 .. 26（浮在条体上方 4.8 px、不相连）
```

即渲染层把 **`RowBox.y`（＝行顶）当成了条心**——`TaskBounds.y`（条心）与 `RowBox.y`（行顶）**相差 `rowHeight / 2 = 12 px`**。
三者因此被同一条错误解释：手柄悬在条体上方（报文 ①）、连接点整体上移 12 px（报文 ③）、
而命中判定只按 `x`（纯几何、本身正确）⇒ **用户按"看到的位置"点不到**（报文 ④）。
**纯函数与打包产物的采样当时都通过**，正是因为它们不依赖 y。

**处置**：`rowHandlesFor` 新增**显式入参 `barCenterY`**（`row.barY + row.barHeight / 2`）、
`GanttChart.vue` 与 `measure.ts` 都传条心；`interaction.spec.ts` 加"竖向中心同源"判据
（遍历真实 `ViewModel.rows` 断言两种算法相等、`row.y ≠ 条心`、手柄在条内、连接点竖向中心 = 条心）——
**该判据在旧实现下必然变红**。契约面的措辞见 [ADR 0008 §16.7](../02-adr/0008-列身份所有权与拖拽交互契约.md)。

**第三次复验（2026-10-04）与两处新结论。** 报文："显示基本正常了，但仍不可通过拖动连接点来拉线"。
用 **CDP `Input.dispatchMouseEvent`（真实指针、走浏览器命中测试）**复现后：

1. **可见方块 ≠ 可用命中区**：方块 8 px、内缘贴条端 ⇒ 可用宽度 14 px，条端右侧 `dx = −1..+2` **全部落空**
   （按下去既不建线也不拖动）。修法：连接点**跨在条端上**（`CONNECT_INSET_PX = 2`）、尺寸 8 → **12**、
   命中区 = 可见方块 + 外侧 `CONNECT_HIT_PAD_PX = 4`（可用宽度 → 20 px），并加回归断言；
2. **量到的是旧产物**：`packages/render-core/dist` 停在上一轮构建而 dev 服务器一直用它
   ⇒ DOM 里是旧几何。这是 P-25 那条教训（"负向对照之后必须强制重建"）的**正向版本**：
   **`pnpm dev`/人工复核之前必须先 `pnpm build`**。
   另外：拖动/建线期间连接点与手柄**一律不显示**（行画的是"结果几何"），交互图元因此画在条/菱形**之前**。

**本条的两处记录制订正**（否则记录制会静默给假结果）：① `collectHandleSample` 必须在 hover 之后
（`await nextTick()`）**只数指针所在那一行**的连接点；② 采样点的 x 要**从 DOM 属性读**——
端点手柄在判定区边界（与条端相差 `edgePx`）、连接点在条端外侧，用 `row.xRight` 当"手柄处"会采到连接点上。
