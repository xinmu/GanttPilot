### P-44 机制：一条自引用环

```
pane.clientWidth ──measure()──▶ paneWidth ──▶ contentWidth = max(窗格宽, 内容最右缘…)
        ▲                                              │
        │                                              ▼
   纵向滚动条出现/消失 ◀── 需要滚动吗 ◀── spacer 宽/高 = contentWidth / max(行数×行高, paneHeight)
```

- **输入就是输出**：决定"要不要滚动条"的量（`spacer` 尺寸）由 `contentWidth` 决定，
  而 `contentWidth` 又 `max(..., 窗格宽)` 取的是 **`pane.clientWidth`**——它正是"有没有纵向滚动条"的函数；
- `overflow: auto` 下，纵向滚动条一出现就吃掉 **15 px** 宽，于是"横向要不要滚动条"的判定跟着翻，
  横向条又吃掉高度、影响"纵向要不要滚动条"的判定 ⇒ **两轴互激**；
- 这解释了维护者的两条观察：**与横向滚动条有关**（本轮的线索）而**与文案换行无关**
  （上一轮把文案修成单行，环仍然存在）。

### 修法：让窗格客户区**与滚动条无关**（常驻滚动条）

`.chart-pane { overflow: scroll; }`——两个轴永久占用 15 px ⇒ `clientWidth/clientHeight` **不再随内容变化**
⇒ `contentWidth` 的输入恒定 ⇒ 环从构造上消失（不需要动 `contentWidth` 的公式，因此
**ADR 0007 §15.1 与 P-24 的那些判据一字未改**）。

**代价（明确接受）**：**小文档也会看到灰掉的滚动条**；`c₃` 与记录制里的窗格尺寸随之刷新
（ADR 0007 §11 的回填锚值定义在**合成视口 1280×640** 上、由 spec 断言 ⇒ **不受影响**）。

### 判据：窗格客户区必须与"滚动条是否被需要"无关（**确定性可验证**）

`smoke:build` 的「布局稳态」新增：把 **spacer 缩到 10×10**（等价于"内容短到不需要滚动"）再量客户区，
**必须一字不变**。

| 变体 | 实测 | 判定 |
|---|---|---|
| **修后**（`overflow: scroll`） | 内容变化前后客户区一致 | ✅ 通过 |
| **负向对照**（`overflow: auto`，跑完即还原） | **693×672 → 678×672**（纵向滚动条出现，恰好吃掉 15 px） | ❌ 冒烟失败 ⇒ 判据有**确定性**判别力 |

> **落地时踩到的两件事（都值得记）**：
> ① 判据的第一版是"临时把 `overflow` 换成 `hidden` 再量"——那等于**移除**滚动条，客户区当然会变，
> 于是**正确实现也被判红**；负向对照当场把这条错判据抓了出来。修法：改测"**内容缩到不需要滚动**"。
> ② smoke 的 Chrome 一直用默认窗口 ~800×600，而左表列占 ~785 px ⇒ 图表列被挤到 **0 px 宽**，
> 判据在**退化布局**上量数（旧口径也"通过"）。修法：`--window-size=1600,900`。

### 明确不做

1. **不改 `contentWidth` 的公式**（`max(窗格宽, …)` 是 P-24 的口径，它带来"短文档也能横向铺满"的好处；
   改它要动 ADR 0007 §15.1 与 `viewModel.spec` 的"空文档回落窗格宽"判据）；
2. **不加 `scrollbar-gutter: stable`**（对"纵向条是否出现"有效，但对**横向条 ⇒ 高度**这条腿无效，
   而本次的环两轴都走）；
3. **不隐藏滚动条**（`::-webkit-scrollbar { display: none }` 会让"能不能滚"失去视觉线索）。
