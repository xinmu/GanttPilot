### P-31 提示条规则的落点必须在命令通道

**1. 报文（维护者，六步复现）**：

1. 重置演示数据；
2. 拖动任务 4 条体 → 右上「可撤销 有 · 可重做 无」，下方状态栏无提示；
3. `Ctrl+Z` → 「可撤销 无 · 可重做 有」，无提示；
4. 再次 `Ctrl+Z` → 出现「命令被拒绝：`SESSION_NOTHING_TO_UNDO` —— 没有可撤销的步骤」；
5. **再次拖动任务 4 条体** → 「可撤销 有 · 可重做 无」，**提示未消失**（这里应该消失）；
6. 再次 `Ctrl+Z` → 提示消失（撤销这条通道是生效的）。

即：**规则正确（第 3、6 步生效），但第 5 步的拖动提交没有让它生效**。

**2. 根因**：[P-30](裁决记录.md) 的规则**放错了层**——它落在 `App.vue` 的 `applyCommandResult()`，而**拖动/建线的松手提交**由 [`useGesture`](../../apps/web/src/composables/useGesture.ts) 直接调它自己的 `dispatch` / `dispatchLink` 回调（`(command) => project.dispatch(command)`），**从不经过** `applyCommandResult`。于是"成功且真的改了 ⇒ 清掉失败提示"在这条路径上不成立。

同一类疏漏在 P-28 → P-30 已经发生过一次（那次的窄口径只覆盖撤销/重做）。本条的修法因此不是"再补一个调用点"，而是**消除"靠调用点记得调用"这件事本身**。

**3. 裁决**：提示条的**状态与迁移整体移入命令通道**：

- `useProject()` 持有 `notice: Ref<StatusNotice | null>`，并在 **`commit()`** 里调用 `noticeAfterDispatch`
  ——`commit()` 是 `dispatch` / `undo` / `redo` / `ingestDocument` 的**唯一汇合点**，也是既有 `lastFailure` 的更新处；
- `App.vue` 只**渲染** `project.notice`，并以 `setNotice()` 呈报**非命令**消息（导入进度与结果、手势被拒绝、
  重置提示、测量钩子报错）——`apps/web` 的任何命令调用点都**不再自己碰提示条**；
- `reset()` 整份换文档时一并清提示（旧提示讲的是上一份文档上的尝试）。

**4. 判据与负向对照**：规则本体（纯函数）仍在 `pnpm gate`（`render-core/SPEC.md` §九 G5 ⑩，5 例）；
**落点**属应用层，按 P-9 / P-21 的既有分层只能人工 + 记录制：

- **脚本化预验** `tmp/batch-c-verify.mjs`（真实 CDP 输入事件 + 打包产物）**19/19**，其中 **M7a–M7e** 就是维护者的六步：
  拖动 → `Ctrl+Z` → 栈底 `Ctrl+Z`（出提示）→ **再次拖动 ⇒ 提示消失** → `Ctrl+Z` ⇒ 仍为空；
- **负向对照**：把规则**放回 `App.vue`**（＝ P-30 的落点）后重跑 ⇒ **18/19，只有 M7d 变红**，报文与维护者第 5 步
  逐字一致（「可撤销 有 · 可重做 无」＋ `SESSION_NOTHING_TO_UNDO` 未消失）⇒ 该判据对本缺陷**有判别力**（跑完立即还原）。

**5. 与既有裁决/ADR 的关系**：**不取代、不修改**任何 `Dn/Rn/Tn/Pn`；**P-30 的规则一字未改**
（失败才产生提示、成功且 `changed` 即清掉失败提示、无操作照旧），本条只改它的**落点**；`P-29` 仍由 `P-30` 收口；
**不改 ADR 正文**（提示条是应用层呈现，不是契约）；不放宽任何 DoD。

**6. 代价（明确接受）**：

- 提示条成为**会话层状态**（`useProject` 的公共面 +2 个符号）——换来的是"任何一条命令通道都不可能绕过它"；
- `App.vue` 不再碰提示条 ⇒ 将来若要"某条命令不清提示"的特例，必须改 `commit()`（这是**有意**的：特例应当显眼）；
- DOM 层**仍无门禁判据**（`apps/web` 没有判据入口，P-19 遗留 3 / P-21 遗留 4）。
