### P-4 验证环境以 WPS 为准，Microsoft PowerPoint 备查、不阻塞

**裁决内容**

1. **开发过程全部使用 WPS**；
2. **门禁以 WPS 验证为准**——包含人工操作验证与 COM 自动化验证；
3. **Microsoft PowerPoint 作为备查项，不构成开发与合并的阻塞**。

**依据**

- S1 执行期间本机唯一可用的演示文稿软件是 WPS Presentation（注册表中的 `PowerPoint.Application`
  ProgID 实为 WPS 劫持），全部 L1–L4 证据均在该环境取得；
- S1 已实测 **WPS 引擎本身支持连接符跟随**（原生 `AddConnector` + `BeginConnect/EndConnect`
  建立的连线在形状移动后端点保持吸附并重算走线），因此以 WPS 为门禁环境**具备判别力**，
  不是"因为没有别的工具而将就"；
- 单人项目、无 Microsoft Office 授权环境，若坚持"Office 2016+/365 必过"，
  将得到一条**无人能关闭的门禁**——这正是 P-1 要避免的"处处半成品"的镜像错误（门禁永远开着）。

**落地动作**（已完成）

| 条款 | 改动 |
|---|---|
| G1-a 的"真机" | 原指 Microsoft PowerPoint 2016/365 → **WPS Presentation**；S1 的 G1-a 据此判定**通过** |
| [EX-05](需求基线.md) | 「Office 2016+/365/WPS **必过**」→ 「**WPS 必过**；Microsoft PowerPoint **备查**（不承诺）」 |
| G7 兼容矩阵与出口条件 | 同口径收窄；增加一条"备查记录"项，并禁止在未验证前对外承诺 PowerPoint 行为 |
| [README](../../README.md) 已知限制 | 新增「验证环境以 WPS 为准；Microsoft PowerPoint 未经验证，不承诺其下拖动跟随行为」 |

**代价（明确接受）**

- 产品**不对外承诺** Microsoft PowerPoint 下的拖动跟随行为；
- 输出仍为**标准 OOXML 原生形状**（`p:cxnSp` + `a:stCxn/endCxn`、`p:grpSp` + 显式 `chOff/chExt`），
  **未使用任何 WPS 私有扩展**——因此"在 PowerPoint 下大概率可用"是合理预期，但**未经验证**，
  故只写"备查"、不写"保证"。这是**承诺收窄，而非技术降级**；
- 反向风险：WPS 的 COM 自报 `Name="Microsoft PowerPoint"`、`Version="12.0"`。
  **该伪装字符串不构成"已用 PowerPoint 验证"的证据**，任何相关判断须先确认进程为 WPS 还是 `POWERPNT.EXE`。

**与既有裁决的关系**：**仅澄清，不取代**任何 Dn/Rn/Tn/Pn 条目。
S1 结果**未触发** [首版能力顺序](../01-roadmap/首版能力顺序.md) §四的产品叙事降级规则——
"拖动跟随"保留，"折线降级"仍只是 connector 异常时的技术预案。

**升级路径（不阻塞，留作后手）**：若收到"PowerPoint 下不跟随"的用户反馈，或战略上需要，
按 [备查清单](../../spikes/g0-s1-pptx-connector/evidence/powerpoint/README.md) 执行**一次**验证即可
把 PowerPoint 提升为门禁；届时同步改写 EX-05、G7 与 README，并追加新裁决。

**第四轮遗留待定**：无新增。第二轮的五项待定项仍然有效（见上）。

### P-5 xlsx 往返：WPS 为一等验证环境；导入容差为硬性要求

**裁决内容**

1. **xlsx 往回的验证环境与 P-4 同口径**：**以 WPS 表格为准**——「打开 → **仅保存**」与
   「打开 → **编辑** → 保存」两种往返均为一等判据；
2. **Microsoft Excel 与 Google Sheets 为备查 / 未验证**：不构成开发与合并的阻塞，
   **不对外承诺**其往返行为；**Google Sheets 本轮明确不做**（本机无可用自动化通道）；
3. **导入侧容差为硬性要求**（S2 实测驱动，属 G3 的实现约束，详见 S2 结论 §八）：
   - 日期必须同时接受 **真日期 / 数值序列号 / ISO 文本**；**导出必须用 `Date.UTC` 构造**
     （本地零点构造会写出带小数的序列号，Excel 显示**前一天**）；
   - 进度同时接受分数与百分数点位（**≤ 1 视为分数，> 1 视为百分数**）；
   - 里程碑同时接受 布尔 / `是`·`否` / `TRUE`·`FALSE` / `1`·`0`；
   - **不得**依赖数字格式码的文本、`alignment.indent` 的取值、部件哈希与样式体积
     （WPS 会重写整个容器，并把 `yyyy-mm-dd` 转义为 `yyyy\-mm\-dd`）。

**依据**

- S2 的三层证据全部通过：L1 自往返（含两条独立读取路径逐格一致、逐字节确定性）、
  L2 WPS「仅保存」、L2b WPS「编辑后保存」；且 5 条**字节级负向对照**证明判据有判别力；
- WPS 只在「格式码转义」与「容器重写」上留下差异（11 个部件重写/新增，
  `styles.xml` 2176→20577 字节、新增 `docProps/custom.xml`），**未触碰任何单元格的值与类型**——
  说明 T-2 的核心前提「**可见列自足**」在真实第三方往返下成立；
- 本机无 Microsoft Excel（`Excel.Application` 被 WPS 劫持并自报 `Name="Microsoft Excel"`、
  `Version="12.0"`），与 P-4 记录的环境事实同源。

|---|---|
| [《证伪实验计划》§Spike-2](证伪实验计划.md) | 插入「执行状态」：重定义 G2-a/G2-b/G2-c、新增 G2-d（备查）、记录三处实测更正 |
| [《首版能力顺序》G0-S](../01-roadmap/首版能力顺序.md) | S2 标记为**已完成**（附结论链接）；门禁判定 G2-a/b/c 通过、G2-d 备查 |
| [《首版能力顺序》G3](../01-roadmap/首版能力顺序.md) | 新增指引：G3 的实现约束以 S2 结论 §八「G3 交接清单」为准 |

| [README](../../README.md) 已知限制 | 新增「xlsx 往返以 WPS 为准；Microsoft Excel 与 Google Sheets 未验证、不承诺」 |

**代价（明确接受）**

- 产品**不对外承诺** Microsoft Excel 与 Google Sheets 下的往返行为——这是**承诺收窄，而非技术降级**；
- S2 的 fixture 与判定集只覆盖**规范工作簿**：脏文件（合并表头、多行表头、缺列、公式型日期）、
  列映射向导、缩进式解析、CSV、规模上限仍由 **G3 的出口条件**承担；
- 「WPS 打开无修复弹窗」在 S2 中只取得**脚本口径**结论（打开无异常、`DisplayAlerts=false` 下不阻塞、
  保存后产物可被两条独立读取路径完整解析）；**未做界面层人工观察**，如需按 S2 的 README 复跑目视一次。

**与既有裁决的关系**：**仅细化，不取代**任何 Dn/Rn/Tn/Pn 条目；
S2 结果**未触发**《首版能力顺序》§四的任何产品叙事降级规则。

### P-6 CPM 性能：DoD 收紧到 1 ms 级；EN-04 的改写理由改为"避免整表 DOM 重建"

**裁决内容**

1. **判定口径**：三条门禁按协议判定，G3-a/G3-b/G3-c 必须有明确结论；判定值取 **median-of-suites 的 p99**，
   主口径 **Node 24.15.0**（与 CONTRIBUTING / CI 一致），Node 26.7.0 作记录。结果为
   **G3-a 通过、G3-b 通过、G3-c 已量化**。
2. **G2 的 DoD 收紧**：1,000 任务 / 1,500 依赖的**全量重算 p99 ≤ 1 ms**；
   原文 EN-08 的 **100 ms 保留为产品侧"不回归天花板"**。依据：实测最差 p99 = **52.1 µs**（约 19× 余量）。
3. **EN-04 的改写理由变更**（**语义不变**：拖拽期只做受影响子图的日期传播、松手后合并重算）：
   理由从"引擎算不动（浮动全局耦合引发 O(V) 位移）"改为"**避免整表 DOM 重建**"。
   新增口径：**引擎侧 ≤1 ms/帧**；**10 ms/帧保留为"含渲染的整帧总预算"**；松手后合并重算仍为 ≤200 ms。
4. **新增"增删依赖边"条目**：CSR 重建 + 重算 **p99 ≤ 1 ms** @1,000/1,500（实测最差 180 µs）。
5. **测量环境边界（必须与数字一起引用）**：S3 **只测 Node 侧内核**；
   浏览器/绘制侧的整帧预算**未测**，因此 **"拖拽 ≥30fps"（G5 门禁）未被 S3 验证**，G5 必须用真实浏览器复测。
6. **不改变任何产品承诺**：本裁决**未触发**《首版能力顺序》§四的任何叙事降级规则；亦不对外承诺浏览器侧帧率。

**依据（摘要）**

- 全量重算 p99：**27.8 / 49.1 / 52.1 µs**（宽而浅 / 深链 / 密集交叉，1,000 任务 + 1,500 依赖）；
  松手后合并重算（含逆向/浮动/关键路径）最差 **60.3 µs**；非关键编辑的闭包传播 **0.55–0.60 µs**；
  关键编辑的闭包传播最差 **27.1 µs**（深链，闭包 940/1,000）；
- **观测点（非门禁）**：2,000/3,000 全量重算 p99 = **129.8 µs**；5,000/7,500 p99 = **345.1 µs**；
- **正确性**：10 个手工推导用例（76 条判定）全过；1,000 张随机图不变量零违规；
  两套日历实现互证一致；**1,000 个随机图 + 200 个成环图与独立 Python 参照实现逐字段 0 不一致**（R-4 方案 ④ 落地）；
- **判别力对照**：NC1 2,360×（阈值 3×）、NC2 820×（10×）、NC3 2.8×（1.5×）——
  未达阈值即判"测量无力"，避免把恒真式当结论；
- 三条**在 S3 过程中新发现的语义事实**（必须带进 G2 / v0.5）：
  ① **混合关系图上"关键集合"可能为空**（44/1,000 张随机图）：含 SS/FF/SF 时"完成最晚的任务"不一定是任何终端的祖先，
  于是所有任务的总浮动都 > 0，`totalFloat === 0` 判据只对**纯 FS 图**成立；
  ② **深链上"受影响子图"可达 940/1,000**，增量与全量同阶（13.7 µs vs 22.8 µs）——
  增量优化的收益来自"不重复做分析层、不重建 DOM"，不是传播本身；
  ③ 主干 `packages/engine/src/date.ts` 的 `countWorkdays` 是**逐日循环且无 `exceptions`**，
  同一工作负载下比索引前缀和慢约 **340×**，需在 G1/G2 重写（S3 已给出参考实现）。

**代价（明确接受）**

- **"拖拽 ≥30fps" 仍然没有证据**：本裁决不把它变成"已通过"，G5 必须在真实浏览器复测整帧预算；

  **median-of-suites**，不是分布尾部极值（报告同时保留最差 suite 的 p99）；
- 未覆盖：Worker 化、动态拓扑序维护的工程实现、约束类型（G-3/G-4）、多日历、2,000 任务的正式压测（v0.5）；
- 参照实现是"另一种写法"而非"标准答案"：它把两侧同时犯同一语义错误的概率压得很低，但不为零，
  故 G2 仍须保留不变量测试与手工用例。
