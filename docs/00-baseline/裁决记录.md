## 一、裁决评估（4 项）

### R-1 lag 按工作日、归属项目日历 —— ✅ 成立，且是**降复杂度**的选择

- 与 D-4（MS Project 惯例、工作日、默认周一至周五 8h）自洽；
- "归属项目"避免了最麻烦的一类问题：当不同任务挂不同日历时，lag 到底按谁的日历推进。统一归属项目日历后，**排程内核只需一个日历状态机**，`compute()` 的签名可以保持简洁；
- 代价：与 MS Project 在"任务独立日历"场景下的结果会不同。但 R-4 已决定不以 MSP 为准，因此**代价为零**。
- **落地要求**：`calendars[]` 数组仍可保留（为未来多日历留位），但 v0.1 语义上只有**项目日历生效**，其余日历字段不参与计算。应在 schema 与文档里写明"字段保留、语义未启用"，避免后来者误用。

### R-2 回退栈替代多快照 —— ⚠️ **成立，但请允许我修正提问中的前提**

**直接回答"是否减少存储需求"：是，而且减少得很多——但存储不是真正的瓶颈。**

存储量级估算（2,000 任务项目）：
| 方案 | 单份体积 | 说明 |
|---|---|---|
| 全量快照 | 约 **300–600 KB** | 2,000 任务 × 约 150–200 B + links + 元数据 |
| 单条命令 delta | 约 **0.1–2 KB** | 只含变更任务/边的 before-after |

即：**回退栈把"每次保存一整份文档"变成"每次操作一小段 diff"**，量级差 2–3 个数量级（100 步 ≈ 100 KB vs 20 份快照 ≈ 8 MB）。**结论：是，显著减少。**

但要注意两个真实问题：

1. **瓶颈是写入延迟与主线程占用，不是容量。** IndexedDB 在常见浏览器下可用空间通常是磁盘剩余的一大比例（GB 级），几百 KB 的快照根本压不垮它。真正的成本是"每 ≤5s 把 400 KB 序列化一次"带来的主线程卡顿——这在拖拽时是可见的掉帧。回退栈天然解决了这一点（写入小、可用空闲回调批量合并）。
2. **纯 LIFO 回退栈无法满足"跨会话的按时间点恢复"。** 栈能回答"撤销上一步/上 N 步"，不能回答"恢复到我昨天早上那版"。原文 US-5 的验收是"回到 10 分钟前的版本"——**在会话内，栈完全能覆盖**；跨会话就断了。

**建议的分层（比任一单独方案都省，且覆盖更全）**：
```
L1 命令回退栈（会话内）       每次编辑一条 delta，内存中，O(变更量)   ← 主打，撤销/重做的唯一真相源
L2 检查点快照（低频）         例如"每 5 分钟 或 每 200 条命令 或 关闭文档时"一份，保留 2–3 份  ← 覆盖跨会话/崩溃恢复
L3 当前文档自动保存           ≤5s，写"最新状态"，不做历史
```
- **只需保留 2–3 份检查点**，而不是"多快照"。存储需求相比原方案下降约一个数量级，同时**保留 US-5**。
- 需要注意的实现点：命令必须携带**逆操作**（或 before/after 镜像）。CPM 级联变更的逆操作在语义上不直观，但**不需要手写——记录受影响任务的 before 镜像即可确定性回滚**。这正好与 IX-03"一次手势 = 一个 Command"契合。
- **建议同步改写 PS-02 与 US-5 的措辞**：从"快照/时间点恢复"改为"命令级撤销/重做 + 低频检查点恢复（会话内逐步撤销；跨会话恢复至最近检查点）"。避免验收标准与实现不符。

### R-3 G-3/G-4 采用建议方案、实现时细化 —— ✅ 成立

建议方案已记录在《评估报告》§3.2：
- **G-3**：约束不阻断排程，改为产生**负浮动 + 冲突标记**；硬约束（Must Start On）与依赖矛盾时标红提示；
- **G-4**：手动任务日期不被引擎改写，但**仍作为前置向前传播**；手动任务不参与关键路径计算。

这两个默认值的价值在于它们**不改变架构**——都只是 `compute()` 内部的分支，字段已在 schema 里。因此"实现时细化"是低风险的。**唯一要求**：细化时要一同定义"冲突标记"在 UI 与导出中的表现（否则导出会静默丢失冲突信息）。

### R-4 不与 MSP 文件格式直接关联、依托 Excel 维护自有 schema —— ✅ 架构上成立，但**触发两处必须同步处理的连锁影响**

**成立的理由**（我支持）：自有 schema + Excel 作为交换面，比"双格式一等公民"简单得多；MSP 的 XER/MPP/XML 是另一个复杂度来源，与"单人项目"严重不成比例。

**连锁影响 A：与原文条款冲突，需明确改动**
| 原文条款 | 影响 |
|---|---|
| P1-06「MS Project XML 导入」 | 与 R-4 直接冲突 → 建议**删除或降为 P2/社区插件** |
| §4.2「与 MS Project XML 计算结果黄金比对一致」 | **该 DoD 作废**，必须替换验证策略（见下） |
| §5 风险登记「以 MS Project XML 导入对冲 .mpp」 | 对冲手段失效 → 非目标 NG-04（不读 .mpp）应升级为**"永不做 .mpp，且不承诺 MSP 互操作"**，明写在 README 以避免 issue 泛滥 |
| §13 开放问题 | 如保留 XML 导入，需重新评估 |

**连锁影响 B（更关键）：EN-01/EN-07 失去权威参照，必须重建验证策略**

这是 R-4 最容易被低估的代价。原文把"与 MS Project 黄金比对"作为排程正确性的**唯一验证手段**，现在它没了，而排程引擎恰是"正确性关键、AI 加速低"的模块。替代方案建议按成本排序：

| 方案 | 说明 | 成本 | 建议 |
|---|---|---|---|
| **① 不变量/性质测试（property-based）** | 不比对具体数值，而断言 CPM 的数学性质：EF = ES + duration；LS ≥ ES；总浮动 ≥ 自由浮动 ≥ 0（无约束时）；链式 lag 的传递性；关键路径上浮动为 0；4 种关系类型的边界方程 | 低 | **必做**（性价比最高） |
| **② 手工推导用例** | 小规模（5–20 任务）覆盖 4 关系 × 正/负/0 lag × 跨层级 × 日历例外，期望值由人工独立推导并**双人/双次推导**交叉确认 | 中 | **必做**（覆盖语义，不覆盖规模） |
| **③ 公开 CPM 测试集** | 查证是否存在可用的公开 CPM/PERT 测试向量与许可 | 低（调研） | 值得花半天调研 |
| **④ 独立参照实现交叉验证** | 用另一种语言/写法（如 Python 小脚本，仅数十行）实现同一算法，对随机生成的 1,000 个项目图做**差分测试**。**两套互相独立的实现同时出错的概率极低** | 中 | **强烈推荐**，这是 MSP 参照被移除后最接近"黄金比对"强度的替代 |
| **⑤ 用 MSP 做一次性旁证（不入库）** | 若你手边有 MSP，可人工比对若干组结果作为一次性 sanity check，但不入仓库（避免许可问题）、不作为 CI 门禁 | 低 | 可选 |

**关键判断**：④（差分测试）是这次裁决后**最值得投入的测试基建**。它把"信任一个外部工具"换成"信任两套独立实现的收敛"，在许可上干净、可入 CI、可自动化扩容到压测规模。建议把"排程内核 + 独立参照实现 + 差分测试"列为 M0 的明确交付物。

## 二、权衡评估（4 项）

### T-1 选 Vue —— ✅ 成立，与文档"可替换性"声明一致，且对拖拽场景确实更优

- 原文 §7.3 已明示前端"可换 Vue/Svelte，仅影响渲染层与交互层"——**这是文档自身预留的合法选择，不构成偏离**；
- 对本项目最关键的收益是**拖拽期间的细粒度更新**：一次拖拽每帧只改少数任务的日期/进度，Vue 的响应式可以做到"只 patch 变化行的 `x`/`width` 属性"，而不触发整表重渲染。这与 IX-01（≥30fps）直接相关；
- 纯 SVG 路线（见 T-4）与 Vue 配合良好：SVG 属性可由响应式数据直接绑定，无需手写 diff。

**落地注意点（不算反对意见，只是避免踩坑）**：
1. **不要对大型任务数组做深层响应式**。2,000 任务 × 每任务多字段的 deep reactive 会产生可观的代理开销。建议用 `shallowRef`/`markRaw` 承载任务集合，**只对"当前可见窗口 + 受影响子图"做响应式**，或使用 `shallowReactive` 行对象 + 显式触发。
2. 引擎与 schema 保持**零框架依赖**（原文铁律保留）：`@ganttpilot/engine`、`xlsx-protocol`、`pptx-renderer` 三包不得 import Vue。
3. 虚拟滚动选用 Vue 生态成熟方案（如 `@tanstack/vue-virtual` / `vue-virtual-scroller`），但注意 T-4 的裁剪要求优先于"用哪个库"。
4. 拖拽库（如 `vue-draggable`/自研手势状态机）——建议**自研手势状态机**，因为三语义拖拽（改开始/改工期/整体移动）与吸附、撤销事务合并耦合太深，通用拖拽库反而增加约束。

### T-2 放弃 xlsx 影子表"无损更新"，保存时接受 schema 规范下的重排 —— ✅ **强烈支持，这是本轮最有价值的一项权衡**

- 它精确消除了我在第一轮指出的设计缺陷（影子 ID 与可见行错位、需要行键对账）；
- 语义变得干净：**导入 = 一次性摄取；此后文档主权归应用；导出 = 输出规范化的当前状态**。失败面从"多路第三方编辑器往返"收敛为"一条导入路径"；
- 连带好处：`__gantt_meta__` 整套机制（隐藏态 bug、Google Sheets 剥离 veryHidden、WPS/Numbers 不可验证）**全部不再需要**，测试矩阵大幅缩小；
- 与 R-4 自洽：自有 schema 是唯一真相源，Excel 只是交换格式。

**必须一并写清的三条契约（否则用户会认为"丢数据"是 bug）**：
1. **可见列必须自足**：任务身份、层级、依赖、工期/日期、进度、里程碑全部可在可见列表达——**继承依赖即可，不再有隐藏元数据**。这也让"用户用 Excel 手工维护"成为合法用法。
2. **导出重排的规则要文档化**：按 WBS 顺序、规范化列序、日期格式、依赖列语法。用户改动的列顺序/颜色/公式**不会被保留**，需在导出前或 README 说明。
3. **导入时要给"重排/丢弃"报告**：哪些列未被识别、哪些行缺日期、哪些依赖语法解析失败、哪些边因成环被丢弃。这是 G-8 的具体落地方式。

**建议同步改写**：XL-04（影子表）→ **删除**；XL-05（round-trip 100% 无损）→ 改为"**导入后的文档由应用拥有；导出为规范化输出，不承诺保留用户原有格式**"；CSV 那条（XL-07）保持"尽力导入"。

### T-3 优先走通 xlsx 导入导出 → 编辑体验 → Web 渲染 → SVG/PPTX 导出；排程/CPM 延后 —— ⚠️ **需要修正**

**这一项我评估为高风险，理由如下（请重点看）**

**A. 排程内核是几何来源，不是"高级功能"。** 甘特条的位置 = 由 `startDate + duration` 推得的日期区间映射到时间轴。**条形几何、依赖连线端点、SVG 导出、PPTX 形状坐标，全部依赖排程结果。** 若排程完全延后，则：
- 甘特图只能画"手填日期"，拖拽后下游不动 —— US-2（"某任务延期 3 天，立即看到下游被推迟"）**做不出来**；
- 依赖连线只能画成静态装饰，无传播语义；
- PPTX 模板 A 要求的"自动摘要：完成率/**关键节点表**"中，关键节点部分无所依附。

**B. 首版卖点会被掏空。** 首次使用旅程是"拖入 xlsx → 3 秒出图 → **拖拽感受下游跟着动** → 导出 PPT"。去掉传播后，第三步变成"拖拽只能动一根条"。而"下游跟着动"正是相对 Excel 的唯一不可替代体验——**Excel 本来就能手填日期**，如果没有传播，产品相对"Excel + 截图"的增量就只剩导出格式。

**C. 架构缝会错位。** `compute(tasks, links, calendars, constraints) → Schedule` 是渲染投影与导出投影的共同输入（原文铁律 #2 双投影）。若第一版没有 `Schedule`，则 RenderProjection/ExportProjection 会先按"手填日期"成型，日后接入引擎需要**同时改动投影层 + 三个导出器 + 模板规格**——这正是返工。

**D. 好消息：你其实不需要为此做取舍。** 排程能力可以沿一条清晰的分割线切开，两侧的成本与价值差异极大：

| 层 | 内容 | 成本 | 是否支撑卖点 | 建议 |
|---|---|---|---|---|
| **传播内核** | 工作日的日期算术 + 4 类关系 + lag + 正向传播 + 检环 | **低**（且 Spike-3 本来就要写） | ✅ 支撑"下游跟着动" | **前置到首版** |
| **分析层** | 逆向遍历（LS/LF）、总浮动/自由浮动、关键路径高亮、增量优化 | 中高（浮动全局耦合，即第一轮 §5.3 的风险点） | ❌ 首版可无 | **延后**（与你的意图一致） |

**建议的修正表述**：
> 优先走通 xlsx 导入导出、编辑体验、Web 渲染、SVG/PPTX 导出，**并包含最小排程内核（正向日期传播：4 类关系 + lag + 检环）**；**CPM 分析层（总浮动/自由浮动/关键路径/增量优化）延后**。

这样：US-2 的核心体验（下游跟随、冲突提示、拖拽吸附）保留 → 首版有卖点；`Schedule` 从一开始就是投影与导出的输入 → 架构不返工；而真正昂贵且全局耦合的浮动/关键路径仍然延后 → 尊重你"降低首版难度"的意图。

**E. 需要同步改写的地方**：`EN-01/EN-02`（浮动、关键路径）从 v0.1 移到 v0.5；`US-1` 的"带关键路径的甘特图"改为"带依赖连线的甘特图"；`EN-03` 关键路径高亮移入延后项；PPTX 模板 A 的"关键节点表"降级为"里程碑清单"。**Spike-3 的定位也要调整**：它不再是"首版功能验证"，而是"为分析层的 DoD 定标"。

### T-4 放弃 Canvas+SVG 混合，改纯 SVG —— ✅ **成立，而且比原文方案更好**（前提是裁剪必须做足）

**支持理由（含原文没写到的关键收益）**：
1. **与"所见 = 所导出"铁律天然一致**。原文要求导出不靠截屏，而 SVG 本身就是几何的规范化载体。纯 SVG 下渲染与导出**共享同一套几何与正交路由**，甚至可直接复用同一段路径生成代码；
2. 若 PPTX connector 的降级预案（折线）启用，其端点与走线可直接取自 SVG 的 path —— **降级后的视觉差异最小**，这是混合方案给不了的；
3. 消掉了我第一轮指出的整类同步陷阱：两层坐标基准不一致、`scrollTop` 与固定表头高度差、overlay 的 `pointer-events`、DPR/缩放的两套处理——**纯 SVG 全部不存在**；
4. 调试与可测试性显著提升：SVG 可被断言（结构、属性、快照测试），Canvas 不行。对一个"正确性靠测试护栏"的项目，这是实质收益。

**必须接受并设计进去的前提（否则纯 SVG 会在规模上崩）**：
- 已知实测：2,200 条 SVG 依赖边在**行已虚拟化**的情况下，10× 滚轮滚动仍需约 2.0s。因此**裁剪是第一性要求，不是优化项**：
  - **行窗口裁剪**：只渲染可见行 + 少量缓冲行；
  - **边窗口裁剪：必须用"边所跨行区间 ∩ 可见行窗口"求交**，仅按"两端点是否可见"裁剪会错误隐藏跨屏长箭头；
  - **裁剪先于几何计算**（先筛边，再算 path），且拖拽期不做逐帧 DOM 重建。
- 关键洞察：**在裁剪正确的前提下，SVG 元素数与项目总规模无关，只与窗口大小有关**。这正是纯 SVG 能成立的原因——代价是"必须做对裁剪"。
- 其他工程细节：线条用 `shape-rendering: crispEdges` 避免 1px 抗锯齿模糊；缩放用 `vector-effect="non-scaling-stroke"` 保持线宽；选中态/交互热区可单独用透明 `<path>` 承担；文本标签在缩放时的可读性与可选中性需专门处理。
- **虚拟化代价仍在**：破坏浏览器查找页内文本，需 `aria-rowcount/rowindex`，且要求**固定行高**（若有可折叠的 WBS 层级，需保证展开/收起不破坏行高假设）。
- 建议把"裁剪策略"写成明确的架构决策记录（ADR），因为它是纯 SVG 路线唯一的失败模式。

### P-6 CPM 性能：DoD 收紧到 1 ms 级；EN-04 的改写理由改为"避免整表 DOM 重建"

**裁决内容**

1. **判定口径**：三条门禁按协议判定，G3-a/G3-b/G3-c 必须有明确结论；判定值取 **median-of-suites 的 p99**，
   主口径 **Node 24.15.0**（与 CONTRIBUTING / CI 一致），Node 26.7.0 作记录。结果为
   **G3-a 通过、G3-b 通过、G3-c 已量化**。
2. **G2 的 DoD 收紧**：1,000 任务 / 1,500 依赖的**全量重算 p99 ≤ 1 ms**；
   原文 EN-08 的 **100 ms 保留为产品侧"不回归天花板"**。依据：实测最差 p99 = **52.1 µs**（约 19× 余量）。
3. **EN-04 的改写理由变更**（**语义不变**：拖拽期只做受影响子图的日期传播、松手后合并重算）：
   理由从"引擎算不动（浮动全局耦合引发 O(V) 位移）"改为"**避免整表 DOM 重建**"。
   新增口径：**引擎侧 ≤1 ms/帧**；**10 ms/帧保留为"含渲染的整帧总预算"**；松手后合并重算仍为 ≤200 ms。
4. **新增"增删依赖边"条目**：CSR 重建 + 重算 **p99 ≤ 1 ms** @1,000/1,500（实测最差 180 µs）。
5. **测量环境边界（必须与数字一起引用）**：S3 **只测 Node 侧内核**；
   浏览器/绘制侧的整帧预算**未测**，因此 **"拖拽 ≥30fps"（G5 门禁）未被 S3 验证**，G5 必须用真实浏览器复测。
6. **不改变任何产品承诺**：本裁决**未触发**《首版能力顺序》§四的任何叙事降级规则；亦不对外承诺浏览器侧帧率。

**依据（摘要）**

- 全量重算 p99：**27.8 / 49.1 / 52.1 µs**（宽而浅 / 深链 / 密集交叉，1,000 任务 + 1,500 依赖）；
  松手后合并重算（含逆向/浮动/关键路径）最差 **60.3 µs**；非关键编辑的闭包传播 **0.55–0.60 µs**；
  关键编辑的闭包传播最差 **27.1 µs**（深链，闭包 940/1,000）；
- **观测点（非门禁）**：2,000/3,000 全量重算 p99 = **129.8 µs**；5,000/7,500 p99 = **345.1 µs**；
- **正确性**：10 个手工推导用例（76 条判定）全过；1,000 张随机图不变量零违规；
  两套日历实现互证一致；**1,000 个随机图 + 200 个成环图与独立 Python 参照实现逐字段 0 不一致**（R-4 方案 ④ 落地）；
- **判别力对照**：NC1 2,360×（阈值 3×）、NC2 820×（10×）、NC3 2.8×（1.5×）——
  未达阈值即判"测量无力"，避免把恒真式当结论；
- 三条**在 S3 过程中新发现的语义事实**（必须带进 G2 / v0.5）：
  ① **混合关系图上"关键集合"可能为空**（44/1,000 张随机图）：含 SS/FF/SF 时"完成最晚的任务"不一定是任何终端的祖先，
  于是所有任务的总浮动都 > 0，`totalFloat === 0` 判据只对**纯 FS 图**成立；
  ② **深链上"受影响子图"可达 940/1,000**，增量与全量同阶（13.7 µs vs 22.8 µs）——
  增量优化的收益来自"不重复做分析层、不重建 DOM"，不是传播本身；
  ③ 主干 `packages/engine/src/date.ts` 的 `countWorkdays` 是**逐日循环且无 `exceptions`**，
  同一工作负载下比索引前缀和慢约 **340×**，需在 G1/G2 重写（S3 已给出参考实现）。

**落地影响**

### P-9 不引入 OnlyOffice；LibreOffice headless 作为结构与渲染哨兵（**哨兵 ≠ 门禁**）

**裁决内容**

1. **不引入 OnlyOffice Document Server**，也不为其立 spike。理由：代价与风险不成比例（§2），
   且它在两项关键能力上是**负面**的（§3 的透传陷阱、§4 的写出器丢吸附）。
2. **代价（实测，供未来复议时直接引用）**：镜像压缩层 1.30 GB / 落盘 **3.32 GB** /
   闲置 737 MiB–1.35 GiB / 拉取 **500 s**（经镜像源；`registry-1.docker.io` 直连 15 s 超时）/
   首启动 3–6 s / 单次转换 1.1 s / 许可 **AGPLv3 + Section 7 附加条款**；
   且 `/cool/convert-to/<fmt>` 属 **WOPI 路由、默认关闭**（`WOPI_ENABLED=false` → 全部 404），
   必须显式开开关才可用。
3. **透传陷阱（本次最重要的记录）**：OnlyOffice 的**同格式**转换（`pptx→pptx`、`xlsx→xlsx`）是
   **逐字节透传**——`ppt/slides/slide1.xml`、`xl/worksheets/sheet1.xml`、`xl/styles.xml`、
   `xl/sharedStrings.xml` 的 sha256 与输入**完全相同**，它只重打包容器（39→20 / 16→10 条目）。
   因此「往返后 `stCxn/endCxn` 仍存活」这类判据在 OO 上是**假阳性、零信息量**。
   → **通则：任何"用转换器验证补丁结构存活"的方案，必须先证明该转换器真的重写了载荷部件**
   （比对部件 sha256），否则判据无效。
4. **写出器保真**：把 OO 逼到必须重写的异种格式（`pptx→odp`）后，其 connector **丢失**
   `draw:start-shape` / `draw:end-shape` 与 glue point（退化为只剩绝对坐标的装饰线）；
   同一路径下 LibreOffice **完整保留**。
5. **哨兵分工（不改 P-4）**：

   | 角色 | 选谁 | 依据 |
   |---|---|---|
   | **门禁（唯一）** | **WPS**（不变） | "拖动后端点跟随"（G1-a）只有**交互式编辑器**能验；转换/渲染工具结构上不可能 |
   | **结构哨兵** | **LibreOffice `→pptx`** | 真重写容器（sha 变、id 重编号）而 `stCxn/endCxn` + `idx` 存活 → 证明补丁产物经**真实第三方写出器**后结构不坏 |
   | **渲染哨兵** | **LibreOffice `→pdf`** | 吸附语义**与肘形走向**都与 WPS 同向；OnlyOffice 在肘形上离群（与 P-8 一致） |
   | OnlyOffice | **不采用** | §2–§4 |

6. **哨兵 ≠ 门禁（必须写进 G7 措辞）**：哨兵只能证明"**结构未坏**"与"**渲染同向**"，
   **不能**替代 G1-a 的真机拖动判据；G7 的门禁仍以 **WPS** 为准。

**依据（实测摘要；**同尺量化，禁止目视**）**

- 同一份 `A-absorption.pptx`（`slide1.xml` sha256 `d302859f…`，逐字节**同一输入**）三方渲染，
  按连线像素**包围盒**换算（页宽 720 pt）：
  **WPS 真机** x 160.2..519.8 / y 105.8..239.8；**LO** x 159.7..519.7 / y 106.0..239.6；
  **OO** x 160.4..519.1 / y 105.4..239.6
  → **吸附语义三方一致**（`bar-a` 下边中点 → `bar-b` 上边中点，误差 <1 px）；
- **肘形走向**：WPS 与 LO = 下→右→下；**OO = 右→下→右（离群）**；
- **负向对照**（删除 connector 整段）：LO **0.192%**、OO **0.222%** 像素差异 → 哨兵对"缺失"有判别力；
  LO 与 OO 互差 **0.503%**（来源为肘形，**非**吸附差异）；
- **成本对照**：LibreOffice 四类转换（`pptx→pdf/pptx`、`xlsx→xlsx/csv`）各 **1–3 s**、离线、无守护进程
  （本开发机已内置）。

**归属与前提（重要，防止误用）**

- LibreOffice 在**本开发机**是 **DSH harness 内置**（`@deepseek-ai/libreoffice-kit-win32-x64`），
  **不是 GanttPilot 的依赖**：不在 `package.json`、不在 pnpm workspace、不在
  `THIRD_PARTY_NOTICES` / `license:check` 范围。因此 §5 的成本口径是**本机口径**——
  **CI 与贡献者机器需自行提供**（届时属**环境依赖**，不是仓库依赖），接入远端仓库时再定落地方式。

**复现步骤（最小形式，记录以免重复探索）**

1. 取镜像 `onlyoffice/documentserver`（docker.io 直连超时，可经镜像源）；
2. 起容器——**关键：必须开 WOPI**：`-e JWT_ENABLED=false -e WOPI_ENABLED=true -p 8088:80`，
   并以 `-v` 把宿主工作目录挂进容器（`wslc` 下用 `-v '<Win路径>:/work'`）；
3. 转换：容器内 `curl -F 'data=@/work/in/x.pptx' http://127.0.0.1/cool/convert-to/<fmt> -o /work/out/…`；
4. **判定①结构**：解包比对**载荷部件的 sha256**（先证"是否真重写"）+ `stCxn/endCxn` 计数 +
   锚点 `id` → 形状名解析；
5. **判定②渲染**：渲染成图后**取连线像素包围盒**与 fixture 已知几何换算比对。

> **方法论教训（本次踩过，务必保留）**：吸附/走线类判断**必须量化，不得目视**。
> 本次初稿即因目视把"沿形状下边水平走线的一段"误读为"从右缘出"，得出**方向相反**的结论，
> 经与 S1 既有像素量化基准同尺重测后才更正。另：跨栅格化器的像素数不可直接互比，
> 只有**包围盒/拓扑**级比较才跨渲染器有效。

**证据可得性（诚实声明）**：本次证据来自**临时探针**，工件位于 gitignore 的 `tmp/`、**未入库**
（探针镜像已按要求删除）；故本裁决以「**内联数字 + 上述复现步骤**」承载，**不依赖临时文件存活**。

**与既有裁决的关系**：**不取代、不修改** P-4（WPS 仍为唯一门禁）与 P-6；与 **P-8** 第 3 条
（"OnlyOffice 不得用作走线基准"）一致并互为支撑。

**第九轮遗留待定**

1. **接入远端仓库时确定 CI 侧 LibreOffice 哨兵的落地方式**（安装来源 / runner 预装 / 镜像）；
   在此之前哨兵只在**本地或手动**运行，不进常驻 CI；
2. **LO 重写后产物的走线未验**：本次只验了 LO `pptx→pptx` 的**结构存活**，**未渲染**其重写产物；
   若将来要把结构哨兵升级为走线哨兵，需先补测该路径。

### P-13 落地期的口径补齐落 ADR 0005；两处实现机制按实测订正

**裁决内容**

1. **口径缺口一律追加 ADR，不在实现里顺手决定**。ADR 0004 冻结了锚点规则、汇总/里程碑、项目起点、
   负 lag 截断、`Schedule` 形状、检环 API 与验证口径，但**没有**写 `ScheduleResult` 的整体形状、
   `Schedule` 数组的索引约定与汇总行哨兵、工期解析优先级、项目起点第②级"锚点"指哪些日期、
   有效图与结构图的两种口径、容量规划入口、两处有意抛出。以上全部落 **ADR 0005**，
   **ADR 0004 的冻结内容一字未改**（只在「落地」行与影响段加指针）。

2. **两处实现机制按实测订正，可观察语义不变**（ADR 0005 §7 写明映射）：

   - **容量**：传播本身是纯整数算术（`Schedule` 只出序号），因此 ADR 0004 §7 的
     "容量不足 ⇒ `withHorizon(2×)` 重建重算"落成**入口一次性扩容到覆盖全部文档日期**；
     "同一输入在任意容量下得到逐项相同的 `Schedule`"由单测守住（含"小容量日历导致
     `projectFinish` 超出其工作日总数"的用例）。
   - **日期解析**：热路径上 `isoToDayNumber`（正则 + `Date.UTC` + 反查，G1.2 已冻结不改）
     必须**每次调用只解析一次**并缓存序号——不缓存时 1,000 任务全量传播 p99 约 **2.5 ms**
     （超 DoD），缓存后 **530 µs**。这是"日历不进传播热路径"这条原则在 I/O 边界上的具体落地。

3. **检环口径统一为"结构性"**：`wouldCreateCycle(links, candidate)` 的签名看不到任务层级，
   因此让 `compute` 也用"排除汇总端点"的图检环会产生两个真相源；改为**传播忽略汇总端点边、
   检环（`compute` 与预检）一律用全部边**。后果是一个只经由汇总端点的环也会拒绝排程——
   **保守方向**，不会产出错误排程（G3 导入丢弃、G5 预检拒绝都建在同一判定上）。

4. **DoD 口径的实测记录**：产品口径的 `compute()`（含日期解析、工期解析、诊断收集与结果分配）
   在 1,000 任务/1,500 依赖上 **p50 = 326 µs / p99 = 530 µs**（最差 suite p99 = 644 µs），
   对 **p99 ≤ 1 ms** 有约 **1.9×** 余量；**S3 的 52.1 µs 是只测传播内核的窄口径**（预建 CSR、
   无日期与诊断），两者不可直接比较。EN-08 的 100 ms 仍保留为产品侧不回归天花板。
   差分（1,000 DAG + 200 成环图）实测约 **4.5 秒**、0 不一致；性能负向对照实测 **3.4×**（阈值 1.5×）。

**依据（摘要）**

- **"只写实现必须定的口岸"**：ADR 0005 的 14 条补齐项里，只有 3 条（结果形状、哨兵、项目起点第②级）
  会影响下游公共面，其余是同一事实的落地表述——若不写下来，G3/G4/G7 会各自推一遍；
- **两处订正都不是语义变更**：容量订正后序号与 ADR 0004 §7 的不变量完全一致；
  检环订正后 `compute` 与 `wouldCreateCycle` 才可能做出**同一个**判定（ADR 0004 §3 的立论正是反对两个真相源）；
- **证据层不改写**：S3 的数字与结论照旧，本轮只**补充**产品口径的实测（同 P-10 第 3 条的手法）。

**代价（明确接受）**

- **多一份 ADR 与一份包内规范**（`SCHEDULE.md`），文档登记成本上升；
- **结构性检环偏保守**：只经由汇总端点的环也会让 `compute` 拒绝排程（换来的是判定口径唯一）；
- **`endDateStale` 对汇总任务也报**：诊断条数比"只报叶子"多，但"文档里日期与工期不一致"
  这件事不该因层级而静默；
- **热路径引入调用内 `Map` 缓存**（同一次 `compute` 内按 ISO 去重）：换来约 5× 的性能改善，
  代价是一次调用的临时内存与"缓存必须是调用内局部"的纪律（写进 CONTRIBUTING 红线）。

**与既有裁决的关系**：**补齐与订正机制，不取代、不修改**任何 Dn/Rn/Tn/Pn 条目；
P-12 的范围收窄（只交全量 + 闭包、增量移出 v0.1）与 P-6 的性能口径均不变；
**不放宽**任何 DoD，也不触发《首版能力顺序》§四 的任何叙事降级规则。

**第十三轮遗留**：`spikes/g0-s3-cpm-perf/` 的处置（S3 结论 §九 原写"G2 落地后本目录整体删除"）
**留待 G8 一并定**——它目前仍是多份文档引用的证据层（ADR 0004 §9、ADR 0005、路线图都链到它），
删除会让这些引用悬空；可复用的基建已由 G2 重写并落在 `packages/engine` 与 `tools/cpm-reference/`。

### P-14 G3 的列契约、容差与诊断码表在 ADR 0006 冻结；六项口径一次裁决

**裁决内容**

1. **G3 的开工前置 = ADR 0006 落库**（本轮已落）。手法与 P-12 对 G2 相同：
   **形状与语义在开工前冻结，G3 内不再做设计决定**；契约变更须追加 ADR 并同步路线图 G3。
   ADR 0006 覆盖：公共 API 形状、9 列契约、日期/工期/进度/里程碑/依赖的**容差闭集**、
   公式口径、双解析优先级、**协议层诊断码表（闭集）**、成环边丢弃顺序、落盘形态、
   导出物白名单与确定性判据、依赖与捆绑、验证与门禁、明确不做。

2. **导出写「文档数据」，不写「排程结果」**——**订正** [ADR 0004](../02-adr/0004-排程契约.md) §影响中
   "导出（G3）写排程结果：导出的 Excel 与甘特图一致，且'导出 → 再导入'得到同一 `Schedule`"一句。
   理由：排程结果写进文件后，导入回来即为**文档日期**，对"有前置任务"的行会被
   `compute` 的锚点情形③**推导覆盖**并报 `dateOverridden`（[SCHEDULE.md](../../packages/engine/SCHEDULE.md) §四.3），
   "同一 `Schedule`"就取决于"导出的是哪一次的 `Schedule`"。
   **"与甘特图一致"改判为**：把导出物重新导入后，`compute(导入文档, createScheduleCalendar(导入文档))`
   与 `compute(原文档, …)` **逐字段深比较相等**（含诊断的码与 taskId 集合）。
   ADR 0004 的冻结内容其余**一字未改**，原文不改写（本记录只增不改）。

3. **公式只读缓存值，且"三类空"必须区分**：空单元格 / 公式无缓存值 / 公式被扁平化。
   协议层永不读公式文本、永不自研求值器（NG-06 / XL-08 不变）；
   公式存在但**无缓存值**（ExcelJS 给 `{formula, result: undefined}`）→ 按**值缺失**处理 +
   `XLSX_FORMULA_WITHOUT_CACHED_VALUE`(**info**)，并与排程侧 `undated` **并列展示、不合并**。
   依据：**两条独立实现互证**——ExcelJS 与 openpyxl 3.1.5（`data_only=True`）都把它暴露为 `undefined`/`None`，
   与空单元格同形；若当作"无日期"静默放过，该任务会回落项目起点，用户看到的是"日期没了"。

4. **成环边丢弃必须确定性，且不得用 `compute` 兜底**：按「**文档行序 × 单元格内前置出现顺序**」
   逐条调 `wouldCreateCycle(已接受的边, 候选)`，`cyclic` 即丢弃该条 + `XLSX_CYCLE_EDGE_DROPPED`（带成环路径），
   **丢弃后不回插、不做回溯**。理由：`compute` 遇环**整个失败**且失败结果的诊断面只有一条 `cycle`
   （SCHEDULE.md §八末），"先 compute、失败再补救"这条捷径不存在；丢弃顺序若不确定，
   "自往返一致"会变成偶发失败。

5. **xlsx 路径不做公式注入转义，CSV 路径仍须转义**：依据 S2 §六.3 实测——危险前缀文本经 ExcelJS
   以**共享字符串**落盘（`t="s"`），WPS 保存前后从未被解释为公式；**但 CSV 没有这层保护**
   （XL-10 的最终责任在 G3，本轮就此定案）。CSV 导入（XL-07）**复用同一套列契约、容差表与诊断码表**，
   导出 CSV 不在 v0.1 承诺内（D-2）。

6. **ExcelJS 以运行时依赖进入 `xlsx-protocol`，浏览器侧必须动态导入**：
   实测 `dist/exceljs.min.js` = **925.5 KB min / 251.6 KB gzip**，包内**无 ESM 入口**
   （只有 `main`(CJS) 与 `browser`(UMD 单文件)），**不可 tree-shaking**；版本**钉 `4.4.0`**，
   升级须重跑确定性/日期序列号/格式码三项证据。
   **本块不设 chunk 体积门禁**（首屏预算是 G4 的指标），G3 只要求**记录实测体积**。
   依赖内部存在 `document.*`/`window.*` 探测代码（已实测），**不违反**"三包零 DOM"铁律——
   铁律约束我们的源码，该差异在 ADR 0006 §11 显式记录。

| E8 | 公式语义（两实现互证） | ExcelJS：无缓存值 → `{formula, result: undefined}`；openpyxl：`data_only=False` 读文本、`data_only=True` 读缓存值、无缓存值读 `None` |
| E9 | 中文跨语言读取 | ExcelJS 写出 → openpyxl 读回，表名与含 `=` 的备注**逐字正确**；**控制台码页会把中文显示成乱码**，参照实现必须走 UTF-8 文件或 `PYTHONIOENCODING=utf-8` |

**依据（摘要）**

- G3 的技术不确定性**不在"能不能读写 xlsx"**（S2 已证），而在**口径唯一性**：
  导出内容（第 2 条）、公式语义（第 3 条）、丢弃顺序（第 4 条）三处若不写死，
  下游必然以"三处实现各一个版本"的形式返工——与 P-12 拒绝"以 `Gn.m` 消化不确定性"的立论同源；

  但它**必须是闭集**且与另两层同形（ADR 0006 §7），最终清单三层拼接、UI 只认一个数组；

  ① 导出物**新形状**（列宽/冻结/加粗）与"WPS 打开无修复提示"——历史上"需要修复"多来自这一类别，

  ② 251.6 KB 整块 gzip 对 G4"首屏 ≤1s"的正面撞击（对策：动态导入 + 记录实测）。

**代价（明确接受）**

### P-15 G3 落地期的四条口径补齐、两处实测订正，与依赖许可的处置

**裁决内容**

1. **三个 Protocol 入口是 `async`**（`detectColumns` / `importXlsx` / `importCsv` / `exportXlsx`）。
   ADR 0006 §11 要求浏览器侧**动态 `import('exceljs')`** 以把 925.5 KB min / 251.6 KB gzip 挡在首屏
   主 chunk 之外，而 `import()` 必然使签名返回 Promise。**ADR 0006 §1 的类型形状不变**
   （`ImportResult`/`ExportResult`/`XlsxDiagnostic` 逐字保持），变的只是"函数返回 Promise"——
   这是 §11 那条工程约束的**必然推论**，不是对 §1 的修改。Node 侧 ESM/CJS 互操作已实测
   （`import ExcelJS from 'exceljs'` 可用；命名空间键只有 `default`，**不能**具名导入）。

2. **任务 id 与「工作表编号」的分工**：文档里的 `outlineNumber` 是**派生值**（ADR 0002 ③），
   因此 (a) 任务的 `id` 取**确定性序号**（`t1`/`t2`/…，顺序生成，不用全局自增——同一次导入必须逐次可复现）；
   (b) **前置任务列按工作表里写的 `WBS` 编号解析**（那是用户认知的 `1.2`）；
   (c) 解析顺序固定为 **先按层级重编号 → 再用「工作表编号 ↔ 任务 id」映射解析依赖**；
   (d) `links[].from/to` 是**任务 id**（ADR 0004 §4–§6 的冻结形状，`tools/cpm-reference` 的输入协议亦如此），
   因此 ADR 0006 §7 的"文档行序"落成**工作表行序**、`wouldCreateCycle` 收到的边用**任务 id**。
   这一条解释了 ADR 0006 未写明的衔接：**WBS 编号是"表里的坐标"，任务 id 是"文档里的身份"**。

3. **任务名为空的文档不允许导出**（`XLSX_ROW_MISSING_NAME`，`ok:false`）。schema 要求 `name` 非空，
   但 `validateDocument` 对空名只给 warning，因此这种文档**可以被构造出来**。
   导出要么写一个空串（违反 ADR 0006 §2 的"空值 = 单元格缺失"），要么写缺失（回来变成"任务名为空"的
   error 行）。两种写法都无法自往返，故**拒绝导出**——不写出一份自己都读不回来的文件。
   同类拒绝还包括"文档校验有 error 级诊断"与"任务名为空"。

4. **`unzipper` 传递依赖由 `pnpm-workspace.yaml` 的 `overrides` 抬到 `0.12.5`（MIT）**。
   实测：`exceljs@4.4.0` 声明的 `unzipper@^0.10.11` 会拖入 `fstream@1.0.12`、`binary@0.3.0`、
   **`buffers@0.1.1`（其 `package.json` 的 `license` 字段为空、上游仓库已不可达）**、`chainsaw@0.1.0`
   与 `traverse@0.3.9`（两者声明 `MIT/X11` 这类非 SPDX 标识）。`unzipper@0.12.5` 已不再依赖
   `fstream`/`binary`/`buffers`，于是 `pnpm license:check`（`--prod`）能在**不新增白名单豁免**的前提下通过；
   **代价**：读路径走 `unzip.Parse({ forceStream: true })`，已用真实读写全链路实测可用（8 个 spec 全绿）。
   **不做的事**：不为"许可不可判定"的包开白名单豁免——把风险留在依赖树上比留在裁决里更危险。
   同时 `scripts/check-licenses.mjs` 的表达式解析补上 **`AND`** 分支（`(MIT AND Zlib)` 必须两个都宽松才通过；
   只看"任一分支"会误放行 `MIT AND GPL-3.0-or-later`），并把 `Zlib` / `MIT/X11` 登记为宽松许可。

5. **两处实测订正（可观察语义不变）**：
   - **「带时刻」的判据只认序列号的小数部分**。真日期路径上的 `Date` 是序列号换算出的绝对时刻，
     其小时数反映的是**时区偏移**（UTC+8 下 `getHours()` 恒为 8、`getMinutes()` 为 0），
     用它判定会把**每一个整日日期**都误报成 `XLSX_DATE_HAS_TIME`。因此该码只在**数值序列号路径**上判定。
   - **日期读回用本地 getter**（`isoFromDate`）。ExcelJS 把序列号读成"绝对时刻"（`excelToDate`），
     在"写与读同一时区"的常态下，本地 getter 读出的年月日恰好是用户在 Excel 里看到的日历日；
     用 UTC getter 反而会在 UTC+8 的常见场景下**差一天**（这正是 ADR 0006 §8 要避免的失败模式）。
     **已知边界**：跨时区（写与读偏移不同）时序列号对应的本地日历日可能偏移一天——
     这是"真日期 + 序列号"编码的固有属性，写进 PROTOCOL.md §九.1。
   - 另有一处**类型层实测**：`exceljs@4.4.0` 的 `index.d.ts` 里 `Cell` 继承了一个全局 `Address`
     声明（`col: string`），因此列号必须取 `eachCell` 回调的第二参（运行时 `cell.col` 是数，
     类型上不是）——与 S2 记录的"全局 `Buffer` 声明"同一类问题。

6. **`XLSX_TEXT_TRIMMED` 是补登，不是新开码**：ADR 0006 §4 的文本行明确要求
   "与文档语义相关的前后空白 → `XLSX_TEXT_TRIMMED`(info)"，但 §7 的码表漏登了它。
   本轮按 §4 实现并补登进闭集（**协议层码表 22 条**），PROTOCOL.md §七显式标注该差异。
   语义按 §8"文本原样"落地：**返回值仍是原样字符串**，trim 只用于判定用途。

7. **记录（非门禁）的实测数字**（Windows / Node 26.7.0 / 本机）：

   | 口径 | 实测 |
   |---|---|
   | 200 行端到端（`bytes → importXlsx → compute`） | 中位 **12.6 ms** / 最慢 43.7 ms（对"≤3 秒"约 **238×** 余量） |
   | 其中 `importXlsx` / `compute` | **8.8 ms** / **0.56 ms** |
   | 200 行导出物 | 14,707 字节 / **10 个部件** |
   | `exceljs` 浏览器入口 | `dist/exceljs.min.js` = **925 KB**、`exceljs.bare.min.js` = 842 KB |
   | 部件指纹确定性 | 同一文档两次导出**部件内容逐字节相同**（整文件哈希不作判据，有反向证据用例） |
   | LibreOffice 结构哨兵 | 本机 PATH 上无 `soffice` ⇒ **记录"未运行"并跳过**（哨兵 ≠ 门禁，P-9） |

**依据（摘要）**

- 第 1/2/3 条都是**"只写实现必须定的口岸"**：ADR 0006 的语义面一字未改，缺的是把"表里的坐标"
  与"文档里的身份"分开的那道缝、以及 §11 的工程约束对签名的影响。不写下它们，
  G4/G5 会各自推一遍——与 P-13 补齐 ADR 0005 的立论同源。
- 第 4 条是**许可可判定性**问题，不是洁癖：`buffers@0.1.1` 没有任何许可声明、上游不可达，
  按 PRD-06 无法登记；而"抬一个已被我自己实测过的传递依赖"是有界、可复现、可回退的动作。
  实测证据：改版后 8 个 spec（含双向跨语言差分与字节变造负向对照）全绿。
- 第 5 条两处都是**实测发现的口径漏洞**（并把发现过程写进注释与用例）：
  若不改，`XLSX_DATE_HAS_TIME` 会在本机每个日期上误报，而"日期差一天"会静默发生。
- 第 6 条是**文档内部的漏登**：ADR 0006 §4 与 §7 在这一点上不自洽，按"码表是闭集、
  不为新原因随手开码"的口径，只能补登并留痕（本记录只增不改）。

**代价（明确接受）**

### P-16 G4 不分解；以"开工前置 ADR + 准入定标实验"消化不确定性

**1. G4 不分解**（不产生 `G4.m` 子块）。P-10 拆 G1 的四条判据对 G4 **逐条不成立**：

| P-10 判据 | G1 的情形 | G4 的情形 | 成立？ |
|---|---|---|---|
| 出口条件与子系统**多对多** | 4 条分属 schema / 日历 / 命令层 / 常驻护栏 | 5 条是**同一条渲染管道**的五种证据透镜（规模 / 结构 / 流畅 / 几何 / 编辑不变式）；只有"依赖线路由几何"是可切出的子面，而它是**中间层**不是能力 | ❌ |
| 真实依赖边是**并集而非交集** | G2 只需日历+schema，不需命令层 | G5 要几何 + 视口 + 命中反算；G7 要几何但**不要窗口裁剪**（导出是全量渲染）⇒ **存在"只要一半"的下游** | ⚠️ **部分成立**（唯一支持分解的判据，理由见下） |
| 风险与可逆性**不均** | G1.1 已被 S3 去风险 vs G1.3 是难逆承诺 | 风险**集中在一处**：裁剪/规模（T-4/P-8 原话"纯 SVG 路线唯一的失败模式"）；几何路由已由 P-8 定策略，属"难逆但**可冻结**"（ADR），不是两个风险段 | ❌ |
| **反方**（内部耦合 / 半成品 / 粒度） | 已处理并否决 | 见下 | ❌ |

**唯一支持分解的判据为什么不足以支撑分解**：G7 确实只需要几何子集，但

- **P-2 已定"导出后置"**（G7 在 G5 之后），因此"让 G7 早知道几何"**不产生任何排序收益**；
- "导出不做窗口裁剪"本身是 [ADR 0007](../02-adr/0007-渲染几何与裁剪契约.md) §10 的**一条语义**，
  不是拆门禁的理由；
- 而**"无可见交付"不构成否决理由**——G1.2/G1.3/G2/G3 都没有 UI 先例，本项目从未要求门禁必须可见。

**反方最强处与它的解法**：G4 的证据天然分两类——**Node 可判定**（几何、路由、裁剪选择）与
**只有浏览器可判定**（首屏、掉帧）。单门禁的强弱会被最弱证据决定，等于让"几何错了"与"浏览器慢了"
混在一张报告里。**但解法是验证矩阵分层（第 6 条），不是新编号**：Node 可判定者进 `pnpm gate`，
浏览器计时先做**记录制**（P-9 的同款手法）。真正不可判定的那条（计时）**不会因为多一个编号而变得可判定**。

**2. G4 的开工前置 = [ADR 0007](../02-adr/0007-渲染几何与裁剪契约.md) 落库 + [G4-S](证伪实验计划.md) 完成**
（门禁 `S4-a`…`S4-d` 各有明确判定）。分工：**ADR 冻结形状与语义，G4-S 回填数值与可行性**；
**数值未回填时，G4 的对应出口条件不得判"通过"**（不得把假设写成结论）。
G4 的出口条件新增一条：**"ADR 0007 的数值表（§11）已回填；契约变更须追加 ADR 并同步本节"**——
原 G4 内容要求"把裁剪策略写成 ADR"，但出口条件里**没有**这一条（G1.3 有"ADR 落库"），本轮补齐。

**3. 几何真相源的包边界（本条是包边界裁决，不是门禁分解）**：
新增零 DOM / 零框架包 **`packages/render-core`（`@ganttpilot/render-core`）**，
承载"文档 + `Schedule` + `Calendar` + 视口 → 几何"的纯函数计算，供 `apps/web` 与 G7 的导出投影**共用**。
理由（可验证的事实，不是偏好）：

- **根 `vitest.config.ts` 的收集范围是 `packages/*/src/**/*.spec.ts`（`environment: 'node'`）**——
  几何放进 `apps/web` 就**自动落在 `pnpm test` / `pnpm gate` 之外**（现状核实：`apps/web` 今天没有任何测试入口）；
- G7 的 `pptx-renderer` 零 DOM，无法 import Vue 应用内的模块，复制一份就是**两个真相源**
  （ADR 0005 §8 已经用"同一事实两个真相源"否决过一次别的方案）；
- 铁律 #2"双投影共享几何"需要一个**双方都能依赖的载体**。

该包**并入 ADR 0001 的零框架/零 DOM 约束集**（`tsconfig` 无 DOM lib + ESLint 三条边界规则 + 护栏自检）。
既有文档中的"三包"措辞**不改写**，自本条起按「**计算层各包（含 `render-core`）**」解读
（沿用 P-10 第 3 条的映射手法）。

**4. 时间轴口径（本块最重要的语义决定）**：**x 轴按自然日连续排列，非工作日照常占位并视觉区分**
（与 [D-4](裁决记录.md) 的 MS Project 惯例同源）。冻结公式：

- 左边界 `x = (dayOfOrdinal(es) − axisOriginDay) · pxPerDay`；
- **右边界 `x = (dayOfOrdinal(ef − 1) + 1 − axisOriginDay) · pxPerDay`**——
  必须用 `ef − 1` 再 +1，否则跨周末的任务（周五 + 周一）会多出一段空隙；汇总条同规则取
  `summaryEs`/`summaryEf`；`es[i] === -1` 是**唯一的汇总判别式**（SCHEDULE.md §三已指定 G4 必须用它）；
- 里程碑（零时长）几何上以所在工作日**格的中点**为中心，属视觉约定，不改变"零时长"语义；
- 轴线起点 = 项目起点所在刻度单位的起点，再向左留 `AXIS_LEFT_GUTTER_DAYS`
  （**该 gutter 是 P-8 的 SS/SF"左出回绕"走线的前提**）；
- **序号 ↔ 日期翻译必须用同一个 `createScheduleCalendar(document)`**，`-1` 哨兵绝不可喂给 `dayOfOrdinal`；
- **与 G5 的分工**：拖拽在自然日上发生、语义在工作日上运算，因此 G4 提供 `ordinalAtX`（吸附候选），
  **吸附时机由 G5 的手势状态机决定**；该分工不在 G5 重新定义。

**5. 裁剪契约**（ADR 0007 §6，四条 + 两条负向对照）：行窗口 = 可见行 + 上下各 `ROW_BUFFER` 行；
**边窗口 = 边所跨行区间 ∩ 可见行窗口**；**折叠隐藏的行不画其边**（否则悬空线）；
**文档里的全部 `links` 都画**（含被传播忽略的汇总端点边，用样式区分，**不新开诊断码**）——
渲染呈现的是**文档数据**，与 SCHEDULE.md §四.6 的"有效图 vs 结构图"不冲突；
**裁剪先于几何计算**；拖拽期不重建 DOM；元素预算
`#elements ≤ c₁·visibleRows + c₂·visibleEdges + c₃`（常数由 G4-S 回填）。

**6. 门禁分层（替代 G4 原有的定性出口条件）**：

| 层 | 判据 | 级别 |
|---|---|---|
| ① 几何期望值表（声明式，内核无权改基准） | 4 类关系出/入边、stub、正交折点、端点贴合条边中点、跨周末右边界规则 | **进 `pnpm gate`** |
| ② 裁剪结构断言（纯函数窗口选择 + Node 侧渲染计数） | 元素数满足上界且**与文档总规模无关**；跨屏长边不被误裁 | **进** |
| ③ 不变量 | 反算往返、边端点落在条边上、汇总条覆盖子树 | **进** |
| ④ 负向对照 | 端点可见性裁剪必须被检出丢边；关掉窗口裁剪必须被检出元素数增长 | **进**（否则②可能是恒真式） |
| ⑤ 浏览器计时（首屏 / 10× 滚动 / 帧预算） | 与《评估报告》§5.4 的 2,200 边 / 约 2.0s **同尺**对照 | **先进记录制**；G4-S 定标后由裁决决定是否升级 |
| ⑥ 人工目视 | 仅备查 | **不进**（"必须量化、不得目视"，P-9） |

**优先走零新增依赖路径**：`vue@3.5.43` 自带 `@vue/server-renderer`（已在锁文件中），
可在 Node 侧 SSR 出 SVG 做元素计数与结构断言；纯函数层在现有 `environment: 'node'` 下直接断言。
若要引入浏览器自动化（如 Playwright）或 DOM 环境（jsdom/happy-dom），须走 CONTRIBUTING 的依赖准入流程，
并在裁决中记录"**是否进门禁、缺失时是失败还是跳过**"（P-12 口径）。

**首屏口径**（必须与数字一起引用）：数据来源 = **合成夹具 + `createScheduleCalendar` + `compute`**
（G6 未落地，不依赖持久化）；**不含** xlsx 导入（`exceljs` 925 KB 只准动态 `import()`，ADR 0006 §11）；
环境（浏览器与版本、headed/headless、机型、Node 版本、`pxPerDay` 档位）**必须与数字一起登记**；
**"无可见掉帧"必须量化**（如 p95 帧时长 ≤ 16.7 ms 或长任务计数），否则不予判定。

**7. G4 的范围边界（一次写清"G4 内不做"）**：拖拽三语义、拖拽建线、撤销/重做 UI、冲突标记、

### P-17 G4-S 准入实验的判定与浏览器计时口径

**裁决内容**

1. **`S4-a`…`S4-d` 全部通过**，判定与数值以 G4-S 结论为准（**该 spike 目录已随 G4 落地删除**，
   见第十八轮 P-18 第 6 条；数字与复现入口已转入 `packages/render-core` 的 spec 与
   `scripts/measure-render.mjs`）：

   | 门禁 | 结论 | 关键数字 |
   |---|---|---|
   | `S4-a` | **通过** | 元素预算在 **12/12** 组（4 数据集 × 3 档位）成立；`c₁ = 3`、`c₂ = 3`、`c₃ = 116/70/89`（日/周/月）；10× 规模跨度元素总数 **1.104×**（317 → 350）、渲染行恒为 32；对照（关掉窗口裁剪）**10.71×** |
   | `S4-b` | **通过** | 仅按端点可见性裁剪会误裁 **314** 条边（4 个滚动位置 33/97/96/88，其中跨屏长边 268）⇒ 求交**必需** |
   | `S4-c` | **通过**（记录制） | 首屏（就绪 → 含依赖线首帧）**18.0–31.2 ms**（日/周/月，1,000 任务 / 1,500 依赖）；10× 滚动 **164.8–167.2 ms**（1,500 边 / 2,200 边两组，对 §5.4 的约 2.0 s 同尺）；主线程 p95 **1.1–2.5 ms**（阈值 16.7）、空白帧空白行 **0**、longtask **0** |

2. **浏览器计时（ADR 0007 §9 第 ⑤ 层）维持"记录制"，不进 `pnpm gate`**。理由三条：
   ① 它需要**本机 Chrome**（门禁必须在任何机器上可跑）；② 它是"测量快照"，换 Chrome 大版本数值必变；
   ③ **真正需要门禁的判据（几何期望值表、裁剪结构断言、不变量、负向对照）已全部在 Node 侧**
   落在 `pnpm test` 的收集范围内——浏览器侧的增量信息只有"耗时量级"。

### P-18 G4 落地期的口径补齐、两处签名/工具链订正与一处判据订正

**1. 包与规范落地。** 新增零 DOM / 零框架包 **`packages/render-core`（`@ganttpilot/render-core`）**，
沿用 ADR §2 的函数名（`buildView` / `visibleRows` / `visibleEdges` / `dayAtX` / `ordinalAtX` /
`taskBounds` / `barXRange` / `routeEdge` / `selectEdges` / `rowWindow` / `countElements`），
并把引擎的命令层与文档面**重导出**（`applyCommand` / `applyToSession` / `createSession` /
`undoSession` / `redoSession` / `reindexDocument` / `validateDocument` / `createScheduleCalendar`
与 `ProjectDocument`/`Schedule`/`DocumentCommand` 等类型）——避免 `apps/web` 自己拼一条直连引擎的隐式路径。
权威规范落 [`packages/render-core/SPEC.md`](../../packages/render-core/SPEC.md)（与 `SCHEDULE.md`/`PROTOCOL.md` 同构）。

**2. 两处订正。**

- **① `ordinalAtX` 显式收 `Calendar`**（`ordinalAtX(view, x, calendar)`）：ADR §2 写的是 `(view, x)`，
  而"序号"只有 `Calendar` 能算。G4-S 已记载这一必要偏离（为了让 `ViewModel` 保持"只有数字与枚举"），
  本轮**确认并继承**，未改任何语义；
- **② 元素模型与计数器的落点**：ADR §9 第 ② 层原写"纯函数 + `@vue/server-renderer` 计数"，
  实际改为**计数器落 `render-core`**（`countElements` 分类累加 + `countElementsByEnumeration`
  逐项枚举，两路必须逐项相等），并在测量钩子里用**实际 DOM 的 `<g>` 数**与模型对照。
  **`@vue/server-renderer` 方案未采用**：它会把 `vue` 拉成 `render-core` 的运行时依赖，
  与"计算层零框架依赖"这条铁律冲突；而它带来的增量信息（"渲染层真的发射了这些元素"）
  已由"两路互证 + DOM 对照"覆盖。**未新增任何依赖**（README/CONTRIBUTING 的依赖准入流程未被触发）。

**3. 一处判据订正。** `evaluateScaleCriteria()` 的行高判据④ 按 **ADR 0007 §11 第 2 项的原文**
用**真除法**（`VIEWPORT.height / rowHeight >= MIN_VISIBLE_ROWS`），而 G4-S 的 `scale-params.mjs`
实现用的是 `Math.floor(...)`。两者在候选 20/24 上均通过、在 28 上均不通过，**选定值 24 不受影响**，
因此不构成契约变更；本轮按"语义 = 文档"实现（复推函数因此可被 spec 断言 `consistent === true`）。

**4. 水平窗口裁剪的落地（P-17 遗留 1 的收口）。** ADR §11.1 ③ 澄清的"第三维：水平窗口"
（轴与刻度只发射视口 x 范围内的元素）**已实现**（`buildAxis`），`c₃` 因此只与
"窗格宽 ÷ `pxPerDay`"有关、与文档总规模无关。**§6 的正文未改**（按 P-17 遗留 1，
把它写进契约正文需另立 ADR）——ADR 只在 §11.1 保留该澄清，并在「落地」段记明已实现。

**5. 记录制证据的口径与工具链。** 新增 [`scripts/measure-render.mjs`](../../scripts/measure-render.mjs)：

### P-19 左表日期列与 `edit.ts` 的派生 `endDate` 使用了未锚定的日历（`APP_CALENDAR`）

**1. 现象（可复现）。** 打包产物（`apps/web/dist`）在演示夹具（`dense`，1,000 任务 / 1,500 依赖）下，
左表同一行出现 **"完成早于开始"**，而甘特图的条形落在 2026-10 至 2027-01（与"开始"列一致）：

```
表头/行文本（页面 DOM 实测）：
  ▾1 | 阶段 1 | 2025-01-01 | 2025-01-13 | …        ← 汇总行
  1.1 | 任务 1 | 2026-10-05 | ≈2025-01-09 | 7 | …   ← 叶子行：完成 < 开始
状态栏：任务 1000 · 依赖 1500 · 可见行 981 · 渲染行 44 · 渲染边 49 · 元素 332/342（c₃ = 63）
```

**2. 根因（已定位到行）。** `Schedule.es` / `ef` / `summaryEs` / `summaryEf` 是**相对项目起点的绝对
工作日序号**，必须用 `createScheduleCalendar(document)` 构造的日历翻译（ADR 0007 §3）。渲染层遵守了这条
（[`useProject.ts`](../../apps/web/src/composables/useProject.ts) 第 99 行把同一个日历交给 `buildView`），
但**左表的文本格式化没有**——它用的是 [`shared.ts`](../../apps/web/src/shared.ts) 第 11 行的

```ts
export const APP_CALENDAR = new Calendar({ id: 'project', exceptions: { nonWorking: [], working: [] } });
```

一个**没有锚点**的日历（`baseDay` 取默认值）。实测：

| 量 | 值 |
|---|---|
| `DEFAULT_PROJECT_BASE_DAY_ISO` | `2025-01-01` |
| `APP_CALENDAR.baseDay` | `20089` = 2025-01-01 |
| `createScheduleCalendar(doc).baseDay` | `20731` = 2026-10-05 |
| 同一序号 `0` 的解释 | APP → **2025-01-01**；正确 → **2026-10-05**（相差 642 个自然日） |

由于"序号相对 `baseDay`"这条口径本身正确（G1.1 冻结），错误**只在消费点暴露**，
且表现为"整列被搬到 2025 年"——它不是随机错，而是一次偏移，因此**看起来很像"旧数据"**，
比崩溃更难被发现。

**3. 影响面（两条路径，一条只错显示、一条会污染文档）。**

| 路径 | 位置 | 后果 |
|---|---|---|
| **显示** | [`shared.ts`](../../apps/web/src/shared.ts) 第 115 / 119 / 124 / 129 行（`cellText` 的 `start` 与 `end`） | 左表"开始/完成"两列错位；汇总行与无日期叶子行同样错 |
| **写入（更严重）** | [`edit.ts`](../../apps/web/src/edit.ts) 第 152–153 行（`derivedEndIso` 用 `APP_CALENDAR.addWorkdays` / `subtractWorkdays` 重算 `endDate`） | 行内编辑改 `start`/`duration` 时会把**错算出的 `endDate` 经命令层写进文档**（与图表显示不一致地入库） |
| **继承风险** | G7 的导出投影（`Schedule` 只出序号，导出必须自行翻译） | 若照抄 `shared.ts` 的写法，导出物会带上同一处偏移 |

**4. 为什么门禁没拦住（这是本条最值得记住的部分）。** `pnpm gate` 当日全绿
（41 个 spec / 539 例，含引擎差分与 xlsx 双向差分），但**它们全部在 `packages/*` 下**：
`apps/web` 的 spec 数为 **0**。因此应用层的格式化与接线**完全不在门禁覆盖范围内**——
这是"计算层零 DOM/零框架"这条铁律换回来的代价（铁律本身必须保留），
代价的具体形态就是**应用层成了一个没有判据的薄壳**。

**4.1 这个缺口是"规划未覆盖"，不是"进度还没走到"（本轮追加的因果判定）。** 三条证据：

- **① 收集范围是显式设计，且 `apps/web` 自 G0 起就在仓库里**：`vitest.config.ts` 第 6 行
  `include: ['packages/*/src/**/*.spec.ts', 'packages/*/lint-boundary/**/*.spec.ts']`、
  `environment: 'node'`、`passWithNoTests: false`——**只收 `packages/*`，不是"还没配"**。
  查证 G0–G4 的出口条件、S1–S4 的门禁、以及[《证伪实验计划》](证伪实验计划.md)全文：
  **没有任何一条要求应用层有判据**（该文件提到 `apps/web` 仅 1 次，且只是"证据落 `apps/web/evidence/`"）。
- **② 这个缺口曾被写下来当决策依据用过**：[ADR 0007](../02-adr/0007-渲染几何与裁剪契约.md) §2
  否决"放进 `apps/web/src/geometry`"的第一条理由原文即"**几何放进应用就自动在 `pnpm test` / `pnpm gate` 之外**"。
  即"`apps/web` 不可测"是**已知前提**；架构的应对是**把可测部分搬进 `packages`**（应对正确且必要），
  但**没有同时决定"留在应用层的那部分怎么办"**。
- **③ 决定性的一条：G4 落地时把它记成了"现状核实"而不是待办**：[P-16](裁决记录.md) 原文有
  "现状核实：`apps/web` 今天没有任何测试入口"。即 **G4 开工前就核实过应用层没有判据，G4 照样落地**，
  既未列为开工前置、也未列为出口条件。因此这不是"还没走到"——**这一步已经走过了**（G4 已完成、
  P-18 判定出口条件全部通过）。

**缺口的真实形状**：G4 的落点判断是"应用层只做消费，把可测的纯函数都搬进 `render-core`"。
该前提对**几何**成立（几何全搬走，90 例），但错位缺陷**不是几何问题，而是几何的输入换算问题**——
而换算恰恰是**留在应用层、且从未被判断过**的那部分。它没在 G4 暴露，是因为 G4 的出口条件
把注意力全放在几何正确性、裁剪有效性与性能口径上（都有量化判据），而 `cellText` 当时看起来
只是"把数字格式化成字符串"的琐碎事——**直到它因增长出 `null` 口径、汇总/里程碑分支、
派生显示值与日历翻译而变成真实业务逻辑**。

**一句话归纳**：`apps/web` 的结构性缺口从 G0 就在、且被写进 P-16 当作"现状核实"；
但"**它该不该继续没有判据**"从未被当作一个决策做过——本次是它第一次导致真实缺陷。
**公平地说，"还没走到"确实存在于另一半**：G5 及以后（拖拽交互、IndexedDB、PPTX 导出）
会引入真正的组件/集成/E2E 测试需求并伴随依赖准入问题；**但今天的缺陷不属那一半**，
它是应用层的**纯逻辑**缺陷，本可以被一条**零新增依赖**的断言拦住。

**5. 排期与验收（修复归 G5 的开工前置，本轮不动代码）。** 已在[《首版能力顺序》§三 G5](../01-roadmap/首版能力顺序.md)
登记两条：一条"开工前置"、一条未完成项。**§4.1 的因果判定改变了修复的形状**：既然缺口是
"**落点判断**"而不是"缺测试框架"，最优解就不是给 `apps/web` 搭测试环境，
而是**执行 ADR 0007 §2 已经确立的"落点即门禁"原则**——把可测的纯函数迁进 `packages`，
它们就自动进 `pnpm gate`，**零新增依赖、零新测试框架**。据此，修复口径改为三条：

- **① 迁落点（主口径，取代原先的"显式收 `Calendar`"单条）**：把 `cellText` 与 `derivedEndIso`
  从 `apps/web/{shared,edit}.ts` 迁进 **`packages/render-core`**，并把 `Calendar` 作为**显式入参**
  （与 `ordinalAtX(view, x, calendar)` 同手法：凡"只有日历能算"的量，都必须显式收日历，
  P-18 第 2 条①的先例）。迁移后它们**自动落在 `vitest.config.ts` 的收集范围内**，
  在现有 `environment: 'node'` 下即可断言（两者都不碰 DOM / Vue）。`APP_CALENDAR` 若保留，
  只允许用于**与项目起点无关**的纯工作日算术；
- **② 必须先裁决一个依赖方向障碍**（本轮核实）：`cellText` 的签名需要 `ColumnKey`，
  而 `ColumnKey` 定义在 `xlsx-protocol`；现状依赖为 `render-core → engine`、
  `xlsx-protocol → engine + exceljs`。若 `render-core` 直接 import `xlsx-protocol`，
  就会经它**把 925 KB 的 `exceljs` 拉进渲染包的依赖图**，与"计算层零框架/零 DOM"及体积纪律冲突。
  两条候选（**待裁决，不在本条内自行决定**）：

  | 候选 | 做法 | 代价 |
  |---|---|---|
  | **A（倾向）** | **列身份的所有权反转给 `render-core`**：列是渲染抽象，`ColumnKey`/`COLUMN_SPECS` 由 `render-core` 拥有，`xlsx-protocol` 从它 import | 依赖方向变为 `engine ← render-core ← xlsx-protocol`（单一方向、不拉 `exceljs`）；同时消掉 P-18 遗留的"第二个列真相源"隐患，G7 导出投影可复用同一份列语义。代价是要动 `xlsx-protocol` 的导出面（该包已发布语义，属**契约变更**，须追加 ADR 或一次裁决） |
  | **B** | `render-core` 以 `import type` 仅取 `ColumnKey`（类型擦除，不产生运行时边） | 改动最小；但依赖方向从此变得可疑，且 `render-core` 的类型检查会经由 `xlsx-protocol` 的类型入口——**需实测确认类型依赖是否仍会牵出 `exceljs` 的类型图** |

- **③ 判据与负向对照**（沿用 P-13/P-15/P-18 的纪律）：至少断言
  ①"开始 ≤ 完成"（全部行，含汇总与无日期叶子）、②左表"开始/完成"与 `render-core` 的
  `dayOfOrdinal(es/ef − 1)` **同源**、③行内编辑改 `start` 后写回的 `endDate` 与图表一致；
  并**必须自带负向对照**：把 `APP_CALENDAR` 换回（或改其 `baseDay`）必须让上述断言**失败**，
  否则它们只是恒真式。

> **对 G5 出口条件第 0 条的同步**：该条目前写的是"`cellText` 与 `derivedEndIso` 改为显式收 `Calendar`"，
> 应读作本条 §5 的 ①+②+③（**先定依赖方向，再迁移落点，再落判据**）。
> 若 A/B 两条候选在本轮无法裁决，则**降级执行**：先按本条 §5 ①的"显式收 `Calendar`"在应用层原位修正
> （最小改动、立刻消除错位与文档污染），并把"迁移落点"作为紧随其后的第二步——**但第 ③ 条判据不得省**。

**6. 顺带登记的相邻脆弱点（不在本条修复范围内）。** `APP_CALENDAR` 另有一个**固定地平线**问题：
它由 `Calendar` 默认地平线（`spanDays` 默认 1,460 天）界定的窗口约为 `2025-01-01 … 2028-12-30`，
而**文档的真实日期范围与它无关**。因此"日期换算成功/失败"会取决于用户文档恰好落在哪个区间
（超出即 `catch` 返回 `undefined` → 静默留空）。修复时**一并改为按文档锚定**（`createScheduleCalendar`），
可同时消掉这一类"会随文档漂移的静默失败"。若修复时判断该问题需要独立口径，则**另立 ADR**，不在本条内吞掉。

**依据（摘要）**

- 本条**不推翻任何历史裁决**：ADR 0007 §3 的原文就是正确答案，缺陷是**实现未遵守自己的契约**，
  因此不动 ADR、不改语义，只登记"实现偏离 + 覆盖缺口 + 修复排期"；
- 与 P-18 的关系：P-18 判定"G4 的出口条件全部通过"**仍然成立**——11 条出口条件里没有一条
  要求"左表日期与图表同源"（G4 的出口条件判的是几何、裁剪、折叠、负向对照与首屏/滚动性能）。
  **这是出口条件集合的覆盖面缺口**，而不是 P-18 的判定错误；本条据此把它补进 G5 的前置；
- 手法沿用 P-13/P-15/P-18（"落地期发现 → 一次裁决登记 → 归入下一个能力块的前置"）。

**代价（明确接受）**

- **G4 的"已完成"要带一个星号**：界面主链路可用，但**左表日期列在当前演示数据下是错的**，
  在 G5 前置修完之前不得对外演示该列；本条把这句话写进权威登记处，避免"看起来已完成"被误读；
- **多一次往返**：修复动作本身很小（几处签名 + 追加入参），但它被排到 G5 而非立即做——
  接受这段窗口期内 `apps/web` 的日期显示不可信。

**第十九轮遗留待定**

1. **`APP_CALENDAR` 的地平线脆弱点**（本条 §6）：修复时按文档锚定，或另立 ADR 定口径；
2. **列身份的所有权（依赖方向）**（本条 §5 ②）：候选 A（`ColumnKey`/`COLUMN_SPECS` 所有权反转给
   `render-core`，会动 `xlsx-protocol` 的导出面 ⇒ **契约变更**）与候选 B（`import type` 仅取类型，

4. **是否给 G4 的出口条件补一条"左表与图表日期同源"**：属对已完成能力块的判据回填，

### P-20 候选 A 的裁决与 P-19 修复的落地

**1. 依赖方向的裁决：候选 A。** P-19 §5 ② 的两条候选里选 **A（所有权反转给 `render-core`）**，
理由与代价见 [ADR 0008](../02-adr/0008-列身份所有权与拖拽交互契约.md) §1–§3。
依赖方向因此变为 `engine ← render-core ← xlsx-protocol`；`xlsx-protocol` 的**公共 API 面一个符号不减**
（`columns.ts` 转型再导出）。

**2. P-19 §5 三条的落地。**

| 条 | 落地 |
|---|---|
| ① 迁落点 | `cellText` / `derivedEndIso` / 值→命令映射（`editToCommand`/`collapseToCommand`）与日期文本工具全部落 `render-core/src/viewText.ts`，**`Calendar` 为显式入参**；`apps/web` 的 `shared.ts`/`edit.ts` 删除，界面直接从 `@ganttpilot/render-core` 取 |
| ② 依赖方向 | 见上（候选 A）。P-19 §5 ② 的"需实测类型图是否牵出 `exceljs`"在候选 A 下**不再适用**；改为**正面断言**：`boundary.spec.ts` 断言发布源与**构建产物**都没有指向 `exceljs` 的模块边 |
| ③ 判据 | `dateText.spec.ts`（开始 ≤ 完成 / 与 `Schedule` 同源 / 派生完成与显示的"开始"同源）、`editCommand.spec.ts`（编辑 `start`/`duration` 写回的 `endDate` 与 `compute` 一致）、`dateTextNegative.spec.ts`（NC1/NC2）、`textFixtures.spec.ts`（前提自证：20089 vs 20731、642 天）——**全部进 `pnpm gate`** |

**3. 落地期抓出的两处真实错位（P-19 未预见，均由判据 ① 在本轮当场检出并修掉）。**

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① | **零时长任务（里程碑）显示"完成早于开始"**，实测 **49 行** | 通用式 `startOrdinal + 工期 − 1` 在 `工期 = 0` 时退化为 `startOrdinal − 1`（"前一个工作日"） | `工期 ≤ 0` ⇒ 完成 = 开始（与 `derivedEndIso` 的 `durationDays <= 0` 分支同口径） |
| ② | 被推导覆盖（`dateOverridden`）或早于 `baseDay` 被截断（`clampedStart`）的行可能反向 | "开始"列显示**文档** `startDate`，而"完成"列用**排程** `ef − 1` —— **两列出自两个起点**，各自都对 | 派生「完成」与**显示的「开始」**同源：`startOrdinal = (文档 startDate 的序号) ?? es` ⇒ `end = dayOfOrdinal(startOrdinal + 工期 − 1)` |

两处都**不新造语义**：`ef = es + 解析工期`（[SCHEDULE.md](../../packages/engine/SCHEDULE.md) §九 不变量 1）
在显示层的展开；`derivedEndIso` 与此同构，因此"左表写回的 `endDate`"与"图表条右端"不可能分叉。

**4. 一处实测发现（对 P-19 正文的补充，不改其结论）。** `derivedEndIso` 的输入输出都是 ISO，
而 `ordinalOfDay` / `dayOfOrdinal` 在同一日历内互为逆运算（锚点项互相抵消）⇒
**换一份日历不改变它的结果**。因此 P-19 §3 表格里"`derivedEndIso` 会把错算的 `endDate` 写进文档"
这句要读作：**风险来自调用方喂给它的 `start`**（以及 §6 的地平线容量），
而不是它自己会算错日期。缺陷本体在 `cellText`（它拿 `Schedule` 的**序号**去翻译）。
本条的判据据此调整为"派生完成与**显示的**开始同源"（更强，且真的会在错误口径下失败）。
