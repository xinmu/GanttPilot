# M0 W1–3 证伪实验计划（Spike Plan）

| 项 | 内容 |
|---|---|
| 目的 | 在写任何产品代码之前，用最小成本证实或**证伪**三个"被文档当作既定事实"的高风险假设 |
| 依据 | 《评估报告》§5.1–§5.3、§7 D-3 |
| 总时长 | 每项 1–3 天，合计约 5–8 个工作日（可串行、可并行） |
| 铁律 | **spike 代码不进主干**；判据必须是"真机可观察行为"，不是"库能编译/文件能打开" |
| 产出 | 每个 spike 一份 `结论.md`（能/不能/代价 + 证据截图或录屏 + 决策建议） |

> 通用纪律：**先证伪，再优化**。任何一个 spike 若在第 1 天就出现"根因不可绕开"的证据，立即停止并出结论，不要为救活假设而延长实验。

## Spike-1：PPTX 原生 connector 吸附与 group 坐标（最高优先级）

**要回答的问题**：任务条被拖动时，依赖线是否仍然吸附并自动改道？父子分组是否在首次打开即正确？

**已知前提（已核验）**：pptxgenjs 4.0.1 **不支持** connector（无 `cxnSp/stCxn/endCxn`）**也不支持** group（无 `addGroup`）。因此本 spike 验证的不是库能力，而是**"自研 OOXML 补丁"这条路是否走得通**。

### Day 1 — 制造工件（不搭产品管线）
1. 手写最小 fixture：2 个 `roundRect` + 1 个 `bentConnector2/3`，用 `<p:cNvCxnSpPr><a:stCxn id idx/><a:endCxn id idx/></p:cNvCxnSpPr>` 双侧吸附；再加 1 个菱形里程碑、1 个含 2 个子形状的 `grpSp`（`off/ext` 与 `chOff/chExt` 都必须显式且正确）。
2. 容器复用 pptxgenjs 产物：`pptx.write({outputType:'uint8array'})` → JSZip 打开 → 重写 `ppt/slides/slide1.xml` → 重新打包。**同时验证容器可打补丁。**
3. 同一几何再用 `custGeom` + `points` 出一版折线（即文档声明的降级方案），用于视觉对比。

> **执行状态（2026-10-03）：S1 已执行，本目录见 [`spikes/g0-s1-pptx-connector/`](../../spikes/g0-s1-pptx-connector/)（结论：[结论.md](../../spikes/g0-s1-pptx-connector/结论.md)）。
> 三处对上述协议的实测更正：**
> 1. 锚点的容器元素是 **`p:nvCxnSpPr > p:cNvCxnSpPr`**（**`p:` 前缀**）；**子元素**才是 `a:stCxn`/`a:endCxn`——
>    即上面第 1 步的写法**正确**。
>    （此处曾"更正"为 `a:cNvCxnSpPr`，**该更正有误，已撤销**，见 [裁决 P-7](裁决记录.md)。）
>    WPS 原生产物佐证见 `spikes/g0-s1-pptx-connector/evidence/wps/D-native-slide1.xml`
>    （三份真实文件中 `a:cNvCxnSpPr` 各出现 **0** 次、`p:cNvCxnSpPr` 各 **2** 次）。
> 2. **原生产物不写 `<a:cxnSpLocks/>`**，补丁应与原生一致。
> 3. **`a:stCxn@idx` 是 preset geometry 的连接点序列，不是 PowerPoint COM 的枚举值**——`roundRect` 下
>    OOXML 为 `0=上 1=左 2=下 3=右`，COM 为 `1=上 … 4=右`，**相差 1**。写错通常不报错，只吸附到错误的边。
> 4. **L1–L4 已闭环（均基于 WPS 引擎）**；**L5 已由人工在 WPS 真机上拖动确认：端点跟随，且与自动化结果一致**。
>    **裁决 P-4（2026-10-03）：验证环境统一为 WPS——开发与门禁均以 WPS 为准，Microsoft PowerPoint 备查、不阻塞。**
>    因此 G1-a 的原判据"真机 PowerPoint 拖动"改由 **WPS 真机人工验证**承担，**G1-a 已闭合**。
>    代价：产品**不对外承诺** PowerPoint 下的跟随行为，需写入 README 已知限制。
>    完整结论与权衡见 [`spikes/g0-s1-pptx-connector/结论.md`](../../spikes/g0-s1-pptx-connector/结论.md) §七。
>    另一个必须记住的陷阱：**WPS 的 COM 自报 `Name="Microsoft PowerPoint"`、`Version="12.0"`**，
>    该字符串**不构成"用 PowerPoint 验证过"的证据**（本 spike 脚本一律用 `KWPP.Application` 创建实例）。

### Day 2 — 真机协议与补丁器
4. 真机（**现行口径：WPS**；Microsoft PowerPoint 备查）打开 fixture：**不得出现"需要修复"弹窗**。
5. **拖动任务条**，观察 connector 端点是否保持吸附并自动改道 —— 这是唯一有效判据。
6. 保存后 diff XML：编辑器是否重写了 `stCxn/endCxn` 或 `a:avLst`？**这个 diff 就是补丁器要生成的正确形态**（比任何文档都权威）。
7. Keynote 重复步骤 5 并记录（Keynote 已有反证，明确不保证）。
8. 实现最小补丁器：**运行时解析 `name → id`**（**不要硬编码 `id = idx+2`**，只把它当作可断言的实现细节），
   追加 `cxnSp`，断言无 id 重复、`idx` < 目标连接点数量。

### 通过门禁
| 门禁 | 判据 | 失败后的动作 |
|---|---|---|
| G1-a | 真机（**现行口径：WPS**）拖动后端点仍吸附并改道 | **connector 跟随卖点不可交付** → 折线降级方案成为产品形态，PRD 叙事需改（"可编辑形状"仍在，但"拖动跟随"删除） |
| G1-b | WPS 同样通过 | 正式下调 §8/§4.2 的"WPS 必过"承诺为"尽力兼容" |
| G1-c | group 首次打开即正确、无修复弹窗 | group 延后，改用扁平形状 + 命名约定 |
| G1-d | 无 id 冲突、无修复弹窗 | 补丁策略重设计 |

> **G1-a 的"真机"定义已变更**：原文指 Microsoft PowerPoint；已由 **裁决 P-4** 改为 **WPS 为准**。
> 本表保留原措辞并在此注明变更，以免与历史记录冲突。

**注意**：Keynote 已有反证（Apple 官方兼容矩阵：连接线 imported as straight lines），**不要把它当作失败**，但它必须从"尽力兼容"降级为"明确不保证"，写入 README。
**不要用 LibreOffice 通过作为成功证据**——合法 ≠ 路由正确（正确的 `stCxn/endCxn` 仍可能渲染出错误走向）。

## Spike-2：xlsx 影子表经第三方编辑器往返的存活率

**要回答的问题**：`__gantt_meta__` 在真实用户工作流（Excel → 保存 → 回传）后是否仍可用？"无损往返"承诺的边界在哪里？

> **执行状态（2026-10-03）：S2 已执行，且范围因 [T-2](裁决记录.md) 大幅缩小。**
> 影子表策略已废弃，因此原 G2-a（影子 payload 可解析）与 G2-c（隐藏态可用）**作废**，
> 原 G2-b（编辑后行键对账率）作废并被「**可见列逐字段语义相等**」取代。
> 结论见 [`spikes/g0-s2-xlsx-roundtrip/结论.md`](../../spikes/g0-s2-xlsx-roundtrip/结论.md)。
>
> **实测范围**：① ExcelJS 能否稳定读写本项目产出的**规范工作簿**；② WPS 打开后「**仅保存**」与
> 「**编辑后保存**」两种往返下，**可见列语义**是否仍可解析。**不含**影子表、隐藏态、行键对账。
>
> | 门禁（重定义后） | 判据 | 判定 |
> |---|---|---|
> | **G2-a** | 规范工作簿经 ExcelJS 写→读后与**声明式期望值表**逐字段相等；两条独立读取路径逐格一致；确定性成立 | **通过** |
> | **G2-b** | WPS「打开 → 仅保存」后可见列语义 100% 可解析且逐字段相等 | **通过** |
> | **G2-c** | WPS「打开 → 编辑 → 保存」后被编辑字段按新值正确读取、其余零漂移 | **通过** |
> | **G2-d（新增）** | Microsoft Excel —— **本机不可得 → 备查、不阻塞**（与裁决 P-4 同口径） | **备查** |
>
> **三处对上述协议的实测更正**（直接影响 G3 实现）：
> 1. **日期必须用 `Date.UTC` 构造**。ExcelJS 的序列号由**绝对时刻**推导
>    （`dateToExcel(d) = 25569 + d.getTime()/86400000`，源码核验），本地零点构造在 UTC+8 下落盘为
>    `46299.6667`，**Excel 显示前一天**（已现场取证）。
> 2. **不能比对数字格式码的文本**。WPS 会把 `yyyy-mm-dd` 转义成 `yyyy\-mm\-dd`——「仅保存」路径的
>    42 处落盘差异**全部**属于这一类，数值与类型未变；解析只能判「是否日期格式」。
> 3. **WPS 会重写整个容器**：11 个部件被重写/新增（`styles.xml` 2176→20577 字节、新增
>    `docProps/custom.xml`），但**不触碰任何单元格的值与类型**——「可见列自足」由此成立。
>
> **遗留**：Google Sheets 往返**本轮明确不做**（用户裁决，无本机自动化通道），仅记录；
> Microsoft Excel 为**备查项**（不通过、不失败、不对外承诺）。

### 步骤
1. 用 ExcelJS 生成含 `__gantt_meta__` 的样板文件（含任务表 + 依赖边表 + 视图状态 payload，带版本戳）。**先单独验证隐藏态**：ExcelJS 4.4.0 已知 bug 会导致隐藏表仍可见（issue #2911）——记录实际行为，必要时在 zip 层改 `workbook.xml`。
2. 走一圈真实往返，每条路径单独记录"名称/内容/隐藏态/公式缓存"四项存活情况：
   - Excel 打开 → 仅保存 → 回传；
   - Excel 打开 → **编辑若干行** → 保存 → 回传（关键路径）；
   - Google Sheets 导入 → 导出 xlsx；
   - WPS 打开 → 保存；
   - 用户手动删除隐藏表（模拟"清理工具"）。
3. 对每条路径记录：影子 payload 是否可解析、版本戳是否保留、**行键能否与可见表对账**。

### 通过门禁
| 门禁 | 判据 | 失败后的动作 |
|---|---|---|
| G2-a | Excel 仅保存路径：payload 100% 可解析 | 影子表方案整体不可用，退回"纯可见列语义"路线 |
| G2-b | 编辑后仍能对账（行键匹配率可量化） | 承诺改为"尽力还原"，并强制显示差异报告 |
| G2-c | 隐藏态可用（不裸露给用户） | 在 zip 层补丁，或改为"显式元数据表 + 文档说明" |

### 必须写入设计的结论（无论通过与否）
- **影子表是缓存，不是真相源**；可见列必须自洽，导入以可见列为准做行键对账。
- WPS / Numbers 的往返**不得对外承诺**，只能靠自有 fixture 把关。

> **S2 执行后的修订（2026-10-03）**：上一条随 T-2 一并收窄——
> 影子表删除后不再有「缓存/真相源」之分，**导入以可见列为唯一准据**；
> 「WPS 往返不得对外承诺」的原判据**被实测部分推翻**：WPS 的「仅保存」与「编辑后保存」两种往返
> 在本项目规范工作簿上**逐字段语义相等**，因此 S2 的 G2-b/G2-c 已判**通过**（口径为 WPS，
> 与 [裁决 P-4](裁决记录.md) 一致）。**Microsoft Excel 与 Google Sheets 仍未验证，不得对外承诺。**

## Spike-3：CPM 性能与"增量重算"的真实边界

**要回答的问题**：1,000 任务 / 1,500 依赖下，全量重算的真实耗时分布（p50/p99）是多少？拖拽期间"受影响子图传播"的真实耗时分布如何，10ms/帧能否作为通用保证？

> **执行状态（2026-10-03）：S3 已执行**，本目录见 [`spikes/g0-s3-cpm-perf/`](../../spikes/g0-s3-cpm-perf/)
> （结论：[结论.md](../../spikes/g0-s3-cpm-perf/结论.md)）。
>
> **口径**：主口径为 **Node 24.15.0**（与 CONTRIBUTING / CI 一致），Node 26.7.0 作记录；
> `p50/p95/p99` 取 **median-of-suites**（5 个 suite × 1,000 次迭代），并保留最差 suite 的 p99。
> **本 spike 只测 Node 侧内核**：浏览器/绘制侧的整帧预算未测，G5 必须复测（结论 §六.1）。
>
> | 门禁 | 判据 | 实测（Node 24 主口径） | 判定 |
> |---|---|---|---|
> | **G3-a** | 全量重算 p99 ≤ 100 ms @1,000/1,500 | 三个数据集 **27.8 / 49.1 / 52.1 µs** | **通过**（余量约 1,900×） |
> | **G3-b** | 非关键编辑传播 p99 ≤ 10 ms | **0.60 µs**（闭包 25 个任务）/ **0.55 µs**（闭包 26）；深链数据集中无浮动任务，按协议跳过并留痕 | **通过** |
> | **G3-c** | 关键路径编辑耗时被量化（预期不满足 10 ms） | 闭包传播 **0.8 µs**（27/1000）/ **27.1 µs**（**940/1000**）/ **2.0 µs**（89/1000）；松手后合并重算 p99 ≤ **60.3 µs** | **已量化**；"不满足 10 ms"**未出现**（10 ms 是含渲染的整帧预算，引擎侧只占约 0.3%） |
>
> **两处对上述协议的实测更正/补充**：
> 1. **必须做批量计时。** 本机 `hrtime.bigint()` 分辨率约 100 ns，而闭包传播只要 30–60 ns；
>    不按 `batchSize` 批量计时会把 p50 测成"等于分辨率"（判据见结论 §三.4）；
> 2. **负向对照必须绑在"闭包最大"的场景上。** 非关键编辑的闭包常只有几个节点，
>    在那个规模上 NC2/NC3 的比值会被噪声淹没（同机实测可在 0.5×–2× 间跳）；
>    本 spike 因此把对照绑到关键编辑场景，并把 NC3 阈值从 2× 下调到 1.5×（实测 2.8–3.4×）。
>
> **DoD 定标结论（详见结论 §四）**：三条门禁余量都在 ≥10× 档，建议 **G2 的 DoD 从"p99 ≤ 100 ms"
> 收紧到"p99 ≤ 1 ms @1,000/1,500"**（100 ms 保留为产品侧不回归天花板）；**EN-04 的改写理由需从
> "引擎算不动"改为"避免整表 DOM 重建"**——实测引擎侧在 1,000–5,000 任务规模上都不是瓶颈。
>
> **同时执行的两项验证基建**（对 R-4 的落地，G2 可直接复用）：
> ① **独立 Python 参照实现差分测试**（1,000 个随机 DAG + 200 个成环图，逐字段 0 不一致）；
> ② 手工推导用例 + 随机图不变量（1,000 张）+ 正确性/性能两侧的**负向对照**（证明判据有判别力）。

### 步骤
1. 先写**最小可用 CPM**（TS，纯函数、零 DOM）：正向/逆向两趟 + 总浮动/自由浮动 + 关键路径。日历按 D-4 口径（工作日、周一至周五 8h、项目时区日期基准）。
2. 造三组数据：
   - 宽而浅（大量并行、少层级）；
   - 深链（长依赖链，例如 1,000 节点单链）；
   - 密集交叉（跨层级、扇入扇出、含 10% 关键路径移动）。
3. 测三类操作的 p50/p99：
   - 全量重算；
   - 非关键任务改工期（局部传播）；
   - **关键路径任务改工期 / 增删依赖边**（预期引发 O(V) 位移）。
4. 单独测**常数因子**来源：日期运算、Map 查找、对象分配——确认瓶颈是算法还是实现细节。

### 通过门禁
| 门禁 | 判据 | 失败后的动作 |
|---|---|---|
| G3-a | 全量重算 p99 ≤ 100ms @1,000/1,500 | 引擎实现需优化（预分配、扁平数组、避免日期对象） |
| G3-b | 非关键编辑传播 p99 ≤ 10ms | EN-04 需进一步收窄适用范围 |
| G3-c | 关键路径编辑的耗时被量化（预期不满足 10ms） | **按 §5.3 的建议改写 DoD**：拖拽期只做日期传播，浮动/关键路径松手后合并重算（≤200ms），必要时移入 Worker |

### 预期结论（供对照，不作为预设）
总浮动全局耦合（并行链 A 变长会改变无关链 B 的浮动），因此 G3-c 大概率不达标。**这不是失败，而是把一条不可实现的 DoD 换成可实现的 DoD。**
