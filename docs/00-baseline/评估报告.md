## 0. 结论摘要（TL;DR）

**总体判断：产品定位与架构方向成立，但"一版 P0 全量 + 40 周"的排期不成比例；文档在三个"正确性关键"模块上把风险最高的假设写成了既定事实，缺少证伪实验。**

| 维度 | 评级 | 一句话结论 |
|---|---|---|
| 定位与差异化 | **成立** | "Excel 进 → 排程引擎 → 可编辑 PPTX 出"链路确实无成熟开源方案覆盖；PPTX 原生形状是真实卖点 |
| 架构设计 | **较好** | 计算层独立包 + 双投影 + 命令层唯一入口，是能被验证的好架构；三处概念未落到可实现的语义 |
| P0 范围 | **过大** | 6 大模块同时作为 MVP 必须项，等价于把"引擎 + 编辑器 + 三导出器 + 往返协议 + 持久化"全塞进 P0，无内部切分线 |
| 排期与产能 | **不作承诺** | 原文"约 40 周"无工时分解、无速度假设、无维护预算；**维护者已裁定不做严格排期**，故周数改为参考区间，改用"可验证出口条件"作为门禁（§7 D-1） |
| 技术假设 | **两项被证伪（已核验）** | pptxgenjs 4.0.1 **不支持 connector、也不支持 group**（源码级核验），EX-03 必须改写为"自研 OOXML 补丁引擎"；"≤10ms/帧增量重算"作为**通用保证不成立**（浮动时间全局耦合）；xlsx"影子表无损往返"仅在文件未被编辑时成立 |
| 需求可验收性 | **中** | 验收标准写得比一般 PRD 好（有数值），但日历/工期/约束/浮动等语义缺失，导致 DoD 不可判定 |
| 开源运营 | **缺预算** | M2 起 issue/社区时间未计入产能；成功指标与里程碑退出条件存在"营销结果当工程门禁"的循环 |

**三条最重要建议**

1. **先做三个证伪实验（spike），再冻结 M0 范围**：① PPTX 原生 connector 吸附 + group 坐标（最重要，决定卖点是否成立）；② xlsx 影子表经 Excel/WPS/Google Sheets 往返存活率；③ 1,000 任务 CPM 全量重算与拖拽重算的真实耗时曲线。三项各 1–3 天，产出"能/不能/需降级"的结论，直接决定 M0/M1 排期。**核验结果已把 ① 的判断从"要不要验证"变成"必须自研 XML 补丁并用真机拖拽试验证"（§5.1）。**
2. **给 P0 划一条可砍线**：把 P0 拆为 `P0-core`（引擎 + 单页甘特 + 拖拽 + SVG/PNG + xlsx 导入导出）与 `P0-extended`（PPTX 三模板、影子表无损往返、虚拟滚动 2000 任务），并明确 v0.1 只需 `P0-core + PPTX 模板 A`。
3. **补齐 5 个语义空白**（日历/工期单位、约束冲突策略、手动任务参与排程规则、浮动时间算法边界、IndexedDB 容量与快照保留策略）——这些是引擎开工的前置条件，见 §3.2。

## 1. 信息导入：需求与路线图结构化摘录

（结构化重建，用于后续追溯；内容忠于原文，标注了原文位置）

### 1.1 产品定义
- 定位：把 Excel 计划变成专业排程甘特图，一键输出**可编辑**汇报 PPT；单文档、本地优先、MIT。
- 用户：咨询顾问/交付 PM（导出质量优先）、中小团队 TL（轻量上手）、自由职业/乙方（单人闭环）。
- 价值主张：Excel 的轻 + Project 的引擎 + PPT 的出口。

### 1.2 非目标（原文 §2）
协作编辑；资源求解/资源均衡；企业级（项目组合/工时单/跨项目依赖）；`.mpp` 读写；规模承诺（≤2,000 任务/3,000 依赖）；Excel 公式与宏解释。

### 1.3 P0 能力清单（原文 §4.1）
| 模块 | 能力 |
|---|---|
| 数据模型 | WBS 树（自动编号/Tab 调级/折叠）、核心字段、4 类依赖 + lag、建边检环、无日期节点容错 |
| 调度引擎 | CPM 正逆向（ES/EF/LS/LF、总浮动/自由浮动）、关键路径高亮、增量重算、循环依赖阻断 |
| 视图渲染 | 条形/进度/里程碑/汇总条、左表右图、行内编辑、依赖连线（正交路由 + 类型箭头）、日/周/月/季缩放、虚拟滚动 |
| 交互 | 拖拽三语义、拖拽建线、撤销重做（手势级事务合并）、冲突即时提示 |
| xlsx 往返 | 缩进/编号双解析 + 向导、导出影子 sheet、round-trip 一致性、CSV 尽力导入 |
| 导出 | SVG（语义化）、PNG（多倍率）、PPTX 原生形状（模板 A/B/C） |
| 持久化 | 本地自动保存、本地快照/时间点恢复 |

P1：约束、手动/自动双模式、基线、筛选分组排序、PPT 主题跟随、MS Project XML 导入、键盘流、批量操作、可选云同步、飞书 L0/L1。
P2：网络图、资源直方图、成本字段、多基线、自定义字段、任务拆分、打印分页、PWA、飞书 L2/L3、插件。

### 1.4 路线图（原文 §15–16）
| 阶段 | 周期 | 主题 | 里程碑 | 退出条件 |
|---|---|---|---|---|
| M0 | W1–12 | 引擎与编辑器 | 仓库公开 | 黄金测试 100% 过；性能基准达标；本人日用 |
| M1 | W13–20 | 三导出 + xlsx 往返 | v0.1 首发 | US-1/2/3/4 走通；种子用户反馈回收 |
| M2 | W21–28 | 分发与部署形态 | v0.5 公测 | Demo 上线；npm 三包发布；指标达标 |
| M3 | W29–40 | 互操作/稳定/社区 | v1.0 | XML 导入；飞书 L0；社区基建完备 |

每阶段内置降级序列（M0：仅 FS → 去动画 → 虚拟化阈值降到 500；M1：模板 B/C 延后 → 主题跟随延后 → 锁 16:9；M2：筛选分组延后 → 基线延后 → 只发 engine 包；M3：飞书 L0 延后 → XML 收窄至 FS → 案例转问卷）。

### 1.5 技术架构约束（原文 §7）
8 层分层；三条铁律：计算层独立零 DOM 依赖、双投影（渲染/导出）共享几何、本地优先。技术栈建议 TS + React + pptxgenjs + ExcelJS + 纯静态部署；运行时依赖必须 OSI 许可并记入 `THIRD_PARTY_NOTICES`。

## 3. 需求可实现性审查（语义缺口）

### 3.1 已具备的良好验收质量
有数值门槛（≤100ms、≤10ms/帧、≤5s 自动保存、≤3 步向导、30fps）、有兼容矩阵（Office 2016+/365/WPS 必过、Keynote 尽力）、有 golden 比对意图、有降级序列。这在同类文档中属于上游水平。

### 3.2 会导致"无法开工/无法验收"的语义空白

## 4. 路线图与产能独立评估

### 4.1 产能口径不可验证
原文给出"约 40 周""每阶段内置 20% 缓冲""全职单人 + AI 辅助"，但**没有任何工作量分解单元**（人时/人日/故事点），也没有 AI 加速率的量化依据（"UI 3–5×""算法低"是直觉判断）。因此：

- 40 周**既无法被证实也无法被反驳**——这不是估算，是期望；
- 20% 缓冲是否已含在 40 周内**表述不明**（原文"总口径约 40 周；每阶段内置 20% 缓冲"两种读法都通），按最不利读法，实际承诺可能只是 40 周本身；
- **维护者已明确：个人项目、不做严格排期（§7 D-1）。** 因此本文对该项的结论收敛为：**删除以周为单位的承诺**，保留"能力顺序 + 可验证出口条件"；周数仅在需要对外沟通时作为区间参考，不作为自我考核指标。

### 4.2 范围与产能不成比例（主要风险）
P0 六个模块实际上是四类**互相独立的高难度工程**：
1. 排程引擎（正确性关键，AI 加速低）；
2. Canvas/SVG 混合渲染 + 虚拟滚动 + 拖拽状态机（工程量最大）；
3. xlsx 双解析 + 影子表无损往返（脏数据长尾无底洞）；
4. PPTX 原生形状/connector/group 生成（OOXML 细节，AI 加速低）。

按原文自述，其中 3 项属于"AI 加速低、靠人调试"的类别，而这三项恰好是全部 P0 的核心。**结论：在没有任何一个模块先落地验证速度之前，用 40 周承诺这三项 + 全部 P1 的一半（M2 塞入约束/手动模式/基线/筛选分组），风险显著偏高。**

### 4.3 降级序列的有效性评估
降级序列存在，是加分项，但存在两个问题：
- **降级项都在外围，不在主链路**：M0 可砍到"仅 FS"，但 FS 也是引擎；M1 可砍模板 B/C，但 PPTX 模板 A 是卖点本身。**没有一条降级路径能在"PPTX connector 用 pptxgenjs 做不出来"时救场**——那才是真正的单点失败；
- **降级未与里程碑退出条件对齐**：M3 退出条件含"飞书 L0"，而降级序列允许"飞书 L0 延后至 v1.x"，即 v1.0 可在不满足退出条件的情况下发布。需明确**哪个是硬门禁、哪个是愿望**。

### 4.4 成功指标被当作工程门禁（逻辑循环）
§10 明示"参考线非承诺"，§15 却把"指标达标"写进 M2 退出条件。开源 star/周活/外部 PR 是**营销与社区结果**，不是工程可控产物。若照此执行，M2 可能因"star 没到 800"而无法退出，进而挤压 M3。
**建议**：把 M2/M3 退出条件改为**可控交付物**（Demo 可访问、三包发布、测试覆盖、文档齐备），指标降级为"发布后观察项"，与阶段门禁解耦。

### 4.5 未计入的产能消耗
- **社区维护**：M2 起 issue 响应 SLA"< 48h"（§10）需要每周固定时间盒，但产能模型只算"构建"不算"维护"；
- **行政流程**：飞书 L0 提审预留 4 周已识别（加分），但"市场入口 7 日留存优于其他入口"作为 L1 进入条件是**数据依赖型门禁**，在无入口前无法测量——属于循环条件，建议改为时间盒；
- **测试与 CI 基建**：原文把 CI 全绿列为硬门槛，但 M0 W1–2 的工作项里只写"数据模型/引擎 v0/仓库与 CI 护栏先行"，**测试框架与 CI 流水线的搭建本身是工作项**，宜显式列出。

### 4.6 里程碑排期的一个具体紧张点
M1 的 W13–17 要在 5 周内完成"双投影 + SVG/PNG 导出 + PPTX 形状引擎（模板 A）+ 三端手动兼容测试"，而 PPTX 形状引擎恰是文档自认的"AI 加速低"类别。这与 M0 用 12 周做引擎 + 渲染 + 拖拽相比，**单位时间内的难度密度明显更高**。建议把 PPTX 形状引擎的 spike 提前到 M0（见 §5）。

## 5. 外部技术假设核验（已完成，含证据）

> 核验方法：下载并检索 pptxgenjs 4.0.1 实际发布包源码与类型定义；查证 ExcelJS/SheetJS 仓库 API、issue、registry 与安全公告；引用第三方性能实测与算法文献。以下结论**推翻或修正了原文的两项既定假设**。

### 5.1 PPTX 原生形状 / connector 吸附 / group —— **原文假设被证伪**

| 原文要求（§4.2 EX-03） | 核验结论 |
|---|---|
| 任务条 = 圆角矩形 `roundRect` | ✅ 原生支持 |
| 里程碑 = 菱形 preset | ✅ 原生支持 |
| 依赖 = connector 且**吸附连接点**、拖动时跟随 | ❌ **pptxgenjs 不支持**。4.0.1 产物中只有 `<p:sp>`，全包检索 `cxnSp`/`stCxn`/`endCxn` **零命中**；维护者明示 "The library does not currently support connectors"（[#527](https://github.com/gitbrent/PptxGenJS/issues/527)），相关 PR [#777](https://github.com/gitbrent/PptxGenJS/pull/777)/[#1059](https://github.com/gitbrent/PptxGenJS/pull/1059) 至今未合并 |
| 父子 = group（局部坐标换算正确） | ❌ **pptxgenjs 无 `addGroup`**。维护者称"将在 v4.0 提供"（[#307](https://github.com/gitbrent/PptxGenJS/issues/307)），而 v4.0.0 已发布但未兑现 |
| 兼容矩阵：Office 2016+/365/WPS 必过 | ⚠️ **WPS 无任何可信一手证据**，属最大未验证假设。Keynote 已有反证：Apple 自家兼容矩阵写明连接线"imported as straight lines"（[Apple](https://www.apple.com/ca/keynote/compatibility/)）——即 Keynote 不保留吸附语义 |
| 降级预案：connector 异常退化为折线形状 | ✅ `custGeom` + `points` 可用于折线，降级路径技术上存在 |

**结论**：`EX-03` 不能再作为"选用 pptxgenjs 即可实现"的条目，应改写为**"自研 OOXML 补丁引擎"**这一独立工程量（估 1–2 周，含 golden 文件）。可行性判断依据：pptxgenjs 的 shape id 生成规则确定（`idx+2`）且 `shapeName` 可映射 name→id，因此可在 zip 层重写 `ppt/slides/slideN.xml` 注入 `<p:cxnSp>`；`pptx.write({outputType:'uint8array'})` + JSZip 已具备管道。
**残留风险**：**"合法"不等于"路由正确"**——正确的 `stCxn/endCxn` 仍可能渲染出错误的折线走向（[python-pptx #946](https://github.com/scanny/python-pptx/issues/946)）。因此"用 LibreOffice/能打开无报错"不能作为通过标准，**必须在真机 PowerPoint 里拖动任务条验证吸附**。

**建议的 2 天证伪实验（通过/失败门禁明确）**
- Day 1：手写最小 fixture（2 个 roundRect + 1 个 `bentConnector` 并写 `stCxn/endCxn`、1 个菱形、1 个含 2 子形状且 `off/ext` 与 `chOff/chExt` 均正确的 `grpSp`），复用 pptxgenjs 产物作容器并在 zip 层打补丁；同一几何再用 `custGeom` 折线出一版用于视觉对比。
- Day 2：真机 PowerPoint 2016/365 打开 → 应无"需要修复"弹窗 → **拖动任务条，观察端点是否仍吸附并自动改道** → 保存并 diff XML（PowerPoint 重写了什么，就是补丁的目标形态）；同法在 WPS / Keynote 记录通过与否；再实现最小补丁器（`shapeName` → `id = idx+2`，追加 cxnSp，断言无 id 重复且 `idx` < 目标连接点数量）。
- 门禁：(a) 真机拖动后端点仍吸附；(b) WPS 同样通过，否则**正式下调"WPS 必过"这一承诺**；(c) group 首次打开即正确、无修复弹窗。**若 (a) 失败，connector 跟随这一卖点不可交付，折线降级方案即成为产品形态——必须在 Day 2 定，而不是第 3 个月定。**

### 5.2 xlsx 影子表往返与库选型

**库选型**
- **ExcelJS = MIT**（确认）。但原文对 SheetJS 的理由不准确：**SheetJS CE 是 Apache-2.0，不是许可受限**；真正的问题是 npm `xlsx` 停留在 0.18.5、带弃用提示、且 ≤0.19.2 存在 CVE-2023-30533（原型污染），GitHub 公告明确"npm 上找不到非易受攻击版本"（[GHSA-4r6h-8v6p-xvw6](https://github.com/advisories/GHSA-4r6h-8v6p-xvw6)）。**结论不变（避开 npm `xlsx`），但理由要改为"停止维护 + 已知漏洞"。**
- ExcelJS 自身维护偏弱：最新发布 v4.4.0（2023-10-19）、**813 个开放 issue**；浏览器包体 **932 KB min / 256 KB gzip**，对"纯前端静态部署"是实打实的负担。
- 替代方案各有硬伤：`node-xlsx` 依赖被冻结的 `xlsx`；`write-excel-file` **只写不读**；`fflate` + `unzipit` + 手写 OOXML 是唯一干净出路但要自研读取器；`@e965/xlsx` 等为第三方转发的 0.20.3，有供应链风险。
- 已知能力边界：仅 XLSX/CSV，**不支持 `.xls`(BIFF)**（面向"用户手里很脏的旧文件"是真实风险）；条件格式相关 bug 长期未合（[#3015](https://github.com/exceljs/exceljs/issues/3015)、[#2803](https://github.com/exceljs/exceljs/pull/2803)）；不重算公式缓存值，需 `fullCalcOnLoad`。

**影子表往返**
- `__gantt_meta__` 名称合法；Excel 会保留 `hidden`/`veryHidden`。
- ⚠️ **但 ExcelJS 自身隐藏态写入有 bug**（[#2911](https://github.com/exceljs/exceljs/issues/2911)：设为 hidden 后仍显示）——影子表可能以可见标签页交付，需在 zip 层修 `workbook.xml`，或显式纳入测试项。
- Google Sheets 不尊重 `veryHidden`，会**显示**该表并丢弃公式缓存值；WPS/Numbers 往返**无可信证据**，只能靠自有 fixture 把关，**不应对外承诺**。
- **原文未识别的设计缺陷**：所谓"无损"仅在用户**未编辑**时成立。一旦用户在 Excel 里改动行，影子 ID 与依赖边表即与可见表错位。**行键对账（row-key reconciliation）才是这类设计真正崩掉的地方。** 建议：影子表定位为**缓存而非真相源**，可见列必须自洽，payload 带版本戳，导入时以可见列为准做对账。

### 5.3 CPM 性能与"增量重算"的真实边界

- **全量 ≤100ms：成立**。CPM = 两次 O(V+E) 遍历；参照原生 Zig 拓扑排序 10 万节点 + 4 千边仅 18ms（[benchmark](https://github.com/williamw520/toposort/blob/master/README.md)），1,000/1,500 在 JS 下为个位毫秒量级。风险不在算法而在常数因子（日历/日期运算、Map 查找、分配抖动）。
- **"增量重算 ≤10ms/帧"作为通用保证：不成立**。总浮动**全局耦合**：两段并行链 A、B，把 A 拉长以致项目终点右移，B 的总浮动随之改变，而 B 既非 A 的后继也非其前驱。ES/EF 依赖祖先、LS/LF 依赖后继，浮动需要两次遍历；任何使项目完成日移动的编辑都会引发 LS/LF 的 O(V) 位移。增删依赖边还等价于动态图拓扑序维护，最坏 O(V)（[Pearce & Kelly, JEA 2007](http://www.doc.ic.ac.uk/~phjk/Publications/DynamicTopoSortAlg-JEA-07.pdf)）。另外 16.7ms 帧内 10ms JS 只余约 6ms 给样式/布局/绘制，且均值掩盖 p99 尖峰。
- **建议改写 DoD**：`EN-04` 改为"**拖拽期间只做受影响子图的日期传播**（非关键编辑 ≤10ms/帧）；**浮动与关键路径在松手后合并重算**（≤200ms）；关键路径移动时允许降级为合并重算或移入 Worker"。这既保留可测性，也避免写一个必然违约的指标。

### 5.4 虚拟滚动与 Canvas/SVG 混合

- 虚拟化结论成立：第三方实测 5,300 行从 94,920 个 DOM 节点/约 2.1s 首屏，窗口化后降到 2,115 节点/约 1.1s（[LeanZero](https://dev.to/mihai_leanzero/leanzero-management-virtualising-a-5300-issue-gantt-33c1)）。1,000 行 ≤1s 合理。代价：破坏浏览器查找页内文本、需 `aria-rowcount/rowindex`、需固定行高、滚动容器（非视口）驱动窗口。
- ⚠️ **真正的悬崖是 SVG 依赖线**：同一实测中 2,200 条边（8,800 个节点）在**行已虚拟化**的情况下，10× 滚轮滚动仍耗约 2.0s。因此 `VW-05/VW-06` 必须把**"行窗口 × 边跨度求交裁剪"设计成第一性要求**（仅按端点裁剪会错误隐藏长箭头），且裁剪先于几何计算，拖拽期不做逐帧 DOM 复用。
- 同步陷阱：两层必须统一用**模型坐标**（overlay 内禁止 `getBoundingClientRect`）；`scrollTop` 需扣除固定表头高度；可见窗口只能有一个真相源；overlay 需 `pointer-events: none`（路径除外）否则 Canvas 拖拽失效；两层各自处理 DPR/缩放。
