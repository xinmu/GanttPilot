### P-33 G6 的落地口径与两项待定的定值

**一并定下的三件事**（都是 G6 开工前置里点名"排期时须一并定"的）：

1. **复核口径 = 打包产物**（沿用既有纪律）：全部记录制证据与人工复验都在 `pnpm build` 之后跑；
   `pnpm dev` 的数字不进证据（`P-24` 遗留的"两种口径"由此不再悬空）。
2. **检查点触发条件与保留份数**（收口待定清单 §七）：**每 5 分钟 / 每 200 条命令 / 关闭（隐藏）时**、
   **保留 3 份**；配额超限降级为**只保留 1 份**并提示。数值住在 `packages/engine/PERSISTENCE.md` §二
   （由 spec 断言），**形状**住在 ADR 0009——因此调值不需要新 ADR。
3. **「`scroll` 敏感量」盘点**（收口待定清单 §四，P-25/P-32 点名"要在 G6 之前"做）：
   只读盘点 13 处消费者，逐条给出基准，结论是**动作面为零**（未发现第 5 个同族缺陷），
   并把不变量落在 [`packages/render-core/SPEC.md`](../../packages/render-core/SPEC.md) §九：
   **只有 `pointerFromClient` 叠加 `scroll*`；其下游至多做平移 / 窗口换算 / 抵消负号**。
   证据：[`apps/web/evidence/scroll-consumers-audit.md`](../../apps/web/evidence/scroll-consumers-audit.md)。

**落地期被抓出来的两条实现不变量**（写进 `PERSISTENCE.md` §四，且都由实测逼出）：

- **写入量**：增量部分的体积与文档规模解耦（2,000 任务：整份 623.4 KB / 1.4 ms 对增量记录 0.15 KB /
  0.3–0.8 ms）；同时**诚实登记**——记录里的 `base` 带整份基线快照，基线建立之后每次写入含一份固定基线体积，
  把它改成"存储引用"属 v0.5 的优化。
- **整份替换文档必须重定基线**：实测缺陷——换夹具后基线仍是上一份文档的快照，于是每次写盘都把旧文档带上
  （记录 316 KB，而当时的文档只有 300 KB 级）。产品上对应"导入 / 恢复换了整份文档"。

**出口条件的判定**（数字与口径见 [首版-记录-G6-G8](../01-roadmap/首版-记录-G6-G8.md)）：

| 出口条件 | 判定 |
|---|---|
| ① 自动保存 ≤5s 且拖拽期间不产生可见掉帧 | **通过**（打包产物、开/关两组同尺：帧间隔 p95 **17.0/17.1 ms**、拖动期写入 **0**、松手→落盘 **4.9 ms**） |
| ② 会话内可逐步撤销 ≥50 步、LIFO 正确 | **通过**（`persistence.spec.ts`，进 `pnpm gate`；含跨检查点与重做栈） |
| ③ 强制杀进程后重开恢复到最近检查点 | **通过**（Node 侧 killsim + 记录制真机；按 ADR 0009 §8 的**字面**口径：不早于最近检查点） |
| ④ 2,000 任务文档的存储占用与写入耗时实测 | **通过**（记录制：整份 623.4 KB、增量 0.15 KB、put p50/p95 0.3/0.8 ms、用量 251 KB） |

**明确留给后续的**（登记避免"看起来已完成"）：

- 把检查点基线改成"存储引用"以消掉那份固定基线体积（v0.5 的写入量优化）；
- 多标签**合并**（本块只做"互斥停写 + 提示"，合并是非目标 NG-01）；
- 会话锚点 / 滚动位置 / 档位的跨会话恢复（ADR 0009 §6 明确不做，写入 README 已知限制）。
