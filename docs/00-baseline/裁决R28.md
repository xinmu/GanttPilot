### P-28 批次 C 的落地与两条口径

**1. 事实（本轮实测）**：复核的两项是同一个根因的两面——**应用层把"版本变化"当成了"用户正在编辑的那个值变了"**：

- `notice` 只在新的 `show()` 或下一次失败时被覆盖，**成功的 `undo()`/`redo()` 不清它**：空栈时按 `Ctrl+Z`
  得到的「命令被拒绝：`SESSION_NOTHING_TO_UNDO` —— 没有可撤销的步骤」会一直挂在状态栏上，
  即使栈里随后确实有了可撤销的东西（复核 9.2）。注意工具栏按钮带 `:disabled="!canUndo"`，
  **只有快捷键那条路能触发该失败**；
- `TaskTable` 的 `watch(revision) → cancelEdit()` 让**任何**版本变化都关掉输入框（连同用户敲了一半的草稿）：
  别的任务被拖动、别的列被改，都会把编辑态打掉——"编辑态优先"（ADR 0008 §10）事实上不成立（复核 9.1）；
- 该判定**此前没有任何判据**：`apps/web` 的 spec 数为 0，根 `vitest.config.ts` 只收 `packages/*/src`，
  因此这类"入口层算出来的输入"只能靠人工复核发现（P-21 §4 的结论在本轮再次成立）。

**2. 裁决**：把可判定的部分迁进 `packages/render-core`（落点即门禁，P-19 §5 ②）：

- `rawCellText({ document, taskId, column })`：该任务该列的**原始字段文本**；任务不存在 ⇒ `undefined`，
  字段缺失（`null`）⇒ `''`，派生列（`wbs` / `predecessors`）⇒ `''`。它同时取代了 `apps/web` 私有的 `rawOf`
  （**同类信息只有一处陈述**，P-27 §2）；
- `isEditStale({ before, after, taskId, column })`：该任务该列的原始值在两个版本间**真的变了**才为真；
  编辑态的观察点由 `revision` 数字换成**文档身份**（`document`），取消条件由本函数判定；
- **成功的 `undo()` / `redo()` 清提示**（`applyCommandResult` 的 `clearNoticeOnSuccess`，只有这两个调用点传 `true`）
  ——与 `useProject.commit()` 成功即清 `lastFailure` 同口径：提示描述的失败已被这一步推翻。

**3. 本轮新登记的两条口径**（后续实现不得各自另定）：

| # | 口径 | 理由 |
|---|---|---|
| ① | 比较的是**原始字段文本**（`rawCellText`），**不是** `cellText` 的显示值 | 编辑框的草稿种子本来就是原始值；派生显示值（`end` 的 `≈…`、`wbs` 的 `outlineNumber`）与"被编辑的字段"无关，比显示值会把"只有派生显示变了"误判为陈旧 |
| ② | **只用一条规则：值变即取消**。行被折叠隐藏或滚出渲染窗口**不算**变化（草稿保留，行回来后输入框复活） | 与今天"滚出/滚回"的既有行为一致（滚动不改 `revision`，状态不随 DOM 消失而清）⇒ **不新增行为类别**；且这正是"编辑态优先"的字面含义 |

**4. 执行顺序（本轮判定，替代此前"入口在待定清单"的悬置）**：**`C → B → G6`**。

- `C` **必须先于 `G6`**：它改的 `App.vue` / `TaskTable.vue` 正是 G6"跨会话恢复"必然要接的那一处
  （恢复后撤销栈与提示的状态、编辑态如何处置），先落 C 可避免同一处改两遍；
- `B` **排在 `G6` 的出口条件①之前**：批次 B 会给行加端点手柄（[P-21](裁决记录.md) §3 原文点名它属
  "G5 若给行加交互热区必须另加常数"那一类），**重定 `ELEMENT_MODEL_G5.overlay` 与 `c₄`** ⇒
  G6 出口条件① 的"拖拽期间不产生可见掉帧（需实测证明）"若先测、B 后落，数字必然作废（先例：
  两栏布局改动后由 P-23 同轮刷新 `drag-timing` 证据）；
- `B` 不是 `G6` 的**硬前置**：[待定清单](../01-roadmap/首版-待定清单.md) 里 B/C 的归属只写"G5 返工"，
  而"要卡在 G6 之前"的项（`scroll` 敏感量盘点）是**显式标注**的 ⇒ 本条顺序是按耦合关系判的，
  不是从文档字面推出的；
- **不阻塞的合法路径**：`B` 的契约修订（ADR 0008 §5/§7/§11 + `DRAG_EDGE_PX`）与 `G6` 的新契约
  （ADR 0009 持久化）**并行起草**，代码按 `C → B → G6` 落 ⇒ "契约先行"不会变成串行等待。

**5. 与既有裁决/ADR 的关系**：

- **不取代、不修改**任何 `Dn/Rn/Tn/Pn` 条目；`P-21` §3 的批次 C 原文**一字未改**（本条的"落地"是它的执行）；
- **不改 ADR 0008 正文**（P-21 §3 写明批次 C「是否改契约：否」）：§10 的"编辑态优先"是既有契约，
  本批只是让它在事实上成立；增补一句口径的需求若出现，走 ADR 0008 附录的增补节；
- **不放宽**任何 DoD（`c₁`–`c₄`、文档 schema、诊断码表、性能判据全部不变）；**G5 的五条出口条件勾选保留**，
  状态行加注"批次 C 待人工复验"（手法同 P-21 §5.4 的星号）；
- 与 [P-27](裁决记录.md) §2 的分层一致：判据登记在 [`render-core/SPEC.md` §九](../../packages/render-core/SPEC.md)，
  落地动作登记在记录层，未决项仍只进[待定清单](../01-roadmap/首版-待定清单.md)。

**6. 代价（明确接受）**：

- **提示清空是窄口径**（只认成功的 `undo()`/`redo()`）：若用户在"没有可撤销的步骤"之后**只做了编辑**，
  那句提示仍会停留；更宽的口径（"任何成功命令都清失败提示"）与 `lastFailure` 的既有语义更一致，
  但**超出 P-21 原文**，列为遗留候选（见下）；
- **DOM 层仍无判据**（输入框是否真的还在、提示是否真的消失）：`apps/web` 没有判据入口，
  只能人工复核（M1–M5）；这是 P-19 遗留 3 / P-21 遗留 4 的既有缺口，本批不擅自引入测试框架（依赖准入需单独裁决）；
- `ELEMENT_MODEL_G5.overlay` 与 `c₄` 的调整**推迟到批次 B**，G6 出口条件① 的实测因此必须等 B 落地。

**第二十八轮遗留待定**

1. **批次 B（R3/R4 + `c₄` + `DRAG_EDGE_PX`）**：按 [P-21](裁决记录.md) §3 原样保留，等一次 ADR 0008 修订
   （入口选型：端点手柄 vs gutter 连点；`DRAG_EDGE_PX = 6` 是否连同 `c₄` 一起调）——入口仍在[待定清单](../01-roadmap/首版-待定清单.md) §一；
2. **提示清空的加宽口径**（候选：任何成功命令都清失败提示）＝ 台账 **`P-29`**（**未决**，
   见[首版-待定清单](../01-roadmap/首版-待定清单.md) §三）；
3. **批次 C 的人工复验（M1–M5）**：待维护者按记录层的表逐条确认，报文补进[首版-记录-G5](../01-roadmap/首版-记录-G5.md)
   的「批次 C 的返工」；**未复验前不构成可用性承诺**；
4. P-24/P-25 的其余遗留项（会话锚点形状、`--align` 的档位/视口盲区、`apps/web` 判据入口、复核流程口径）不变。
