### P-41 记录制的两处补强

**0. 一句话问题陈述。** 这两行都不是能力缺口，而是**记录制自身的可信度**：

- **问题一 = 判据没覆盖"机制被激活"的区域**：`--align` 只跑日档 + 固定视口 ⇒ 月档的 3 px 条
  （[ADR 0008 §16.1](../02-adr/0008-列身份所有权与拖拽交互契约.md) 的 `edgePx` 收缩）、命中容差、
  以及**尺寸变化之后**的重算（R6 家族）都没有读数；
- **问题二 = 取证时刻没有判据守着**：滚动后的读数取在"`nextTick` + **两帧**"这个**无人守的常量**上，
  换浏览器/换节流策略时它会静默给出**假红或假绿**。

批次①（[P-40](裁决R39.md)）把**应用层的判定**押在 `smoke:build` + 记录制上之后，"这条防线可信"就成了前提。

**1. 覆盖度：判"判据的前提"（`diagnoseScrollCoverage`）。**

| 项 | 内容 |
|---|---|
| 问题 | 探测位置取绝对像素 + 一个"超大值"（`9_999_999`）让浏览器夹到 `maxScroll`。**当内容整幅不滚动时**（周/月档的小文档：`contentWidth ≤ 窗格宽`），那两个位置被夹回 `0`，与 `(0,0)` **完全等价** ⇒ 探针输出"6 位置全绿"，而**横向什么都没测**——R12（轴的横向双重偏移在 `scrollLeft = 0` 处恒为 0）的同族形态 |
| 修法（两层） | ① **位置改为比例**（`0 / 0.5 / 1` 的两个方向组合，共 6 个），在**钩子内**按真实 `maxScroll` 解析成像素（`ALIGN_POSITION_FRACTIONS` / `ALIGN_FRACTIONS`）；② **覆盖度本身做成判据**：整次测量必须有横向与纵向行程，否则 `no-horizontal-travel` / `no-vertical-travel` ⇒ **判失败**，并报出"请求非 0 却被夹回 0 的位置数" |
| 判据位置 | `render-core/align.ts`（纯函数、**进 `pnpm gate`**）：`diagnoseScrollCoverage(facts)` 收"请求 vs 实际"对；`summarizeAlignment(verdicts, coverage?)` 把覆盖度并进 `ok` 与机制集合 |
| 口径 | **"没测到"不能记成 ✅**（P-12"缺失即失败，不静默跳过"）。一次无法激活机制的测量只能记成"这次测量不构成该方向的判据" |

**2. 档位：把"机制被激活的区域"扩到周/月档。**

| 项 | 内容 |
|---|---|
| 问题 | `--align` 只跑日档。而 `pxPerDay` 变小会让条宽进入 **3 px** 区——`edgePx = min(6, max(0, (条宽 − MIN_MOVE_ZONE_PX) / 2))` 正是为它定的（[P-32](裁决R31.md) §16.1），命中容差 `HIT_TOLERANCE_PX = 2` 也在边界上。门禁侧有 `interaction.spec.ts` 的纯函数断言，**打包产物上零读数** |
| 修法 | `--align-zooms=day,week,month`（默认全档）；钩子新增 `zoom` 选项，走**用户点工具栏的同一个** `chart.setZoom`（`App.vue` 的 `alignHost.setZoom`，不另开测试后门）。**请求了档位却没接线时显式失败**，不静默回退日档 |
| 成本 | **不需要重新导航**：`--align` 不是计时测量（主口径因"自就绪起"会被前一档污染才必须每档导航）；三个档位共用一次导航 ⇒ 成本是"多两组采集" |

**3. resize 迁移：覆盖 R6 家族里唯一没被覆盖的那一半（`diagnoseResizeMigration`）。**

| 项 | 内容 |
|---|---|
| 问题 | 几何里有相当一部分来自**被测量出来的尺寸**（`paneHeight` ← `ResizeObserver`）。P-23 的只读诊断**排除**了"挂载时测量时机"这一个候选，但**"尺寸变化之后"从未被测过**：`--align` 一次运行固定视口，主口径每档也是新导航固定视口，ADR 0007 §11 的锚值干脆定义在 1280×640 上 |
| 形态 | **同一次导航内**：基视口 → 设滚动到**行程中点**（`keepScroll: true`，**不复位**）→ `Emulation.setDeviceMetricsOverride` 改视口 → **不重设滚动**、只 `reread` 一次 |
| 判据 | ① **前提自证一**：窗格尺寸**真的变了**，否则 `resize-not-observed`（"没变"不能与"变好了"共用一个绿）；② **前提自证二**：滚动位置**活下来了**（实际读到 0 ⇒ 覆盖度判失败 ⇒ 该轮不构成判据）；③ **迁移本体的自洽性复用同一份机制表**（`pane-measure-stale` / `table-body-height-mismatch` / `svg-box-not-1to1` / `scroll-out-of-sync` / 行差 / 空白带）——**不新开机制码** |
| 落地时当场踩到的坑 | 第一版把 `before` 那一轮也按"只读"复位了滚动 ⇒ 迁移后读到 `0·0`，而**机制恰在 0 处不可见**（同一个陷阱的第三次出现：R12 → P-22 遗留 1 → 本轮）。修法：`keepScroll` 显式豁免 + 位置存活性前提自证。**这条被证据表直接抓住**（"迁移前滚动位置 11479·5119" 一栏） |

**4. 稳定读数：把"取在应用处理完之后"做成判据（`settleStableRead`，**全仓唯一实现**）。**

| 项 | 内容 |
|---|---|
| 问题 | 旧口径是"设 `scrollTop` → `nextTick` + **两帧**"（P-23 遗留 6）。这个常量**不在门禁里、也不在判定里**：rAF 被节流、或应用一帧做不完时，读到的是"状态已变、DOM 未变"的中间态 ⇒ **假红**（把"没画完"读成"没对齐"）或**假绿**（旧值恰好通过），且不会报警 |
| 修法 | 每帧读一次**指纹**（DOM 真值 + `ViewModel.scrollTop/Left` + `contentWidth` + 前 3 行行中心 + spacer 尺寸），**连续两帧一致**即止；到 `STABLE_READ_BUDGET_FRAMES = 12` 帧仍不一致 ⇒ `stable: false` ⇒ 调用方**判红**（"读数在 12 帧内未稳定"）。**快路径仍是 2 帧** ⇒ 正常运行零额外开销 |
| 为什么指纹里含 `ViewModel.scrollTop/Left`（②-γ 的安全子集） | "应用已应用该滚动位置"的最强信号是应用自己的状态，但它**不能单独作为终止条件**——那会把"应用真的不同步"读成"还没轮到我"，从而**掩盖**真缺陷（而 `scroll-out-of-sync` 正在断言这件事）。它只作为指纹的一部分 |
| 共用范围 | `--align` 的每个位置 + **`--drag` / `--persist-drag` 的初始滚动**（它们随后就派发指针事件、读 DOM 几何，属同一类"读数是判据"的场景）。**主口径刻意不换**——两条理由见 §9 |
| 结论 | "等待值"从**魔法常量**变成**判据**：不稳定就是失败，而不是静默取第二个帧 |

**5. 负向对照（三条，全部临时变造、跑完即还原；工件在 gitignore 的 `tmp/nc-evidence/`）。**

| # | 变造 | 必须变红 | 实测 |
|---|---|---|---|
| ① | **完全不等**（`settleStableRead` 直接返回）：读数取在"状态已变、DOM 未变"的中间态 | 必须有机制现形 | **6 个位置里 5 个红**，机制 = `scroll-out-of-sync`（DOM 已滚、`ViewModel` 未跟上）⇒ **等待是判据的承重件**，不只是文案 |
| ② | **位置全取 0**（比例 `(0,0)` ×6） | `no-horizontal-travel` / `no-vertical-travel` + 整体失败 | 行对齐仍全绿（最大行差 **0.000 px**）而整体 **❌**、退出码 1 ⇒ 这正是旧口径会写成"✅"的那次**假绿** |
| ③ | **resize 到同一尺寸**（`--align-resize=1280x800`） | `resize-not-observed` | 窗格 374×587 → 374×587、Δ `0 × 0` ⇒ 前提自证 ❌、整体 **❌**、退出码 1 |

**8. 两处"想当然"的处置（都由本轮自己撞出来，记下来比结论更重要）。**

**(a) 主口径为什么不换等待实现（§4 的例外）。** 落地时先把稳定性自检也加进了主口径的 `paintOnce`
（放在 `frameMs` 计时**之后**、耗时从滚动墙钟里扣掉），结果**两路互证当场变红**：

```
[measure] dense/day：errors: 实际 DOM 与元素模型不一致：DOM 行/边 = 15/14，模型 = 30/41
```

`15/14` 是**演示计划**的规模，而模型是 `dense` 夹具。根因：`runMeasurement` **不把夹具装进应用**——
它自己 `buildView` 再 `applyView`，而 `App.vue` 只在 `loadDocument` 里 `project.reset`，
因此页面自己的文档始终是演示计划；任何后台重算（`ResizeObserver → measure()`）都会用
**应用自己的视图**覆盖掉刚推上去的视图。**多等帧 = 把这条已知脆弱的窗口拉宽。** 两条结论：

1. 主口径的 `frameMs` 口径就是"提交 + DOM 更新 + **双 rAF 等待**"，换掉它等于改口径、历次首屏数字全不可比；
2. 它的读数一致性由**两路互证**守着（`errors` 非空即 `status: error`）——本轮它刚刚证明了判别力
   （这正是 P-23 §5 修过的那条互证：曾经"看着全绿、其实互证已失效"）。

⇒ 回退该处：`settleStableRead` 用在**读数是判据**的场景（`--align` 每位置 + `--drag`/`--persist-drag` 的初始滚动），
主口径保持原样并在此写明理由。

**(b) 拖动帧预算的一处"不是回归的差异"（连同对照实测）。** 本机当次会话里 `--drag` 给出
**帧间隔 p95 35.3 ms**（判据 ≥30 fps ⇒ ≤33.3 ms），与已入库的 **16.8 ms** 相差一倍。为了判定它是否由本轮引起，
临时把拖动前的等待**变造回旧口径**（`nextTick` + 两帧）重跑一次：

| 口径 | 帧间隔 p50 / p95 | 主线程 p95 | 其它判据 |
|---|---|---|---|
| 本轮（稳定读） | 16.6 / **35.3 ms** | 5.90 ms | 位移 ✅（`startDate 2026-10-08`）、DOM 变化帧 3、松手 13.1 ms |
| 变造回旧口径 | 16.6 / **36.6 ms** | 7.70 ms | 位移 ✅、DOM 变化帧 3、松手 11.6 ms |

**两种口径在同一会话里给出同一量级** ⇒ 35 ms 不是本轮改动引起的，而是
[P-26](裁决R24-26.md) 记过的那件事：**量到的其实是"机器当时有多忙"**（那一轮它是性能 spec 的偶发超阈）。
处置：**不用负载态快照覆盖安静态快照**（`drag-timing-chrome154.md` 恢复为上一版），并把这条对照
如实登记在此——它是"记录制数字只在同口径、同负载状态下可比"的又一份现场证据。

**批次②的明确不做**

1. **不做视口矩阵**（原候选 ②-B：`--align-viewports=1280x800,900x600`）——收益最小（窄窗格的边界情形由人工复核覆盖），
   而迁移轮已经覆盖了"尺寸变化"这一类；需要时加参数即可（判据形状不变）；
2. **不给主口径换掉固定双 rAF**（§8(a) 的两条理由）；
3. **不新开机制码**表达"过期重算"：`pane-measure-stale` / `table-body-height-mismatch` /
   `svg-box-not-1to1` / `scroll-out-of-sync` 已经覆盖，重复登记会让证据分叉；
