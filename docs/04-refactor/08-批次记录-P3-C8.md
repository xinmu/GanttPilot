**2. 为什么"零引用"不等于"多余"：9 份 raw 逐份实测**

判据一：`-raw.json` 与 `.md` 是不是**同一次运行**——用两侧都有的 `采集时刻` 逐位比对（raw 取自 `env.采集时刻`，md 取自环境表的 `| 采集时刻 | … |` 行）：

| raw（字节） | 与它成对的 `.md` | raw 的采集时刻 | 逐位相等 |
|---|---|---|---|
| `chart-align-diagnostic-before-fix-raw.json`（66,771） | `chart-align-diagnostic-before-fix-chrome152.md` | `2026-10-04T08:30:37.287Z` | ✅ |
| `chart-align-raw.json`（347,381） | `chart-align-chrome154.md` | `2026-10-06T13:17:38.645Z` | ✅ |
| `drag-timing-dense-2000-raw.json`（11,223） | `drag-timing-dense-2000-chrome154.md` | `2026-10-06T12:04:22.432Z` | ✅ |
| `drag-timing-raw.json`（11,172） | `drag-timing-chrome154.md` | `2026-10-06T12:00:20.125Z` | ✅ |
| `import-cyclic-sample-raw.json`（1,525） | `import-cyclic-sample-chrome152.md` | `2026-10-04T14:01:55.712Z` | ✅ |
| `offline-single-file-raw.json`（2,150） | `offline-single-file-chrome154.md` | **两侧都没有**（schema 是 `chromeMajor/artifact/flows*`） | 按名字 + 生成器成对写出 |
| `persist-drag-timing-raw.json`（3,440） | `persist-drag-timing-chrome154.md` | `2026-10-06T12:01:22.529Z` | ✅ |
| `persist-storage-2000-raw.json`（1,367） | `persist-storage-2000-chrome154.md` | `2026-10-04T19:54:55.313Z` | ✅ |
| `render-timing-raw.json`（15,621） | `render-timing-chrome154.md` | `2026-10-06T13:17:08.512Z` | ✅ |

**8/9 逐位相等**（第 9 份按 schema 不同另记）。这不是巧合：`scripts/measure-render.mjs` 与 `scripts/offline-artifact-probe.mjs`
每写一份 `.md` 就**成对**写一份 raw（`writeFileSync(evidencePath, …)` 紧挨着 `writeFileSync(join(evidenceDir, '…-raw.json'), …)`，
共 7 处调用点）。**每一份 raw 都是某一份已登记证据的机器可读孪生件**。

判据二：raw 里有没有 `.md` 里没有的东西——有，而且是 `.md` 自己声明的：

- `chart-align-chrome152.md`（6 处）/ `chart-align-chrome154.md`（19 处）：`（共 31 行；证据表只列首 10 + 末 4 行，**逐行值见 raw JSON**）`；
- `render-timing-chrome152.md` / `render-timing-chrome154.md`（各 2 处）：`首屏的起点是"文档与 Schedule 就绪"（**`compute` 单列在原始 JSON 的 `prepareMs`**）`。

判据三：**规则**。`DOC-SPEC §4.5` 的两级处置把「真机落盘的 XML、渲染 PNG、**计时原始数据**」列为
**不可再生的外部工具观测**（可再生的探针代码删、结论与证据留档）——raw 就是这里说的"计时原始数据"。

判据四：**生成器用不带版本号的文件名**。`measure-render.mjs` 写的是 `chart-align-raw.json` / `render-timing-raw.json`…
而同一族**有两份已提交的 `.md`（chrome152 与 chrome154）**⇒ 现存这份 raw 是**最近一次运行**的读数，
**旧那份已被覆盖**。这恰恰是"必须把『它属于哪一次运行』钉在登记里"的理由：
`chart-align-chrome152.md` 的 6 处「逐行值见 raw JSON」今天指的是 **154 那次**的数据（原文按归档层不改写，指向以登记为准）。

> **⇒ 结论**：计划里"删 4 份（`chart-align-diagnostic-before-fix` / `render-timing` / `drag-timing-dense-2000` / `import-cyclic-sample`）"
> 的判据只是 `git grep <文件名>`（**链接图**），因此漏掉了两种"所有者存在"的形态：**孪生配对**（时刻相等）与
> **兄弟 `.md` 的明文 deferral**（不带文件名）。按"**有没有可解析的所有者**"重判，9/9 都有人——
> 病不在"文件多余"，在"**没人指**"。何况删掉 4 份而**不动生成器**是不对称的：下一次 `measure-render.mjs`
> 会把它们原样写回来（成为未跟踪文件）。生成器侧的具名化与已提交证据**同批**做才不产生分叉，
> 而那是 **P4 的集中重取**（见 [04-验收与门禁](04-验收与门禁.md) 的 P4 行）；本批只做登记与守卫。

**判据一：这一批不能靠"改证据"收口。** `DOC-SPEC §4.6` 与两条先例（`P-41 §9(a)` / `P-44 §9(a)`）把

"会作废证据的改动**与重取同批**"。这 6 处里 4 处是**观测本身**（WPS 自报的安装路径、`%TEMP%` 下的临时副本、
"本机 Office 目录为空"），2 处是我方生成器的**写法**（`--import` 回显的输入路径、`file:///` 打开方式）——
后者可以并且应该改，但改了就会让**生成器输出与已提交证据分叉**（`measure-render.mjs` / `offline-artifact-probe.mjs`
跑一遍就不再逐字节重现盘上的证据）。⇒ 6 处**全部**走例外表，生成器侧改动登记给 **P4**。

**判据二：例外必须按行收窄，否则等于把守卫关掉。** `externalPathCheck.allow` 的匹配面是
`path`（或 `pathRegex`）+ 可选 `lineRegex`（对**该行正文**）：只写 `path` 就是"整份文件放行"，
同一个文件里**新写**的本机路径会静默通过。因此 5 条规则**都带 `lineRegex`**（6 处命中落在 5 行上，
`template-a-demo-wps.md` 的 `%TEMP%` 那行有两个路径 ⇒ 一条规则覆盖两处）。

### C8-d 记录（**生成物的自指：一次 `docs:index` 到不了不动点**）

**1. 发现路径**

C8-a 加完 `evidenceRawCheck` 后跑 `pnpm docs:index` **一次**，`docs:check` 却报
`[生成物] docs/01-roadmap/首版-文档索引.md 与它的来源不一致（陈旧）`——而生成器刚跑过。当时记下"第二遍才对"
（`2042.0 KB` → `2042.1 KB`），C8-b/c 又各撞了一次，于是本批把它查实。

**2. 机制：生成物**自指****

`doc-artifacts.mjs` 的 `renderDocIndex()` 里：

```js
for (const entry of index.docs) { … const kb = statSync(absolute).size / 1024; totalKb += kb; }   // ← 它自己也在 index.docs 里
…
`**合计 ${totalKb.toFixed(1)} KB**（${ROWS.length} 份）…`
```

「合计」与"它自己那一行"的体量都取自**盘上**，而这份文件**自己**就是被索引的一份 ⇒ 写盘会改变下一轮读到的数。
一次运行的语义因此是：**用"写之前的自己"算出来的数字，写进"写之后的自己"**。

**3. 复现（探针 `tmp/c8d-probe.mjs`，用完即删；改动是真实的"新增一份文档"）**

| 步骤 | 结果 |
|---|---|
| 造一份新文档 + 在 `doc-index.json` 里登记（模拟真实动作） | —— |
| 跑**一次** `node scripts/make-doc-index.mjs` | `[docs] 已刷新 …（140 份文档 / 2059.6 KB / 未决 0 条）` |
| 逐字节比对：盘上 vs 就地重算 | ❌ **不一致**：盘上 `合计 2059.6 KB`、自己那行 `14.5 KB`；重算 `合计 2059.7 KB`、`14.6 KB` |
| `docs:check` | `exit 1`，1 条 `[生成物] … 与它的来源不一致（陈旧）：跑 pnpm docs:index 重新生成` |

**这条错误的处方本身也不完整**：门禁说"再跑一次生成器"，但**再跑一次**才会对（第二遍用 14.6 KB 算）。
换句话说：C7-i 的检查**判对了**（它抓到了一个真实的陈旧件），而生成器**做不到它承诺的"跑一次就好"**。

> 为什么以前没暴露：C7-i 之前**没有任何检查**比对生成物与来源（`N10`/D10 记的就是这个代价）；
> 而人手工跑两次是常态（第二次通常顺手就跑），所以症状一直被当成"没跑干净"。

**4. 修法：迭代到不动点（不改判据、不放宽检查）**

`make-doc-index.mjs`：渲染 → 写盘 → **再渲染** → 与刚写下的内容逐字节比对，不同就再写，直到相同；
上界 `MAX_PASSES = 5`，**超过就 `exit 1` 并把"自指"这件事写进错误文案**——
生成器自己的不收敛必须是响亮的，不能留下一个"看起来跑过了"的陈旧件。

**为什么是"迭代"而不是"把索引自己从合计里剔掉"**：后者会让「合计」变成一句假话
（要么少算自己，要么得在文案里加"不含本文件"的补丁）；迭代保住"合计 = 盘上全部被索引文档的体量"这条语义。
**为什么 `make-round-index.mjs` 不用同样处理**：`renderRoundIndex()` 的输入是 `docs/00-baseline/裁决R*.md`
的扫盘结果（轮次主题 + 台账条目），**不含任何体量** ⇒ 无自指（实测：现状再跑一次逐字节不变）。

**5. 负向对照（同一探针，改动前 / 改动后）**

| # | 状态 | 变异（新增一份文档） | 期望 | 实测 |
|---|---|---|---|---|
| A | **改动前** | 跑一次生成器 | 陈旧 ⇒ `docs:check` 红 | ✅ 盘上 `2059.6 / 14.5` vs 重算 `2059.7 / 14.6`；`exit 1`、1 条 `[生成物]` 错误 |
| B | **改动后** | 同一个变异、同样只跑一次 | 到不动点 ⇒ `docs:check` 绿 | ✅ `2 轮收敛`；逐字节一致；`exit 0`、0 条 `[生成物]` |
| C | 改动后（稳态） | 不改变任何文档、跑一次 | 1 轮收敛、逐字节不变 | ✅ 日志 `1 轮收敛` |
| D | 清理 | 删掉探针文档 + `git checkout` 两个文件 | 复原、`exit 0` | ✅ |

A 与 B 是**同一变异的两侧**：这就是"这条修法确实是那个拦截点"的证明（而不是"改完就不红了"的空断言）。

**6. 与 C7-i 记录的关系：订正一处归因**（不修改那份记录——记录层不改写）

[批次记录-P3-C7](07-批次记录-P3-C7.md) §C7-i 的第 2 张表里记着：

> `docs/01-roadmap/首版-文档索引.md` | **不同**：盘上那一行写 `14.2 KB`、重算是 `14.4 KB` ⇒ **它当时就是陈旧的**
> （我在 C7-a/b 之后改过多份文档却没重跑 `pnpm docs:index`）。…**跑一次 `pnpm docs:index` 后一致**

本批的实测说明这条归因**不完整**：那份文件当时**已经**是"跑过生成器之后"的状态，
"自己那一行与盘上体量不符"**正是自指的签名**（生成器写下的文本里，自己那一行与「合计」用的是**写之前**的体量），
而"再跑一次就一致"也与自指的收敛行为吻合（第二遍读到的是第一遍写下的体量）。
⇒ 正确说法是：**既有"当时确实有别的文档改动没重跑"的成分，也有"重跑一次本来就不够"的必然成分**；
后者在 C7-i 写记录时还看不见（那时没有比对生成物的检查），本批才把它复现出来。
**那条对照（⑤"新登记一份文档而不重跑生成器 ⇒ 恰好 1 条红"）的完整形态也因此是**：
不重跑 ⇒ 红；**重跑一次 ⇒ 仍然红**（自指）；重跑两次（或让生成器迭代）⇒ 绿——本批的 A/B 就是后两格。
