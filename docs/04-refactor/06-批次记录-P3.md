### C6-b 记录（**N11 的根因修复：夹具必须是最后一个写入者**；含确定性 A/B）

**根因（实测，不再是推断）**：初始会话恢复是 `usePersistence` 在 `onMounted` 里发的**异步** IIFE
（`store.loadLatest` → `planRestoreOf` → `args.restore(...)`），而 `args.restore` 会**整份替换会话
（文档 + 两个栈 + `revision`）**。关键事实：**IndexedDB 按 origin 隔离，而同一轮测量的多次导航
共用同一个 origin** ⇒ **第一次导航**（演示计划，15 行）写下的"全新会话基线"会被**第二次导航**
恢复回来。若那次恢复落在 `loadDocument` 的 `project.reset(夹具)` **之后**一步，页面就回到演示计划
⇒ 测量方的模型（1,000 任务 ⇒ 31/41）与页面上的 DOM（15/14）是**两份文档** ⇒ 互证翻红、脚本 `exit 1`。

**为什么原先的修法方向修不动它**：05 §四.12 记的方向是"等夹具真的被渲染 / 连续两帧同构"。
实测证伪：这不是"还没渲染完"，而是**页面自己又换了一份文档**——多等帧只会把窗口拉得更宽
（P-41 §4 的现场教训正是这个）。真正的判据是**写入顺序**，不是等待时长。
**也不是 profile 污染**：`startStaticServer` 用 `listen(0)` ⇒ 每次运行一个新端口、一个新 origin；
跨运行的 profile 与 N11 无关（这一点先前被想当然地写成"profile 里有旧会话"）。

**确定性复现（临时变造，A/B 后已删除）**：① `usePersistence` 把恢复推迟 2 s；② `App.vue` 把
"夹具装载 → 读数"的窗口拉宽 3 s ⇒ 恢复必然落在窗口内。用一次性探针（两次导航 + 同视口）观测：

| 观测点 | 修前 | 修后（同一变造） |
|---|---|---|
| 主口径 `errors` | ❌ `["实际 DOM 与元素模型不一致：DOM 行/边 = 15/14，模型 = 31/41"]`（**逐字复现 N11 的历史报文**） | ✅ `[]` |
| 主口径 `domCounts` vs `counts` | `15/14` vs `31/41`（两份文档） | **`31/41` vs `31/41`** |

**修法（两处，都是"顺序"而不是"等更久"）**：

1. `usePersistence` 暴露 **`restoreSettled: Promise<void>`**：`enabled === false`（`?persist=0`，无恢复）
   立即结算；成功在 `args.restore(...)` **及其后的检查点写入之后**结算；**失败也结算**（`.finally`）
   ——否则等待方会挂死，把一个可判定的问题变成挂死（P-12 的"缺失即失败"精神）。
2. `App.vue` 的 `loadDocument` 改成 **`await persistence.restoreSettled` → `project.reset(夹具)` → `nextTick()`**
   ⇒ **夹具成为最后一个写入者**。**口径不变**：这个 `await` 发生在 `runMeasurement` 的计时起点
   **之前**，`primaryMs` 仍是"装好夹具 → 含依赖线首帧"，历次首屏数字可比。

**正常路径复验（修后、**无**变造）**：主口径 ×2（`day` / `week`）、`--drag`（`move` 与

**0. 先比对：四列对照（本批的强制前置）**

一次性脚本 `tmp/compare-depths.mjs`（**跑完不留**，下表即其逐行输出）在同一批文档上跑四份实现：**组件旧**（`TaskTable.vue` 里那 7 行，逐字抄）、
**引擎旧**（C6-e 之前的 `depthOf`，逐字抄）、**引擎新**（`engine.computeDepths`，从构建产物导入）、
**树口径**（`buildTaskTree` 的 `depth`，可达节点）。实测（`---` 表示该节点在树里不可达）：

| 文档形状 | 节点 | 组件旧 | 引擎旧 | 引擎新 | 树 | 判读 |
|---|---|---|---|---|---|---|
| 良构（a→b→c） | a / b / c | 0 / 1 / 2 | 0 / 1 / 2 | 0 / 1 / 2 | 0 / 1 / 2 | 三者全同 |
| 悬空 `parentId`（a→ghost，b→a） | a / b | **1 / 2** | **0 / 0** | **0 / 1** | 0 / 1 | 组件把"指向不存在的父"当成一级子节点；引擎旧把**整条链**归 0 |
| 自环（a→a，b→a） | a / b | **64 / 64** | 0 / 0 | **0 / 1** | 0 / 1 | 组件的 `depth < 64` 截断把自环变成第 64 级 |
| 二环（a↔b） | a / b | **64** | 0 | 0 | 不可达 | 环上节点在树里到不了；0 是退化值（`validateHierarchy` 报 `TREE_CYCLE`） |
| 深链 100 级 | d65…d99 | **64（截断）** | 65…99 | **65…99** | 65…99 | 组件的 64 是"防环"的副产物，把深链也压平了 |

**裁决**：换用 `engine.computeDepths`，**并且先把引擎自己修到与 `buildTaskTree` 同口径**。
理由只有一条但足够：左表的**缩进**必须与 **WBS 编号 / 行序**同源——同一行上"WBS 列显示 `1.1`"与
"缩进 0 px"（或"WBS 显示 `1`、缩进 764 px"）是自相矛盾的，而脏数据下组件那套给出的正是这种组合。

**1. 引擎侧：一条没人守的同源关系（比对当场抓出）**

- 旧实现把"上溯遇到悬空 `parentId`"落成**整个结果归 0**，而注释写的是"悬空 `parentId`…按 0 处理"——
  读起来像指**那一个任务**，实现的落点是**整条链**（上表第 2 行：`b` 的父 `a` 存在，树给 1，它给 0）。
- 新实现把**根判定**与 `buildTaskTree` 对齐并写进文档注释：**根 = `parentId` 为空 / 悬空 / 自指**，
  上溯到最近的根逐跳计数；**长度 ≥ 2 的环 ⇒ 0**（树里不可达）。悬空/自指的那个任务**自己是根**，
  已计的跳数**照算**——于是它的子树按真实层级（`b` = 1），而不是整棵归 0。
- **不设深度上限**：上限是 `MAX_OUTLINE_DEPTH`（由 `validateHierarchy` 判）的事；截断会静默改变缩进。
- 顺带把 O(n²) 改成 O(任务数 × 深度)：`byId` 只建一次（新增 `indexById`，`guardDepth` 也改用它）。
- **判据（进 `pnpm gate`）**：`wbs.spec.ts` 新增「`computeDepths` 与 `buildTaskTree` 的 depth 逐节点一致」，
  覆盖 5 类文档（良构 / 悬空 / 自环+后代 / 二环+环上后代 / 100 级深链），另断言深链第 100 个是 **99**、
  环上节点**不在树里**但结论是 0。原有用例（悬空/成环退化 0）保持不变、仍绿。
