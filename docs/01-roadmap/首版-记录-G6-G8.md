### 三、实测数字（打包产物，记录制；口径与数字一起读）

**出口条件③（杀进程后重开）**：**判据在引擎侧**（`planRestoreOf` 的优先级与"坏候选只跳过"、
以及"写者被杀后仍能恢复到**最后一次成功写入**（`rev` ≥ 最近检查点）"的 killsim —— 都在
`persistence.spec.ts`，**进 `pnpm gate`**）。记录制那一栏**不作判定**（见 §四 第 6 条）；
真机形态按 ADR 0009 §8 归**人工复验**（浏览器杀进程不触 `beforeunload`）。

**出口条件①（`--persist-drag`，Chrome 154 / headless=new / DPR 1 / 1,000 任务）**

| 持久化 | 帧间隔 p50 | 帧间隔 p95 | 主线程 p50 | 主线程 p95 | longtask | 拖动期写入 | 松手→落盘 |
|---|---|---|---|---|---|---|---|
| 开 | 16.6 ms | 16.8 ms | 2.00 ms | 2.50 ms | 0 | **0** | **5.5 ms** |
| 关（`?persist=0` 对照组） | 16.6 ms | 16.8 ms | 2.00 ms | 3.20 ms | 0 | 0 | — |

**判定**：帧间隔 p95 ≤ 33.3 ms（≥30 fps）**两组都成立**；拖动期持久化写入 **0** 次
（回退栈相对全量快照的收益）；松手 → 落盘 **5.5 ms** ≪ 5,000 ms。

证据：[`persist-drag-timing-chrome154.md`](../../apps/web/evidence/persist-drag-timing-chrome154.md) +
[`persist-drag-timing-raw.json`](../../apps/web/evidence/persist-drag-timing-raw.json)
（Chrome 152 的首轮版本留档在同一目录，作为跨版本对照）。

**出口条件④（`--storage-metrics`，2,000 任务 / 3,000 依赖）**

| 项 | 值 |
|---|---|
| 整份文档规范文本 | **623.4 KB**（序列化 2.0 ms） |
| 单条"最新状态"记录 | **0.15 KB** |
| 单条 IDB `put` p50 / p95 | **0.3 / 1.6 ms** |
| `navigator.storage.estimate()` 用量 / 配额 | **490.6 KB / 10,240 MB** |

**判定**：单条增量记录 **0.15 KB** 对整份文档 **623.4 KB**（Res-2 的"每次操作一小段 diff"成立）；
单条 put **1.6 ms**（p95）远小于"每 ≤5 s 一次"的预算。

> **一条必须一起读的诚实口径**：记录里的 `base` 带**整份基线快照**，因此基线建立之后每次写入
> 还含一份固定的基线体积（"杀进程仍能恢复"的代价）。上表量的是**基线为空/已重定**时的那一次写入。
> 把基线改成"存储引用"属 v0.5 的写入量优化，已登记在 §五。

证据：[`persist-storage-2000-chrome154.md`](../../apps/web/evidence/persist-storage-2000-chrome152.md) +
[`persist-storage-2000-raw.json`](../../apps/web/evidence/persist-storage-2000-raw.json)。

### 四、返工与实测抓到的缺陷（逐条）

1. **跨轮污染**（记录制当场抓到）：第一次采样报出 316 KB 的"增量记录"，而当时的文档只有 300 KB 级。
   根因有**两个**，都不是"公式写错"：
   - **启动恢复**把上一轮的检查点接进来 ⇒ 记录里带着**旧文档的基线**；
     修法：记录制在**导航前清库**（`persistProbe` 里 `indexedDB.deleteDatabase`）。
   - **换夹具后基线仍指旧文档** ⇒ 每次写盘都把旧文档带上；
     修法：加**硬重定基线**（`usePersistence.rebaseNow()`，先作废内存里的 `base` 再写新检查点），
     并登记成**实现不变量③**（产品上对应"导入 / 恢复换了整份文档"）。
2. **"松手→落盘"恒为空**：`flushNow` 走的是策略的 `tick`，在去抖窗口内动作是 `none` ⇒ 什么都不写。
   修法：`flushNow` 改为**强制收口**（不等去抖窗口，按步数阈值决定要不要先落新检查点），
   登记成**实现不变量②**。
3. **存储测量落到 1,000 任务**：`?dataset=dense-2000` 是给**页面**建夹具用的，钩子参数替代不了它；
   而 `demo.ts` 的解析不认识 `dense-2000` ⇒ 静默退回主口径。
   修法：测量 URL 带 `dataset`，且 `App.vue` 的 `buildFixtureDocument` 改走 `measure.ts` 的
   `specOfDataset`（**与 spec、与判据同源**）。
4. **`up` 之后的 `kind` 是 `released`**（状态机使然）而不是 `idle`：旧断言把它报成错。
   修法：只拒"仍在 `dragging`/`linking`"。
5. **写入耗时采样量到 0 ms**：`flush()` 在"没有未落盘变更"时是空操作。
   修法：测量用 `writeRecordNow()`（**不理会策略**直接写一条记录）——只服务记录制，不进产品路径。

6. **"重开恢复"这条对照在该场景里没有判别力**（如实登记，避免被读成"已通过"）：
   `--persist-drag` 把**页面换成测量夹具**，而重开时页面会 `project.reset` 成演示文档
   （测量钩子只加载夹具、不加载"用户文档"）⇒ 重开后的 `revision` 必然回到 0。
   处置：证据文件里**不作判定**、只如实报数字；出口条件③的判据留在引擎侧
   （`planRestoreOf` + killsim，进 `pnpm gate`），**真机形态（强制杀进程 / 关页后重开）归人工复验**
   （ADR 0009 §8 的字面口径：恢复到**不早于**最近检查点）。
7. 顺带修掉两个"看起来能跑"的实现问题：**`publishRevisionMirror` 在定义前被 `watch` 调用**（TDZ，
   镜像从未写入）与**测量钩子多余的 `loadDocument(fixture)`**（它走 `project.reset`，
   会把"刚编辑的会话"整份换掉）。

> 七条里有六条是**记录制当场抓出来的**（纯函数 spec 结构上抓不到）——这正是 P-9/P-17 分层的价值。

### 五、人工复验（打包产物，2026-10-05）

维护者按其报文逐条复验，**三处反馈**：

| # | 反馈 | 处置 |
|---|---|---|
| 1 | 状态栏那一栏的"已保存 / 检查点 N 份 / 待落步数" | **口径错**（见下），已改字段与文案后**复验通过** |
| 2 | "编辑后 5 秒内的落盘，拖动后显示『已保存 04:12:35 · 检查点 1 份 · 待落步数 3』是否表示成功？" | 是：说明拖动提交的那一步已在 5 s 内落盘。但那个"3"暴露了 #1 的措辞错误 |
| 3 | 强制结束标签页 / 杀进程后重开 | **复验通过**（恢复到不早于最近检查点） |

**#1 是记录制与实现都没抓到的一处"名不副实"（维护者的报文当场抓出）**：
旧字段 `lastPostSteps` 的语义是"**最近一次写入**覆盖的增量步数"（`post` 长度），
而状态栏把它写成"**待落**步数"——两者不是一回事：拖动提交 1 步、写盘后 `rev` 因 `flushed` 再 +1，
于是显示 3；而"已保存"之后**本该是 0**。处置：

- 字段换成 `unsavedSteps` = 当前 `session.revision` − 最近一次成功写盘时的 `revision`
  （唯一真相源 = 会话版本）；文案改为**只在 >0 时**显示"· 未落盘 N 步"
  ⇒ "已保存"之后该段必然消失，这本身就是"自动保存真的发生了"的可观察证据；
- 复验后状态栏为「持久化：已保存 04:16:58 · 检查点 1 份」。

**#2 顺带暴露的另一件事（不是缺陷，是打开方式）**：维护者反馈"`pnpm build` 后打开
`apps/web/dist/index.html` 页面空白，目前是在 `pnpm dev` 下验证"。根因是**浏览器拒绝在
`file://` 下加载 ES module**（CORS）——产物没坏。但它照出一个真缺口：
**此前没有任何门禁碰过 `dist/`**（700+ 条判据都在包源码上，记录制又只跑"已就绪"之后的路径）。处置：

- 新增 `pnpm smoke:build` 并**接入 `pnpm gate`**（`build` 之后）：HTTP 伺服 `dist/` →
  无头 Chrome 打开 → 断言"无应用级错误 + 标题/工具栏/图表窗格/SVG/状态栏持久化那一栏都渲染了"；
- README 增「预览与人工复验（**打包产物口径**）」一节：`pnpm build` + `pnpm preview`，
  并写明**不要直接打开 `dist/index.html`**（含原因）。

> 因此本块的复核口径仍是**打包产物**（`P-33` 已定）；维护者此前的验证在 `pnpm dev` 下完成，
> 请在 `pnpm preview` 下按同一份清单再走一遍（三处的数字已在打包产物上采集并写入证据文件）。
