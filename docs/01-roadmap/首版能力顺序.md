## 一、排序原则

1. **证伪优先**：最可能推翻产品假设的未知项先做，只花 1–3 天，且**不写产品代码**。
2. **内核先行、分析层延后**（T-3 修正）：日期传播内核是**几何来源**（条形位置、连线端点、SVG/PPTX 坐标全由它推导），必须早做；而 CPM 分析层（浮动/关键路径）全局耦合、成本高、不支撑首版卖点，延后。
3. **一条主链路走通胜过五条半成品**：优先级按"能否让'导入 → 出图 → 拖动 → 导出'闭环推进"排序，而非按模块重要性排序。
4. **导出后置**：SVG/PPTX 导出依赖渲染几何与排程结果，必须在 G4/G2 之后；提前做只能得到空壳。
5. **护栏先于功能**（原文前提）：测试框架与 CI 是"正确性关键模块"的准入门槛，与 spike 同期建立。

- `dayOfOrdinal(k = workdayCount)` 的语义定为"**最后一个工作日之后的首个工作日**"

- **地平线容量**：按"全部工期 + 正 lag"的上界规划，不足时扩容重算；
- 保留 `parseIsoDate` 的严格校验与 `[start, end)` 半开区间语义（现有 `date.spec.ts` 用例作为回归基线）。

- [x] 日期算术单测覆盖：跨周末、跨 `exceptions`（两类覆盖 + 同日冲突优先级）、负向推进、跨年、月中起算；

**落地记录**

- **文件**：`packages/engine/src/date.ts`（重写，+600 行）；新增 `packages/engine/src/loopCalendar.ts`
  （逐日循环的**测试侧**互证实现，**不经 `index.ts` 导出**——它不是公共 API）；
  测试 `date.spec.ts`（13 → 46 例）与新增 `loopCalendar.spec.ts`（5 例）。
- **公共 API**：新增 `Calendar`（索引日历：`isWorkday` / `ordinalOfDay` / `dayOfOrdinal` /
  `workdaysBetween` / `isoOfOrdinal` / `isoOfDay` / `dayOfIso` / `addWorkdays` / `subtractWorkdays` /
  `offsetWorkdays` / `withHorizon`）、`isoToDayNumber` / `dayNumberToIso` / `weekdayOf` / `addDays` /
  `diffDays` / `horizonDaysFor`、常量 `DEFAULT_PROJECT_BASE_DAY_ISO` / `DEFAULT_HORIZON_DAYS` /
  `HORIZON_GUARD_DAYS`，以及类型 `CalendarSpec` / `CalendarExceptionsSpec` / `CalendarLike` /
  `CalendarOptions` / `DayNumber`。`parseIsoDate` / `isWorkday` / `countWorkdays` / `DEFAULT_WORK_DAYS` /
  `WorkdayCount` **签名与语义保持兼容**（`countWorkdays` 追加可选第 4 参 `exceptions`，
  实现由逐日循环换成闭式周算术 + 例外日修正）。`PLANNED_GATE` 按 [裁决 P-10](../00-baseline/裁决记录.md)
  由 `'G1'` 改为 `'G1.1'`。
- **序号锚点（本块冻结的新口径）**：序号**相对 `Calendar.baseDay`** 计数，而非相对 1970-01-01——
  `ordinalOfDay(d)` = `[baseDay, d)` 内的工作日数，`dayOfOrdinal(0)` = `baseDay` 当天或其后的首个工作日，
  于是 `workdaysBetween` 与 `countWorkdays` 的半开区间语义是同一个东西。**负数序号无定义**：
  负向推进越到 `baseDay` 之前即抛 `RangeError`，**不做静默截断**（截断属 G2 的 `clampedStarts`，S3 §五.4）。
- **容量**：`Calendar` 的地平线由 `baseDay + spanDays` 界定，默认 1,460 天；
  容量上界用 `horizonDaysFor(Σ工期 + Σ正 lag)` 规划，不足时 `withHorizon(2×)` 重建重算
  （测试已覆盖「先抛错、扩容后与直接构造大窗口逐项相同」）。
- **互证**：`loopCalendar.spec.ts` 在 3 套日历 × 600 天逐日判定 + 201 个序号映射上逐项比对，
  并把区间计数与兼容入口 `countWorkdays` 做**三方一致**；另有一条**负向对照**（把逐日实现的序号偏移 1 必须被检出），
  证明互证不是恒真式。
- **未新增依赖**，`pnpm gate`（lint / typecheck / test / build / license:check）全绿。

- [x] 1,000 任务 + 1,500 依赖**全量传播 p99 ≤ 1ms**（原文 EN-08 的 100ms **保留为产品侧不回归天花板**；
  收紧依据见裁决 P-6：S3 实测最差 p99 = 52.1 µs，余量约 19×）。
  **实测（Node 24，本机）**：产品口径的 `compute()`（含日期解析、工期解析、诊断收集与结果分配）
  **p50 = 326 µs / p99 = 530 µs**（最差 suite p99 = 644 µs）⇒ 对 1ms 有约 **1.9×** 余量；
  注意 S3 的 52.1 µs 是**只测传播内核**的窄口径（预建 CSR、无日期与诊断），两者不可直接比较；
- [x] `affectedClosure` 只断言**结构性事实**（闭包规模、深链覆盖全图），**不加时序门禁**；
  `schedule.closure.spec.ts`：深链 1,000 节点上闭包 = 全图、从链尾出发 = 1 个、结果按文档序且与种子顺序无关。

**明确延后至 v0.5**（EN-01/02/03）：逆向遍历 LS/LF、总浮动/自由浮动、关键路径高亮；**增量优化**
（含"闭包内逆后序重算"）一并延后——若 G5 的浏览器实测整帧不达标再引入，届时以实测为依据。
**原因**：浮动/关键路径全局耦合（评估报告 §5.3），成本高且不支撑首版卖点；增量在 v0.1 无收益（见内容第 1 条）。

  共享导入，它们的自检会随导入重复计数——与 G1.2 的 `fixtures.spec.ts` 同一手法）。
- **公共 API**：`compute` / `wouldCreateCycle` / `affectedClosure` / `createScheduleCalendar`、
  常量 `LEAF_SENTINEL`；类型 `Schedule` / `ScheduleResult` / `ScheduleSuccess` / `ScheduleFailure` /
  `ScheduleDiagnostic` / `ScheduleDiagnosticCode` / `SessionAnchor`。
  `PLANNED_GATE` 由 `'G1.3'` 改为 **`'G2'`**，`COMPLETED_GATES = ['G1.1','G1.2','G1.3','G2']`。
  `computeInto`/预分配复用按 ADR 0004 §5 **不进公共 API**（实现细节）。
- **冻结的口径**（详见 [SCHEDULE.md](../../packages/engine/SCHEDULE.md) 与 [ADR 0005](../02-adr/0005-排程内核落地补齐与结果形状.md)）：
  ① `Schedule` 各数组**按文档序索引**，汇总行 `es === -1`（唯一的汇总判别式）、叶子行 `summary* === -1`；
  ② 锚点四情形 + 项目起点三级回落（第②级取**全部任务日期**的最小值，会话锚点**不参与**，
  否则"源任务全无日期"的文档会让起点退化成 `baseDay`、违反 ADR 0004 §4 自己的不变量）；
  ③ **有效图 vs 结构图**：传播排除汇总端点边（并报 `summaryIgnored`），**检环用全部边**——
  因为 `wouldCreateCycle(links, candidate)` 的签名看不到层级，让两侧同口径才不会出现"预检说成环、
  `compute` 说没问题"的两个真相源；
  ④ `clampedStarts` 与 `clampedStart` 诊断**同源同数**（含"文档日期早于 `baseDay`"与"项目开始日早于 `baseDay`"）；
  ⑤ `endDateStale` 是**文档级一致性**诊断，对**所有任务**（含汇总）判定；工期解析只对叶子有意义；
  ⑥ `createScheduleCalendar` 收口容量规划（`baseDay` = 文档最早日期；`spanDays` = `horizonDaysFor(日期跨度 + Σ工期 + Σ正 lag)`），
  用它构造的日历**永不触发内部扩容**（有单测守住）。
- **实测订正（两处，都写进 ADR 0005）**：① 容量与 `baseDay` 都**不改变任何序号**——传播是纯整数算术，
  ADR 0004 §7 的"容量不足 ⇒ `withHorizon(2×)` 重算"落成**入口一次性扩容到覆盖全部文档日期**；
  ② 热路径上 `isoToDayNumber` 必须**每次调用只解析一次**（同一 ISO 再按调用内 `Map` 去重）：
  不缓存时全量传播 p99 ≈ 2.5 ms，缓存后 **530 µs**——这是"日历/日期不进传播热路径"这条原则的具体落地代价。
- **互证与负向对照**：正确性侧——独立检查器（逐日循环 vs 索引前缀和、父链重算 vs 逆文档序累加）+
  跨语言差分（另一套图算法/数据结构）三层；负向对照——篡改排程结果、偷换依赖类型、
  FS→SS 改变结果、差分比对器篡改、性能侧朴素实现（实测 **3.4×** 慢，阈值 1.5×）。
- **未新增依赖**（运行时与开发侧都是零新增；**Python 3 成为门禁前置**，仅差分步骤使用，
  与 [S3 §九](../../spikes/g0-s3-cpm-perf/结论.md) 同口径），`pnpm gate` 全绿；
  构建产物经 Node 直接 import 冒烟验证可消费（同 G0/G1 的手法）。

### G5 编辑体验：拖拽三语义 + 撤销重做

**内容**

## 六、v0.1 完成定义（DoD 汇总）

**一句话**：把一个常见结构的 Excel 计划拖进网页，**3 秒内看到带依赖连线的甘特图**，拖动任务条时**下游跟着动**且一步 Ctrl+Z 可整体回退，然后**导出一份图形原生可编辑的 PPTX**；全程断网可用，数据存在本地。

**必须同时成立**
1. `packages/engine`、`xlsx-protocol`、`pptx-renderer` 三包零 DOM/框架依赖，CI 全绿为合并门槛；
2. 排程与 xlsx 协议有**独立验证手段**（不变量测试 + 手工用例 + 差分测试），不依赖外部商业工具；
3. 1000 任务下渲染与传播性能达标，且**裁剪有效性可测**；
4. PPTX 为原生形状（**永不为位图**），兼容性结论**有真机证据**（**真机 = WPS**；Microsoft PowerPoint 备查、不阻塞）；
5. 所有已知限制（**PowerPoint 未验证**、Keynote、MSP 互操作、规模上限、导出不做格式保留）**写入 README**。

**不构成 v0.1 阻塞**：模板 B/C、关键路径、浮动、基线、筛选分组、云同步、飞书。
